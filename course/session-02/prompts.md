# 2회차 — 이렇게 말하세요

AI에게 넣을 문장 원문이다. **글자 그대로** 복사해서 쓰고 `{ }` 안만 우리 회사 말로 바꾼다. 각 문장 아래 한 줄은 "왜 그렇게 말하는지"다.

오늘 끝내야 하는 것은 하나다. **실제 주소에서 직원이 자기 폰으로 넣으면 저장되고, 다시 열어도 남아 있는 앱.**

저장소를 다시 받지 않는다. 번들은 1회차에 설치돼 있고, 스킬은 **이름으로 부른다.**

## 오늘 여는 대화

작업 하나 = 새 대화 하나. 오늘은 대화를 네 번 연다. 이어 갈 것은 AI가 `.owner/state.md` 의 "다음 행동"에서 읽는다.

| 순서 | 새 대화에서 넣는 문장 | 같은 대화에서 이어지는 것 |
|---|---|---|
| 1 | P1 2차 인터뷰 | — |
| 2 | P2 3차 인터뷰 | — |
| 3 | P3 초안 | 검수(P7) 먼저 → 확인 표 → P4 작업 보고서 |
| 4 | P5 저장·배포 | P6 직원 폰 확인 → 검수(P7)·보고서 |

---

## P1 — 2차 인터뷰 「일의 흐름·막히는 곳」 (약 25분)

```
indeans-erp-interview 스킬을 읽고 2차 인터뷰를 시작해 주세요.
과제로 직원에게 1차 요약을 읽어 주고 빠진 것을 세 줄 적어 왔습니다. 그것부터 받아 주세요.
한 번에 하나씩만 물어봐 주시고, 답이 짧으면 예를 들어서 다시 물어봐 주세요.
```

> **왜 이렇게 말하나** — 과제 세 줄을 먼저 받게 해야 1차 요약의 빈 곳을 고친 다음에 흐름을 묻는다. 세 줄을 못 적어 왔으면 AI가 요약을 다시 읽어 주고 "직원분이라면 빠졌다고 할 것 한 가지"만 묻는다.
>
> 2차는 회사 업종에 맞춰 일의 흐름을 훑고, 그중 앱에 먼저 담을 **흐름 하나**를 끝까지 따라간다 — 어디서 시작해 어디서 끝나는지, 단계, 단계마다 누가 하고 무엇으로 끝났다고 아는지, 안 되는 날. 마지막에 가장 귀찮은 일 세 가지를 순위대로 묻는다. 지난번에 미뤄 둔 질문이 있으면 그것부터 묻는다.

---

## P2 — 3차 인터뷰 「범위·확정」 (약 20분, 새 대화)

2차가 끝나면 AI가 "3차는 새 대화에서"라고 알려 준다. **새 대화를 열고** 넣는다.

```
indeans-erp-interview 스킬을 읽고 3차 인터뷰를 시작해 주세요.
화면과 적을 항목은 먼저 제안해 주시고, 맞는지는 제가 고르겠습니다.
이번에 만들지 않을 것도 같이 정해 주세요. 앱은 아직 만들지 마세요.
```

> **왜 이렇게 말하나** — 화면은 세 개로 정해져 있다(목록 · 상세·입력 · 오늘 현황). AI가 업종과 2차 답으로 무엇을 보일지 먼저 제안하고, 대표님은 맞는지 틀린지만 고른다. 대표님이 고친 말이 이긴다.
>
> "만들지 않을 것"을 같이 정하는 이유는, 안 정하면 화면이 조용히 다섯 개, 여섯 개로 늘어나기 때문이다. 범위는 늘어날 때가 아니라 **정할 때** 잡는다. 미룬 것마다 언제 꺼낼지(권한 단계 · 운영 보고 단계 등)가 붙는다 — 2회차 밖의 배치는 아직 가안이다.
>
> 3차 끝에 2주 뒤 직접 잴 숫자 1~2개(가치 가설)를 정한다 — 횟수·건수·시간으로, 금액은 적지 않는다(예: 진행 상황을 묻는 전화 하루 몇 번 · 월말 정리 몇 시간). 약속이 아니라 2주 뒤 같은 방법으로 다시 재 볼 가설이다.
>
> 끝에 1회차에 고른 화면 구조가 이 흐름과 맞는지 AI가 한 번 견준다. 맞지 않으면 알려 주기만 하고 바꾸지는 않는다.

---

## P3 — 초안 만들기 (새 대화)

```
indeans-erp-draft 스킬을 읽고 초안을 만들어 주세요.
company 폴더의 문서와 1회차에 고른 디자인을 그대로 쓰고, 화면은 세 개까지만 만들어 주세요.
만들기 전에 지금 상태를 커밋해 두고, 화면마다 설계 선언을 먼저 보여 주세요.
```

> **왜 이렇게 말하나** — 설계 선언은 화면마다 다섯 줄이다: 이 화면이 끝내 주는 일 · 가장 자주 여는 사람 · 어떤 기기로 · 가장 많이 누를 것 하나 · 일부러 넣지 않을 것. 이것을 먼저 보면 문서를 잘못 읽었는지 화면이 나오기 전에 잡을 수 있다.
>
> AI는 만들기 전에 구조안을 한 번 보여 주고 "이대로 만들까요?"라고 묻는다. 고칠 것이 있으면 그때 말한다. 다 만들면 대표님이 직접 눌러 볼 확인 표를 하나씩 읽어 준다 — AI의 "완료했습니다"로 대신하지 않는다.
>
> 지금 만드는 초안은 **이 브라우저 안에만** 저장된다. 진짜 저장은 P5에서 한다.

---

## P4 — 초안 작업 보고서

초안을 다 눌러 보면 AI가 이어서 보고서를 만든다. 안 만들고 끝났으면 이 문장을 넣는다.

```
indeans-erp-report 스킬을 읽고 오늘 만든 것을 보고서로 만들어 주세요.
어느 화면이 무엇을 하는 화면인지, 왜 그렇게 만들었는지 제가 읽을 수 있는 말로 적어 주세요.
화면 사진도 같이 넣고, 다 되면 브라우저로 열어 주세요.
```

> **왜 이렇게 말하나** — 끝내야 하는 것은 "초안이 돌아간다"가 아니라 **"초안이 돌아가고, 무엇을 만들었는지 내가 읽을 수 있다"** 까지다. 보고서는 파일 한 장으로 내 컴퓨터에만 만들어지고 어디로도 보내지지 않는다. 사실과 다른 줄이 있으면 그 자리에서 말한다.

## P5 — 저장·배포 (새 대화)

```
indeans-erp-data 스킬을 읽고 저장과 배포를 시작해 주세요.
백업 방법부터 정하고, Supabase 프로젝트·표·잠금을 거쳐 1회차에 만든 GitHub 저장소에 올린 다음 Vercel 로 배포해 주세요.
제가 직접 눌러야 하는 화면은 순서대로 하나씩 알려 주시고, 비밀값은 화면에 출력하지 마세요.
마지막에는 직원이 자기 폰으로 넣고 다시 열어 보는 것까지 확인하겠습니다.
```

> **왜 이렇게 말하나** — 순서가 핵심이다. **백업 방법 → 표와 잠금 → 연결 → 배포.** "저장 먼저, 백업은 나중에"로 가면 그 나중은 대개 오지 않는다.
>
> 잠금(행 수준 보안)은 표를 만들 때 같이 건다 — "로그인했고 우리 회사 명단에 있으면 본다" 하나. **화면에서 숨기는 것과 데이터에서 막는 것은 다르다.** 막혔다는 증거는 명단에 없는 계정으로 열었을 때 비어 있는 것뿐이다.
>
> 표를 바꾸는 일은 번호 붙은 파일(`supabase/migrations/0001_…`)로만 하고, 실행하기 전에 고정 검사(`npm run check`)를 통과시킨다. 배포 직전에는 훅이 커밋·빌드·검사를 한 번 더 돌린다 — 걸리면 배포가 멈추고 이유가 나온다. 훅을 끄지 말고 이유를 고친다.
>
> 데이터베이스 비밀번호와 키는 대화 기록에 남지 않게 화면에 찍지 않는다. 공개용 키만 앱에 넣고, 비밀 키(`service_role` · `secret`)는 복사하지 않는다.

### 화면에서 막혔을 때 (Supabase · GitHub · Vercel)

```
{Supabase / GitHub / Vercel}에서 {무엇을} 하려는데 {어느 화면}에서 막혔습니다.
화면에 보이는 문구는 이렇습니다: "{그대로 복사}"
지금 보이는 메뉴는 {보이는 메뉴 이름들}입니다. 다음에 무엇을 누르면 되는지 한 단계만 알려 주세요.
```

> **왜 이렇게 말하나** — 메뉴 이름은 자주 바뀐다. 지금 보이는 글자를 주면 AI가 거기에 맞춘다. 가장 흔한 막힘 셋: 배포한 주소만 화면이 빈다(Vercel에 환경 변수 두 줄을 안 넣었다) · 앱에서 아무것도 안 보인다(로그인을 안 했거나 명단에 없다 — 잠금이 제대로 걸린 것) · Vercel 가져오기 목록에 내 저장소가 없다(Vercel의 GitHub 권한에 그 저장소를 더한다).

## P6 — 직원이 자기 폰으로 넣고 다시 보기 (오늘의 확인)

저장·배포 대화가 마지막 단계까지 오면 AI가 순서를 안내한다. 안내가 빠졌으면 이 문장을 넣는다.

```
직원 계정을 하나 만들고 우리 회사 명단에 직원으로 넣어 주세요. 이름 칸에는 실명을 적지 말아 주세요.
직원이 자기 폰으로 배포 주소에 들어가 실제 업무 한 건을 넣고, 다시 열었을 때 그대로 보이는지 확인하는 순서를 알려 주세요.
비밀번호는 화면에 출력하지 마세요.
```

> **왜 이렇게 말하나** — 오늘의 완료선은 대표님 노트북이 아니라 **직원 폰**에서 확인한다. 직원이 수업 자리에 없으면 주소와 계정을 메신저로 보내 그 자리에서 한 건 넣어 달라고 한다. 연락이 안 되면 직원 계정으로 대표님 폰에서 넣어 보고, 직원 폰은 과제로 넘긴다.
>
> 지금은 회사 명단에 있는 사람이 모두 같은 것을 본다. 대표만 봐야 할 칸(금액 같은 것)은 아직 앱에 넣지 않는다 — 누가 무엇을 보는지 나누는 것은 권한 단계에서 한다.

---

## P7 — 검수를 요구받았을 때

작업을 끝내려 할 때 "검수가 필요한 변경이 있습니다"라는 말이 나오면 이 문장을 넣는다.

```
indeans-erp-check 스킬을 읽고 검수를 진행해 줘.
무엇이 바뀌었는지 먼저 목록으로 보여 주고, 감독이 반려하면 고친 뒤 다시 판정받아 줘.
끝나면 결과를 보고서에 더해 줘.
```

> **왜 이렇게 말하나** — 오늘은 화면이 새로 생기고(초안), 저장 구조·잠금·배포 설정이 바뀐다(저장·배포). 둘 다 검수 대상이다. 초안 뒤에는 디자인 감독이, 저장·배포 뒤에는 설계·데이터 감독이 본다. 반려가 나와도 실패가 아니라 정상 동작이다 — 고치고 다시 받는다(최대 2번). 시간이 없으면 감독 판정까지만 받고 실측은 다음으로 미룰 수 있다.

---

## 막혔을 때 (오류 전달)

```
(1) 하려던 것: {무엇을 하려 했는지}
(2) 기대한 결과: {무엇이 되기를 바랐는지}
(3) 실제 결과: {무엇이 됐는지}
(4) 오류 원문: {화면의 빨간 글씨를 그대로 붙여넣기}

원인을 찾아 고치기 전에, 무엇 때문인지 한 줄로 먼저 알려 주세요.
```

> **왜 이렇게 말하나** — 네 가지를 나눠 적으면 AI가 추측하지 않는다. 요약하면 어느 줄에서 났는지가 사라진다.

## 되돌릴 때

```
방금 고친 것 때문에 앱이 안 됩니다. 마지막으로 잘 되던 상태로 되돌려 주세요.
되돌리기 전에 지금 상태를 따로 저장해 두고, 무엇이 지워지는지 먼저 알려 주세요.
```

> **왜 이렇게 말하나** — 되돌리는 것은 실패가 아니라 절차다. 되돌릴 수 있으면 더 과감하게 시도할 수 있다. 오늘부터는 실제 데이터가 들어가므로 무엇이 지워지는지 먼저 듣는 것이 더 중요하다.

## 말하지 않는 것

- 고객 실명·연락처·계좌·금액. 오늘 넣는 실제 업무 건도 앱 화면에서만 넣고, 대화창에 옮겨 적지 않는다.
- 데이터베이스 비밀번호·키·토큰. 대표님이 화면에서 복사해 설정 파일과 배포 화면의 비밀 칸에만 넣는다.
- "알아서 다 연결해 줘". 대표님이 눌러야 하는 화면(Supabase · GitHub · Vercel)이 있다 — 한 단계씩 듣고 누른다.
