# 3회차 — 이렇게 말하세요

> 3·4회차 배치는 가안 — 2회차 정리 뒤 확정(2026-10-08)

AI에게 넣을 문장 원문이다. **글자 그대로** 복사해서 쓰고 `{ }` 안만 우리 회사 것으로 바꾼다. 각 문장 아래 한 줄은 "왜 그렇게 말하는지"다.

오늘 끝내야 하는 것은 하나다. **고른 채널에서 대표가 ERP 운영 보고를 실제로 받는 것.** 완료 기준이 분명하다 — **내 컴퓨터와 AI를 모두 꺼도 보고가 온다.** 내 컴퓨터가 켜져 있을 때만 오는 것은 보고 체계가 아니다.

오늘 순서는 **보낼 곳 먼저**다. 디스코드·텔레그램을 둘 다 만들고(P1~P2), 그다음 무엇을·언제·누구에게 받을지 정하고(P3), 서버에 걸고(P5), 첫 수신을 확인한다(P6). 보낼 곳 없이는 보고를 만들 수 없다.

---

## P1 — 받을 창구 만들기 (디스코드·텔레그램 둘 다)

```
indeans-erp-channel 스킬을 읽고 시작해 줘.
디스코드와 텔레그램을 둘 다 만들 거야. 내가 직접 눌러야 하는 화면은 순서대로 하나씩 알려 줘.
비밀값은 .env.local 과 서버 쪽 비밀 저장에만 두고, 화면에 출력하거나 저장소에 올리지 마.
```

> **왜 이렇게 말하나** — 둘 다 만들어 보는 이유는 **한쪽이 막혔을 때 다른 쪽으로 갈 수 있기 때문**이다. 회사마다 쓰는 것이 다르고, 직원이 이미 쓰는 것이 있으면 그쪽이 낫다.
>
> 비밀값(웹훅 주소·봇 토큰)은 **한 번 새면 누구나 우리 채널에 글을 쓸 수 있다.** 화면에 출력하지 말라고 먼저 말해 둔다 — 대화 기록에 그대로 남는다.

---

## P2 — 실제로 도착하는지 확인

```
두 곳에 각각 한 줄씩 시험 발송을 해 줘. 내 폰에 도착하는 것까지 확인할 거야.
안 오면 어디까지 갔는지(만들기 → 주소 → 권한 → 보내기) 순서대로 짚어 줘.
company/channel.md 에 받는 사람과 여기로 보내지 않을 것을 적어 줘.
```

> **왜 이렇게 말하나** — "연결했습니다"는 연결이 아니다. **폰에 글자가 뜬 것**이 연결이다.
>
> "보내지 않을 것"을 같이 적는 이유: 채널은 저장소가 아니다. 고객 실명·연락처·계좌·금액은 보고 문장에 넣지 않는다. 지금 정해 두지 않으면 나중에 항목을 늘리다가 섞인다.

---

## P3 — 무엇을·언제·누구에게 (운영 보고 인터뷰)

```
indeans-erp-digest 스킬을 읽고 시작해 줘.
무엇을·언제·누구에게 받을지 한 번에 하나씩 물어봐 줘.
대표가 받을 것과 직원이 받을 것을 나눠서 물어보고, 내가 답하기 전에 항목을 정하지 마.
```

> **왜 이렇게 말하나** — 보고는 **앱을 열지 않아도 알아야 할 것**만 담는다. 열어 봐야 아는 것을 다 넣으면 아무도 안 본다.
>
> 받는 사람을 나누는 이유: 대표가 받을 것(오늘 들어온 건수·안 움직인 건)과 직원이 받을 것(내가 할 일)은 다르다. 같은 글을 모두에게 보내면 양쪽 다 자기 것이 아니라고 느낀다.

---

## P4 — 보내기 전에 문장부터 보기

```
예약을 걸기 전에 오늘 자 보고를 한 번 만들어서 문장만 보여 줘.
숫자가 실제 데이터와 맞는지 내가 대조할 수 있게 무엇을 어떻게 세었는지 같이 적어 줘.
아직 보내지는 마.
```

> **왜 이렇게 말하나** — 숫자가 틀린 보고는 안 오느니만 못하다. 한 번 틀리면 그다음부터 안 믿게 된다. **무엇을 세었는지**를 같이 받아야 대표가 화면과 대조할 수 있다.

---

## P5 — 서버에 예약 걸기

```
이 보고를 서버에서 자동으로 보내게 걸어 줘. 내 컴퓨터와 AI를 꺼도 와야 해.
시각은 한국 시간 {아침 8시}로 해 줘.
보낸 기록과 실패 기록을 남기고, 같은 날 두 번 보내지 않게 막아 줘.
걸고 나서 예약이 실제로 등록됐는지 조회해서 보여 줘.
```

> **왜 이렇게 말하나** — "예약했습니다"라고 적혀 있어도 서버에 줄이 없으면 예약된 것이 아니다. **등록됐는지 조회해서 보여 달라**고 해야 그 자리에서 확인된다.
>
> 시간대를 한국 시간으로 못 박는 이유: 서버는 대개 세계 표준시로 돈다. 그냥 "8시"라고 하면 오후 5시에 온다.

---

## P6 — 첫 수신 확인

```
예약 시각을 잠깐 몇 분 뒤로 바꿔서 한 번 받아 보고, 도착하면 원래 시각으로 되돌려 줘.
도착한 내용과 앱 화면의 숫자가 같은지 대조해 줘.
```

> **왜 이렇게 말하나** — 내일 아침까지 기다려서 확인하면, 안 왔을 때 고칠 자리에 아무도 없다. **수업 시간 안에 한 번 받아 본다.** 되돌리는 것까지 한 문장에 넣어야 시각이 몇 분 뒤인 채로 남지 않는다.

---

## P7 — 받아 보고 문구 고치기

```
받아 보니 {무엇}이 빠졌고 {무엇}은 필요 없어.
보고 항목을 고치고 company/digest.md 도 같이 고쳐 줘.
예약은 다시 걸지 말고 보내는 내용만 바꿔 줘.
```

> **왜 이렇게 말하나** — 예약을 다시 걸면 같은 보고가 두 개 걸려 하루에 두 번 온다. **내용만 바꾼다**를 명시한다.

---

## P8 — 보고가 안 올 때

```
오늘 보고가 안 왔어. 발송 기록부터 보여 줘.
예약이 돌았는지, 돌았는데 보내기에서 실패했는지, 아예 안 돌았는지 순서대로 짚어 줘.
원인을 찾기 전에 고치지 마.
```

> **왜 이렇게 말하나** — 안 온 이유는 셋 중 하나다. 예약이 안 돌았거나, 돌았는데 보내기가 실패했거나, 보냈는데 내 폰에서 알림이 꺼져 있거나. **기록을 먼저 보면** 어디를 고칠지가 바로 나온다.

## P9 — 오늘 것 검수·보고

```
indeans-erp-check 스킬을 읽고 오늘 바꾼 것을 검수해 줘.
정해진 시각에 나가는 보고의 조건이 바뀌었으니 그 부분을 특히 봐 줘.
비밀값이 저장소나 화면에 노출되지 않았는지도 같이 확인해 줘.
끝나면 보고서로 만들어 열어 줘.
```

> **왜 이렇게 말하나** — 정해진 시각에 자동으로 나가는 것은 **내가 안 보는 사이에** 돈다. 조건이 틀리면 모르는 채로 계속 틀린다. 그래서 검수 대상이다.

## 막혔을 때 (오류 전달)

```
(1) 하려던 것: {무엇을 하려 했는지}
(2) 기대한 결과: {무엇이 되기를 바랐는지}
(3) 실제 결과: {무엇이 됐는지}
(4) 오류 원문: {화면의 빨간 글씨를 그대로 붙여넣기}

원인을 찾아 고치기 전에, 무엇 때문인지 한 줄로 먼저 알려 주세요.
```

> **왜 이렇게 말하나** — 네 가지를 나눠 적으면 AI가 추측하지 않는다. 채널 쪽 오류는 특히 원문에 답이 들어 있다(주소가 틀렸나, 권한이 없나, 형식이 틀렸나).

## 되돌릴 때

```
방금 고친 것 때문에 앱이 안 됩니다. 마지막으로 잘 되던 상태로 되돌려 주세요.
되돌리기 전에 지금 상태를 따로 저장해 두고, 무엇이 지워지는지 먼저 알려 주세요.
```

> **왜 이렇게 말하나** — 되돌리는 것은 실패가 아니라 절차다. 다만 **서버에 걸어 둔 예약은 되돌려도 남는다** — 예약까지 지울지 먼저 물어보게 한다.

## 권한 단계 (가안) — 2회차에서 옮겨 온 문장

> 2026-10-08 개편으로 사람·권한(누가 무엇을 보는지 · 역할별 화면 · 로그인 나누기)은 2회차에서 빠져 「권한 단계」로 옮겼다. 3회차에 둘지는 2회차를 정리한 뒤 정한다(가안). 아래 세 문장은 옛 2회차 원문을 **그대로** 옮긴 것이다 — 권한 단계를 확정할 때 `indeans-erp-people` 개정판(노출 표 → 롤백 시뮬 → 가장 권한 낮은 자리에서 실측)에 맞춰 다시 본다.

### 권한 1 — 사람·권한 인터뷰 (옛 2회차 P9)

```
indeans-erp-people 스킬을 읽고 시작해 줘.
질문은 한 번에 하나씩. 다 묻기 전에는 코드를 만들지 마.
'절대 보이면 안 되는 것'을 물을 때는 내가 '없다'고 해도 넘어가지 말고,
금액·단가·다른 고객 건·직원끼리 안 보였으면 하는 것을 하나씩 짚어서 다시 물어봐.
작업 전에 되돌릴 지점(커밋)을 먼저 만들어 줘.
```

> **왜 이렇게 말하나** — 권한 설계의 출발점은 "무엇을 보여 줄까"가 아니라 "무엇은 절대 안 된다"이다. 이 목록이 나중에 확인할 체크리스트가 된다.

### 권한 2 — 권한을 앱에 반영 (옛 2회차 P10)

```
인터뷰 내용을 company/people.md 로 저장하고 앱에 반영해 줘.
1) 로그인을 붙이고, 아무나 가입되는 화면은 만들지 마
2) 대표와 직원 두 역할로 나누고, 역할마다 첫 화면을 정해 줘
3) 내가 말한 '보면 안 되는 것'은 어느 화면에서도 안 보이게 해 줘

--- 아래는 AI에게 주는 규칙입니다. 뜻을 모르셔도 됩니다. 지우지 말고 그대로 두세요 ---
· 역할 칸은 비워 둘 수 없게 하고 활성 여부 칸을 둘 것
· 역할 판정 함수의 실행 권한은 절대 회수하지 말 것
· 모든 표를 먼저 잠그고 필요한 것만 역할별로 다시 열 것
· 권한 검사는 '이 역할이면 허용'으로 쓰고 '이 역할이 아니면 거부'로 쓰지 말 것
· 화면에서 숨기는 것으로 끝내지 말고 데이터를 가져오는 자리에서 막을 것
· 내가 고른 두세 가지 행동에만 누가 언제 했는지 기록을 남길 것
· 기존 마이그레이션 파일은 고치지 말고 새 번호로 만들 것
```

> **왜 이렇게 말하나** — "이 역할이 아니면 거부"로 쓰면 역할이 비어 있는 계정이 검사를 그냥 통과한다. 빈칸은 "아니오"가 아니다.

### 권한 3 — 권한 확인 — 가장 권한 낮은 자리에서 (옛 2회차 P11)

```
역할별 테스트 계정을 만들어 주고, 내가 직접 로그인해서 확인할 순서를 알려 줘.
company/people.md 의 '보면 안 되는 것' 목록을 한 줄씩 대조할 수 있게 표로 정리해 줘.
목록 화면뿐 아니라 상세·검색·사진이나 파일까지 확인할 곳을 알려 줘.
역할 칸이 빈 계정도 하나 만들어 줘. 그 계정으로는 아무것도 안 보여야 맞는 거지?
테스트 계정은 가짜 이름으로 만들고, 비밀번호는 화면에 출력하지 마.
```

> **왜 이렇게 말하나** — 권한은 가장 권한이 낮은 사람의 자리에서 확인해야 한다. 관리자 화면에서 규칙만 보는 것은 확인이 아니다.
>
> 로그아웃한 상태로 목록 화면 주소를 직접 열어 보는 것도 같이 한다. **화면에서 안 보이는 것과 데이터가 막힌 것은 다르다.**
