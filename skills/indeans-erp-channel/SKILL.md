# 인디언즈 알림 채널 연결

**이 스킬의 역할은 "보고를 받을 창구 만들기"다.** 무엇을 언제 보낼지 정하고 서버에 예약하는 일은 `indeans-erp-digest` 가 한다. 여기서는 **보낼 곳**과 **받는 사람**을 정하고, 그곳으로 글자 한 줄이 실제로 도착하는 것까지 확인한다.

운영 보고 단계의 첫 실습. 창구가 없으면 운영 보고를 만들 수 없으니 이 스킬이 먼저다.

인디언즈가 알림을 운영하며 굳힌 원칙 하나를 그대로 쓴다: **알림은 "관련자에게만" 간다.** 모두에게 같은 것을 보내면 직원 방에 대표만 볼 것이 섞이고, 소음이 늘어 결국 아무도 안 본다. 그래서 창구를 만들기 전에 **누가 무엇을 받는지 표로 먼저 정한다.**

## 언제 쓰나

- 앱이 보내는 보고·알림을 폰으로 받고 싶을 때.
- 직원도 알림을 받게 하거나, 창구를 하나 더 늘리거나, 받는 사람을 바꿀 때.
- 보내던 것이 갑자기 안 올 때(주소가 무효가 됐는지 확인).

쓰지 않는 경우: 무엇을 언제 보낼지(→ `indeans-erp-digest`), 작업이 끝날 때 보여 주는 보고서(→ `indeans-erp-report`), 앱 화면 안 배지·표시(→ `indeans-erp-review`).

## 시작 전 상태 진단

먼저 읽고 판정한다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | `channel.discord`·`channel.telegram`, 저장·배포가 끝났는지 |
| `.owner/accounts.md` | 1회차에 이미 만든 **디스코드 서버·채널**, 텔레그램 가입 여부(비밀값은 없다) |
| `company/channel.md` | 창구를 이미 만들었나(있으면 '진행 중') |
| `company/people.md` | 역할 — 누가 받아야 하나, **보면 안 되는 것**(직원 방에 보내면 안 되는 것과 같다) |
| `company/profile.md` | 회사 이름(보고 첫 줄) |
| `.env.local` · `.gitignore` | 비밀값을 둘 자리가 있나, 커밋에서 빠져 있나 (**값은 화면에 출력하지 않는다**) |

**상태 문서가 실제와 다르면 문서를 믿지 않는다.** "연결됨"이라고 적혀 있어도 테스트 발송이 도착하지 않으면 연결된 것이 아니다.

- **처음** — `company/channel.md` 없음 → 절차 0부터. `.owner/accounts.md` 에 서버·채널이 이미 있으면 3절의 만들기 단계는 건너뛰고 웹후크만 받는다.
- **진행 중** — 한쪽만 있음 → 있는 쪽은 테스트 발송으로 살아 있는지만 보고, 없는 쪽을 만든다.
- **완료** — 라우팅 표가 있고 테스트가 도착함 → 「앞선 수강생 분기」.

판정을 한 문장으로 먼저 알린다. 예: "디스코드 서버는 1회차에 만들어 두셨습니다. 받는 사람부터 정하고, 웹후크와 텔레그램 봇을 만들어 한 줄씩 보내 보겠습니다."

## 절차

### 0. 되돌릴 지점과 비밀 파일 확인

```bash
git add -A
git commit -m "알림 채널 연결 전 상태"
```

`git check-ignore -v .env.local` 이 한 줄을 내는지 본다. 안 나오면 `.gitignore` 에 `.env.local` 을 먼저 추가하고 커밋한다. **웹훅 주소나 봇 열쇠가 한 번 올라가면 파일을 지워도 기록에 남는다.**

### 1. 왜 둘인가 (2분, 세 문장)

> 디스코드는 **쌓이는 쪽**입니다. 지난 보고를 찾아보고 파일도 올려 둘 수 있습니다.
> 텔레그램은 **바로 아는 쪽**입니다. 폰에 즉시 뜨고 대표님 혼자 보기에 편합니다.
> 둘 중 하나는 회사 사정에 따라 안 쓰게 됩니다. 둘 다 만들어 두고, 쓰다가 고르시면 됩니다.

슬랙을 이미 쓰는 회사면 `references/slack.md` 로 셋째 창구를 안내한다. 슬랙을 기본으로 바꾸지는 않는다.

### 2. 수신자 라우팅 — 누가 어느 방에서 무엇을

질문은 하나씩.

1. > "앱이 알려 줘야 할 사람이 누구입니까? 대표님만인가요, 직원도인가요?"
2. (직원도면) > "직원이 받으면 **안 되는** 것이 있나요?" — `company/people.md` 의 "보면 안 되는 것"을 먼저 읽어 주고 더할 것만 받는다.
3. > "이 중에 **받았다는 표시가 꼭 필요한** 알림이 있습니까? 예를 들어 꼭 읽어야 하는 공지 같은 것이요."

답으로 `company/channel.md` 2절의 **라우팅 표**를 채운다.

| 받는 사람 | 창구(방) | 무엇을 받나 | 언제 | 확인 필요 | 보내지 않는 것 |
|---|---|---|---|---|---|
| 대표 | 대표용 방 | 운영 보고(전체) | 정해진 시각 | 없음 | — |
| 직원 | 직원용 방 | 오늘 할 일 건수 | 정해진 시각 | 없음 | 금액·다른 사람 평가·확정 안 된 일정 |

판단 기준:

- **방은 받는 사람 종류마다 하나.** 대표만이면 대표용 하나로 끝낸다. 직원도면 대표용·직원용 **둘로 나눈다** — 직원 방에는 직원이 앱에서도 못 보는 것을 보내지 않는다(노출 표와 같은 규칙이다).
- **같은 문장을 두 방에 보내지 않는다.** 직원용은 항목을 줄인 다른 문장이다(`indeans-erp-digest` 가 만든다).
- **고객은 회사 채널에 넣지 않는다.** 고객에게 알릴 것은 앱 안의 고객 화면이나 이 과정 밖의 문자·메일 서비스로 한다. 회사 디스코드 서버·텔레그램 그룹에 고객을 초대하면 다른 고객 건과 내부 대화가 같이 보인다.
- **확인 필요**는 대부분 "없음"이다. 처리가 필요한 일(기한 지난 건)은 앱에서 그 건을 처리하면 확인된 것이고, 다음 보고에 남은 건수로 다시 나온다. 읽었다는 표시가 정말 필요한 공지만 "있음"으로 두고, 그 방법(앱 안 확인 버튼·확인 기록·보관 기간)은 `indeans-erp-digest` 가 만든다.
- 답이 애매하면 대표용 하나로 시작한다. 늘리는 것은 나중에 5분이면 된다.

### 3. 디스코드 웹훅 — 대표가 직접 누른다

`references/discord.md` 를 화면 순서대로 읽어 주고 대표가 누른다. `.owner/accounts.md` 에 서버·채널이 이미 있으면 1번은 건너뛴다.

1. 서버(없으면 만들기) → 라우팅 표의 방마다 **채널** 하나(예: `운영보고`, `직원알림`).
2. 그 채널의 **톱니(채널 편집)** → **연동** → **웹후크** → **새 웹후크** → 이름을 알아보게(예: `우리회사 보고`) → **웹후크 URL 복사**.
3. 방이 둘이면 두 번째 채널에서 한 번 더.
4. 만든 서버·채널 **이름**을 `.owner/accounts.md` 디스코드 줄에 더한다(주소는 적지 않는다).

이 주소가 곧 열쇠다. **주소를 아는 사람은 누구나 그 채널에 글을 쓸 수 있다**(읽지는 못한다). 화면 공유·캡처·문서에 붙이지 않는다.

### 4. 텔레그램 봇 — 대표가 직접 누른다

`references/telegram.md` 순서대로. `@BotFather` → `/newbot` → 봇 이름 → 봇 아이디(`_bot` 으로 끝남) → **봇 열쇠(토큰)** 를 받는다 → 봇과의 대화방에서 **`/start` 를 보낸다**(안 하면 봇이 먼저 말을 걸 수 없다) → 받을 방 번호(`chat_id`) 확인. 직원도 받으면 텔레그램 **그룹**을 만들어 봇을 초대하고 그 그룹의 방 번호를 하나 더 받는다(그룹 번호는 음수 — 정상이다).

### 5. 비밀값을 두는 곳은 두 군데뿐이다

| 어디 | 무엇을 | 왜 |
|---|---|---|
| `.env.local` | 내 컴퓨터에서 테스트 발송할 때 쓰는 값 | 커밋되지 않는다 |
| Supabase 의 설정 표 `app_secret` | 서버가 정해진 시각에 보낼 때 쓰는 값 | 내 컴퓨터가 꺼져 있어도 서버가 읽어야 한다 |

```
DIGEST_DISCORD_URL=<대표용 웹후크 주소>
DIGEST_TELEGRAM_TOKEN=<봇 열쇠>
DIGEST_TELEGRAM_CHAT_ID=<대표용 방 번호>
```

- 직원용 방이 있으면 이름 끝에 `_STAFF` 를 붙여 따로 둔다(`DIGEST_DISCORD_URL_STAFF` 등). 대표용과 한 이름에 섞지 않는다.
- **`VITE_` 를 붙이지 않는다.** `VITE_` 로 시작하는 값은 앱을 쓰는 사람 화면까지 따라 내려간다.
- 서버 쪽 저장은 `indeans-erp-digest` 의 `references/cron-sql.md` 2절 순서를 따른다(안전선 두 줄을 빼지 않는다).
- **소스·마이그레이션·회사 문서에는 값을 적지 않는다.** 문서에는 이름만(`DIGEST_DISCORD_URL`). 고정 검사(`npm run check`)가 파일에 적힌 웹후크 주소·봇 열쇠를 찾으면 막는다.
- 값이 새면 디스코드는 웹후크를 지우고 새로 만들고, 텔레그램은 `@BotFather` 의 `/revoke` 로 새 열쇠를 받는다. 지우면 옛 주소는 바로 죽는다.

### 6. 테스트 발송 — 도착을 눈으로 본다

`assets/channel-test.template.mjs` 를 `scripts/channel-test.mjs` 로 복사해 실행한다(Node 18 이상).

```bash
node scripts/channel-test.mjs
```

- 두 창구에 한 줄씩 보내고 어디에 성공·실패했는지 찍는다. **비밀값은 찍지 않는다.**
- 대표가 **폰에서 실제로 도착한 것을 보고 "왔다"고 말할 때까지** 끝내지 않는다. 명령이 오류 없이 끝난 것은 도착의 증거가 못 된다.
- **도착을 본 뒤, 주소 끝 한 글자를 일부러 바꿔 한 번 더 보내 실패가 어떻게 보이는지 미리 본다**(어느 창구가 실패했는지·응답 번호). **확인한 뒤 원래대로 되돌리고** 한 번 더 보내 도착까지 확인한다. 바꾼 주소를 그대로 두면 이후 보고가 전부 조용히 실패한다.
- 보내는 글자 규칙: 디스코드 2,000자·텔레그램 4,096자까지 — 보고는 **10줄 이내**. 짧은 시간에 여러 번 보내면 잠시 막힌다. **고객 실명·연락처·금액·계좌는 보내지 않는다** — 채널은 회사 밖 서비스다.

### 7. 문서로 남긴다

`assets/channel.template.md` 를 채워 `company/channel.md` 로 저장한다. 절 제목과 순서를 바꾸지 않는다 — `indeans-erp-digest` 가 이 문서를 읽는다.

### 8. 상태 문서 갱신과 커밋

`.owner/state.md` — 현재 기능("대표용 디스코드·텔레그램 창구 있음(테스트 도착 확인)") · 미해결 문제 · 다음 행동("운영 보고 만들기(`indeans-erp-digest`)"). `.owner/progress.json` — `channel.discord`·`channel.telegram` 을 `true`, `updated_at`.

```bash
git add -A
git commit -m "알림 채널: 수신자 라우팅·창구 연결·테스트 발송"
```

화면·저장 구조·권한을 바꾸지 않았으면 검수는 생략된다(위험 등급 4). 검수 훅이 요구하면 `indeans-erp-check` 를 부른다.

## 하지 않는 것

- 웹훅 주소·봇 열쇠·방 번호를 소스·문서·커밋·화면에 적지 않는다. `VITE_` 이름에 넣지 않는다.
- 대표를 대신해 디스코드·텔레그램 계정을 만들지 않는다. 계정과 방은 회사 것이어야 한다.
- 같은 문장을 대표용·직원용 두 방에 보내지 않는다. 고객을 회사 채널에 넣지 않는다.
- 무엇을 언제 보낼지 여기서 정하지 않는다(`indeans-erp-digest`).
- 도착을 확인하지 않고 "연결했습니다"라고 보고하지 않는다.
- 슬랙·카카오·문자 연동을 이번 단계에 벌이지 않는다. 슬랙은 `references/slack.md` 의 선택 안내까지다.

## 앞선 수강생 분기

창구가 이미 살아 있으면 하나만 고른다.

1. **직원용 방 분리** — 대표용과 직원용 방을 나누고, 라우팅 표의 '보내지 않는 것'을 노출 표(`people.md`)와 한 줄씩 대조한다. 목록이 없으면 언젠가 섞여 나간다.
2. **한쪽이 죽었을 때** — 보고가 실패하면 다른 창구로 한 번 더 보내는 규칙을 라우팅 표에 적는다. 구현은 `indeans-erp-digest` 의 실패 기록과 함께 붙인다.
3. **소음 줄이기** — 오는 것이 많아 안 보게 됐으면 창구를 늘리지 말고 **보내는 항목을 줄인다.** "매일 오는데 아무 행동도 안 하게 되는 줄"을 찾아 뺀다.

## 자주 막히는 지점

- **디스코드에 아무것도 안 온다** — 주소를 끝까지 복사했는지, 채널이나 웹후크를 지우지 않았는지 본다.
- **텔레그램에 안 온다** — 대개 봇에게 `/start` 를 안 보낸 것이다.
- **방 번호를 못 찾는다** — 봇에게 아무 말이나 한 줄 보낸 뒤 다시 확인한다.
- **그룹에 초대했는데 안 온다** — 그룹 번호는 음수(`-100...`)다. 개인 방 번호를 쓰고 있지 않은지 본다.
- **오류 없이 끝나는데 안 온다** — 응답 번호를 본다. 200대가 아니면 도착하지 않은 것이다.
- **값을 실수로 커밋했다** — 파일만 지워도 기록에 남는다. 웹후크는 다시 만들고 봇 열쇠는 `/revoke` 로 새로 받는다.
- **직원이 "대표 방 것도 보여요"라고 한다** — 같은 방을 같이 쓰고 있다. 라우팅 표대로 방을 나누고, 직원 방 웹후크를 새로 만든다.
- **회사 정책상 디스코드·텔레그램을 못 쓴다** — 이미 쓰는 도구(슬랙·이메일)로 간다. 둘 다 안 되면 보고를 **앱 안 화면**으로 받는 방식을 `indeans-erp-digest` 에서 정한다.
