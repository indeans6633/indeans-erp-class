# 인디언즈 검수 (감독·검증 호출)

**이 스킬의 역할은 "감독·검증 호출"이다.** 이미 바꾼 것이 괜찮은지 보는 자리다. 무엇을 고칠지 정하고 실제로 고치는 자리는 `indeans-erp-review`(가져온 앱 진단·개선)다. 둘을 겹쳐 하지 않는다.

이 검수는 **1회차 설치 직후부터** 돈다. 실사용 준비 단계는 새로 켜는 자리가 아니라 "이미 돌던 체계를 이해하고 복구를 연습하는" 자리다.

인디언즈가 자체 앱에서 쓰는 원칙을 그대로 옮겼다: **되돌리기 어려운 실수(권한 누수·돈 데이터 오염)는 배포 전에 감독이 보고, 되돌릴 수 있는 실수(화면)는 가볍게 본다.** 모든 변경을 같은 무게로 검수하면 정작 위험한 변경을 볼 힘이 남지 않는다.

## 언제 쓰나

- 작업을 끝낼 때 검수 훅이 종료를 막고 요구했을 때(가장 흔하다).
- 화면·저장 구조·권한·돈·배포 설정·삭제 조건을 바꾼 직후, 그리고 배포 바로 전.
- 대표가 "이대로 괜찮은지 봐 줘"라고 할 때.

## 위험 등급표 — 누가 무엇을 보나

훅(`.owner/hooks/erp-check.mjs`)은 "검수가 필요한 변경인가"만 가른다. **누가 볼지는 이 표로 정한다.** 여러 줄에 걸리면 가장 높은 등급을 따른다. 줄 수로 판단하지 않는다 — 한 줄이어도 1등급이면 1등급이다.

| 등급 | 바뀐 것 | 감독 | 검증(`erp-verifier`) | 그 밖 |
|---|---|---|---|---|
| 1 감독 필수 | **권한**(역할·로그인·정책·공개 범위·새 뷰·데이터를 돌려주는 새 함수) · **돈**(금액 칸·계산·입금·증빙) · **새 표 구조**(표·칸 추가·삭제·이름·형식) · **삭제 조건**(지우는 동작·되돌릴 수 없는 처리) · **배포 설정**(`vercel.json`·환경 변수·접속 정보·설치 부품) | `erp-supervisor` (화면도 바뀌었으면 `erp-design-supervisor` 같이) | 필수. 정책·제약이면 적용 전 롤백 시뮬 + 역할별 실측, 돈이면 손계산 1건, 배포면 배포 뒤 스모크 | 권한·돈은 적용 뒤 `erp-auditor` 감사 1회 |
| 2 화면 | 새 화면·화면 동작·배치(데이터·권한 영향 없음) | `erp-design-supervisor` | 캡처 375·1280 — 기능당 1회. 고친 뒤 다시 찍을 때는 바뀐 화면만 375 | — |
| 3 감독 생략 | 읽기 전용(이미 허용된 조회를 다른 모양으로 보여 주기)·보고 문구·설정 값(알림 시각 등)·1등급이 아닌 마이그레이션(인덱스 추가 등) | 생략 | 그 동작만 1회(예: 보고 함수를 한 번 불러 본다) | 고정 검사 `npm run check` |
| 4 생략 | 문구·주석·정해진 색 안의 색·문서 | 생략 | 생략(빌드로 확인) | 표식만 갱신 |

- "읽기 전용"이어도 **새 뷰·데이터를 돌려주는 새 함수는 1등급**이다. 새 노출 경로이고, 뷰는 잠금을 건너뛸 수 있다.
- 대표가 "빨리"라고 해도 등급은 내려가지 않는다. 시간이 없으면 감독 판정까지만 받고 실측을 다음으로 미루는 것은 된다(자주 막히는 지점).
- 이 표는 `erp-supervisor` 의 위험 등급표와 같은 줄이다. 하나를 고치면 다른 하나도 고친다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/last-check.json` | 마지막으로 검수를 마친 지점(`commit`)·요구 횟수(`nag`) |
| `git status --porcelain` · `git log --oneline -5` · `git diff --stat` | 실제로 무엇이 바뀌었는지. **기억이 아니라 이것을 근거로 한다** |
| `.owner/state.md` · `.owner/progress.json` | 이번에 무엇을 하려 했는지·미해결 문제 |
| `company/*.md` | 요청 범위·"이번에 만들지 않을 것"·고른 디자인·권한·돈 규칙 |
| `.owner/precedents.md` | 판례 노트 — 이번 변경과 같은 유형의 사고·반려가 있었나 |
| `.claude/agents/` · `.codex/agents/` | 에이전트 4종(`erp-supervisor`·`erp-design-supervisor`·`erp-verifier`·`erp-auditor`)이 있는지 **파일을 눈으로** 확인 |
| `reports/` | 오늘 같은 작업의 보고서가 이미 있는지(있으면 갱신) |

- **바뀐 것 없음** → "검수할 변경이 없습니다"라고 알리고 멈춘다.
- **4등급뿐** → 이유를 한 줄로 말하고 절차 8(표식)만 한다.
- **3등급까지** → 절차 1 → 5(그 동작만) → 8 → 9.
- **1·2등급** → 절차 1~9 전부.
- **에이전트 없음** → 설치기를 다시 돌리게 안내한다. 그래도 없으면 `.claude/agents/<이름>.md`(또는 `.codex/agents/<이름>.toml`)를 직접 읽어 그 기준으로 점검하고 **"감독 에이전트 없이 자체 점검했다"를 보고서에 적는다.**

판정을 한 문장으로 먼저 알린다. 예: "목록 화면과 표 칸이 바뀌었습니다 — 1등급(새 표 구조)입니다. 감독 판정부터 받겠습니다."

## 절차

### 1. 변경 요약과 등급

감독에게 보낼 요약을 만든다. **파일 목록을 그대로 붙이지 않고** 여섯 줄로.

```
무엇을 하려 했나: {대표의 요청 원문 또는 상태 문서의 다음 행동}
무엇을 바꿨나: {화면·저장·권한·돈 기준으로 2~4줄}
바꾼 파일: {경로 목록 — 감독이 직접 읽는다}
위험 등급: {1~4 와 걸린 줄 — 예: 1(새 표 구조·권한)}
확인받고 싶은 것: {스스로 걸리는 지점. 없으면 "없음"}
범위 밖으로 손댄 것: {있으면 솔직히. 없으면 "없음"}
```

이 요약이 보고서 본문의 뼈대가 된다. `indeans-erp-review` 가 넘긴 **"디자인 감사" 표**(찾기만 한 화면 문제 목록)가 있으면 "확인받고 싶은 것"에 그대로 붙인다 — 그 표는 `erp-design-supervisor` 가 판정한다.

### 2. 감독 판정 받기 (1·2등급)

- Claude Code 에서는 감독을 **서브에이전트로 띄워**(에이전트 이름을 지정해) 요약을 그대로 보낸다. 둘 다 필요하면 **같이 띄운다**(서로의 답을 보지 않아도 된다).
- Codex 에서는 `.codex/agents/<이름>.toml` 로 등록된 사용자 정의 에이전트를 부른다: `erp-supervisor 에이전트로 이 변경을 검토해 줘.`
- 보낼 것: 요약 + 바꾼 파일 경로 + (화면이면) 캡처 경로. 감독은 제안이 아니라 **저장소에 있는 실제 코드**를 읽는다.

받는 답은 **승인 / 조건부 승인(수정사항) / 반려(이유)** 중 하나다. 요약하지 말고 지적 원문을 그대로 들고 다음 단계로 간다.

### 3. 조건부·반려 — 고치고 다시, 멈추는 기준은 처음에 정해 둔다

- **반려** → 지적을 고치고 **같은 감독에게 다시** 받는다. 승인 전에는 다음 단계로 가지 않는다.
- **조건부 승인** → 조건을 다 반영한 뒤 "조건 N개 반영"을 알리고 확인받는다.
- **다시 받기는 최대 2번.** 두 번 반려되면 멈추고 대표에게 지적 원문과 세 갈래를 보여 준다: 한 번 더 고친다 / 범위를 줄인다 / 되돌린다. 끝없이 고치고 다시 받는 것은 검수가 아니라 표류다.
- **막는 것은 "이번 작업이 만든 회귀 + 이번 범위 안의 치명"뿐이다.** 감독이 원래 있던 문제를 짚으면 `.owner/state.md` 미해결 문제에 적고 대표에게 한 줄로 묻는다 — 이번 작업을 그것으로 막지 않는다.
- 감독 판정과 대표 지시가 다르면 **대표 지시가 우선**이다. 다만 어긋난 내용(무엇을 왜 지적했는지)을 대표에게 그대로 알리고, 대표가 그대로 가자고 하면 그 사실을 보고서에 남긴다.
- 감독이 "범위 밖"이라고 한 것은 되돌리고, 되돌린 것도 보고서에 적는다.

### 4. 롤백 시뮬 (정책·제약·데이터를 바꾸는 SQL 이 있을 때)

마이그레이션을 데이터베이스에 **적용하기 전에** `references/rollback-sim.md` 의 틀로 한 번 돌려 본다. 바꾸고·세고·결과를 일부러 오류로 띄워 **전부 되돌리는** 방식이다(SQL Editor 는 마지막 한 문장의 결과만 보여 주기 때문). 결과(직원 N줄·대표 N줄·로그인 안 함 막힘 / 맞는 값 들어감·틀린 값 막힘)를 보고서에 옮기고, 기대와 다르면 적용하지 않고 2단계로 돌아간다. 적용한 뒤에는 `company/data.md` 실행 기록에 한 줄.

### 5. 검증자 실측

승인(또는 조건 반영)이 끝나면 `erp-verifier` 에게 실측을 맡긴다(Claude 는 서브에이전트, Codex 는 `erp-verifier 에이전트로 실측해 줘.`). 검증자는 판정하지 않는다 — 실제로 띄워 보고 본 사실만 돌려준다. 해당되는 것만 순서대로:

1. 앱 띄우기(`npm run dev`) — 출력에 찍힌 **실제 주소**를 쓴다.
2. 화면 사진 — `node .owner/hooks/capture.mjs --url <실제 주소> --path "<경로>"`(375·1280). 버튼을 눌러야 나오는 화면은 `--click "<버튼 글자>"` 를 더한다(예: `--path "/" --click "오늘 할 일"`). **화면 오류 건수를 함께 받는다.**
3. 빌드 — `npm run build` 성공/실패와 오류 원문. 고정 검사 `npm run check` 결과.
4. **저장·재접속** — 입력한 뒤 새로고침, 다른 브라우저·다른 계정으로 다시 접속해도 남아 있는지.
5. **역할별 접근 차단**(권한이 있는 앱) — 다른 역할 계정으로 숨긴 화면 주소를 직접 열고, 그 역할로 표를 읽어 본다. **화면에서 안 보이는 것은 차단이 아니다.**
6. **돈**(돈이 바뀐 경우) — 실제 1건을 넣고 화면의 합계·남은 돈을 대표가 계산기로 맞춰 본다.
7. **배포 뒤 스모크**(배포한 경우) — 주소·새 파일 200·없는 파일 404·로그인 없이 목록 주소.
8. **휴대폰 실기**(새 화면·입력 폼인 경우) — 검증자가 만든 확인표를 대표가 자기 폰으로 따라 하고 결과를 받아 적는다.

검증자가 "못 했다"고 한 항목은 못 한 것으로 적는다. 추측으로 채우지 않는다.

### 6. 감사 (권한·돈을 적용한 뒤 1회)

권한이나 돈 구조를 데이터베이스에 적용했으면 `erp-auditor` 를 부른다. 감사관은 **읽기 전용** 질의를 `.owner/tmp/audit.sql` 로 만들어 준다 → 대표가 SQL Editor 에서 실행해 결과 표를 `.owner/tmp/audit-result.csv` 로 저장 → 감사관을 다시 불러 결과를 읽게 한다. 감사 기록은 **`reports/<날짜>-감사.md`** 에 남는다(건수와 행 번호(id)만 — 고객 이름·금액 값은 없다). **치명 발견이 있으면 배포하지 않고** 그것부터 고친다. 감사관은 고치지 않는다 — 고치는 것은 2단계로 돌아가는 새 작업이다.

### 7. 보고서

`indeans-erp-report` 로 보고서를 만든다. **"검수 결과" 절**에: 위험 등급, 감독 판정(원문 요지), 롤백 시뮬 결과, 실측 결과(사진 장수·화면 오류 건수·빌드·저장·접근 차단·손계산), 감사 결과, 조건부였으면 무엇을 고쳐 다시 승인받았는지. 같은 작업의 보고서가 있으면 **같은 제목·같은 `--slug`** 로 다시 만들어 갱신한다. 감독 없이 자체 점검했으면 그 사실을 적는다.

### 8. 검수 표식 갱신

보고서까지 끝난 뒤 `.owner/last-check.json` 을 갱신한다. **커밋을 먼저 하고, 그 커밋 번호를 적는다.**

```
git add -A
git commit -m "검수 — {무엇을 바꿨나}"
git rev-parse HEAD
```

```json
{
  "commit": "{git rev-parse HEAD 결과}",
  "at": "{지금 시각 — 2026-10-08T14:30:00+09:00 형태}",
  "tool": "claude",
  "grade": 1,
  "result": "승인",
  "report": "reports/2026-10-08-오늘-현황-화면-추가.html"
}
```

- `tool` 은 지금 쓰는 도구(`claude` 또는 `codex`). `nag` 칸은 지운다(요구 횟수를 되돌린다).
- `result` 는 마지막 판정: `승인` / `승인(조건 반영)` / `감독 생략 — 3등급(읽기 전용)` / `생략 — 문구만`.
- **3·4등급으로 생략한 경우에도 같은 파일을 갱신하고 두 칸을 비우지 않는다.** `commit` 에는 지금 `HEAD`(커밋할 것이 없으면 `git rev-parse HEAD` 결과 그대로), `skipped_files` 에는 생략한 파일 경로 배열. 훅은 이 목록의 파일이 그 `commit` 이후 다시 바뀌지 않았으면 건너뛴다 — 비워 두면 다음에 같은 파일을 또 요구한다.

```json
{ "commit": "{HEAD}", "at": "{지금 시각}", "tool": "claude", "grade": 4, "result": "생략 — 문구만", "skipped_files": ["src/screens/ListScreen.tsx"] }
```

- **판정을 받지 않았는데(1·2등급) 이 파일을 갱신하지 않는다.** 그건 검수를 건너뛴 것이다.

### 9. 상태 문서와 판례 노트

- `.owner/state.md` — "현재 기능"에 이번에 확인된 것, "미해결 문제"에 미룬 지적·검증자가 못 한 항목·감사 주의 항목, "다음 행동"에 다음 스킬. `.owner/progress.json` 의 해당 값과 `updated_at`.
- **반려를 받았거나, 되돌렸거나, 감독이 놓친 것이 나중에 발견됐으면** `.owner/precedents.md` 에 한 줄 더한다(형식은 `indeans-erp-routine` 의 `references/precedents.md`). 같은 유형이 이미 있으면 그 줄의 '같은 유형' 칸에 번호를 잇고 승격 칸을 `대기` 로 바꾼다 — 주간 점검 때 규칙으로 올린다.

마지막으로 대표에게 3줄: 판정(등급 포함) / 실측·감사에서 확인된 것 / 남은 것.

## 판정 캘리브레이션 — 감독의 답을 다루는 법

- **승인이어도 실측이 다르면 실측이 이긴다.** 감독은 코드를 읽었고, 검증자는 화면을 봤다. 둘이 어긋나면 그 사실이 곧 다음 확인 항목이다.
- **조건부 승인은 "방향이 맞고 빠진 조각만 채우면 되는" 경우다.** 조건이 한 줄씩 확인할 수 없을 만큼 크면 반려로 받아들이고 계획부터 다시 세운다.
- **반려가 기본인 경우** — 잘 되던 기능의 퇴행 · 저장된 내용의 오염(예: 금액에 다른 값이 섞임) · 요청 밖의 규칙 변경이 함께 들어 있음 · 판례 노트에 이미 있는 유형의 재발.
- 감독 둘의 말이 다르면 권한·데이터·돈은 `erp-supervisor`, 화면은 `erp-design-supervisor` 가 최종이다. 겹치는 지점(숨긴 화면)은 권한 쪽을 따른다.
- 같은 지적이 세 번째면 사람이 조심하는 대신 판례 노트에서 규칙으로 승격한다(`indeans-erp-routine`).

## 산출물

| 경로 | 내용 |
|---|---|
| `reports/<날짜>-<제목>.html` | 검수 결과가 들어간 작업 보고서 |
| `reports/<날짜>-감사.md` | 감사를 했으면 감사 기록(건수·행 id 만, `erp-auditor` 가 쓴다) |
| `.owner/last-check.json` | 검수를 마친 지점(커밋·시각·도구·등급·판정·보고서. 생략이면 `commit`·`skipped_files`) |
| `.owner/precedents.md` | 반려·되돌림·놓침이 있었을 때 한 줄 |
| `.owner/state.md` · `.owner/progress.json` | 갱신 |
| 커밋 1개 | `검수 — {무엇을 바꿨나}` |

## 하지 않는 것

- 무엇을 고칠지 정하기(`indeans-erp-review`). 감독 판정 없이(1·2등급) 표식만 갱신하기.
- 감독의 지적을 요약하거나 순한 말로 바꿔 전달하기. 원문을 그대로 대표에게 보여 준다.
- 반려를 받은 채로 다음 단계·배포로 넘어가기. 롤백 시뮬 없이 정책·제약을 적용하기.
- 검증자에게 판정을, 감독에게 실측을, 감사관에게 수정을 맡기기.
- 실측하지 않은 항목을 "확인했다"로 적기.
- 검수 훅·배포 직전 훅을 지우거나 끄기. 요구가 반복돼 막히면 검수 훅이 스스로 세 번째부터 경고만 낸다.
- 배포. 배포는 `indeans-erp-data` 의 절차다. 검수는 배포 **전에** 한다.

## 앞선 수강생 분기

1. **복구 실습과 묶기** — 백업에서 되돌린 뒤 같은 검수를 한 번 더 돌린다(`indeans-erp-routine`). 되돌린 뒤에도 같은 판정을 받는지가 진짜 시험이다.
2. **권한 실측만 정기적으로** — 역할이 둘 이상이면 접근 차단 실측(5단계 5번)과 감사(6단계)만 주 1회 돌린다. 직원이 늘 때마다 여기가 먼저 깨진다.
3. **기계 점검 늘리기** — 감독이 같은 유형을 두 번 지적했으면 그 유형을 고정 검사(`scripts/migration-gate.mjs`)의 항목으로 더할 수 있는지 먼저 본다. 기계가 막는 것이 사람의 주의보다 재발을 잘 막는다.

## 자주 막히는 지점

- **훅이 같은 요구를 반복한다** → 표식이 갱신되지 않았다. 절차 8을 커밋 **뒤에** 한다. 두 번 요구한 뒤에는 훅이 막지 않고 경고만 낸다.
- **감독이 "코드를 못 읽었다"고 한다** → 바꾼 파일 경로를 요약에 넣지 않았다.
- **등급이 헷갈린다** → 위험 등급표에서 가장 높은 줄을 고른다. "새 표를 하나 더했는데 화면만 보면 된다"는 없다 — 표가 늘면 1등급이다.
- **롤백 시뮬이 "permission denied to set role"** → 그 사실을 보고서에 적고, 적용 직후 역할별 실측을 바로 한다. 되돌리는 SQL 을 미리 써 둔다.
- **검증자가 앱을 못 띄운다** → `npm run dev` 출력의 실제 주소를 준다. 포트가 쓰이고 있으면 번호가 바뀐다.
- **사진을 못 찍는다** → playwright 가 없다. 사진 없이 나머지 항목을 계속하고 그 사실을 보고서에 적는다.
- **"오늘 시간이 없다"** → 감독 판정까지만 받고, 실측·보고서는 다음 작업 시작 전에 한다. 판정 없이 넘기는 것과는 다르다. 남은 항목을 `.owner/state.md` 미해결 문제에 적는다.
