# 인디언즈 검수 (감독·검증 호출)

**이 스킬의 역할은 "감독·검증 호출"이다.** 이미 바꾼 것이 괜찮은지 보는 자리다.

무엇을 고칠지 정하고 실제로 고치는 자리는 `indeans-erp-review`(가져온 앱 진단·개선)다. 둘을 겹쳐 하지 않는다.

이 검수는 **1회차 설치 직후부터** 돌아간다. 4회차는 새로 켜는 자리가 아니라 "이미 돌던 체계를 이해하고 복구를 연습하는" 자리다.

## 언제 쓰나

- 작업을 끝낼 때 검수 훅이 종료를 막고 요구했을 때(가장 흔하다).
- 화면·저장 구조·권한·배포 설정·삭제 조건을 바꾼 직후.
- 배포(2회차 이후) 바로 전.
- 대표가 "이대로 괜찮은지 봐 줘"라고 할 때.

## 무엇이 검수 대상인가 (영향 기준 — 줄 수로 판단하지 않는다)

| 검수 대상 | 생략 |
|---|---|
| 화면이 늘거나 없어졌다, 화면의 동작이 바뀌었다 | 화면의 글자·문구만 바꿨다 |
| 저장해 두는 항목·표가 바뀌었다(이름·형식·추가·삭제) | 주석·설명만 고쳤다 |
| 누가 무엇을 볼 수 있는지가 바뀌었다(역할·로그인·공개 범위) | 이미 정해진 색 값 안에서 색만 바꿨다 |
| 지우는 동작·되돌릴 수 없는 동작이 생겼거나 조건이 바뀌었다 | 회사 문서(`company/`)·보고서(`reports/`)·회차 자료(`course/`)만 바꿨다 |
| 배포 설정·접속 정보·설치 목록이 바뀌었다 | 진행 기록(`.owner/`)만 갱신했다 |
| 정해진 시각에 나가는 보고·알림의 조건이 바뀌었다 | |

- **한 줄만 고쳐도 위 왼쪽에 들면 검수한다.** 반대로 백 줄을 고쳐도 문구뿐이면 생략한다.
- 생략으로 판단했으면 **그 이유를 한 줄로 대표에게 말하고** 절차 6(표식 갱신)만 한다. 조용히 넘기지 않는다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/last-check.json` | 마지막으로 검수를 마친 지점(`commit`)·요구 횟수(`nag`) |
| `git status --porcelain` · `git log --oneline -5` · `git diff --stat` | 실제로 무엇이 바뀌었는지. **기억이 아니라 이것을 근거로 한다** |
| `.owner/state.md` · `.owner/progress.json` | 이번에 무엇을 하려 했는지·미해결 문제 |
| `company/structure.md` · `design.md` | 요청받은 범위·"이번에 만들지 않을 것"·고른 디자인 |
| `.claude/agents/` · `.codex/agents/` | 감독 에이전트 3종이 설치돼 있는지 |
| `reports/` | 오늘 같은 작업의 보고서가 이미 있는지(있으면 갱신한다) |

판정과 분기:

- **바뀐 것 없음** → 검수하지 않는다. "검수할 변경이 없습니다"라고 알리고 멈춘다.
- **생략 대상** → 이유를 말하고 절차 6만 한다.
- **검수 대상** → 절차 1~7 전부.
- **에이전트 없음** → 설치기를 다시 돌리게 안내한다. 그래도 없으면 에이전트 정의 파일(`.claude/agents/erp-supervisor.md`)을 직접 읽어 그 기준으로 점검하고, **"감독 에이전트 없이 자체 점검했다"를 보고서에 적는다.**

판정을 한 문장으로 먼저 알린다. 예: "목록 화면과 저장 항목이 바뀌었습니다. 감독 판정부터 받겠습니다."

## 절차

### 1. 변경 요약 만들기

감독에게 보낼 요약을 만든다. **파일 목록을 그대로 붙이지 않고** 아래 다섯 줄로 정리한다.

```
무엇을 하려 했나: {대표의 요청 원문 또는 상태 문서의 다음 행동}
무엇을 바꿨나: {화면·저장·권한 기준으로 2~4줄}
바꾼 파일: {경로 목록 — 감독이 직접 읽는다}
확인받고 싶은 것: {스스로 걸리는 지점. 없으면 "없음"}
범위 밖으로 손댄 것: {있으면 솔직히. 없으면 "없음"}
```

이 요약은 보고서 본문의 뼈대가 된다.

### 2. 감독 판정 받기

**설계·데이터·권한**은 `erp-supervisor`가 본다. **화면이 바뀌었으면** `erp-design-supervisor`도 함께 본다(둘 다 해당되면 한꺼번에 부른다).

- Claude Code에서는 `erp-supervisor`를 **서브에이전트로 띄워**(Task 도구에 에이전트 이름을 지정해) 위 요약을 그대로 보낸다. 화면도 바뀌었으면 `erp-design-supervisor`도 같은 방식으로 띄운다 — 둘은 서로의 답을 보지 않아도 되니 **같이 띄운다.**
- Codex에서는 `.codex/agents/erp-supervisor.toml`로 등록된 **사용자 정의 에이전트**를 부른다. 요청 문장에 에이전트 이름을 그대로 넣는다: `erp-supervisor 에이전트로 이 변경을 검토해 줘.` 화면이 바뀌었으면 `erp-design-supervisor`도 같은 방식으로 부른다.

보낼 것: 절차 1의 요약 + 바꾼 파일 경로 + (화면이면) 캡처 경로. 감독은 **제안이 아니라 저장소에 있는 실제 코드**를 읽는다.

받는 답은 셋 중 하나다: **승인 / 조건부 승인(수정사항) / 반려(이유)**. 답을 요약하지 말고 지적 원문을 그대로 들고 다음 단계로 간다.

### 3. 조건부·반려면 고치고 다시 받는다

- 반려 → 지적한 것을 고친다. 고친 뒤 **같은 감독에게 다시** 판정받는다. 승인 전에는 다음 단계로 가지 않는다.
- 조건부 승인 → 조건을 다 반영한 뒤 "조건 반영했다"고 알리고 확인받는다.
- 감독 판정과 대표 지시가 다르면 **대표 지시가 우선**이다. 다만 **어긋난 내용을 대표에게 그대로 알린다**(무엇을 왜 지적했는지 한 줄). 대표가 그대로 가자고 하면 그 사실을 보고서에 남긴다.
- 감독이 "이건 범위 밖이다"라고 하면 되돌린다. 되돌린 것도 보고서에 적는다.

### 4. 검증자 실측

승인(또는 조건 반영)이 끝나면 `erp-verifier`에게 **실측**을 맡긴다. 검증자는 판정하지 않는다 — 실제로 띄워 보고 본 사실만 돌려준다.

- Claude Code에서는 `erp-verifier`를 서브에이전트로 띄운다.
- Codex에서는 `.codex/agents/erp-verifier.toml`의 사용자 정의 에이전트를 부른다: `erp-verifier 에이전트로 실측해 줘.`

맡길 것(해당되는 것만, 순서대로):

1. 앱 띄우기(`npm run dev`) — 출력에 찍힌 **실제 주소**를 쓴다.
2. 화면 사진 — `node .owner/hooks/capture.mjs --url <실제 주소> --path "<확인할 경로>"` (휴대폰 375·PC 1280). **화면 오류 건수를 함께 받는다.**
3. 빌드 — `npm run build` 성공/실패와 오류 원문.
4. **저장·재접속 확인** — 입력한 뒤 새로고침(2회차 이후는 다른 브라우저·다른 계정으로 다시 접속)해도 남아 있는지.
5. **역할별 접근 차단 확인**(권한이 있는 앱만) — 다른 역할 계정으로 숨긴 화면 주소를 직접 열어 보고, 저장해 두는 곳(Supabase)의 정책이 있으면 그 역할로 표를 읽어 보게 한다. **화면에서 안 보이는 것은 차단이 아니다.**

검증자가 "못 했다"고 한 항목은 못 한 것으로 적는다. 대신 추측으로 채우지 않는다.

### 5. 보고서

`indeans-erp-report` 스킬로 보고서를 만든다. 검수에서 나온 것을 **"검수 결과" 절**에 넣는다: 감독 판정(둘), 실측 결과(사진 장수·화면 오류 건수·빌드·저장 확인·접근 차단), 조건부였으면 무엇을 고쳐 다시 승인받았는지.

- 오늘 같은 작업의 보고서가 이미 있으면 **같은 제목·같은 `--slug`로 다시 만들어** 그 파일을 갱신한다.
- 감독 없이 자체 점검했으면 그 사실을 적는다.

### 6. 검수 표식 갱신

보고서까지 끝난 뒤 `.owner/last-check.json`을 갱신한다. **이 순서를 지킨다** — 커밋을 먼저 하고, 그 커밋 번호를 적는다.

```
git add -A
git commit -m "검수 — {무엇을 바꿨나}"
git rev-parse HEAD
```

`.owner/last-check.json`을 아래 모양으로 쓴다. `nag`는 지운다(요구 횟수를 되돌린다).

```json
{
  "commit": "{git rev-parse HEAD 결과}",
  "at": "{지금 시각 — 2026-09-18T14:30:00+09:00 형태}",
  "tool": "claude",
  "result": "승인",
  "report": "reports/2026-09-18-오늘-현황-화면-추가.html"
}
```

- `tool`은 지금 쓰는 도구(`claude` 또는 `codex`).
- `result`에는 마지막 판정을 적는다(`승인` / `승인(조건 반영)` / `생략 — 문구만`).
- 생략으로 판단한 경우도 같은 파일을 갱신한다. 그래야 같은 변경에 또 요구하지 않는다.
- **판정을 받지 않았는데 이 파일을 갱신하지 않는다.** 그건 검수를 건너뛴 것이다.

### 7. 상태 문서 갱신

`.owner/state.md`와 `.owner/progress.json`을 갱신한다.

- `state.md` → "현재 기능"에 이번에 확인된 것, "미해결 문제"에 감독 지적 중 다음으로 미룬 것·검증자가 못 한 항목, "다음 행동"에 다음 스킬.
- `progress.json` → 해당 값과 `updated_at`.

마지막으로 대표에게 3줄: 판정 / 실측에서 확인된 것 / 남은 것.

## 산출물

| 경로 | 내용 |
|---|---|
| `reports/<날짜>-<제목>.html` | 검수 결과가 들어간 작업 보고서 |
| `.owner/last-check.json` | 검수를 마친 지점(커밋·시각·도구·판정·보고서 경로) |
| `.owner/state.md`·`.owner/progress.json` | 갱신 |
| 커밋 1개 | `검수 — {무엇을 바꿨나}` |

## 하지 않는 것

- 무엇을 고칠지 정하기. 그건 `indeans-erp-review`다.
- 감독 판정 없이 표식만 갱신하기. 검수를 건너뛴 것과 같다.
- 감독의 지적을 요약하거나 순한 말로 바꿔 전달하기. 원문을 그대로 대표에게 보여 준다.
- 반려를 받은 채로 다음 단계·배포로 넘어가기.
- 검증자에게 판정을 맡기기(검증자는 실측만 한다). 감독에게 실측을 맡기기.
- 실측하지 않은 항목을 "확인했다"로 적기.
- 검수 훅을 지우거나 끄기. 요구가 반복돼 막히면 훅이 스스로 세 번째부터 경고만 낸다.
- 배포. 배포는 `indeans-erp-data`의 절차다. 검수는 배포 **전에** 한다.

## 앞선 수강생 분기

검수가 익숙해진 대표에게는 아래 중 하나를 제안한다.

1. **복구 실습과 묶기** — 백업에서 되돌린 뒤 같은 검수를 한 번 더 돌려 본다(4회차 `indeans-erp-routine`과 이어진다). 되돌린 뒤에도 앱이 같은 판정을 받는지가 진짜 시험이다.
2. **권한 차단만 따로** — 역할이 둘 이상이면 접근 차단 실측만 정기적으로 돌린다. 직원이 늘 때마다 여기가 먼저 깨진다.
3. **판정 기준 다듬기** — 감독이 같은 지적을 세 번 이상 했으면 그 항목을 `company/design.md`나 `structure.md`에 규칙으로 적어 둔다. 사람이 기억하는 대신 문서가 기억하게 만든다.

## 자주 막히는 지점

- **훅이 같은 요구를 반복한다** → 표식(`.owner/last-check.json`)이 갱신되지 않았다. 절차 6을 커밋 뒤에 한다. 같은 작업에서 두 번 요구한 뒤에는 막지 않고 경고만 낸다.
- **감독이 "코드를 못 읽었다"고 한다** → 바꾼 파일 경로를 요약에 넣지 않았다. 경로를 함께 보낸다.
- **감독 둘의 말이 다르다** → 설계·권한은 `erp-supervisor`, 화면은 `erp-design-supervisor`가 최종이다. 겹치는 지점(예: 숨긴 화면)은 설계·권한 쪽을 따른다.
- **검증자가 앱을 못 띄운다** → 주소를 짐작해서 쓴 것이다. `npm run dev` 출력의 실제 주소를 준다. 포트가 이미 쓰이고 있으면 번호가 바뀐다.
- **사진을 못 찍는다** → playwright가 없다. 없으면 사진 없이 나머지 항목을 계속하고 그 사실을 보고서에 적는다.
- **"오늘 시간이 없다"** → 감독 판정까지만 받고, 실측·보고서는 다음 작업 시작 전에 한다. 판정 없이 넘기는 것과는 다르다. 남은 항목을 `.owner/state.md`의 미해결 문제에 적는다.
