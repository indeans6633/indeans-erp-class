# 인디언즈 두 번째 AI 교차 검수

**이 스킬의 역할은 "두 번째 AI 의 독립 검수 받기"다.** 판정은 `indeans-erp-check`(감독)가 하고, 매주 요구와 결과를 대조하는 일은 `indeans-erp-routine` 의 「두 AI 교차 검토」가 한다. 여기서는 결함 목록을 받아 기록하고 감독에게 넘기는 데까지만 한다.

만든 AI 에게 "잘 됐냐"고 물으면 거의 "잘 됐다"고 한다. 감독 에이전트도 같은 회사의 AI 라 같은 곳을 같이 놓칠 수 있다. 인디언즈는 중요한 판단에서 **다른 회사가 만든 AI 의 독립 의견**을 한 번 더 받는다 — 우리 쪽 결론은 주지 않고 문제와 코드만 준다. 그 방식을 옮겼다.

무겁게 하지 않는다. 대표가 치는 문장 하나, 아래 절차, 프롬프트 틀 하나(`assets/crosscheck-prompt.template.md`)다. 화면 캡처·실측·롤백 시뮬은 검수 훅·감독·검증자·배포 전 훅이 이미 맡으므로 여기서 하지 않는다.

## 언제 쓰나

- `indeans-erp-check` 위험 등급표의 **1등급(감독 필수)** 변경 — 권한(역할·로그인·정책·공개 범위·새 뷰·데이터를 돌려주는 새 함수) · 돈 · 새 표 구조 · 삭제 조건 · 배포 설정. 데이터베이스에 적용하거나 배포하기 **전**, `indeans-erp-check` 보다 먼저.
- 두 번 고쳤는데도 원인이 안 잡히는 버그.
- 대표가 "다른 AI 한테도 봐 달라"고 할 때.

쓰지 않는 경우: 화면·문구·색·문서만 바뀐 일상 수정(2~4등급) — `indeans-erp-check` 로 충분하다. 매번 돌리면 정작 중요한 변경에서 답을 읽지 않게 된다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | 이번에 하려던 일 · 미해결 문제(설치 못 한 도구가 여기 적혀 있다) |
| `.owner/install-state.json` | `target`(claude · codex · both) — 두 도구 자리에 다 설치했는지 |
| `.owner/last-check.json` | 마지막 검수 지점(`commit`) — 이번 범위의 기준. 없으면 `install-state.json` 의 `installed_commit` |
| `git status --porcelain` · `git log --oneline -5` | 실제로 무엇이 바뀌었나. 기억이 아니라 이것을 근거로 한다 |
| `reports/*-교차검수.md` | 같은 변경을 이미 교차 검수했나, 재검수가 몇 번째인가 |
| `codex --version` · `claude --version` | 반대편 도구가 실제로 도는지(숫자가 나오면 있다) |

- 지금 대화가 Claude Code 면 검수자는 Codex, Codex 면 Claude Code 다(반대편 도구).
- `progress.json` 에는 도구 칸이 없다 — 새로 만들지 않는다. 도구 유무는 버전 명령으로 판정한다.

판정과 분기:

- **바뀐 것 없음** → "검수할 변경이 없습니다"라고 알리고 멈춘다.
- **1등급이 아님**(화면·문구·문서만) → "교차 검수 대상이 아닙니다 — `indeans-erp-check` 로 충분합니다"라고 알리고 멈춘다. 대표가 그래도 원하면 진행한다.
- **반대편 도구 있음** → 절차 1~6.
- **반대편 도구 없음**(명령을 찾을 수 없음·로그인 안 됨) → 두 갈래를 보여 주고 대표가 고른다: ① 같은 도구를 새 대화로 부르는 차선책(`references/commands.md` 6절) ② 이번엔 건너뛰고 `indeans-erp-check` 로. 건너뛰면 `.owner/state.md` 미해결 문제에 "교차 검수 못 함 — 두 번째 도구 없음" 한 줄.
- **이 변경의 재검수를 이미 두 번 했다** → 더 돌리지 않는다. 남은 발견을 대표에게 보여 주고 고친다 / 범위를 줄인다 / 되돌린다 중에서 고르게 한다.

판정을 한 문장으로 먼저 알린다. 예: "역할 정책 파일이 바뀌었습니다 — 1등급입니다. Codex 에게 교차 검수를 받겠습니다."

## 절차

### 1. 검수 범위 정하기 (파일 5개 이하)

1. `.owner/tmp/` 가 `.gitignore` 에 없으면 한 줄 더한다. 지금 상태를 커밋한다 — `git add -A` → `git commit -m "교차 검수 전 — {무엇}"`. 검수자가 본 코드가 이 커밋으로 고정되고(되돌릴 지점), 고친 뒤와 나눠 볼 수 있다.
2. 바뀐 파일을 뽑는다: `git diff --name-only {기준 커밋}`.
3. 뺀다: `.env`·`.env.local` · `.owner/` · `reports/` · `company/` · `course/` · 잠금 파일(`package-lock.json`) · 그림 파일. `.env*` 는 비밀값이고, `reports/`·`.owner/` 에는 우리 쪽 결론이 들어 있어 독립성을 깬다.
4. 5개가 넘으면 위험한 순서로 5개만: 표 바꾼 기록(`supabase/migrations/`) → 권한·돈을 판정하는 코드(정책·역할·금액 계산) → 서버 함수 → 저장 코드 → 화면. 뺀 파일은 감독이 본다 — 대표에게 한 줄로 알린다.
5. 400줄이 넘는 파일은 바뀐 부분만(앞뒤 30줄) 붙인다(`references/commands.md` 1절).

### 2. 프롬프트 파일 만들기

`assets/crosscheck-prompt.template.md` 의 「보낼 글」을 「코드 —」 줄까지 `.owner/tmp/crosscheck-{날짜}.txt` 로 옮겨 칸을 채운다(날짜는 이 컴퓨터의 날짜 `YYYY-MM-DD`).

- **문제 서술**: 이 코드가 할 일을 업무 말로 2~3줄(예: 예약 취소 · 주문 출고 · 작업 지시 확정). 끈질긴 버그면 증상 · 재현 순서 · 오류 원문.
- **지켜야 하는 규칙**: `company/*.md` 에서 이 코드에 걸리는 줄만 원문 그대로.
- **코드**: `references/commands.md` 1절 명령으로 줄 번호를 붙인 전문을 이어 붙인다. 손으로 옮기지 않는다. 경로만 주지 않는다 — 검수 도구의 읽기 전용 상자(샌드박스)가 파일을 못 읽어 "확인할 수 없다"로 끝나는 일이 있다.
- **넣지 않는 것**: 우리 AI 의 결론·가설("여기가 의심된다"·"잘 고쳤다") · 감독 판정 · 대화 내용. 넣으면 검수자가 따라 말한다.

보내기 전에 틀 아래 「보내기 전 점검표」 여섯 줄을 확인한다(점검 명령은 `references/commands.md` 2절). 고객·직원 실명 · 전화 · 이메일 · 실제 금액 · 계좌 · 토큰 · 키 · 웹훅 주소 · `.env` 내용이 **하나라도 있으면 멈춘다.** 지우거나 가짜 값으로 바꾸고 다시 점검한다. 검수자는 외부 서비스다 — 보낸 글은 그 회사의 서버로 간다.

### 3. 반대편 도구에 보내기

`references/commands.md` 3절(Claude Code → Codex) 또는 4절(Codex → Claude Code)의 명령을 **그대로** 쓴다.

- **빈 폴더에서 돌린다**(명령에 들어 있다). 프로젝트 폴더에서 돌리면 검수자가 우리 보고서·상태 문서를 읽고, 우리 검수 훅이 검수자의 대화 끝을 가로챈다.
- 명령의 제한 시간을 **10분**으로 잡는다. 도구의 기본 제한 시간이 짧으면 중간에 끊긴다.
- 답은 `.owner/tmp/crosscheck-out-{날짜}.md` 에 저장된다. 열어서 형식(발견 목록 또는 "발견 없음")인지 본다. 총평만 있거나 영어면 같은 파일로 **한 번만** 다시 보낸다.

### 4. 결과 기록

`reports/{날짜}-교차검수.md` 를 만든다(같은 날 다른 변경이면 `-2`). 같은 변경의 재검수는 이 파일에 「재검수 N」 절로 더한다.

```markdown
# 교차 검수 — {무엇을 바꿨나}

- 검수자: {codex | claude} {버전} — 차선책이면 "같은 도구 새 대화"
- 범위: {파일 경로 5개 이하} · 기준 커밋 {짧은 번호} → 검수한 커밋 {짧은 번호}
- 보낸 글: `.owner/tmp/crosscheck-{날짜}.txt` · 비공개 정보 점검: 통과(명령 CLEAN + 점검표 6줄)

## 첫 검수 — 받은 답 (원문 그대로)

{.owner/tmp/crosscheck-out-{날짜}.md 의 내용을 그대로}

## 처리

| # | 발견(검수자 제목 그대로) | 심각도 | 감독 판정 | 처리(반영/보류) | 이유 |
|---|---|---|---|---|---|
```

- 답은 **원문 그대로** 붙인다. 요약하거나 순한 말로 바꾸지 않는다.
- 처리 표는 절차 5에서 감독 판정을 받은 뒤 채운다.

### 5. 감독에게 넘기고 고치기 (재검수 최대 2번)

`indeans-erp-check` 를 부르고, 그 스킬 절차 1 요약의 **"확인받고 싶은 것"** 칸에 발견을 번호 · 심각도 · 제목 · `파일:줄` 그대로 넣는다(보고서 경로 포함). 그다음은 그 스킬의 절차대로 간다.

- 감독이 맞다고 본 치명·중요는 고친다. 경미는 감독 판단대로 고치거나 미룬다.
- 감독이 아니라고 본 것은 처리 표에 이유와 함께 "보류"로 남긴다. **두 AI 의 말이 갈리면 어느 쪽이 맞냐고 AI 에게 다시 묻지 않는다** — 감독 판정과 검증자 실측으로 가린다.
- 이번 변경이 만든 것이 아닌 원래 있던 문제는 이번 작업을 막지 않는다 — `.owner/state.md` 미해결 문제에 적고 대표에게 한 줄로 묻는다.
- 치명·중요를 고쳤으면 **재검수**: 절차 2~4를 다시 하되 파일 이름 끝에 `-r1`·`-r2` 를 붙이고, 문제 서술 끝에 지난 답의 발견 목록(검수자 원문)과 "이 발견이 고쳐졌는지, 고친 자리에 새 결함이 생겼는지만 본다"를 더한다. 어떻게 고쳤는지는 쓰지 않는다.
- 재검수는 **최대 2번**이다. 매번 "새 공격면을 찾아라"·"앞의 설명을 의심하라"를 더하지 않는다 — 그러면 끝나지 않는다. 두 번째 재검수에도 치명이 남으면 멈추고 대표에게 세 갈래: 한 번 더 고친다 / 범위를 줄인다 / 되돌린다.

### 6. 상태 문서 갱신·커밋

- `reports/{날짜}-교차검수.md` 의 처리 표를 마저 채운다.
- `.owner/state.md` — "미해결 문제"에 보류한 발견, "다음 행동"에 이어 할 일(대개 `indeans-erp-check` 의 남은 절차 또는 적용·배포). `.owner/progress.json` 의 `updated_at`.
- `git add -A` → `git commit -m "교차 검수 — {무엇}"`.

마지막으로 대표에게 3줄: 검수자와 범위 / 발견(치명 N · 중요 N · 경미 N, 그중 감독이 맞다고 본 것) / 남은 것.

## 산출물

| 경로 | 내용 |
|---|---|
| `.owner/tmp/crosscheck-{날짜}.txt` | 보낸 프롬프트(쓰고 버리는 자리 — 커밋하지 않는다) |
| `.owner/tmp/crosscheck-out-{날짜}.md` | 검수자 답 원문 |
| `reports/{날짜}-교차검수.md` | 답 원문 + 처리 표(감독 판정 · 반영/보류 · 이유), 재검수 절 |
| `.owner/state.md` · `.owner/progress.json` | 갱신 |
| 커밋 2개 | `교차 검수 전 — …` · `교차 검수 — …` |

## 하지 않는 것

- 일상 수정(화면·문구·문서)에 쓰기.
- 우리 AI 의 결론·가설·감독 판정을 프롬프트에 넣기. "이렇게 고쳤는데 괜찮지?"는 검수가 아니다.
- 고객·직원 실명 · 연락처 · 금액 · 계좌 · 비밀값 · `.env` 내용을 보내기.
- 두 도구의 결과를 섞어 한쪽 말만 믿기. 발견을 감독 판정 없이 바로 고치거나 버리기.
- 검수자에게 파일을 고치게 하기(명령에 읽기 전용이 들어 있다). 검수자를 프로젝트 폴더에서 돌리기.
- 화면 캡처·빌드·롤백 시뮬을 이 스킬에서 직접 돌리기 — 검증자·검수 훅·배포 전 훅의 일이다.
- 재검수를 두 번 넘게 돌리기.

## 앞선 수강생 분기

1. **설계 단계 교차 검수** — 권한 단계·돈 흐름 단계처럼 큰 일은 구현 **전에** 계획서(예: `company/people.md` 의 노출 표 + 정책 초안 SQL)를 같은 틀로 보낸다. 「코드」 자리에 계획서를, 문제 서술에 "아직 만들지 않았다 — 이 계획대로 만들면 생길 결함을 찾는다"를 쓴다. 고치는 값이 가장 싼 때다.
2. **같은 지적이 두 번이면 기계 검사로** — 교차 검수에서 같은 유형이 두 번 나오면 판례 노트(`.owner/precedents.md`)에 적고, 고정 검사(`scripts/migration-gate.mjs`) 항목으로 올릴 수 있는지 본다(`indeans-erp-routine`).

## 자주 막히는 지점

- **"파일을 읽을 수 없다·확인할 수 없다"는 답** → 경로만 주고 코드를 안 붙였다. 줄 번호를 붙인 전문을 붙인다(commands.md 1절).
- **10분이 넘는다** → 파일을 3개로 줄인다. 그래도 넘으면 대표가 새 터미널 창에서 같은 명령을 직접 실행하고, 끝나면 commands.md 5절 문장으로 이어 간다.
- **답이 영어로 온다** → 프롬프트 파일 맨 끝의 "한국어로 답한다." 줄이 빠졌다. 넣고 한 번만 다시 보낸다.
- **사용량 한도·"입력이 너무 길다"** → 도구 구독의 사용량을 쓰는 일이다. 파일 수를 줄이거나 바뀐 부분만 붙이고, 한도면 풀린 뒤 다시 한다.
- **PowerShell 에서 한글이 `???` 로 간다** → 파이프(`|`)나 `>` 로 보냈다. commands.md 의 `cmd /c` 꼴을 그대로 쓴다.
- **답 끝이 검수가 아니라 "검수 스킬을 부르겠다"는 말이다** → 프로젝트 폴더에서 돌려 우리 훅이 끼었다. 빈 폴더에서 돌린다.
