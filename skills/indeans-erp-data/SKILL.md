# 인디언즈 데이터·백업·배포

2회차 실습. 목표는 기능 추가가 아니다. **넣은 것이 남고, 아무나 못 보고, 잃어버려도 되찾을 수 있게** 만들고, 직원이 자기 폰으로 접속해 입력한 것이 다시 접속해도 남아 있는 데까지 간다.

순서를 지킨다. **백업 방법 → 표와 잠금 → 연결 → 배포.** 백업을 뒤로 미루면 "나중에 백업"이 되고, 그 나중은 대개 오지 않는다.

인디언즈가 자체 앱을 운영하며 굳힌 규칙 세 가지를 그대로 쓴다. 표를 바꾸는 일은 **번호 붙은 파일로만** 한다. 파일을 실행하기 전에 **게이트 점검**을 통과시킨다. 배포 직전에는 **훅이 커밋·빌드·고정 검사를 다시 확인**한다. 셋 다 "잘 되던 앱이 표 하나 바꾼 뒤 조용히 깨지는" 흔한 사고에서 나온 것이다.

## 언제 쓰나

- 새로고침하면 입력한 게 사라질 때(예시 데이터나 브라우저 저장만 쓰는 상태).
- 직원이 자기 기기로 열 **주소**가 필요할 때.
- 표·칸을 더하거나 바꿀 때 — 이후 어느 단계에서든 3·4절의 번호 규약과 게이트를 쓴다.
- 백업·복구 방법을 정해 두어야 할 때.

쓰지 않는 경우: 역할 나누기(→ 권한 단계 `indeans-erp-people`), 화면 개선(→ `indeans-erp-review`), 채널 연결(→ `indeans-erp-channel`), 돈 계산(→ `indeans-erp-money`).

## 시작 전 상태 진단

먼저 읽고 판정한다. 읽기 전에 말을 걸지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | 현재 기능 · 미해결 문제 · 어디까지 끝났나 |
| `.owner/accounts.md` | 1회차에 가입한 계정 — GitHub 아이디·**비공개 저장소 이름**, Supabase 조직, Vercel 팀(비밀값은 없다) |
| `company/structure.md` | 화면 목록 · **한 건에 적는 항목 표**(표 설계의 원본) · 이번에 만들지 않을 것 |
| `company/scope.md` · `company/profile.md` | 관리 단위, 회사가 쓰는 말(표·칸 주석에 그대로 넣는다) |
| `company/improve-plan.md` | `데이터 영향: 있음` 으로 표시된 항목 |
| `company/backup.md` · `company/data.md` | 백업 방법·마이그레이션 실행 기록·배포 주소가 이미 있나 |
| `src/` 의 저장 담당 파일 · 예시 데이터 파일 | 지금 데이터를 어디에 넣고 있나, 바꿀 화면은 몇 개인가 |
| `supabase/migrations/` | 이미 만든 파일과 **마지막 번호** |
| `package.json` | `check` 스크립트(고정 검사)가 있나 |
| `.env.local` · `.gitignore` | 접속 정보가 있나, 커밋에서 빠져 있나 (**값은 화면에 출력하지 않는다**) |

**상태 문서가 코드·배포와 다르면 문서를 믿지 않는다.** 실제(파일·빌드·주소)를 확인한 뒤 문서를 고치고 시작한다.

- **처음** — `supabase/migrations/` 도 `.env.local` 도 없다 → 절차 0부터.
- **절반** — 프로젝트는 만들었는데 표가 없거나 앱이 아직 예시 데이터를 쓴다 → 빠진 단계부터. 절차 1(백업)은 건너뛰지 않는다.
- **완료에 가까움** — 표·연결·배포가 다 돼 있다 → 4절 게이트를 붙였는지 보고, 12절 직원 확인이 없으면 그것부터. 다 됐으면 「앞선 수강생 분기」.

대표에게 한 문장으로 알린다. 예: "데이터베이스는 아직 없습니다. 백업 방법을 먼저 만들고 표를 만들겠습니다."

## 계정이 없을 때

GitHub·Supabase·Vercel 계정은 1회차에 가입해 오는 것이 전제다(`.owner/accounts.md` 의 세 줄). 비었으면 **먼저 `indeans-erp-setup` 의 계정 절차로 보낸다.** 가입은 몇 분이면 끝나고, 오늘 할 일의 대부분이 계정 위에서 돈다.

가입이 오늘 안 되면(인증 메일 지연·회사 보안 정책) 멈추지 않되 **저장 전환은 하지 않는다** — 연결도 안 된 앱을 데이터베이스로 갈아엎으면 열리지 않는 화면 앞에 대표만 남는다.

1. 백업(절차 1)과 표 설계(절차 3·4의 **파일 작성과 게이트까지**)는 그대로 한다. 내려받기 버튼도 지금 붙인다.
2. 표·잠금 SQL은 번호 파일로 써 두고 **실행하지 않는다.** 실행하지 않았다는 것을 파일 맨 위 주석에 한 줄로 적는다.
3. `.env.local` 은 자리표시 값으로 만들고(`VITE_SUPABASE_URL=`·`VITE_SUPABASE_ANON_KEY=`, 값은 비운다) `git check-ignore -v .env.local` 로 커밋에서 빠지는 것까지 확인한다. 절차 7~12는 하지 않고 `npm run build` 성공까지만 본다.
4. `company/data.md` 의 확인 항목은 **'확인 불가 — 계정 없음'** 으로 남긴다. 화면의 "지금은 이 브라우저에만 저장됩니다" 안내는 그대로 둔다(아직 사실이다).
5. 끝맺음에서 이어 할 문장을 줄여 만들지 않는다 — "계정(또는 Supabase 프로젝트)을 만든 뒤 새 대화에 교재 P5 문장(`course/session-02/prompts.md`)을 그대로 넣으시면 남은 단계부터 이어 갑니다"라고 알린다(진단이 '절반'으로 잡는다).

## 절차

### 0. 되돌릴 지점과 비밀 파일 확인

```bash
git add -A
git commit -m "데이터 연결 전 상태 저장"
```

**`.env.local` 을 만들기 전에** `git check-ignore -v .env.local` 을 실행해 한 줄이 나오는지 본다(`*.local` 한 줄만 있어도 덮인다 — 글자 그대로 찾지 않는다). 안 나오면 `.gitignore` 에 먼저 추가하고 커밋한다. 접속 정보가 한 번 올라가면 지워도 기록에 남는다.

### 1. 백업을 먼저 만든다

`references/backup-restore.md` 를 읽고 `assets/backup.template.md` 를 `company/backup.md` 로 만든다. 계정이 없어도 그대로 할 수 있다. 정할 것 네 가지를 한 번에 하나씩 묻는다.

1. > "데이터가 다 날아가면 **무엇이 가장 아깝습니까?**"
2. > "그걸 **누가, 얼마나 자주** 내려받으시겠어요? 요일까지 정해 주세요."
3. > "내려받은 파일을 **어디에 두시겠어요?** 대표님 말고 그 위치를 아는 사람이 한 분 더 있나요?"
4. > "다 날아갔을 때 **누가 되돌립니까?**"

그리고 **앱 안에 내려받기 버튼**을 넣는다(목록 화면 위, 엑셀에서 열리는 파일).

- **백업 버튼은 언제나 전체를 받는다.** 화면에 보이는 것만 받게 만들면, 목록 기본값이 "끝난 것 빼고"로 바뀌는 순간 백업에서 끝난 건이 통째로 빠진다. 보이는 것만 받는 버튼이 따로 필요하면 둘로 나누고 이름에 '전체'를 넣는다.
- 파일 이름은 `날짜_화면이름.csv`. 한글이 깨지지 않게 파일 맨 앞에 표시 문자를 넣는데, 코드에는 `String.fromCharCode(0xFEFF)` 로 만든다 — 눈에 안 보이는 글자를 붙여넣지 않고, 역슬래시로 적는 이스케이프(`'\uFEFF'`)도 AI 도구가 파일에 쓰는 과정에서 실제 글자로 바뀌어 들어가는 일이 있어 쓰지 않는다. 쓴 뒤 `grep -c $'\xef\xbb\xbf' 파일` 이 0 인지 본다.
- 버튼을 누른 뒤 **파일을 열어 내용이 실제로 들어 있는지 눈으로 본다.** 빈 파일이 만들어지는 실수가 흔하다.

`company/backup.md` 에 "무엇을 잃으면 아픈가 · 내려받는 법 · 주기 · 두는 곳 · 누가 되돌리나 · **되돌리는 순서**"를 적는다. 되돌리는 순서를 문장으로 적어 두지 않으면 백업이 아니다. 실제로 되돌려 보는 연습은 실사용 준비 단계(`indeans-erp-routine`)에서 한다.

### 2. Supabase 프로젝트 — 대표가 화면에서

`references/supabase-steps.md` 를 화면 순서대로 읽어 주고 대표가 누른다. 1회차에 만든 조직(`.owner/accounts.md`) 안에서 New project → 이름(회사 영문 약자)·**데이터베이스 비밀번호**(한 번만 보인다 — 비밀번호 관리 앱이나 종이에)·지역(가까운 곳) → **Settings > API Keys** 에서 Project URL 과 **공개용 키**(`anon` 또는 `publishable`)만 복사한다. **비밀 키(`service_role`·`secret`)는 복사하지 않는다** — 앱에 들어가면 모든 잠금이 무력화된다. 만든 프로젝트 이름을 `.owner/accounts.md` Supabase 줄에 더한다(키는 적지 않는다).

- **무료 프로젝트는 동시에 두 개까지**이고, **일주일 넘게 아무도 안 쓰면 잠시 멈춘다.** 연습용으로 여러 개 만들지 않는다. 회차 사이에 앱이 갑자기 안 열리면 대시보드에서 그 프로젝트의 다시 켜기(Restore)를 누르고 몇 분 기다린다 — 데이터는 그대로다. 직원이 매일 쓰기 시작하면 멈출 일이 없다.

### 3. 표 설계와 번호 규약

`company/structure.md` 의 항목 표를 데이터베이스 표로 바꾼다. 대표에게는 "엑셀 시트 한 장 = 표 하나"라고 설명한다.

- **표는 세 개 이하로 시작한다.** 회사 · 쓰는 사람 · 업무 표 하나(관리 단위 — 납품 건·방문 건·예약 건 등).
- 모든 표에 `id` · `created_at` · `updated_at`. 표·칸 이름은 영문 소문자, **회사 말은 주석으로**(`comment on column`).
- **상태·분류처럼 값이 정해진 칸은 영문 코드로 저장하고 화면 글자는 앱이 갖는다.** 한글 값을 저장하면 단계 이름을 바꾸는 순간 과거 기록이 목록에서 사라진다.
- `improve-plan.md` 의 `데이터 영향: 있음` 칸은 이렇게 묻는다: **"지금 넣을까요, 다음에 붙일까요? 다음에 붙여도 지금 넣은 자료는 그대로 있습니다."** 안 쓸 칸을 미리 만들지 않는다. `structure.md` 의 '이번에 만들지 않을 것'은 표에도 넣지 않는다 — 특히 **금액 칸은 권한 단계 전에는 넣지 않는다**(지금은 회사 사람 모두가 같은 것을 본다).

파일은 `assets/0001_init.template.sql` 을 복사해 `supabase/migrations/0001_init.sql` 로 만든다. 폴더 이름 `migrations` 는 **'표를 바꿔 온 기록'** 이라고 한 줄로 알려 준다. 번호 규약:

- 파일명은 `NNNN_무엇.sql` — 네 자리 번호 + 영문 소문자·밑줄(`0002_add_memo_column.sql`).
- **다음 번호는 기억으로 정하지 않는다.** 폴더를 열어 마지막 번호를 확인하고 +1 한다(PowerShell `Get-ChildItem supabase/migrations`, macOS `ls supabase/migrations`). 다른 대화·다른 도구가 그 사이 파일을 만들었을 수 있다.
- **한 파일 = 한 가지 일.** 표 추가와 권한 변경을 한 파일에 섞지 않는다 — 되돌릴 때 같이 사라진다.
- **실행한 파일은 고치지 않는다.** 바꿀 게 생기면 다음 번호 파일을 만든다. 이 규칙 하나가 "내 컴퓨터에선 되는데 배포본에선 안 되는" 상황의 절반을 없앤다. `0001` 은 권한 단계 전까지는 다시 실행해도 같지만, 권한 단계를 적용한 뒤에는 **스스로 멈춘다**(다시 돌면 좁혀 둔 권한이 넓어지기 때문이다).
- 실행하면 **`company/data.md` 의 실행 기록 표에 한 줄**(파일·날짜·결과). 감독은 이 기록으로 "파일만 있음"과 "실제로 돎"을 가른다.

### 4. 게이트 점검 — 실행하기 전에

파일을 SQL Editor 에 붙이기 전에 아래를 하나씩 본다. 하나라도 비면 실행하지 않는다.

| 점검 | 무엇을 보나 |
|---|---|
| 표 | 새 표마다 기본 칸 세 개, 회사 말 주석, 안 쓸 칸 없음 |
| 인덱스 | 자주 거르는 칸(소속·날짜·상태)과 연결 칸(`…_id`)에 `create index` |
| 정책 동반 | **같은 파일에** `enable row level security` + 읽기·넣기·고치기·지우기 정책을 따로 + `revoke all … from anon` |
| 롤백 가능 | 정책·제약을 바꾸는 파일은 실행 전 **롤백 시뮬**(`indeans-erp-check` 의 `references/rollback-sim.md`). 지우기·옮기기·이름 바꾸기가 있으면 백업을 먼저 받고, 되돌리는 SQL 을 파일 맨 위 주석에 적는다 |
| 스키마 캐시 | 파일 끝에 `notify pgrst, 'reload schema';` — 앱이 새 표·칸을 "schema cache 에서 찾을 수 없음"으로 못 보는 일을 막는다 |
| 고정 검사 | `npm run check` 통과 |

**고정 검사 붙이기(처음 한 번).** `assets/migration-gate.template.mjs` 를 `scripts/migration-gate.mjs` 로 복사하고 `package.json` 의 `scripts` 에 `"check": "node scripts/migration-gate.mjs"` 를 넣는다(이미 `check` 가 있으면 `"<기존> && node scripts/migration-gate.mjs"`). 이 검사는 네트워크 없이 파일 글자만 보는 **정적 휴리스틱**이다 — 잠금 없는 표(G1)·정책 없는 표(G2)·안전장치 없는 권한 높은 함수(G3)·정책 함수를 못 부르게 된 것(G4)·파일에 적힌 비밀값(G5)·잠금을 건너뛰는 뷰(G6)·대상 없거나 로그인 안 한 사람 대상인 정책(G12)·로그인 안 한 사람에게 준 권한(G13)·"로그인만 하면 전부" 읽기 정책(G14)·돈 표의 필수 규칙 누락이나 검사 꺼짐(G15)·DO 블록 안에서 보안 설정 바꾸기(G16)는 **막힘**, 나머지는 주의다. 판정은 모든 파일을 순서대로 읽은 뒤의 마지막 상태로 한다(뒤에서 `alter` 로 바꾼 것 포함). 막힘이 하나라도 있으면 실행·배포하지 않는다. 통과했다고 잠겼다고 말하지 않는다 — 롤백 시뮬·역할별 실측·감사가 따로 확인한다. 오탐이면 그 파일에 `-- gate-allow: G2 표이름 (사유)` 를 적는다(사유 필수).

실행: SQL Editor 에 파일 내용을 붙여 넣고 Run → Table Editor 에서 표가 보이면 성공 → 실행 기록 한 줄.

### 5. 행 수준 잠금 — 처음부터 걸고 시작한다

표를 만들자마자 잠근다. 나중에 잠그기로 미루면 대개 안 잠근다. 설명은 `references/rls-basics.md`, 명령은 `0001_init.sql` 에 이미 들어 있다. 대표에게는 이렇게 말한다.

> 데이터베이스에 "이 **줄**을 누가 볼 수 있나"를 줄마다 물어보는 문지기를 세우는 겁니다. 화면에서 숨기는 것과는 다릅니다.

**화면 숨김 ≠ 차단.** 화면에서 버튼·칸을 숨기는 것은 편의다. 주소를 직접 입력하거나 다른 앱으로 같은 주소를 부르면 화면을 지나 데이터에 닿는다. 실제 방어선은 데이터베이스의 행 수준 규칙이고, **막혔다고 말할 근거는 "다른 계정으로 열었을 때 안 보였다"뿐이다.**

이번에 넣는 규칙은 하나다: **로그인했고, 그 사람이 우리 회사 명단에 있으면 본다.** 권한 단계에서 역할을 나눌 때는 이 넓은 규칙을 **먼저 지우고** 좁힌다 — 규칙은 더할수록 넓어지고, 좁은 규칙을 더해도 넓은 규칙이 그대로 통과시킨다.

### 6. 접속 정보 — `.env.local`

```
VITE_SUPABASE_URL=https://<프로젝트>.supabase.co
VITE_SUPABASE_ANON_KEY=<공개용 키>
```

- 대시보드가 `publishable` 로 표시해도 변수 이름은 `VITE_SUPABASE_ANON_KEY` 로 통일한다.
- **`VITE_` 로 시작하는 값은 앱을 쓰는 사람에게 보인다.** 그래서 공개용 키만 넣는다. 공개용 키가 보여도 되는 이유는 5절의 문지기다 — 문지기가 없으면 이 키는 그냥 열쇠가 된다.
- 실수로 커밋했으면 대시보드에서 키를 새로 발급하고 새 값으로 바꾼다.

### 7. 예시 데이터에서 진짜 데이터로

1. `npm install @supabase/supabase-js` → `src/lib/supabase.ts` 에 접속 객체 하나만(화면마다 만들지 않는다).
2. **최소 로그인 화면** — 이메일·비밀번호, 로그인/로그아웃, 새로고침해도 로그인이 유지되게(세션 복원). 가입은 **대표가 계정을 만들어 주는 방식**으로 두고 누구나 가입되는 화면을 열지 않는다.
3. 저장 자리를 **한 화면씩** 데이터베이스로 바꾼다(목록 → 상세/입력 → 오늘 화면). 바꿀 때마다 확인하고 커밋한다.
4. 목록 조회에는 **정렬과 개수 제한**(`order(...).limit(...)`)을 기본으로. 제한 없는 조회는 데이터가 쌓이면 오류 없이 조용히 잘린다.
5. 예시 데이터 파일은 지우지 않는다(화면이 안 나올 때 비교 기준).
6. "지금은 이 브라우저에만 저장됩니다" 안내는 **실제로 저장되는 것을 확인한 뒤에만** 지운다. 화면 설명이 사실과 달라지면 신뢰를 잃는다 — 지우는 쪽으로도.
7. 1절의 내려받기 버튼이 **새 저장소를 읽는지** 확인한다. 옛 저장소를 읽으면 백업이 빈 파일이 된다.

### 8. 잠금 확인 — 앱에서

SQL Editor 는 관리자 권한으로 돌아 잠금을 지나친다 — 거기서 보이는 것은 증거가 아니다.

1. Authentication > Users 에서 대표 계정을 만들고, SQL Editor 에서 명단(`app_users`)에 넣는다(`0001` 아래쪽 안내).
2. 앱에서 대표 계정으로 로그인 → 목록이 보인다.
3. **명단에 넣지 않은 두 번째 계정**으로 로그인 → 목록이 **비어 있어야** 한다. 한 줄이라도 보이면 잠금이 안 걸린 것이다.
4. 확인이 끝나면 두 번째 계정을 지운다. 결과는 `company/data.md` 잠금 확인 표에. 실측은 `erp-verifier` 에게 맡겨도 되지만 "비어 있었다"는 관찰이 결과에 있어야 한다.

### 9. 인터넷 주소 — GitHub 푸시 → Vercel 가져오기

1. 1회차에 만든 **비공개 저장소**(`.owner/accounts.md` 의 GitHub 줄 — `https://github.com/<아이디>/<저장소>`)에 연결해 올린다: `git remote -v` 로 이미 연결돼 있는지 먼저 보고, 없으면 `git remote add origin <그 주소>`. 올리기 전에 `git status` 로 `.env.local` 이 빠졌는지 본 뒤 `git branch -M main` → `git push -u origin main`(처음 한 번은 GitHub 로그인 창이 뜬다 — 대표가 직접 허용한다). 저장소가 없으면 그때 비공개로 만든다(공개로 만들지 않는다).
2. vercel.com(GitHub 로 로그인) → **Add New… > Project** → 그 저장소 **Import** → 빌드 설정은 기본값(Vite 자동 인식). **목록에 저장소가 안 보이면** Vercel 의 GitHub 앱이 그 저장소를 볼 권한이 없는 것이다 — 같은 화면의 GitHub 앱 설정(Configure GitHub App / Adjust GitHub App Permissions)에서 저장소 접근에 그 저장소를 더하고 돌아온다.
3. **Environment Variables** 에 `.env.local` 의 두 줄을 그대로 넣는다. 빠뜨리면 배포된 화면만 비어 나온다(가장 흔한 막힘).
4. Deploy → 주소(`…vercel.app`)를 `company/data.md` 와 `.owner/progress.json` 의 `app.deploy_url` 에 적는다. 이후 `git push` 하면 자동으로 다시 배포된다.

요금제 한 줄을 대표에게 알린다: 수업은 Vercel 무료(Hobby)로 배포한다 — 무료는 개인·비상업 용도라 회사에서 계속 쓰려면 Pro(월 $20) 전환이 약관상 맞다. 바꿀지는 대표가 정한다(AI 가 대신 결제하지 않는다).

**배포 직전 확인 훅.** 이 프로젝트에는 `.owner/hooks/erp-predeploy.mjs` 가 등록돼 있다. `vercel` 배포 명령, 그리고 배포 주소가 생긴 뒤의 `git push` 바로 전에 ① 앱 파일에 커밋 안 한 변경이 없는지(vercel 명령일 때) ② `npm run build` ③ `npm run check` 를 돌리고, 걸리면 배포를 멈추고 이유를 보여 준다. 막히면 고치고 다시 한다 — 훅을 끄지 않는다. 이 훅은 실수를 막는 안전장치이지 보안 경계가 아니다 — 다른 폴더를 올리는 명령(`--cwd`)은 확인하지 않고 알리기만 하고, npm 을 못 찾으면 알리고 통과시킨다. 미리 돌려 보려면 `node .owner/hooks/erp-predeploy.mjs --debug "vercel --prod"`.

### 10. 배포 뒤 읽기 전용 스모크

배포할 때마다 세 가지를 **읽기만** 해서 본다. 이 단계에서 데이터를 넣거나 지우지 않는다.

1. **주소 열기** — 폰과 PC에서 배포 주소를 연다. 로그인 화면이 뜬다.
2. **목록 조회** — 대표 계정으로 로그인해 목록을 연다. 건수가 내 컴퓨터에서 본 것과 같다.
3. **로그인 안 한 상태로 목록 주소 열기** — 시크릿 창에서 `https://<앱>/<목록 경로>` 를 직접 연다. 데이터가 아니라 로그인 화면이 나와야 한다.

더 깊은 확인(새 화면 파일은 200, 없는 파일 주소는 404, 공개용 키만으로 표를 읽으면 빈 결과)은 `erp-verifier` 의 '배포 뒤 스모크'에 맡긴다. 결과는 `company/data.md` 배포 기록에 한 줄.

### 11. 백업 마무리

- 대시보드 내보내기(Table Editor → Export to CSV) 방법을 `company/backup.md` 에 적는다.
- Database > Backups 를 열어 **자동 백업이 있는지** 적는다. 무료 요금제에는 없다 — 그러면 1절의 내려받기가 유일한 사본이고, 주기를 주 1회로 잡는다.

### 12. 직원이 넣고 다시 보기 — 2회차 완료 확인

1. 직원 계정 1개를 만들고 명단에 `staff` 로 넣는다(`0001` 아래쪽 안내 — 이름 칸은 실명 대신 역할로).
2. 직원이 **자기 폰으로** 배포 주소에 로그인해 **실제 업무 1건**을 입력한다.
3. 로그아웃 → 다시 로그인(또는 대표 폰에서) → 그 건이 보인다.
4. 수업이 끝나기 전 실제 업무 데이터를 3건까지 넣어 보고, 넣으면서 걸린 것을 `company/log.md` 에 적는다. 다음 개선 1번이 대개 여기서 나온다.

지금은 회사 사람 모두가 같은 것을 본다. 대표만 봐야 할 것이 있으면 그것은 권한 단계(`indeans-erp-people`)에서 나눈다 — 그 전까지 그런 칸을 앱에 넣지 않는다.

## 하지 않는 것

- 백업 방법을 정하기 전에 데이터를 옮기지 않는다.
- 비밀 키(`service_role`·`secret`)를 앱이나 `.env.local` 에 넣지 않는다.
- 행 수준 잠금 없이 표를 만들지 않는다. 게이트 막힘을 남긴 채 실행·배포하지 않는다.
- **화면에서 숨긴 것을 "막았다"고 보고하지 않는다.** 다른 계정으로 열어 비어 있는 것을 본 뒤에만 그렇게 말한다.
- 한 번 실행한 마이그레이션 파일을 고치지 않는다. 다음 번호 파일로 고친다.
- 배포 직전 훅을 끄거나 우회하지 않는다. 역할 나누기는 여기서 하지 않는다(`indeans-erp-people`).
- 실제 고객 이름·연락처·금액을 대화창이나 외부 서비스에 복사해 넣지 않는다. 확인은 앱 화면에서 한다.

## 앞선 수강생 분기

이미 연결·배포·직원 확인이 끝났으면 하나를 고른다.

1. **파일 잠금** — 사진·문서를 올리는 앱이면 파일 저장소(Storage)에도 같은 규칙을 건다. 목록만 막고 파일을 열어 두면 주소를 아는 사람에게 그대로 열린다. 목록·상세·파일 세 경로를 적고 하나씩 막는다.
2. **바뀐 기록 남기기** — 상태·날짜처럼 덮어쓰면 이전 값이 사라지는 칸에 변경 이력 표를 붙인다(무엇에서 무엇으로·누가·언제). 되돌릴 수 없는 세 가지(`backup.md` 7절) 중 두 번째를 막는 장치다.
3. **게이트 넓히기** — 같은 실수가 두 번 나온 유형을 `scripts/migration-gate.mjs` 에 항목으로 더한다. 사람이 조심하는 것보다 기계가 막는 쪽이 재발을 잘 막는다.

## 자주 막히는 지점

- **앱에서 아무것도 안 보인다** — 대부분 문지기가 제대로 걸린 것이다. 로그인했는지, 명단에 그 계정이 있는지 본다.
- **SQL Editor 에서는 보이는데 앱에서는 안 보인다** — 정상이다. SQL Editor 는 관리자 권한이다.
- **"Could not find the table … in the schema cache"** — 새 표를 앱이 아직 모른다. `notify pgrst, 'reload schema';` 를 한 번 실행하고 화면을 새로 고친다.
- **배포가 훅에 막혔다** — 메시지의 [항목]을 읽는다. 커밋 안 한 변경이면 커밋, 빌드 실패면 오류 끝부분을, 고정 검사면 G 번호를 고친다.
- **`npm run check` 가 G1·G2 로 막는다** — 새 표에 잠금이나 정책이 빠졌다. 같은 파일에 넣는다. 비밀값 표처럼 일부러 정책을 안 두는 표는 허용 주석에 사유를 적는다.
- **배포한 주소만 화면이 비어 있다** — Vercel Environment Variables 누락. 넣은 뒤 Redeploy 해야 반영된다.
- **회차 사이에 앱이 갑자기 안 열린다(데이터를 못 불러온다)** — 무료 Supabase 프로젝트가 일주일 안 써서 멈췄다. 대시보드에서 Restore → 몇 분 뒤 다시 연다.
- **Vercel 가져오기 목록에 저장소가 없다** — Vercel 의 GitHub 앱 권한에 그 저장소를 더한다(9절 2번).
