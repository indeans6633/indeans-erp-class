# 인디언즈 데이터·백업·배포

2회차 실습. 목표는 기능 추가가 아니다. **넣은 것이 남고, 아무나 못 보고, 잃어버려도 되찾을 수 있게** 만드는 것이다.

순서를 지킨다. **백업 방법을 먼저 만들고 그다음 데이터를 옮긴다.** 반대로 하면 "나중에 백업"이 되고, 그 나중은 대개 오지 않는다.

## 언제 쓰나

- 새로고침하면 입력한 게 사라질 때(예시 데이터나 브라우저 저장만 쓰는 상태).
- 직원이 자기 기기로 열 **주소**가 필요할 때.
- 백업·복구 방법을 정해 두어야 할 때.

쓰지 않는 경우: 역할 나누기(→ `indeans-erp-people`), 화면 개선(→ `indeans-erp-review`), 채널 연결(→ `indeans-erp-channel`).

## 시작 전 상태 진단

먼저 읽고 판정한다. 읽기 전에 말을 걸지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · 미해결 문제 · 다음 행동 |
| `.owner/progress.json` | 어디까지 끝났나 |
| `company/structure.md` | 화면 목록 · **한 건에 적는 항목 표** — 표 설계의 원본 |
| `company/scope.md` · `company/profile.md` | 관리 단위, 회사가 쓰는 말(표·칸 주석에 그대로 넣는다) |
| `company/improve-plan.md` | `데이터 영향: 있음` 으로 표시된 항목 |
| `company/backup.md` | 백업 방법이 이미 정해졌나 |
| `src/` 의 저장 담당 파일 · 예시 데이터 파일 | 지금 데이터를 어디에 넣고 있나, 바꿀 화면은 몇 개인가 |
| `supabase/migrations/` | 이미 만든 표가 있나 |
| `.env.local` · `.gitignore` | 접속 정보가 있나, 커밋에서 빠져 있나 (**값은 화면에 출력하지 않는다**) |

**상태 문서가 코드·배포와 다르면 문서를 믿지 않는다.** 실제(파일·빌드·주소)를 확인한 뒤 문서를 고치고 시작한다.

판정과 분기:

- **처음** — `supabase/migrations/` 도 `.env.local` 도 없다 → 절차 0부터 순서대로.
- **절반** — 프로젝트는 만들었는데 표가 없거나 앱이 아직 예시 데이터를 쓴다 → 있는 것만 확인하고 빠진 단계부터. 절차 1(백업)은 건너뛰지 않는다.
- **완료에 가까움** — 표·연결·배포가 다 돼 있다 → `company/backup.md` 를 채우고 「앞선 수강생 분기」로 간다.

대표에게 한 문장으로 알린다. 예: "데이터베이스는 아직 없습니다. 백업 방법을 먼저 만들고 프로젝트를 만들겠습니다."

## 계정이 아직 없을 때

Supabase·Vercel·GitHub 계정이 늦어져도 **멈추지 않는다.** 다만 **저장 전환은 하지 않는다** — 연결도 안 된 앱을 데이터베이스로 갈아엎으면 열리지 않는 화면 앞에 대표만 남는다.

1. 백업(절차 1)과 표 설계(절차 3의 **파일 작성까지**)는 **그대로 한다.** 이게 오늘의 본편이다. 내려받기 버튼도 지금 붙인다 — 예시 데이터를 읽는 채로도 파일이 만들어지고 열린다는 것까지 확인할 수 있다. 절차 2(프로젝트 만들기)는 계정이 열리는 날 대표가 화면에서 한다.
2. 표·잠금 SQL은 **새 번호 파일로 써 두고 실행하지 않는다**(`supabase/migrations/0001_init.sql`). 실행하지 않았다는 것을 파일 맨 위 주석에 한 줄로 적는다.
3. `.env.local` 은 **자리표시 값으로 만들어 두고**(`VITE_SUPABASE_URL=`·`VITE_SUPABASE_ANON_KEY=` 두 줄, 값은 비운다), `git check-ignore -v .env.local` 로 커밋에서 빠지는 것까지 확인한다. 절차 6(저장 전환)·7(잠금 확인)·8(배포)은 **하지 않는다.** 대신 `npm run build` 가 성공하는 것까지 확인한다.
4. `company/data.md` 의 확인 항목은 **'확인 불가 — 계정 없음'** 으로 남긴다. 빈칸으로 두지 않는다.

화면에 붙어 있는 "지금은 이 브라우저에만 저장됩니다" 안내는 **그대로 둔다.** 아직 사실이기 때문이다. 계정이 열리는 날 2·3번을 실제로 실행하고 그 안내를 지우는 것이 과제다.

## 절차

### 0. 되돌릴 지점과 비밀 파일 확인

```bash
git add -A
git commit -m "데이터 연결 전 상태 저장"
```

**`.env.local` 을 만들기 전에** `.gitignore` 에 그 줄이 있는지 **먼저** 본다. 순서를 바꾸지 않는다 — 파일부터 만들면 그 사이에 한 번 커밋되는 사고가 난다.

`.gitignore` 를 열어 `.env.local` 이 덮이는지 **지금** 확인한다. `*.local` 한 줄만 있어도 덮인다 — 글자 그대로 `.env.local` 을 찾아 없다고 판단하지 않는다. 확실히 하려면 `git check-ignore -v .env.local` 을 실행해 한 줄이 나오면 된 것이다. 안 덮이면 먼저 추가하고 커밋한다. 접속 정보가 한 번 올라가면 지워도 기록에 남는다.

### 1. 백업을 먼저 만든다

`references/backup-restore.md` 를 읽고 `assets/backup.template.md` 를 `company/backup.md` 로 만든다. 이 단계는 **데이터베이스 계정이 없어도 그대로 할 수 있다.** 계정 만들기가 늦어지면 여기부터 한다.

정할 것은 네 가지다. 한 번에 하나씩 묻는다.

1. > "데이터가 다 날아가면 **무엇이 가장 아깝습니까?**"
2. > "그걸 **누가, 얼마나 자주** 내려받으시겠어요? 요일까지 정해 주세요."
3. > "내려받은 파일을 **어디에 두시겠어요?** 대표님 말고 그 위치를 아는 사람이 한 분 더 있나요?"
4. > "다 날아갔을 때 **누가 되돌립니까?**"

그리고 **앱 안에 내려받기 버튼을 넣는다.** 목록 화면 위쪽에 버튼 하나다. 목록을 엑셀에서 열리는 파일로 저장한다.

- **목록에 필터가 걸릴 수 있으면 백업 단추는 전체를 받는다.** 화면에 보이는 것만 받게 만들면, 뒤 회차에 목록 기본값이 "끝난 것 빼고"로 바뀌는 순간 백업에서 끝난 건이 통째로 빠진다. 지금 보고 있는 것만 받는 버튼이 따로 필요하면 **버튼을 둘로 나누고 이름에 '전체'를 넣는다.**
- 파일 이름은 `날짜_화면이름.csv`.
- 엑셀에서 한글이 깨지지 않게 파일 맨 앞에 표시 문자를 넣는다. 코드에는 보이지 않는 문자를 붙여넣지 말고 `'\uFEFF'` 라고 적는다 — 눈에 안 보이는 글자는 나중에 누가 지워도 아무도 모른다.
- 버튼을 누른 뒤 **파일을 열어 내용이 실제로 들어 있는지 눈으로 본다.** 빈 파일이 만들어지는 실수가 흔하다.

`company/backup.md` 에 "무엇을 잃으면 아픈가 · 어떻게 내려받나 · 주기 · 두는 곳 · 누가 되돌리나 · 되돌리는 순서"를 적는다. **되돌리는 순서를 문장으로 적어 두지 않으면 백업이 아니다.**

백업에서 실제로 되돌려 보는 연습은 4회차 `indeans-erp-routine` 에서 한다. 이 회차에서는 **파일이 만들어지고 열린다는 것까지** 확인한다.

### 2. Supabase 프로젝트 만들기 — 대표가 화면에서

대신 해 줄 수 없는 단계다. `references/supabase-steps.md` 를 열어 화면 순서대로 읽어 주고, 대표가 누른다. 핵심만:

1. supabase.com 가입(GitHub 계정으로 로그인 가능) → **New project**.
2. 프로젝트 이름(회사 영문 약자 권장), **데이터베이스 비밀번호**(한 번만 보인다 — 비밀번호 관리 앱이나 종이에 적어 둔다), **지역**은 가까운 곳(한국이면 서울).
3. 생성까지 1~3분 기다린다.
4. **Settings > API Keys** 에서 두 가지를 복사해 둔다: **Project URL**, **공개용 키**(화면에 `anon` 또는 `publishable` 로 표시된다. 둘 중 보이는 것을 쓴다).
5. **비밀 키**(`service_role` 또는 `secret`)는 **복사하지 않는다.** 이번 수업에서 쓸 일이 없고, 앱에 넣으면 모든 잠금이 무력화된다.

확인: 대시보드 왼쪽에 Table Editor·SQL Editor·Authentication 메뉴가 보이면 된 것이다.

### 3. 표 설계 — 회사 말을 그대로 옮긴다

`company/structure.md` 의 항목 표를 데이터베이스 표로 바꾼다. 대표에게는 "엑셀 시트 한 장 = 표 하나"라고 설명한다.

설계 규칙:

- **표는 세 개 이하로 시작한다.** 회사 · 쓰는 사람 · 업무 표 하나. 업무 표가 곧 관리 단위다(납품 건, 방문 건, 예약 건, 작업 지시 등).
- 모든 표에 기본 칸 세 개: `id`(고유 번호) · `created_at`(만든 시각) · `updated_at`(고친 시각).
- 표·칸 이름은 영문 소문자로 두고, **회사가 쓰는 말은 주석으로 붙인다**(`comment on column`). 화면 라벨은 회사 말, 코드 안쪽은 영문 — 이렇게 두면 부르는 말이 바뀌어도 데이터는 그대로다.
- **상태·분류처럼 값이 정해진 칸은 영문 코드로 저장한다. 화면 글자는 앱이 갖는다.** 한글 값을 그대로 저장하면 나중에 단계 이름을 바꾸는 순간 과거 기록이 목록에서 사라진다.
- `company/improve-plan.md` 에 `데이터 영향: 있음` 으로 표시된 칸을 여기서 같이 넣는다. 넣을지는 이렇게 묻는다: **"이건 지금 넣을까요, 다음에 붙일까요? 다음에 붙여도 지금 넣은 자료는 그대로 있습니다."** 안 쓸 칸을 미리 만들지 않는다.
- `company/structure.md` 의 '이번에 만들지 않을 것' 에 있는 항목은 표에도 넣지 않는다.

파일은 `assets/0001_init.template.sql` 을 복사해 `supabase/migrations/0001_init.sql` 로 만든다. 폴더 이름 `migrations` 는 **'표를 바꿔 온 기록'** 이라는 뜻이라고 한 줄로 알려 준다. 번호 규약:

- 파일명은 `0001_`, `0002_` 처럼 **네 자리 번호 + 무엇을 하는지**(`0002_add_memo_column.sql`).
- **이미 실행한 파일은 고치지 않는다.** 바꿀 것이 생기면 다음 번호 파일을 새로 만든다. 이 규칙 하나가 "내 컴퓨터에선 되는데 배포본에선 안 되는" 상황의 절반을 없앤다.

실행: 대시보드 **SQL Editor** 에 파일 내용을 붙여 넣고 Run. Table Editor에서 표가 보이면 성공이다.

### 4. 행 수준 잠금 — 처음부터 걸고 시작한다

표를 만들자마자 잠근다. **나중에 잠그기로 미루면 대개 안 잠근다.** 설명은 `references/rls-basics.md`, 명령은 `0001_init.sql` 에 이미 들어 있다.

대표에게는 이렇게 설명한다.

> 데이터베이스에 "이 **줄**을 누가 볼 수 있나"를 줄마다 물어보는 문지기를 세우는 겁니다. 화면에서 숨기는 것과는 다릅니다.

**화면 숨김 ≠ 차단.** 이 한 줄이 이번 회차에서 가장 중요하다.

- 화면에서 버튼·칸을 안 보이게 하는 것은 **편의**다. 데이터는 이미 그 사람의 기기까지 내려와 있다.
- 주소를 직접 입력하거나, 브라우저의 개발자 화면을 열거나, 다른 앱으로 같은 주소를 부르면 화면을 지나 데이터에 닿는다.
- 실제 방어선은 데이터베이스의 행 수준 규칙 하나다. **막혔다고 말할 수 있는 근거는 "다른 계정으로 열었을 때 안 보였다"뿐이다.**

이번 회차에 넣는 규칙은 하나다: **로그인했고, 그 사람이 우리 회사 사람이면 본다.** 로그인만 한 계정은 아무것도 못 본다.

`indeans-erp-people` 로 역할을 나눌 때 **이 넓은 규칙을 먼저 좁혀야** 한다. 규칙은 더할수록 넓어지지, 좁아지지 않는다 — 좁은 규칙을 나중에 추가해도 넓은 규칙이 그것을 덮는다.

### 5. 접속 정보 — `.env.local`

프로젝트 맨 위에 `.env.local` 파일을 만든다.

```
VITE_SUPABASE_URL=https://<프로젝트>.supabase.co
VITE_SUPABASE_ANON_KEY=<공개용 키>
```

- 대시보드가 키를 `publishable` 로 표시해도 변수 이름은 `VITE_SUPABASE_ANON_KEY` 로 통일한다. 이름을 한 곳으로 고정해야 코드가 안 흔들린다.
- **`VITE_` 로 시작하는 값은 앱을 쓰는 사람에게 보인다.** 그래서 이 칸에는 공개용 키만 넣는다. 비밀 키·데이터베이스 비밀번호는 절대 넣지 않는다.
- 공개용 키가 보여도 괜찮은 이유는 4단계의 문지기 때문이다. 문지기를 안 걸면 이 키는 그냥 열쇠가 된다.
- `.env.local` 은 **커밋하지 않는다.** 실수로 올렸으면 대시보드에서 키를 새로 발급하고 새 값으로 바꾼다.

대표에게 남길 한 문장: "이 파일은 내 컴퓨터에만 있고, 배포할 때는 배포 화면에 따로 붙여 넣습니다."

### 6. 예시 데이터에서 진짜 데이터로

1. `npm install @supabase/supabase-js`
2. `src/lib/supabase.ts` — 접속 객체 하나만 만든다. 화면마다 따로 만들지 않는다.
3. **최소 로그인 화면** — 이메일·비밀번호 한 칸씩, 로그인/로그아웃. 역할 나누기는 `indeans-erp-people` 이 한다. 지금은 대표 계정 하나면 된다. 가입은 **대표가 초대해서 만드는 방식**으로 둔다. 누구나 가입되는 화면을 열어 두지 않는다.
4. 브라우저 저장을 쓰던 자리를 데이터베이스 읽기·쓰기로 바꾼다. 목록 → 상세/입력 → 오늘 화면 순서로, **한 화면씩** 바꾸고 그때마다 확인한다.
5. 목록 조회에는 **정렬과 개수 제한**을 기본으로 넣는다(`order(...).limit(...)`). 제한 없는 조회는 데이터가 쌓이면 오류 없이 조용히 잘린다.
6. 예시 데이터 파일은 지우지 않는다. 화면이 안 나올 때 비교할 기준이 된다.
7. 초안이 화면에 붙여 둔 **"지금은 이 브라우저에만 저장됩니다" 안내 문구를 지운다 — 실제로 연결돼 저장이 되는 것을 확인한 뒤에만.** 아직 연결 전이면 그 안내는 사실이므로 그대로 둔다. 화면의 설명이 사실과 달라지는 것이 첫 번째 신뢰 손실이고, 그것은 **지우는 쪽으로도 생긴다.**
8. 1단계의 내려받기 버튼이 **새 저장소를 읽는지** 확인한다. 예시 데이터를 읽던 채로 남으면 백업이 빈 파일이 된다.

각 화면을 바꾼 뒤 커밋한다: `git commit -am "목록 화면을 데이터베이스로 전환"`.

### 7. 잠금 확인 — 앱에서만, 그리고 검증은 위임한다

확인은 **반드시 앱에서** 한다. 대시보드 SQL Editor는 관리자 권한으로 돌아 잠금을 지나치기 때문에, 거기서 데이터가 보이는 것은 아무 증거가 못 된다.

1. Authentication > Users 에서 대표 계정을 만든다(이메일·비밀번호, 확인 메일 없이 생성).
2. SQL Editor에서 그 계정을 사람 명단 표에 넣는다(`0001` 파일 아래쪽 안내 참고).
3. 앱에서 대표 계정으로 로그인 → 목록이 보인다.
4. **명단에 넣지 않은 두 번째 계정을 만들어 로그인** → 목록이 **비어 있어야** 한다. 한 줄이라도 보이면 잠금이 안 걸린 것이다.
5. 확인이 끝나면 두 번째 계정을 삭제한다.

4번이 이번 회차에서 가장 중요한 한 걸음이다. "로그인했으면 보여 준다"로 대충 걸어 두면, 사람이 늘어난 다음에야 새는 걸 알게 된다. 그때는 이미 샌 뒤다.

결과를 `company/backup.md` 가 아니라 `company/data.md` 의 잠금 확인 표에 적는다. **실측은 `erp-verifier` 에게 맡겨도 된다** — 다만 4번의 "비어 있었다"는 관찰이 반드시 결과에 있어야 한다.

### 8. 인터넷 주소 만들기 — GitHub 푸시 → Vercel 가져오기

1. GitHub에 **비공개(Private)** 저장소를 만들고 푸시한다. 공개로 만들지 않는다.
2. 푸시 전에 `git status` 로 `.env.local` 이 올라가지 않는지 확인한다.
3. vercel.com 로그인(GitHub 계정) → **New Project** → 방금 만든 저장소 **Import**.
4. 빌드 설정은 기본값 그대로 둔다(Vite는 자동 인식된다).
5. **Environment Variables** 에 `.env.local` 의 두 줄을 그대로 입력한다. 이 단계를 빠뜨리면 배포된 화면만 비어 나온다 — 가장 흔한 막힘이다.
6. Deploy → 주소(`...vercel.app`)를 받는다. 폰으로 열어 로그인해 본다.
7. 이후 `git push` 하면 자동으로 다시 배포된다.

주소와 배포일을 `company/data.md` 에 적는다.

### 9. 백업 마무리와 실제 데이터 3건

- 대시보드 쪽 내보내기 방법(Table Editor → Export to CSV)을 `company/backup.md` 에 적는다.
- Database > Backups 를 열어 **자동 백업이 있는지** 확인해 적는다. 무료 요금제에는 자동 백업이 없다 — 그러면 1단계의 내려받기가 유일한 사본이라는 뜻이고, 주기를 주 1회로 잡는다.
- 수업이 끝나기 전 **실제 업무 데이터 3건**을 폰으로 넣어 본다. 지어낸 데이터가 아니라 이번 주에 실제로 있었던 건으로 넣는다. 넣으면서 걸린 것을 `company/log.md` 에 적는다 — 다음 회차 개선 1번이 대개 여기서 나온다.

### 10. 검수와 상태 문서

저장 구조·권한 조건·배포가 모두 바뀌었으므로 **`indeans-erp-check` 를 호출한다.** 감독 판정 → `erp-verifier` 실측(저장·재접속·역할별 접근 차단) → 작업 보고서까지 그 스킬이 이어서 한다.

그다음 `.owner/state.md` 를 고친다.

- **현재 기능** — "저장은 Supabase, 주소 있음(폰에서 로그인 확인)" 처럼 사실만.
- **미해결 문제** — 남은 것(예: "직원 계정은 아직 없음").
- **다음 행동** — 다음 스킬(예: "사람·권한(`indeans-erp-people`)").

`.owner/progress.json` 의 `app.supabase_connected`·`app.deploy_url`·`app.backup_documented`·`next_action`·`updated_at` 을 고친다. 없는 키를 새로 만들지 않는다.

```bash
git add -A
git commit -m "데이터·백업·배포와 상태 갱신"
```

## 하지 않는 것

- 백업 방법을 정하기 전에 데이터를 옮기지 않는다. 순서를 바꾸지 않는다.
- 비밀 키(`service_role`·`secret`)를 앱이나 `.env.local` 에 넣지 않는다.
- 행 수준 잠금 없이 표를 만들지 않는다. "나중에 켜자"는 하지 않는다.
- **화면에서 숨긴 것을 "막았다"고 보고하지 않는다.** 다른 계정으로 열어 비어 있는 것을 본 뒤에만 그렇게 말한다.
- 역할 나누기(대표/직원/고객)는 여기서 하지 않는다 — `indeans-erp-people` 이 한다.
- 한 번 실행한 마이그레이션 파일을 고치지 않는다. 다음 번호로 새로 만든다.
- 표를 미리 많이 만들지 않는다. 안 쓰는 표는 나중에 지우기가 더 번거롭다.
- 실제 고객 이름·연락처·금액을 대화창이나 외부 서비스에 복사해 넣지 않는다. 확인은 앱 화면에서 한다.

## 앞선 수강생 분기

이미 연결·배포가 끝났으면 아래에서 하나를 고른다.

1. **팀·지점별 읽기 범위** — 회사 안에서도 "우리 팀 것만" 보여야 하는 데이터가 있으면, 담당 팀 칸을 넣고 규칙에 팀 조건을 더한다. 확인은 7단계와 같은 방식(다른 팀 계정으로 로그인해 비어 있는지).
2. **읽기 전용 계정** — 읽기만 되는 계정을 하나 만들어 본다. 쓰기 규칙과 읽기 규칙을 따로 두고, 쓰기 계정으로 막히는지 확인한다.
3. **파일 잠금** — 사진·문서를 올리는 앱이면 파일 저장소에도 같은 규칙을 건다. 목록만 막고 파일을 열어 두면 주소를 아는 사람에게는 그대로 열린다. 목록 · 상세 · 파일 세 경로를 모두 적고 하나씩 막는다.

## 자주 막히는 지점

- **앱에서 아무것도 안 보인다** — 대부분 문지기가 제대로 걸린 것이다. 로그인은 했는지, 사람 명단 표에 그 계정이 들어 있는지 확인한다.
- **SQL Editor에서는 보이는데 앱에서는 안 보인다** — 정상이다. SQL Editor는 관리자 권한으로 돈다. 확인은 앱에서만 한다.
- **배포한 주소만 화면이 비어 있다** — Vercel의 Environment Variables 누락. 넣은 뒤 다시 배포(Redeploy)해야 반영된다.
- **`VITE_` 없이 변수를 만들었다** — 앱에서 값이 안 읽힌다. 이름을 `VITE_` 로 시작하게 고치고 `npm run dev` 를 다시 시작한다.
- **키를 실수로 커밋했다** — 파일만 지우면 기록에는 남는다. 대시보드에서 키를 새로 발급하고 새 값으로 바꾼다. 지금 쓰는 키가 무효가 되는 것이 정답이다.
- **내려받은 파일이 비어 있다** — 버튼이 옛 저장소(예시 데이터)를 읽고 있다. 6단계 8번을 다시 본다.
- **표를 잘못 만들었다** — 지우고 다시 만들기보다 `0002_` 파일로 고친다. 실제 데이터가 들어간 뒤에는 특히 그렇다.
- **데이터베이스 비밀번호를 잃어버렸다** — 대시보드에서 재설정할 수 있다. 앱 접속에는 이 비밀번호를 쓰지 않으므로 앱은 계속 돈다.
- **무료 요금제라 자동 백업이 없다** — 사실이다. 놀라지 말고 내려받기를 주 1회로 잡고 `company/backup.md` 에 적어 둔다.
