# 인디언즈 디자인 방향 고르기

인터뷰가 끝난 뒤, 초안을 만들기 전에 **화면의 모양과 색을 대표가 눈으로 보고 고르는 자리**다. 말로 설명하지 않고 **그려 놓은 화면 12장을 열어 보여 준다.** 고른 결과는 토큰 파일 한 개로 앱 전체에 적용된다.

## 언제 쓰나

- 인터뷰로 회사 문서가 만들어진 직후(1회차, 5~10분). 초안 생성 바로 전.
- 써 보고 "글자가 작다·색이 안 맞다"가 나왔을 때(방향 바꾸기).
- 고객이 직접 여는 화면을 추가할 때(구조만 다시 검토).

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | 선택한 디자인이 이미 있는지(`design.structure`·`design.color`) |
| `company/design.md` | 고른 조합과 이유가 적혀 있는지 |
| `src/styles/tokens.css` | 파일 첫 줄 주석의 조합 이름(예: `list-navy`) |
| `company/profile.md` | 업태·주 고객·고객이 화면을 직접 보는지·근무자가 밖에서 일하는지 |
| `company/structure.md` | 화면 3개 목록·목록에 검색이 필요한지 |
| `.owner/design/index.html` · `.owner/design/tokens/` | 이미지 세트와 토큰 12벌이 설치돼 있는지 |

판정과 분기:

| 상태 | 판정 기준 | 분기 |
|---|---|---|
| A. 처음 | `tokens.css` 없고 상태 문서에 디자인 없음 | 절차 전부 |
| B. 같은 조합 손보기 | 조합이 이미 있고 대표가 "조금만 고치자" | 토큰 값만 손본다. 파일을 새로 덮지 않는다 |
| C. 조합 바꾸기 | 조합이 있는데 다른 것을 고르려 함 | **먼저 확인한다**: "지금 {조합}으로 되어 있습니다. 바꾸면 화면 인상이 전부 달라집니다. 바꿀까요?" 대표가 예라고 해야 진행 |
| D. 직접 적은 색이 많음 | 화면 파일에 색·크기가 여기저기 직접 적혀 있음 | 한꺼번에 바꾸지 않는다. 화면 하나에 먼저 적용해 보여 주고 대표의 답을 받는다 |
| E. 이미지 세트 없음 | `.owner/design/index.html` 없음 | 설치기를 다시 돌리게 안내한다. 이미지 없이 말로 고르게 하지 않는다 |

판정을 한 문장으로 먼저 알린다. 예: "디자인은 아직 고르지 않았습니다. 그려 놓은 화면을 열어 보여 드리겠습니다."

## 절차

### 1. 되돌릴 지점

```
git add -A
git commit -m "디자인 방향 고르기 전"
```

커밋할 게 없으면 넘어간다. 앱이 이미 있으면 바꾸기 전 화면을 PC(가로 1280)·휴대폰(가로 375)으로 한 장씩 캡처해 둔다(`node .owner/hooks/capture.mjs`). 나중에 비교할 근거다.

### 2. 이미지 세트 열기

```
node .owner/hooks/open.mjs .owner/design/index.html
```

브라우저에 **구조 3줄 × 컬러 4칸** 갤러리가 열린다. 열리지 않으면 경로를 대표에게 알려 주고 직접 열게 한다(파일을 두 번 누르면 열린다).

열자마자 한 줄로 안내한다: **"열두 장 모두 같은 내용으로 그렸습니다. 내용이 아니라 모양과 색만 비교하시면 됩니다."**

### 3. 구조 고르기 (질문 1개)

12장을 한 번에 고르게 하지 않는다. **가로 줄(구조) 셋만** 보게 한 뒤 묻는다.

> 화면 모양이 세 가지입니다. **목록·표형**은 여러 건을 줄로 늘어놓고 비교하는 모양, **진행 보드형**은 단계별로 칸을 나눠 지금 어디쯤인지 훑는 모양, **카드·상세형**은 한 건을 크게 보여 주는 모양으로 **고객이 직접 보는 화면에 적합**합니다. 어느 쪽이 대표님 일에 가까우신가요?

대표가 못 정하면 `company/profile.md`·`structure.md`를 근거로 **한 번만** 권한다. 근거는 이 표를 쓴다.

| 이럴 때 | 권하는 구조 | 근거 문장 |
|---|---|---|
| 한 화면에서 여러 건의 날짜·담당·수량을 비교한다 | 목록·표형(`list`) | "하루에 같은 목록을 여러 번 보신다고 하셨으니" |
| 단계가 3~5개이고 "지금 누구 차례인가"를 자주 묻는다 | 진행 보드형(`board`) | "단계가 네 개이고 담당이 나뉘어 있으니" |
| 고객이 직접 링크를 열거나 고객 앞에서 화면을 돌려 보여 준다 | 카드·상세형(`card`) | "고객이 직접 보신다고 하셨으니" |

- 단계가 7개를 넘으면 진행 보드형을 권하지 않는다. 칸이 너무 많아진다.
- 고객이 보는 화면이 없으면 카드·상세형을 권하지 않는다.
- **권하는 것은 한 번만.** 대표가 다른 것을 고르면 그대로 따른다.

### 4. 컬러 고르기 (질문 1개)

고른 구조의 **그 줄 4칸만** 보게 한 뒤 묻는다.

> 같은 모양에 색만 네 가지입니다. 남색·차콜(진회색)·녹색·갈색입니다. 회사 간판이나 명함과 어울리는 쪽이 있으실까요?

- 회사 로고 색을 그대로 강조색으로 가져오지 않는다. 밝은 색은 글자 대비가 떨어진다. 대표가 로고 색을 말하면 **네 가지 중 가장 가까운 것**을 권한다.
- "아무거나"라고 하면 남색(`navy`)을 쓴다. 가장 무난하고 글자가 잘 읽힌다.
- 두 개를 섞지 않는다. 강조색은 하나다.

조합이 정해지면 소리 내어 확인한다: **"{구조 이름} + {컬러 이름}으로 하겠습니다. 나중에 바꾸실 수 있지만, 화면 인상이 전부 달라지니 오늘은 이걸로 만들겠습니다."**

### 5. 토큰 파일 넣기

조합 이름은 `(list|board|card)-(navy|charcoal|green|brown)` 형식이다. 예: `board-green`.

`src/styles/` 폴더가 없으면 만들고, 고른 조합의 토큰을 복사한다.

맥·리눅스:

```
mkdir -p src/styles
cp .owner/design/tokens/list-navy.css src/styles/tokens.css
cp .owner/design/src/base.css src/styles/base.css
cp .owner/design/src/layout-list.css src/styles/layout.css
```

윈도우 PowerShell:

```
New-Item -ItemType Directory -Force "src\styles"
Copy-Item ".owner\design\tokens\list-navy.css" "src\styles\tokens.css" -Force
Copy-Item ".owner\design\src\base.css" "src\styles\base.css" -Force
Copy-Item ".owner\design\src\layout-list.css" "src\styles\layout.css" -Force
```

- 파일 이름의 `list-navy`를 **고른 조합으로 바꿔** 쓴다. `layout-list`의 `list`도 고른 구조(`list`·`board`·`card`)로 바꾼다.
- `base.css`(공통 바탕: 상단바·버튼·표 기본)와 `layout.css`(고른 구조의 화면 뼈대)는 비교 이미지를 그린 바로 그 CSS다. 초안이 이 둘과 고른 목업(`.owner/design/src/<조합>.html`)의 뼈대를 그대로 이어받아야 화면 인상이 이미지와 같아진다.
- 복사한 뒤 `src/styles/tokens.css`의 첫 줄 주석에 조합 이름이 있는지 확인한다. 다음에 이 파일 하나만 보고도 어느 조합인지 알아야 한다.
- 아직 앱(`package.json`)이 없어도 이 파일은 먼저 둔다. `indeans-erp-draft`가 초안을 만들 때 이 파일을 지우지 않고 그대로 쓴다.

### 6. 앱이 이 파일을 불러오게 하기

앱이 이미 있으면 시작 지점에서 한 번 불러오게 한다. `src/main.tsx` 맨 위:

```ts
import './styles/tokens.css'
import './styles/base.css'
import './styles/layout.css'
```

- `src/main.tsx`가 아직 `./index.css`를 부르고 있으면 그 줄을 위 줄로 바꾼다. **이걸 빠뜨리면 고른 디자인이 화면에 안 먹는다.**
- 앱이 아직 없으면 이 단계를 건너뛰고, `company/design.md`에 "초안 생성 시 불러오기 추가"라고 적어 둔다.

### 7. 화면에 직접 적은 색·크기를 토큰으로 바꾼다

화면 파일에 적힌 `#333`, `font-size: 14px` 같은 값을 `var(--text)`, `var(--fs-body)`로 바꾼다. **한 화면씩** 바꾸고 그때마다 눈으로 확인한다. 목록 → 상세·입력 → 오늘 현황 순서로 한다.

구조별 화면 적용 규칙은 `references/structures.md`에 있다. **화면을 고치기 전에 그 파일의 해당 절을 읽는다.** 세 구조 모두에 공통인 것 하나: **표·격자의 모든 열은 `minmax(0, 1fr)`로 시작한다.** 이것을 빠뜨리면 내용이 긴 건이 들어온 날 화면이 옆으로 밀린다.

### 8. 모바일과 PC 확인

앱이 아직 없으면 이 단계를 건너뛴다(초안을 만든 뒤 `indeans-erp-draft`에서 확인한다).

앱이 있으면 **다른 창에서** 앱을 띄운 뒤 찍는다.

```
npm run dev
```

터미널에 찍힌 주소를 그대로 쓴다(5173이 쓰이고 있으면 5174로 뜬다 — 짐작하지 않는다).

```
node .owner/hooks/capture.mjs --url http://localhost:5173
```

가로 375(휴대폰)와 1280(PC) 두 장이 나온다. 확인할 것:

- 좌우로 밀리는 곳이 하나도 없다. 하나라도 있으면 그 자리에서 고친다.
- 누르는 곳의 높이가 40px 이상(폰에서는 44px — 토큰 `--tap` 기준).
- 글자가 잘리거나 겹치지 않는다.
- 글자 크기가 **4종 이하**, 굵기가 **3종 이하**. 넘으면 가장 비슷한 것끼리 합친다.

### 9. 기록하고 커밋

`assets/design.template.md`를 채워 `company/design.md`로 쓴다. 고른 조합·이유·바꾸면 안 되는 것이 들어간다.

`.owner/state.md`와 `.owner/progress.json`을 갱신한다.

- `state.md` → "선택한 디자인"에 `{구조 이름} + {컬러 이름}` 한 줄과 토큰 경로. "다음 행동"에 다음 스킬(`indeans-erp-draft` 또는 `indeans-erp-check`).
- `progress.json` → `design.structure`(`list`·`board`·`card`), `design.color`(`navy`·`charcoal`·`green`·`brown`), `design.tokens`(`src/styles/tokens.css`), `updated_at`. **파일에 없는 키를 새로 만들지 않는다.**

```
git add -A
git commit -m "디자인 방향 board-green 적용"
```

커밋 메시지의 조합 이름은 고른 것으로 바꾼다. 화면이 바뀌었으면 `indeans-erp-check`로 넘긴다(검수 훅이 자동으로 요구한다).

## 산출물

| 경로 | 내용 |
|---|---|
| `src/styles/tokens.css` | 고른 조합의 토큰(색·서체·크기·간격·모서리·표/카드 규칙). 첫 줄 주석에 조합 이름 |
| `src/styles/base.css` · `src/styles/layout.css` | 비교 이미지를 그린 공통 바탕 CSS와 고른 구조의 화면 뼈대 CSS(`.owner/design/src/base.css`·`.owner/design/src/layout-<구조>.css`에서 복사) |
| `company/design.md` | 고른 조합·이유·바꾸면 안 되는 것. 템플릿 `assets/design.template.md` |
| `.owner/state.md`·`.owner/progress.json` | 선택한 디자인 기록 |
| 커밋 1개 | `디자인 방향 {조합} 적용` |

토큰 값을 회사에 맞게 바꿔도 된다. 단 **강조색은 하나만** 유지한다.

## 하지 않는 것

- 이미지 없이 말로 고르게 하기. 12장을 열어 보여 주는 것이 이 스킬의 전부다.
- 12장을 한 번에 늘어놓고 고르게 하기. **구조 먼저, 그다음 그 구조의 컬러.**
- 토큰 파일을 직접 새로 쓰기. `.owner/design/tokens/`의 12벌 중 하나를 복사한다.
- 두 조합을 섞기. 화면마다 인상이 달라진다.
- 장식 넣기: 그림자, 그라데이션, 둥근 아이콘 배경, 이모지, 불필요한 구분선.
- 강조색을 배경으로 넓게 깔기. 버튼 하나, 선택된 줄 하나가 전부다.
- 빨강을 경고·주의에 쓰기. 빨강은 삭제처럼 **되돌릴 수 없는 행동**에만.
- 글자 크기 4종·굵기 3종 넘기기.
- 화면 코드 새로 만들기. 초안은 `indeans-erp-draft`가 만든다. 이 스킬은 **방향과 토큰**만 정한다.
- 대표 확인 없이 이미 고른 조합을 바꾸기.

## 앞선 수강생 분기

디자인이 이미 정해져 있으면 아래 중 하나를 제안한다(고르는 것은 대표).

1. **두 조합 나란히 보기** — 같은 화면을 다른 컬러 토큰으로 한 번 캡처해 직원에게 어느 쪽이 빨리 읽히는지 물어본다. 결정 근거를 `company/design.md`에 한 줄 남긴다.
2. **밀도 조절** — 한 화면에서 30건 이상을 보는 대표라면 `--row-h`를 줄여 촘촘하게 만든다. 단 손가락으로 누르는 곳은 40px 아래로 내리지 않는다.
3. **고객이 보는 화면만 다르게** — 내부 화면은 지금 조합을 두고, 고객이 여는 화면 한 장만 카드·상세형 규칙으로 만든다. 토큰은 하나로 유지하고 여백·글자 크기만 키운다. 그 사실을 `company/design.md`에 적는다.
4. **인쇄 규칙** — 목록을 종이로 뽑아야 하면 인쇄용 규칙을 따로 둔다(배경색 제거, 선만 남김).

## 자주 막히는 지점

- **이미지가 안 열린다** — `node .owner/hooks/open.mjs .owner/design/index.html`이 실패하면 경로를 대표에게 알려 주고 파일을 직접 두 번 누르게 한다. 그래도 없으면 설치가 덜 된 것이니 설치기를 다시 돌린다.
- **적용했는데 화면이 안 바뀐다** — `tokens.css`를 불러오는 줄이 빠졌거나(절차 6), 화면 파일에 색이 직접 적혀 있어 토큰을 덮고 있다(절차 7).
- **표가 모바일에서 옆으로 밀린다** — 열 폭에 `minmax(0, 1fr)`이 빠졌거나, 줄바꿈 없는 긴 글자(이메일·주소)가 있다. `references/structures.md`의 말줄임 규칙을 적용한다.
- **화면이 너무 밋밋해 보인다** — 절제한 결과다. 색을 더하지 말고 **간격**을 조절한다. 줄 사이가 좁으면 답답해 보인다.
- **어디가 눌리는 곳인지 모르겠다** — 버튼에만 강조색을 쓰고 나머지는 글자만 둔다. 누를 수 있는 것과 없는 것의 차이를 색 하나로 일관되게 만든다.
- **글자가 작아 안 보인다** — 본문 크기를 올리되 4종 규칙은 유지한다. 모두 한 단계씩 올린다.
- **대표가 "셋 다 마음에 안 든다"고 한다** — 어느 부분이 걸리는지 하나만 묻는다(색인지, 빽빽함인지, 글자 크기인지). 대개 컬러 문제이고 구조는 맞다. 구조를 유지하고 컬러만 바꿔 다시 보여 준다.
- **로고 색을 꼭 쓰고 싶어 한다** — 네 가지 중 가장 가까운 것을 고른 뒤, 토큰의 `--primary` 한 줄만 로고 색으로 바꿔 캡처해 보여 준다. 글자가 안 읽히면 그 자리에서 되돌린다.
