# 인디언즈 운영 보고 (ERP 보고)

**이 스킬의 역할은 "실사용 중 받는 운영 보고"다.** 작업이 끝날 때 화면을 보여 주는 보고서는 `indeans-erp-report` 가 만든다. 여기서 만드는 것은 **앱에 쌓인 내용의 요약**이고, 앱을 열지 않아도 알아야 할 것을 정해진 시각에 채널로 보낸다.

운영 보고 단계의 본 실습이고, **완료 기준이 분명하다: 수강생 PC와 AI 도구를 모두 꺼도 보고가 온다.** 내 컴퓨터가 켜져 있을 때만 오는 것은 보고 체계가 아니다.

인디언즈가 보고·알림을 운영하며 굳힌 규칙 다섯 가지를 그대로 쓴다. **받는 사람마다 다른 문장**(같은 문장을 두 방에 보내지 않는다) · **같은 날 같은 보고는 한 번**(기록을 먼저 남기고 보낸다) · **0도 보낸다**(안 온 것과 0인 것은 다르다) · **보낸 기록은 남기고, 기록에는 수명이 있다**(오래된 기록은 예약으로 지운다 — 화면에서 안 보이게 하는 것은 지운 것이 아니다) · **시각은 서버가 한국 시간으로 판단한다**.

## 언제 쓰나

- 정해진 시각에 오늘 할 일·진행 현황·입력 누락을 받고 싶을 때.
- 오던 보고의 항목·시각·받는 사람을 바꾸고 싶을 때.
- 보고가 안 오는데 왜인지 알아야 할 때(발송 기록 확인).

쓰지 않는 경우: 받을 창구가 아직 없다(→ 먼저 `indeans-erp-channel`), 작업 종료 보고서(→ `indeans-erp-report`), 앱 화면 안 표시·배지(→ `indeans-erp-review`).

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | `channel.*`(창구) · `digest.scheduled` · `digest.first_received` |
| `company/channel.md` | 창구 목록·**수신자 라우팅 표**(누가 어느 방에서 무엇을)·비밀값 **이름**·보내지 않는 것 |
| `company/data.md` | **표와 칸 이름**(보고 문장에서 세는 대상)·마이그레이션 실행 기록 |
| `company/flows.md` · `company/workflow.md` | 단계 이름과 "끝났다"의 기준(저장 값 코드) |
| `company/people.md` | 역할별 노출 표 — 직원용 문장에 넣으면 안 되는 것 |
| `supabase/migrations/` | 마지막 번호, 발송 기록 표(`report_log`)가 이미 있나 |
| `company/digest.md` | 있으면 두 번째 — 아래 분기 |

**상태 문서가 실제와 다르면 문서를 믿지 않는다.** "예약했다"고 적혀 있어도 `select * from cron.job` 에 줄이 없으면 예약된 것이 아니다.

- **창구 없음** — `company/channel.md` 가 없거나 시험 발송이 도착하지 않았다 → 멈추고 `indeans-erp-channel` 로 보낸다.
- **처음** — 창구는 있고 `company/digest.md` 없음 → 절차 0부터.
- **진행 중** — 함수는 있는데 예약이 없거나 첫 수신을 못 했다 → 빠진 단계부터.
- **완료** — 정해진 시각에 오고 있다 → 「앞선 수강생 분기」.

판정을 한 문장으로 먼저 알린다. 예: "창구는 살아 있고 보고는 아직 없습니다. 무엇을 언제 받을지 다섯 가지만 여쭙고 서버에 걸겠습니다."

## 절차

### 0. 되돌릴 지점

```bash
git add -A
git commit -m "운영 보고 만들기 전 상태"
```

### 1. 왜 서버에서 보내야 하나 (2분, 세 문장)

> 보고를 내 컴퓨터에서 보내면 컴퓨터를 끄거나 AI 대화창을 닫는 순간 멈춥니다.
> 그래서 **데이터가 들어 있는 쪽(Supabase)** 에 시각을 걸어 둡니다. 서버가 스스로 세어 보고 채널로 보냅니다.
> 다 끝나면 노트북을 닫고 다음 정시에 폰만 봅니다. 그때 와야 완료입니다.

### 2. 인터뷰 — 한 번에 하나, 다섯 문항

**2-1. 무엇을** — "아침에 앱을 열지 않아도 알고 계셔야 하는 것이 무엇인가요? 가장 중요한 것부터 하나씩요."
판단: **항목은 세 개까지.** 넷째부터는 '다음에 넣을 것'으로 내린다. 앱의 데이터로 **셀 수 있는 것**이어야 한다 — 셀 수 없는 답이면 "그걸 앱에서 무엇으로 알 수 있을까요?" 자주 나오는 셋: 오늘 해야 할 건수 · 기한이 지났는데 안 끝난 건수 · 어제 들어온 건수(보기로만 든다).

**2-2. 언제** — "그걸 몇 시에 보시면 가장 쓸모 있습니까? 요일도 정해 주세요."
판단: **하루 한 번으로 시작한다.** 업무 시작 30분 전이 가장 많이 쓰인다. 주말을 뺄지도 여기서 받는다.

**2-3. 누구에게** — `company/channel.md` 의 라우팅 표를 읽어 주고 묻는다: "이 표대로 대표님 방에 이 보고를, 직원 방에는 이렇게 줄인 보고를 보내면 될까요?"
판단: **대표용을 먼저 완성한다.** 직원용은 **항목을 줄인 다른 문장**이다 — 라우팅 표의 '보내지 않는 것'과 `people.md` 노출 표를 한 줄씩 지킨다. 같은 문장을 두 방에 보내지 않는다.

**2-4. 무엇을 안 보내나** — "보고에 고객 이름이나 금액이 들어가야 하나요?"
판단: 채널은 회사 밖 서비스다. 기본은 **건수와 관리 단위 이름까지.** 이름이 있어야 안다고 하면 관리 단위 이름(주문 번호·건 제목)까지만 넣고 **고객 실명·연락처·금액·계좌는 넣지 않는다.** 결정을 `company/digest.md` 에 한 줄로.

**2-5. 안 오면 어떻게 아나** — "어느 날 보고가 안 왔다면, 그걸 어떻게 알아채시겠어요?"
판단: 사람의 기억에 맡기지 않는다. 발송 성공·실패를 **표에 남기고**(절차 4), 주간 점검(`indeans-erp-routine` 5단계)에서 그 표를 본다.

받은 답을 표 한 장으로 되읽어 확인한다: 항목 · 시각 · 요일 · 받는 사람별 문장 · 넣지 않는 것.

### 3. 보고 문장 틀

`assets/digest.template.md` 를 채워 `company/digest.md` 로 저장한다.

- **10줄 이내.** 첫 줄은 회사 이름과 날짜, 그다음 항목 한 줄씩. 표를 쓰지 않는다(채널에서 깨진다).
- **0인 항목도 보낸다**("기한 지난 건: 0").
- 회사가 쓰는 말을 그대로(`company/data.md` 대응표). 세는 조건은 **저장 값 코드**로 쓴다(화면 글자로 세면 이름을 바꾸는 날 0이 된다).

완성된 문장 예시를 대표에게 **한 번 읽어 주고** 확인받는다. 문장을 고치는 것은 지금이 가장 싸다.

### 4. 표·함수·예약 — `references/cron-sql.md` 순서대로

SQL 뼈대는 전부 `references/cron-sql.md` 에 있다. **표·칸 이름은 `company/data.md` 를 보고 바꿔 넣는다.**

1. **확장 켜기** — `pg_cron`(시각 예약) · `pg_net`(바깥으로 보내기).
2. **비밀값 두기** — 창구 주소·열쇠를 설정 표 `app_secret` 에(2절 — 안전선 두 줄을 빼지 않는다). **마이그레이션 파일에 값을 적지 않는다.** 값 넣는 SQL 은 SQL Editor 에서 한 번만 실행하고, 파일에는 이름만.
3. **발송 기록 표** — `report_log`. 같은 날 같은 보고를 두 번 보내지 못하게 **유니크 조건**을 함께.
4. **발송 함수** — 받는 사람마다 하나(`send_owner_digest`, 직원용은 `send_staff_digest`). 시각 검사 → **기록 먼저**(중복 방지) → 세기 → 문장 → 보내기. 로그인 사용자에게 실행 권한을 주지 않는다.
5. **응답 대조와 보관 기간** — 보낸 뒤 응답을 기록에 옮기는 함수(6절)와, **90일 넘은 발송 기록을 지우는 예약**(9절)을 같이 건다. 화면에서 오래된 줄을 안 보이게 하는 것은 지운 것이 아니다 — 기록 표는 예약으로 정리한다.
6. **예약 등록** — `cron.schedule`. **시각은 한국 시간이 아니라 세계 표준시(UTC)로 적는다**(4절 변환표). 함수 안의 날짜·시각 판단은 `Asia/Seoul` 로 한다.

파일은 `supabase/migrations/` 의 **다음 번호**로(예: `0006_report_log.sql`, `0007_digest_function.sql`). 실행 전 `npm run check`(비밀값 표·발송 기록 표는 정책을 일부러 안 두므로 허용 주석이 이미 들어 있다) → 실행 → `company/data.md` 실행 기록 한 줄.

### 5. 손으로 한 번 보내 본다 — 첫 수신 확인

```sql
select public.send_owner_digest();
```

- 폰에서 문장이 오는지 **대표가 직접 본다.** 오면 그 문장을 `company/digest.md` 3절에 그대로 붙인다.
- 안 오면 `references/cron-sql.md` 6절(발송 기록과 응답)을 순서대로 본다. 함수가 성공을 돌려줘도 도착은 별개다.

### 6. 같은 명령을 한 번 더 — 중복 방지 확인

```sql
select public.send_owner_digest();
```

- 이번에는 **"이미 보냈음"** 이 나와야 한다. 두 번째 문장이 폰에 오면 중복 방지가 안 걸린 것이다.
- 별도 절차로 두는 이유: 정해진 시각에 나가는 것은 조건이 틀려도 내가 안 보는 사이에 계속 틀린다. 결과를 `company/digest.md` 에 한 줄로.

### 7. 예약을 걸고 다음 정시를 기다린다

1. 4절로 예약을 등록하고 `select * from cron.job;` 으로 줄을 본다(이름·시각·명령).
2. **노트북을 닫고 AI 대화창도 닫는다.** 다음 정시에 폰만 본다.
3. 왔으면 `.owner/progress.json` 의 `digest.first_received` 를 `true`. **이 확인 없이 운영 보고 단계를 끝내지 않는다.**
4. 안 왔으면 `select * from cron.job_run_details order by start_time desc limit 5;` 로 예약이 돌았는지부터 본다.

수업 시간 안에 정시가 오지 않으면 **임시로 5분 뒤 시각을 하나 더 걸어** 확인하고, 확인 뒤 임시 예약을 지운다(`cron.unschedule`) — 남겨 두면 매일 그 시각에 또 온다.

### 8. 확인이 꼭 필요한 공지 (라우팅 표에 "확인 필요 — 있음"이 있을 때만)

알림은 세 종류로 나뉜다. 대부분은 첫째·둘째다.

| 종류 | 예 | 확인 표시 | 다시 알리기 |
|---|---|---|---|
| 알려 주기만 | 운영 보고 | 필요 없음 | 안 함 |
| 처리가 필요한 일 | 기한 지난 건 | 앱에서 그 건의 상태가 바뀌면 처리된 것 | 다음 보고에 **남은 건수**로 다시 나온다(따로 보내지 않는다) |
| 읽었다는 표시가 꼭 필요한 공지 | 규정 변경·안전 공지 | 앱 안 '확인' 버튼 → 확인 기록 표 | 확인 안 한 사람 **수**만 대표 보고에, 하루 한 번·최대 3번 |

셋째만 `references/cron-sql.md` 8절의 확인 기록 표(`notice_ack`)를 만든다. 채널 메시지에는 읽음 표시가 없으니 확인은 **앱 안에서** 받는다. 확인 기록에도 수명이 있다 — 공지와 함께 90일 뒤 지운다. 횟수 제한 없는 재알림은 스팸이 되고, 스팸이 되면 아무도 안 본다.

### 9. 문구 조정 (첫 수신 뒤 한 번)

> "이 중에 보고도 아무 행동도 안 하게 되는 줄이 있습니까?"

있으면 **뺀다.** 숫자만 있어 판단이 안 되는 줄은 기준을 붙인다(예: "기한 지난 건: 3건 — 가장 오래된 것 5일"). 고친 문장은 함수 안의 문장도 같이 고치고 다음 번호 파일로 남긴다. 하루 받아 보게 하고 다음 회차 시작에 `company/log.md` 에 세 줄로 적어 오게 한다.

### 10. 검수와 상태 문서

새 표(발송 기록·비밀값)와 서버 예약이 생겼으므로 **`indeans-erp-check` 를 호출한다**(위험 등급 1 — 새 표 구조). 감독에게 **비밀값을 어디에 뒀는지(이름만)** 와 **로그인 사용자에게 함수 실행 권한을 주지 않았다는 것**을 함께 넘긴다. 이후 문장만 바꾸는 수정은 3등급이다.

`.owner/state.md` — "매일 <시각> 운영 보고 3줄이 <창구>로 온다(PC 꺼도 확인함)". `.owner/progress.json` — `digest.scheduled`·`digest.first_received`·`updated_at`.

```bash
git add -A
git commit -m "운영 보고: 발송 기록·발송 함수·보관 기간 정리·서버 예약과 첫 수신 확인"
```

## 하지 않는 것

- 내 컴퓨터·브라우저·AI 대화창이 켜져 있어야 도는 방식으로 만들지 않는다.
- 비밀 키(`service_role`·`secret`)·창구 주소·열쇠를 앱이나 마이그레이션 파일에 넣지 않는다.
- 발송 함수의 실행 권한을 로그인 사용자에게 주지 않는다. 이 함수는 서버 예약만 부른다.
- 고객 실명·연락처·금액·계좌를 보고 문장에 넣지 않는다. 같은 문장을 대표용·직원용 두 방에 보내지 않는다.
- 발송 기록 없이 보내지 않는다. 유니크 조건을 빼지 않는다. 보관 기간 정리 없이 기록을 쌓지 않는다.
- 항목을 넷 이상 넣지 않는다. 횟수 제한 없이 다시 알리지 않는다.
- 도착을 확인하지 않고 "보고가 됩니다"라고 말하지 않는다.

## 앞선 수강생 분기

정해진 시각에 오고 있으면 하나만 고른다.

1. **직원용 보고 분리** — `send_staff_digest` 를 대표용과 같은 방식으로 만든다. 라우팅 표의 '보내지 않는 것'과 노출 표를 한 줄씩 대조하고, 직원 계정으로 받는 사람을 확인한다.
2. **놓침 신호 한 줄** — "정해진 날이 지났는데 다음 단계로 안 넘어간 건"을 세는 줄. 항목이 넷이 되면 가장 안 보는 줄을 뺀다.
3. **실패했을 때 다른 창구로** — 발송 기록이 `failed` 인 날에 다른 창구로 한 번 더 보낸다. 두 번 실패하면 대표에게 "보고 체계가 멈췄다" 한 줄만.
4. **보고 체계 자체의 감시** — 주간 점검에서 `report_log` 의 지난 7일 성공 건수를 세어 7(평일만이면 5)이 아니면 1순위로 올린다.

## 자주 막히는 지점

- **시각이 9시간 밀려서 온다** — 예약은 세계 표준시로 돈다. 한국 시간 - 9 를 적는다(4절 변환표).
- **주말만 빼려 했는데 요일이 하루 밀렸다** — 한국 08시는 세계 표준시로 **전날 23시**라 요일도 하루 앞으로 밀린다. 변환표의 요일 칸을 그대로 쓴다.
- **예약이 아예 안 돌았다** — `cron.job` 에 줄이 있는지, `cron.job_run_details` 에 실행 기록이 있는지 순서대로 본다.
- **함수는 성공인데 안 온다** — 보내는 것과 도착은 별개다. 응답 기록을 본다(6절). 401·404 면 주소·열쇠, 400 이면 보내는 모양이다.
- **하루에 두 번 왔다** — 임시 예약이 남아 있다. `cron.job` 에서 이름으로 찾아 지운다.
- **0건인 날은 안 온다** — 0일 때 함수가 중간에 멈추게 쓰였다. 0도 보내도록 고친다.
- **상태 이름을 바꾼 뒤 건수가 0이 됐다** — 함수가 옛 상태 값을 세고 있다. 저장 값 코드로 센다(`indeans-erp-workflow` 절차 7).
- **표 이름이 안 맞는다는 오류** — 뼈대를 그대로 실행했다. `company/data.md` 의 실제 이름으로 바꾼다.
- **한 주 받아 보니 안 본다** — 항목이 많거나 시각이 안 맞는다. 줄을 늘리지 말고 **줄이거나 시각을 옮긴다.**
