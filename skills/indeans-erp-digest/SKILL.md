# 인디언즈 운영 보고 (ERP 보고)

**이 스킬의 역할은 "실사용 중 대표가 받는 운영 보고"다.** 작업이 끝날 때 화면을 보여 주는 보고서는 `indeans-erp-report` 가 만든다. 여기서 만드는 것은 **앱에 쌓인 내용의 요약**이고, 대표가 앱을 열지 않아도 알아야 할 것을 정해진 시각에 채널로 보낸다.

3회차 본 실습이고, **완료 기준이 분명하다: 수강생 PC와 AI 도구를 모두 꺼도 보고가 온다.** 내 컴퓨터가 켜져 있을 때만 오는 것은 보고 체계가 아니다.

## 언제 쓰나

- 정해진 시각에 오늘 할 일·진행 현황·입력 누락을 받고 싶을 때(3회차 본 실습).
- 오던 보고의 항목이나 시각을 바꾸고 싶을 때.
- 보고가 안 오는데 왜인지 알아야 할 때(발송 기록 확인).

쓰지 않는 경우: 받을 창구가 아직 없다(→ 먼저 `indeans-erp-channel`), 작업 종료 보고서(→ `indeans-erp-report`), 앱 화면 안 표시·배지(→ `indeans-erp-review`).

## 시작 전 상태 진단

먼저 읽고 판정한다. 읽기 전에 말을 걸지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · 미해결 문제 · 다음 행동 |
| `.owner/progress.json` | `channel.*`(창구가 있나) · `digest.scheduled` · `digest.first_received` |
| `company/channel.md` | 창구 목록·받는 사람·비밀값 **이름**·보내지 않는 것 |
| `company/data.md` | **표와 칸 이름** — 보고 문장에서 세는 대상 |
| `company/flows.md` · `company/workflow.md` | 단계 이름과 "끝났다"의 기준 |
| `company/people.md` | 대표용·직원용을 나눌지 판단할 근거 |
| `supabase/migrations/` | 마지막 번호, 예약 표(`report_log`)가 이미 있나 |
| `company/digest.md` | 있으면 두 번째 — 아래 분기 |

**상태 문서가 실제와 다르면 문서를 믿지 않는다.** "예약했다"고 적혀 있어도 `select * from cron.job` 에 줄이 없으면 예약된 것이 아니다.

판정과 분기:

- **창구 없음** — `company/channel.md` 가 없거나 시험 발송이 도착하지 않았다 → 여기서 멈추고 `indeans-erp-channel` 로 보낸다. 보낼 곳 없이 보고를 만들 수 없다.
- **처음** — 창구는 있고 `company/digest.md` 없음 → 절차 0부터 순서대로.
- **진행 중** — 함수는 있는데 예약이 없거나 첫 수신을 못 했다 → 빠진 단계부터.
- **완료** — 정해진 시각에 오고 있다 → 「앞선 수강생 분기」로 간다.

판정을 한 문장으로 먼저 알린다. 예: "창구는 살아 있고 보고는 아직 없습니다. 무엇을 언제 받을지 다섯 가지만 여쭙고 서버에 걸겠습니다."

## 절차

### 0. 되돌릴 지점

```bash
git add -A
git commit -m "운영 보고 만들기 전 상태"
```

### 1. 왜 서버에서 보내야 하나 (2분, 세 문장)

> 보고를 내 컴퓨터에서 보내면 컴퓨터를 끄거나 AI 대화창을 닫는 순간 멈춥니다.
> 그래서 **데이터가 들어 있는 쪽(Supabase)** 에 시각을 걸어 둡니다. 서버가 스스로 세어 보고 채널로 보냅니다.
> 다 끝나면 노트북을 닫고 다음 정시에 폰만 봅니다. 그때 와야 완료입니다.

### 2. 인터뷰 — 한 번에 하나, 다섯 문항

**2-1. 무엇을**
> "아침에 앱을 열지 않아도 알고 계셔야 하는 것이 무엇인가요? 가장 중요한 것부터 하나씩요."

판단 기준: **항목은 세 개까지**다. 넷째부터는 `company/digest.md` 의 '다음에 넣을 것'으로 내린다. 항목은 앱에 있는 데이터로 셀 수 있는 것이어야 한다("기분", "분위기"는 셀 수 없다). 셀 수 없는 답이 나오면 되묻는다: **"그걸 앱에서 무엇으로 알 수 있을까요?"**

자주 나오는 세 가지: 오늘 해야 할 건수 · 기한이 지났는데 안 끝난 건수 · 어제 들어온 건수. 대표의 답이 없으면 이 셋을 보기로 든다(고르게만 하고 우기지 않는다).

**2-2. 언제**
> "그걸 몇 시에 보시면 가장 쓸모 있습니까? 요일도 정해 주세요."

판단 기준: **하루 한 번으로 시작한다.** 아침 업무 시작 30분 전이 가장 많이 쓰인다. 두 번(아침·저녁)은 첫 보고가 안정된 뒤에 늘린다. 주말을 뺄지도 여기서 받는다.

**2-3. 누구에게**
> "이 보고를 대표님만 받으시겠어요, 직원도 같은 내용을 받아야 하나요?"

판단 기준:

- "대표만" → 창구 하나(대표용)로 끝낸다.
- "직원도" → **같은 문장을 두 방에 보내지 않는다.** 직원용은 항목을 줄인 별도 문장으로 만든다(`company/channel.md` 의 '직원 방에 보내지 않을 항목'을 그대로 지킨다). 오늘은 대표용을 먼저 완성하고, 직원용은 같은 방식으로 한 번 더 복사한다.

**2-4. 무엇을 안 보내나**
> "보고에 고객 이름이나 금액이 들어가야 하나요?"

판단 기준: 채널은 회사 밖 서비스다. 기본은 **건수와 관리 단위 이름까지**다. 대표가 "이름이 있어야 안다"고 하면 관리 단위 이름(예: 주문 번호·건 제목)까지만 넣고 **고객 실명·연락처·금액·계좌는 넣지 않는다.** 이 결정을 `company/digest.md` 에 한 줄로 적는다.

**2-5. 안 오면 어떻게 아나**
> "어느 날 보고가 안 왔다면, 그걸 어떻게 알아채시겠어요?"

판단 기준: 사람의 기억에 맡기지 않는다. 발송 성공·실패를 **표에 남기고**(절차 4), 주간 루틴에서 그 표를 보는 것으로 정한다(`indeans-erp-routine` 5단계 옆에 한 줄 추가).

받은 답을 표 한 장으로 되읽어 확인한다: 항목 3개 · 시각 · 요일 · 받는 사람 · 넣지 않는 것.

### 3. 보고 문장 틀 만들기

`assets/digest.template.md` 를 채워 `company/digest.md` 로 저장한다. 문장 규칙은 이렇다.

- **10줄 이내.** 첫 줄은 회사 이름과 날짜, 그다음 항목 한 줄씩.
- 표를 쓰지 않는다. 채널에서 표는 깨진다.
- 숫자가 0인 항목도 보낸다("기한 지난 건: 0"). 안 보내면 대표가 "안 온 것"과 "0인 것"을 구분할 수 없다.
- 회사가 쓰는 말을 그대로 쓴다(`company/profile.md`·`data.md` 의 대응표).

대표에게 완성된 문장 예시를 **한 번 읽어 주고** 확인받는다. 문장을 고치는 것은 지금이 가장 싸다.

### 4. 표·함수·예약 만들기 — `references/cron-sql.md` 순서대로

이 절차의 SQL 뼈대는 전부 `references/cron-sql.md` 에 있다. **표 이름과 칸 이름은 `company/data.md` 를 보고 바꿔 넣는다.** 뼈대를 그대로 실행하면 표 이름이 안 맞아 오류가 난다.

순서는 다섯 단계다.

1. **확장 켜기** — `pg_cron`(시각 예약) · `pg_net`(바깥으로 보내기). 대시보드 Database > Extensions 에서 켜도 되고 SQL 로 켜도 된다.
2. **비밀값 두기** — 창구 주소·열쇠를 설정 표 `app_secret` 에 넣는다(`cron-sql.md` 2절 — 안전선 두 줄을 빼지 않는다). **마이그레이션 파일에 값을 적지 않는다.** 값 넣는 SQL 은 대시보드 SQL Editor 에서 한 번 실행하고, 파일에는 이름만 남긴다.
3. **발송 기록 표** — `report_log`. 같은 날 같은 보고를 두 번 보내지 못하게 **유니크 조건**을 함께 만든다.
4. **발송 함수** — 세고, 문장을 만들고, 기록을 먼저 남기고, 보낸다. 로그인 사용자에게 실행 권한을 주지 않는다.
5. **예약 등록** — `cron.schedule`. **시각은 한국 시간이 아니라 세계 표준시(UTC)로 적는다.** 변환표가 `references/cron-sql.md` 4절에 있다.

파일은 `supabase/migrations/` 의 **다음 번호**로 만든다(예: `0005_report_log.sql`, `0006_digest_function.sql`). 이미 실행한 파일은 고치지 않는다.

### 5. 손으로 한 번 보내 본다 — 첫 수신 확인

예약을 기다리지 않고 SQL Editor 에서 함수를 직접 부른다.

```sql
select public.send_owner_digest();
```

- 폰에서 문장이 오는지 **대표가 직접 본다.** 오면 그 문장을 `company/digest.md` 3절에 그대로 붙인다.
- 안 오면 `references/cron-sql.md` 6절(발송 기록과 응답 보는 법)을 순서대로 본다. 함수가 성공을 돌려줘도 도착은 별개다 — 기록 표의 상태를 본다.

### 6. 같은 명령을 한 번 더 부른다 — 중복 발송 방지 확인

```sql
select public.send_owner_digest();
```

- 이번에는 **"이미 보냈음"** 이 나와야 한다. 폰에 두 번째 문장이 오면 중복 방지가 안 걸린 것이다.
- 이 한 걸음을 5번에 묻어 두면 건너뛴다. **별도 절차로 두는 이유가 그것이다** — 정해진 시각에 나가는 것은 조건이 틀려도 내가 안 보는 사이에 계속 틀린다.
- 확인 결과를 `company/digest.md` 에 한 줄로 남긴다.

### 7. 예약을 걸고 다음 정시를 기다린다

1. `references/cron-sql.md` 4절로 예약을 등록한다.
2. `select * from cron.job;` 로 줄이 생겼는지 본다(이름·시각·명령).
3. **노트북을 닫고 AI 대화창도 닫는다.** 다음 정시에 폰만 본다.
4. 왔으면 `.owner/progress.json` 의 `digest.first_received` 를 `true` 로 적는다. **이 확인 없이 3회차를 끝내지 않는다.**
5. 안 왔으면 `select * from cron.job_run_details order by start_time desc limit 5;` 로 예약이 돌았는지 먼저 본다(돌았나 / 안 돌았나에 따라 볼 곳이 다르다).

수업 시간 안에 정시가 오지 않으면 **임시로 5분 뒤 시각을 하나 더 걸어** 그 자리에서 확인하고, 확인 뒤 임시 예약을 지운다(`cron.unschedule`). 임시 예약을 지우는 것을 절차에 넣는다 — 남겨 두면 매일 그 시각에 또 온다.

### 8. 문구 조정 (첫 수신 뒤 한 번)

대표에게 온 문장을 보며 묻는다.

> "이 중에 보고도 아무 행동도 안 하게 되는 줄이 있습니까?"

- 있으면 **뺀다.** 안 보게 되는 줄이 하나 있으면 나머지도 안 보게 된다.
- 숫자만 있어 판단이 안 되는 줄은 기준을 붙인다(예: "기한 지난 건: 3건 — 가장 오래된 것 5일").
- 고친 문장은 함수 안의 문장도 같이 고치고, 다음 번호 마이그레이션 파일로 남긴다.

과제로 하루 받아 보게 하고, 다음 회차 시작에 `company/log.md` 에 세 줄로 적어 오게 한다.

### 9. 검수와 상태 문서

데이터 구조(표)와 서버 예약이 생겼으므로 **`indeans-erp-check` 를 호출한다.** 감독 판정 → 실측 → 작업 보고서까지 그 스킬이 이어서 한다. 감독에게 넘길 때 **비밀값을 어디에 뒀는지(이름만)** 와 **로그인 사용자에게 함수 실행 권한을 주지 않았다는 것**을 함께 적는다.

그다음 `.owner/state.md` 를 고친다.

- **현재 기능** — "매일 <시각> 운영 보고 3줄이 <창구>로 온다(PC 꺼도 확인함)".
- **미해결 문제** — 남은 것(예: "직원용 보고는 아직 없음").
- **다음 행동** — 다음 스킬.

`.owner/progress.json` 의 `digest.scheduled`·`digest.first_received` 를 적고 `updated_at` 을 갱신한다.

```bash
git add -A
git commit -m "운영 보고: 발송 기록 표·발송 함수·서버 예약과 첫 수신 확인"
```

## 하지 않는 것

- 내 컴퓨터·브라우저·AI 대화창이 켜져 있어야 도는 방식으로 만들지 않는다(화면에서 타이머를 돌리거나 사람이 눌러 보내는 방식). 그것은 이 회차의 완료가 아니다.
- 비밀 키(`service_role`·`secret`)를 앱이나 마이그레이션 파일에 넣지 않는다. 창구 주소·열쇠도 파일에 적지 않는다.
- 발송 함수의 실행 권한을 로그인 사용자에게 주지 않는다. 이 함수는 서버 예약만 부른다.
- 고객 실명·연락처·금액·계좌를 보고 문장에 넣지 않는다.
- 발송 기록 없이 보내지 않는다. 기록이 없으면 안 온 날을 알 수 없다.
- 같은 날 같은 보고를 두 번 보내지 않는다. 유니크 조건을 빼지 않는다.
- 항목을 넷 이상 넣지 않는다. 길어진 보고는 안 읽힌다.
- 보고로 화면을 대신하지 않는다. 알림이 놓친 일을 대신 처리해 주지는 않는다.
- 도착을 확인하지 않고 "보고가 됩니다"라고 말하지 않는다.

## 앞선 수강생 분기

정해진 시각에 오고 있으면 하나만 고른다.

1. **직원용 보고 분리** — 항목을 줄인 별도 문장과 별도 방. `company/channel.md` 의 '보내지 않을 항목'을 한 줄씩 대조하고, 직원 계정으로 받는 사람을 확인한다.
2. **놓침 신호 한 줄 추가** — "정해진 날이 지났는데 다음 단계로 안 넘어간 건"을 세는 줄을 넣는다. 항목이 넷이 되면 가장 안 보는 줄을 뺀다.
3. **실패했을 때 다른 창구로** — 발송 기록이 `failed` 인 날에 다른 창구로 한 번 더 보내는 규칙을 넣는다. 두 번 실패하면 대표에게 "보고 체계가 멈췄다" 한 줄만 보낸다.
4. **보관과 정리** — 발송 기록이 쌓이면 90일보다 오래된 줄을 지우는 예약을 하나 더 건다. 표가 커지면 조회가 느려진다.

## 자주 막히는 지점

- **시각이 9시간 밀려서 온다** — 예약은 세계 표준시로 돈다. 한국 시간 - 9 를 적는다(`references/cron-sql.md` 4절 변환표).
- **주말만 빼려 했는데 요일이 하루 밀렸다** — 한국 시간 08시는 세계 표준시로 **전날 23시**라 요일도 하루 앞으로 밀린다. 변환표의 요일 칸을 그대로 쓴다.
- **예약이 아예 안 돌았다** — `cron.job` 에 줄이 있는지, `cron.job_run_details` 에 실행 기록이 있는지 순서대로 본다. 줄이 없으면 등록이 안 된 것이다.
- **함수는 성공인데 안 온다** — 보내는 것과 도착은 별개다. 응답 기록을 본다(`references/cron-sql.md` 6절). 401·404 면 주소·열쇠, 400 이면 보내는 모양이다.
- **응답 기록이 비어 있다** — 응답 기록은 몇 시간 뒤 정리된다. 어제 것을 찾지 말고 지금 한 번 보내 놓고 바로 본다.
- **하루에 두 번 왔다** — 임시로 걸어 둔 예약이 남아 있다. `cron.job` 을 열어 이름으로 찾아 지운다.
- **0건인 날은 안 온다** — 세는 조건이 0건일 때 함수가 중간에 멈추게 쓰인 것이다. 0도 보내도록 고친다. 안 온 것과 0인 것은 대표에게 완전히 다른 뜻이다.
- **표 이름이 안 맞는다는 오류** — 뼈대를 그대로 실행한 것이다. `company/data.md` 의 실제 표·칸 이름으로 바꾼다.
- **보고를 한 주 받아 보니 안 본다** — 항목이 많거나 시각이 안 맞는 것이다. 줄을 늘리지 말고 **줄이거나 시각을 옮긴다.**
