# 인디언즈 초안 생성

## 언제 쓰나

- 인터뷰로 회사 문서가 만들어지고 디자인 방향까지 고른 직후(1회차 마지막 실습).
- 초안이 이미 있고 두 번째 업무 흐름을 붙일 때(4회차·앞선 수강생).

만드는 것은 **첫 버전**이다. 예쁘게 다듬는 것보다 **돌아가는 것**이 먼저다. 끝나면 `indeans-erp-report`로 첫 작업 보고서를 만든다 — 거기까지가 1회차의 필수 완료 결과다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `company/structure.md` | 화면 3개 목록·한 건에 적는 항목표·**이번에 만들지 않을 것**. **이게 없으면 시작하지 않는다** |
| `company/design.md` · `src/styles/tokens.css` | 고른 구조(목록·표형 / 진행 보드형 / 카드·상세형)와 색. 없으면 디자인부터 |
| `.owner/design/src/<구조>-<컬러>.html` · `src/styles/base.css`·`layout.css` | 고른 조합의 목업과 뼈대 CSS — 화면 뼈대(상단바·메뉴·표/보드/카드 배치·클래스 이름)는 여기서 가져온다 |
| `company/flows.md` | 단계·상태 값·기본값 |
| `company/profile.md` | 관리 단위(회사 말), 업태, 화면에서 쓸 말 |
| `company/scope.md` | 이 회차의 성공 기준(체크박스) |
| `.owner/state.md` · `.owner/progress.json` | 어디까지 왔는지·미해결 문제 |
| `package.json` · `src/screens/` · `src/data/sample.ts` | 앱과 화면이 이미 있는지 |

**상태 문서와 실제 파일이 다르면 문서를 믿지 않는다.** 실제를 확인한 뒤 문서를 고치고 시작한다.

판정과 분기:

- **문서 없음** — `company/structure.md`가 없다 → 만들지 않는다. "먼저 `indeans-erp-interview` 스킬로 인터뷰를 해야 합니다"라고 알리고 멈춘다.
- **디자인 없음** — `src/styles/tokens.css`가 없다 → `indeans-erp-design`을 먼저 하라고 알린다(5~10분). 그것 없이 만들면 나중에 화면을 두 번 고치게 된다.
- **문서·디자인 있음, 앱 없음** → 절차 1~13(전체 생성).
- **앱 있음, 화면 3개 미완** → 빠진 화면만 만든다.
- **앱 있음, 화면 3개 완성** → **두 번째 흐름 추가 모드**(절차 14).

판정을 한 문장으로 먼저 알린다.

## 절차

### 1. 되돌릴 지점

```
git add -A
git commit -m "초안 만들기 전"
```

커밋할 게 없으면 넘어간다. 이 커밋이 있으면 무엇이 잘못돼도 여기로 돌아온다.

### 2. 구조안 읽고 한 번 확인하기 (질문 1개)

`structure.md`에서 읽은 것을 아래 형태로 보여 준다.

```
관리 단위: ○○ (영문 키 ○○)
화면 1 목록: ○○ — 한 줄에 ○·○·○
화면 2 상세·입력: 적는 항목 ○개
화면 3 오늘 현황: ○○
상태: ○ → ○ → ○ (기본값 ○)
디자인: {구조 이름} + {컬러 이름}
이번에 만들지 않을 것: ○○ · ○○
```

한 줄을 같이 읽어 준다: "(영문 키는 코드 안에서만 쓰는 이름입니다. 화면에는 회사에서 부르시는 말 그대로 나옵니다.)"

그리고 묻는다: **"이대로 만들까요? 고칠 것이 있으면 지금 말씀해 주세요."**

답을 듣기 전에 파일을 만들지 않는다. 고칠 것이 있으면 `structure.md`를 먼저 고치고 다시 확인한다. **"이번에 만들지 않을 것"에 있는 기능은 넣지 않는다** — 넣고 싶어지면 그 표를 먼저 고친다.

### 3. Vite 프로젝트 만들기

프로젝트 폴더에는 이미 `company/`·`course/`·`.owner/`가 있다. **빈 폴더가 아니면 생성기가 기존 파일을 지울지 물어 온다.** 그 질문을 피하려고 임시 폴더에 만든 뒤 옮긴다.

```
npm create vite@latest .vite-init -- --template react-ts
```

맥·리눅스:

```
cp -R .vite-init/. .
rm -rf .vite-init
```

윈도우 PowerShell:

```
Copy-Item -Path ".vite-init\*" -Destination "." -Recurse -Force
Remove-Item -Recurse -Force ".vite-init"
```

- 옮긴 뒤 `package.json`의 `name`이 임시 폴더 이름(`vite-init`)으로 들어가 있다. **프로젝트 폴더 이름으로 바꾼다** — 2회차 배포 때 이 이름이 주소에 쓰인다.
- 숨은 파일(`.gitignore`)도 함께 와야 한다. 안 왔으면 따로 복사한다. `.gitignore`에 `node_modules`·`.env.local`·`.owner/tmp/` 세 줄이 들어 있는지 확인하고 빠진 줄은 넣는다(`.owner/tmp/`는 스킬이 쓰고 버리는 임시 자리라 커밋하지 않는다).
- 프로젝트에 이미 `README.md`가 있으면 덮이지 않게 주의한다(절차 12에서 우리 것으로 다시 쓴다).
- **`src/styles/tokens.css`를 지우지 않는다.** 디자인 스킬이 넣어 둔 파일이다.

그 다음:

```
npm install
```

2~5분 걸린다. 도중에 끊지 않는다.

### 4. 화면 사진 찍는 도구 넣기

보고서에 넣을 사진을 찍는 도구다. `package.json`이 생긴 지금 한 번만 설치한다.

```
npm i -D playwright
npx playwright install chromium
```

두 번째 줄은 브라우저를 내려받아 2~4분 걸린다. 네트워크가 막으면 붙잡지 않는다 — 사진 없이도 보고서는 만들어진다.

### 5. 파일 구조 만들기

아래 구조로 만든다. **라우터 같은 추가 라이브러리를 설치하지 않는다** — 화면 전환은 `useState`로 한다.

```
src/
  main.tsx          ← tokens.css·base.css·layout.css 를 여기서 불러온다
  App.tsx           ← 화면 3개 전환 + 아래 탭(또는 상단 탭)
  types.ts          ← 한 건의 모양과 상태 값
  data/sample.ts    ← 예시 데이터 8~12건
  lib/storage.ts    ← 브라우저에 저장하고 읽어오기
  screens/ListScreen.tsx
  screens/DetailScreen.tsx
  screens/TodayScreen.tsx
  styles/tokens.css
  styles/base.css   ← 디자인 스킬이 넣은 공통 바탕
  styles/layout.css ← 디자인 스킬이 넣은 고른 구조의 뼈대
```

- 파일 이름·폴더 이름은 위와 똑같이 쓴다. 다음 회차 스킬과 감독 에이전트가 이 경로를 찾는다.
- `src/App.css`·`src/index.css`·`src/assets/`를 지운다. **위 목록에 없는 것은 `src/`에서 전부 지운다**(생성기 판에 따라 들어 있는 파일이 다르다). 단 `styles/` 폴더(tokens·base·layout)는 남긴다.
- 지운 뒤 `src/main.tsx`가 아직 `./index.css`를 부르고 있으면 그 줄을 세 줄(`import './styles/tokens.css'`·`import './styles/base.css'`·`import './styles/layout.css'`)로 바꾼다 — **이걸 빠뜨리면 고른 디자인이 화면에 안 먹는다.**

### 6. 타입과 상태 값

`structure.md`의 항목 표와 `flows.md`의 상태 값을 그대로 옮긴다.

- 영문 키는 `structure.md`에 적힌 것을 쓴다. 새로 짓지 않는다.
- **저장하는 상태 값은 영문 코드로 둔다. 화면에 보이는 글자는 따로 표로 둔다.** 예: `type Status = 'assigned' | 'done'` 와 `const STATUS_LABEL = { assigned: '배정됨', done: '완료됨' }`. 한글 글자를 그대로 저장하면 나중에 단계 이름을 바꾸는 순간 과거 건이 목록에서 사라진다.
- 화면에 보이는 글자는 **회사 말 그대로** 쓴다. 영문 키는 코드 안에서만 쓴다.
- 날짜는 `YYYY-MM-DD` 문자열로 둔다. 시간까지 필요하다고 `structure.md`에 적혀 있을 때만 시간을 넣는다.

### 7. 예시 데이터

`src/data/sample.ts`에 **8~12건**을 만든다.

- 관리 단위와 업태에 맞는 내용으로 만든다(`profile.md`의 말로).
- **상태가 골고루 섞이게** 한다. 각 상태가 최소 1건, 오늘 날짜인 건이 최소 2건.
- 날짜는 오늘을 기준으로 앞뒤로 흩어 놓는다.
- **실제 고객 이름·연락처·금액을 넣지 않는다.** 가상의 이름(`김○○`, `○○상사`)을 쓴다.
- 파일 맨 위에 한 줄 주석: `// 예시 데이터입니다. 실제 고객 정보를 넣지 마세요.`

### 8. 브라우저에 저장하기

`src/lib/storage.ts`에 세 가지만 만든다.

1. `load()` — 저장된 것이 있으면 읽고, 없으면 `sample.ts`를 넣고 그것을 돌려준다.
2. `save(items)` — 통째로 저장한다.
3. `resetToSample()` — 예시 데이터로 되돌린다.

규칙:

- 저장 키는 `erp.<영문키>.v1` 형태로 한 곳에 상수로 둔다. 예: `erp.order.v1`
- 읽기·쓰기를 `try/catch`로 감싼다. 브라우저 설정에 따라 저장이 막힐 수 있다 — 그때도 화면은 떠야 한다.
- 저장된 값이 깨져 있으면 예시 데이터로 되돌리고 화면에 한 줄 안내를 띄운다. 개발 중에는 `load()`가 **두 번 불린다**(React StrictMode). 그 안내는 **한 번 켜지면 그대로 두어야** 두 번째 호출에 꺼지지 않는다.
- **새로고침해도 방금 넣은 것이 남아 있어야 한다.** 이게 이 단계의 유일한 합격 기준이다.
- 이건 그 브라우저 안에만 남는 임시 저장이다. 다른 기기에서는 안 보인다 — 대표에게 한 줄로 말해 준다. 진짜 저장은 2회차(Supabase)다.

### 9. 화면 3개 만들기

규칙은 두 곳에 있다. **화면을 쓰기 전에 둘 다 읽는다.**

- `references/screen-rules.md` — 세 화면의 공통 규칙(무엇을 넣고 무엇을 넣지 않나)
- `indeans-erp-design` 스킬의 `references/structures.md` — 고른 구조의 배치 규칙. **두 문서가 다르면 구조별 규칙이 이긴다.**

요점만:

- **목록** — 한 줄에 3~4가지. 고른 구조가 진행 보드형이면 목록 화면이 보드가 된다.
- **상세·입력** — 새로 만들기와 고치기가 같은 화면. 필수 항목이 비면 저장을 막고 **무엇이 비었는지** 그 항목 옆에 적는다. **단계를 고르는 칸을 처음부터 넣는다**(기본값은 `flows.md` 의 첫 단계). 나중에 붙이면 복구 실습에서 되돌린 건의 단계를 고칠 방법이 없어 전원이 같은 곳에서 막힌다.
- **회사 말 + 조사** — 회사 말을 문장에 끼울 때 조사는 받침에 따라 갈라진다. `'아파트' + '을(를)'` 같은 글자를 화면에 내보내지 않는다. 한 줄로 고르거나(`const jong = (w: string) => (w.charCodeAt(w.length - 1) - 0xac00) % 28` → `jong(w) ? '을' : '를'`, `jong(w) ? '으로' : '로'`) 아예 **조사를 피하는 문장**을 쓴다(`{항목}이 비었습니다`). 자세한 것은 `references/screen-rules.md`.
- **오늘 현황** — 오늘 해야 할 것과 단계별 개수. 숫자를 누르면 그 상태로 걸러진 목록으로 간다.
- 색·글자 크기·여백은 `tokens.css`의 값(`var(--…)`)만 쓴다. 화면 파일에 직접 적지 않는다.
- 화면 뼈대(상단바·메뉴·표/보드/카드 배치)는 고른 목업 `.owner/design/src/<조합>.html`의 구조와 클래스 이름을 그대로 가져와 쓴다. 새 클래스를 만들기 전에 `layout.css`·`base.css`에 있는지 먼저 본다 — 비교 이미지에서 고른 인상이 그대로 나야 한다.
- 휴대폰 가로 375px에서 먼저 맞춘다. 가로로 밀리면 잘못 만든 것이다.
- 비었을 때 화면(0건)을 반드시 만든다. 장식용 이모지를 넣지 않는다.

### 10. 실행해서 보기

```
npm run dev
```

터미널에 찍힌 주소(`http://localhost:5173` 형태, 숫자는 다를 수 있다)를 브라우저에서 연다.

```
node .owner/hooks/open.mjs http://localhost:5173
```

- 흰 화면이면 브라우저에서 `F12`(맥은 `option+command+i`)를 눌러 빨간 글씨를 찾아 고친다.
- 대표에게 **직접 눌러 보게 한다.** AI가 다 확인했다고 말하고 넘어가지 않는다.

### 11. 확인 체크리스트 (대표가 직접)

아래를 하나씩 대표에게 읽어 주고 확인받는다. 안 되는 항목이 있으면 고친 뒤 다시 본다.

| 화면 | 무엇이 보여야 하나 |
|---|---|
| 목록 | 예시 데이터가 보이고, 한 줄만 봐도 "어느 건인지·지금 어느 단계인지" 안다 |
| 목록 | 줄을 누르면 그 건의 상세로 넘어간다 |
| 상세·입력 | 비어 있는 새 건을 만들어 저장하면 목록에 늘어난다 |
| 상세·입력 | 상태를 바꾸고 저장하면 목록의 표시가 바뀐다 |
| 상세·입력 | 필수 항목을 비우고 저장하면 막히고, 무엇이 비었는지 알려 준다 |
| 오늘 현황 | 오늘 해야 할 것이 보이고, 단계별로 몇 건인지 숫자가 있다 |
| 공통 | 브라우저를 새로고침해도 방금 넣은 것이 그대로 있다 |
| 공통 | 휴대폰 크기(375)에서 글자가 잘리거나 가로로 밀리지 않는다 |

`company/scope.md`의 "성공 기준" 체크박스도 같이 채운다.

### 12. README·상태 문서·커밋

`assets/README-template.md`를 채워 프로젝트 루트의 `README.md`로 쓴다.

`.owner/state.md`와 `.owner/progress.json`을 갱신한다.

- `state.md` → "현재 기능"에 되는 일을 한 줄씩(목록·상세·입력·오늘 현황·새로고침해도 남는 저장). "다음 행동"에 "첫 작업 보고서 만들기". 미해결 항목은 "미해결 문제"에.
- `progress.json` → `app.draft_done`·`app.dev_url`, `sessions."1"` 관련 값, `next_action`, `updated_at`.

```
git add -A
git commit -m "초안 앱 1차 — 화면 3개"
```

### 13. 첫 작업 보고서

이어서 **`indeans-erp-report` 스킬**로 넘어간다. 캡처는 그 스킬이 `node .owner/hooks/capture.mjs --url <실제 주소>`로 찍는다(앱은 계속 띄워 둔다).

보고서가 나오면 작업을 끝낸다. 검수 훅이 "검수가 필요한 변경"이라고 하면 `indeans-erp-check`로 넘어간다 — 감독 판정·실측을 마치고 **같은 제목·같은 `--slug`로 보고서를 다시 만들어** 그 결과를 더한다(파일이 하나로 유지된다).

마지막 보고는 3줄: 무엇이 됐는지 / 무엇이 아직인지 / 다음 회차에 할 것(실제 저장과 인터넷 주소).

### 14. 두 번째 흐름 추가 모드

이미 화면 3개가 있을 때만 한다. `.owner/state.md`의 **미해결 문제가 남아 있으면 먼저 닫는다** — 첫 흐름이 안정되기 전에 확장하지 않는다.

1. `company/flows.md`의 "두 번째 흐름" 절을 읽는다. 비어 있으면 `indeans-erp-interview`의 재인터뷰 모드를 먼저 돌리게 안내한다.
2. **기존 화면을 고치지 않는다.** 목록 화면 위에 구분(탭 또는 고르기)을 하나 더해 두 흐름을 나눠 본다.
3. 저장 키를 흐름마다 나눈다. 예: `erp.order.v1`, `erp.repair.v1`
4. 예시 데이터도 흐름마다 따로 8~12건.
5. 첫 흐름의 체크리스트(절차 11)를 **다시 한 번** 통과해야 한다.
6. 커밋 메시지: `두 번째 흐름 추가 — ○○`, 그다음 `indeans-erp-check`.

## 산출물

- 로컬에서 도는 초안 앱 — `src/screens/` 화면 3개, `src/data/sample.ts` 8~12건, `src/lib/storage.ts`
- `src/styles/tokens.css` — 디자인 스킬이 고른 조합 그대로
- `src/styles/base.css`·`layout.css` — 디자인 스킬이 넣은 뼈대 CSS 그대로(목업과 같은 클래스)
- `README.md` — 템플릿 `assets/README-template.md`
- `.owner/state.md`·`.owner/progress.json` 갱신
- 커밋 2개 이상(`초안 만들기 전`, `초안 앱 1차 — 화면 3개`)
- 이어서 `indeans-erp-report`가 만드는 `reports/<날짜>-<제목>.html`

## 하지 않는 것

- 인터뷰. 구조안이 없으면 만들지 않고 멈춘다.
- 디자인 방향 고르기. `indeans-erp-design`이 한다. 토큰 파일을 여기서 새로 쓰지 않는다.
- `structure.md`의 "이번에 만들지 않을 것"에 있는 기능 만들기. 로그인·권한(2회차), Supabase 저장·배포(2회차), 알림·운영 보고(3회차)가 여기 든다.
- 라우터·상태관리·UI 라이브러리 추가 설치. 화면 전환은 `useState`로 충분하다.
- 화면 4개 이상. 세 개로 끝낸다. 더 필요해 보여도 `flows.md`의 "아직 담지 않는 흐름"에 적어 둔다.
- 목록을 정렬·개수 제한 없이 전부 불러오기. 건수가 늘면 조용히 잘린다.
- 실제 고객 정보·금액·연락처를 예시 데이터에 넣기.
- 대표 확인 없이 `structure.md`와 다르게 만들기. 다르게 만들고 싶으면 문서를 먼저 고친다.

## 앞선 수강생 분기

초안이 이미 돌고 있으면 두 번째 흐름 추가(절차 14) 또는 아래 중 하나.

1. **목록 다듬기** — 건수가 많은 회사라면 검색창·기간 고르기·상태별 묶어 보기를 붙인다. 정렬과 개수 제한을 함께 건다.
2. **입력 줄이기** — 직원이 가장 많이 쓰는 화면에서 손이 몇 번 가는지 세고, 기본값·최근 값 불러오기로 줄인다.
3. **내보내기** — 목록을 CSV로 내려받는 버튼 하나. 엑셀을 놓기 어려운 회사에 효과가 크다.

## 자주 막히는 지점

- **생성기가 "폴더가 비어 있지 않다"고 묻는다** → 절차 3의 임시 폴더 방식을 쓴다. "기존 파일 삭제"를 고르면 `company/` 문서가 날아간다. 절대 고르지 않는다.
- **`npm install`이 오래 걸린다** → 처음은 2~5분이 정상이다. 5분이 넘고 오류가 나면 네트워크를 바꿔 다시 한다.
- **`npm run dev`는 도는데 흰 화면** → 브라우저 개발자 도구의 빨간 글씨를 읽는다. 대개 파일 이름 대소문자나 불러오기 경로 문제다.
- **고른 디자인이 화면에 안 보인다** → `src/main.tsx`에 `import './styles/tokens.css'`가 있는지 본다(절차 5). 또는 화면 파일에 색이 직접 적혀 토큰을 덮고 있다.
- **새로고침하면 입력한 게 사라진다** → `save()`가 안 불리고 있다. 저장 버튼과 상태 변경 두 군데 모두에서 저장하는지 본다.
- **글자가 화면 밖으로 밀린다** → 대개 표나 가로 정렬이다. `references/screen-rules.md`의 열 폭 규칙(`minmax(0, 1fr)`)을 적용한다.
- **사진을 못 찍는다** → playwright가 없거나(절차 4) 앱이 안 떠 있다. 앱을 띄운 뒤 그 주소를 `--url`로 준다.
- **대표가 "생각한 거랑 다르다"고 한다** → 좋은 신호다. 코드를 바로 고치지 말고 `structure.md`의 어느 줄과 다른지부터 찾는다. 문서를 고치고 다시 만드는 편이 빠르다.
