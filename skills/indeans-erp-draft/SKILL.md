# 인디언즈 초안 생성

## 언제 쓰나

- 2회차, 2·3차 인터뷰로 구조안이 확정된 직후. 1회차에 고른 디자인을 그대로 쓴다.
- 초안이 이미 있고 두 번째 업무 흐름을 붙일 때(실사용 준비 단계·앞선 수강생).

만드는 것은 **첫 버전**이다. 예쁘게 다듬는 것보다 **돌아가는 것**이 먼저다 — 다만 AI가 만든 티가 나는 장식은 처음부터 넣지 않는다.

2회차는 **초안(이 스킬) → 작업 보고서(`indeans-erp-report`) → 저장 연결과 배포(`indeans-erp-data`)** 로 이어진다. 초안은 첫 걸음이고, 2회차의 필수 완료 결과는 저장·배포까지 끝났을 때 채워진다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/progress.json` | `interview.round`(3이어야 시작한다) · `interview.open_items`(`blocks_draft: true` 항목이 남아 있으면 시작하지 않는다 — 대표 확인이 필요한 미정 항목) · `design.code`(고른 디자인의 코드) · `app.draft_done` |
| `company/structure.md` | 화면 3개 목록·한 건에 적는 항목표·**이번에 만들지 않을 것**. **이게 없으면 시작하지 않는다** |
| `company/design.md` · `.owner/design/choice.json` | 고른 구조·스타일(패밀리)·색(팔레트)·밝기·디자인 코드, 바꾸면 안 되는 것. `choice.json`은 선택창이 남긴 실제 선택이다 — 문서·`design.code`와 다르면 이쪽이 실제다 |
| `src/styles/tokens.css`·`base.css`·`layout.css`·`fonts/` | 디자인 스킬이 넣은 토큰과 뼈대 CSS·글꼴(라이선스 전문 포함). `tokens.css` 첫 줄 주석의 코드가 `design.code`와 같은지 |
| `.owner/design/src/<구조>.html` | 고른 구조(`list`·`board`·`card` 중 하나)의 목업 — 화면 뼈대(상단바·메뉴·표/보드/카드 배치)와 클래스 이름을 여기서 이어받는다 |
| `company/flows.md` · `profile.md` · `scope.md` | 단계·상태 값·기본값 / 관리 단위와 회사 말 / 이번 회차 성공 기준(체크박스) |
| `company/screens.md` | 화면별 설계 선언(있으면 이어 쓴다) |
| `.owner/state.md` | 어디까지 왔는지·미해결 문제 |
| `package.json` · `src/screens/` · `src/data/sample.ts` | 앱과 화면이 이미 있는지 |

**상태 문서와 실제 파일이 다르면 문서를 믿지 않는다.** 실제를 확인한 뒤 문서를 고치고 시작한다.

판정과 분기:

- **인터뷰 덜 됨** — `company/structure.md`가 없거나 `interview.round`가 3 미만이거나 `interview.open_items`에 `blocks_draft: true` 항목이 남아 있다 → 만들지 않는다. "먼저 `indeans-erp-interview`로 2·3차 인터뷰를 마쳐야 합니다"라고 알리고 멈춘다.
- **디자인 없음** — `design.code`가 비었거나 `src/styles/tokens.css`가 없다 → `indeans-erp-design`을 먼저 하라고 알린다(부르면 선택창이 자동으로 열린다, 5~10분). 그것 없이 만들면 화면을 두 번 고치게 된다.
- **문서·디자인 있음, 앱 없음** → 절차 1~16(전체 생성).
- **앱 있음, 화면 3개 미완** → 빠진 화면만 만든다(그 화면의 설계 선언부터).
- **앱 있음, 화면 3개 완성** → **두 번째 흐름 추가 모드**(절차 17).

판정을 한 문장으로 먼저 알린다.

## 절차

### 1. 되돌릴 지점

```
git add -A
git commit -m "초안 만들기 전"
```

커밋할 게 없으면 넘어간다. 이 커밋이 있으면 무엇이 잘못돼도 여기로 돌아온다.

### 2. 구조안 읽고 한 번 확인하기 (질문 1개)

`structure.md`·`design.md`에서 읽은 것을 아래 형태로 보여 준다.

```
관리 단위: ○○ (영문 키 ○○)
화면 1 목록: ○○ — 한 줄에 ○·○·○
화면 2 상세·입력: 적는 항목 ○개
화면 3 오늘 현황: ○○
상태: ○ → ○ → ○ (기본값 ○)
디자인: {구조} · {스타일} · {색} · {밝기} (코드 {design.code})
이번에 만들지 않을 것: ○○ · ○○
```

한 줄을 같이 읽어 준다: "(영문 키는 코드 안에서만 쓰는 이름입니다. 화면에는 회사에서 부르시는 말 그대로 나옵니다.)"

그리고 묻는다: **"이대로 만들까요? 고칠 것이 있으면 지금 말씀해 주세요."**

답을 듣기 전에 파일을 만들지 않는다. 고칠 것이 있으면 `structure.md`를 먼저 고치고 다시 확인한다. **"이번에 만들지 않을 것"에 있는 기능은 넣지 않는다** — 넣고 싶어지면 그 표를 먼저 고친다.

### 3. 앱 뼈대 — Vite 프로젝트

`references/project-setup.md` 1절을 읽고 그대로 한다. 놓치면 되돌리기 어려운 것만:

- 임시 폴더(`.vite-init`)에 만든 뒤 옮긴다. 생성기가 "기존 파일을 지울까요"라고 물으면 **절대 고르지 않는다** — `company/` 문서가 날아간다.
- `package.json`의 `name`을 프로젝트 폴더 이름으로 바꾼다(이 회차 후반 배포 주소에 쓰인다).
- `.gitignore`에 `node_modules`·`.env.local`·`.owner/tmp/` 세 줄. **`src/styles/`(그 안의 `fonts/` 글꼴·라이선스 파일 포함)는 지우지 않는다.**
- `npm install` — 2~5분, 도중에 끊지 않는다.

### 4. 화면 사진 도구

`references/project-setup.md` 2절 — `npm i -D playwright`와 `npx playwright install chromium`을 한 번만(두 번째 줄은 2~4분). 네트워크가 막으면 붙잡지 않는다 — 사진 없이도 보고서는 만들어진다.

### 5. 파일 구조

`references/project-setup.md` 3절의 구조로 만든다. **라우터 같은 추가 라이브러리를 설치하지 않는다** — 화면 전환은 `useState`로 한다. 파일·폴더 이름은 그대로 쓴다(다음 스킬과 감독 에이전트가 이 경로를 찾는다). `src/main.tsx`가 아직 `./index.css`를 부르고 있으면 그 줄을 `tokens.css`·`base.css`·`layout.css` 세 줄로 바꾼다 — **빠뜨리면 고른 디자인이 화면에 안 먹는다.** 글꼴은 따로 부르지 않는다 — `tokens.css` 안의 `@font-face` 가 `./fonts/`(`src/styles/fonts/`)의 파일을 부른다. 그 폴더와 `LICENSE-*.txt` 를 지우거나 옮기지 않는다(지우면 시스템 글꼴로 바뀌고 글꼴 라이선스 고지가 빠진다).

### 6. 타입과 상태 값

`structure.md`의 항목 표와 `flows.md`의 상태 값을 그대로 옮긴다.

- 영문 키는 `structure.md`에 적힌 것을 쓴다. 새로 짓지 않는다.
- **저장하는 상태 값은 영문 코드로 둔다. 화면에 보이는 글자는 따로 표로 둔다.** 예: `type Status = 'assigned' | 'done'` 와 `const STATUS_LABEL = { assigned: '배정됨', done: '완료됨' }`. 한글 글자를 그대로 저장하면 나중에 단계 이름을 바꾸는 순간 과거 건이 목록에서 사라진다.
- 화면에 보이는 글자는 **회사 말 그대로** 쓴다. 영문 키는 코드 안에서만 쓴다.
- 날짜는 `YYYY-MM-DD` 문자열로 둔다. 시간까지 필요하다고 `structure.md`에 적혀 있을 때만 시간을 넣는다.

### 7. 예시 데이터

`src/data/sample.ts`에 **8~12건**을 만든다.

- 관리 단위와 업태에 맞는 내용으로, `profile.md`의 말로 만든다. 홍길동·ABC상사·딱 떨어지는 숫자처럼 가짜 티가 나는 값은 피한다(가상 이름 `김○○`·`○○상사`, 들쭉날쭉한 수량).
- **상태가 골고루 섞이게** 한다. 각 상태가 최소 1건, 오늘 날짜인 건이 최소 2건. 날짜는 오늘을 기준으로 앞뒤로 흩어 놓는다.
- **실제 고객 이름·연락처·금액을 넣지 않는다.** 파일 맨 위에 한 줄 주석: `// 예시 데이터입니다. 실제 고객 정보를 넣지 마세요.`

### 8. 브라우저에 저장하기

`src/lib/storage.ts`에 세 가지만 만든다: `load()`(저장된 것이 없으면 `sample.ts`를 넣고 돌려준다) · `save(items)`(통째로 저장) · `resetToSample()`(예시 데이터로 되돌리기).

- 저장 키는 `erp.<영문키>.v1` 형태로 한 곳에 상수로 둔다. 예: `erp.order.v1`
- 읽기·쓰기를 `try/catch`로 감싼다. 브라우저 설정에 따라 저장이 막힐 수 있다 — 그때도 화면은 떠야 한다.
- 저장된 값이 깨져 있으면 예시 데이터로 되돌리고 화면에 한 줄 안내를 띄운다. 개발 중에는 `load()`가 **두 번 불린다**(React StrictMode). 그 안내는 **한 번 켜지면 그대로 두어야** 두 번째 호출에 꺼지지 않는다.
- **새로고침해도 방금 넣은 것이 남아 있어야 한다.** 이 단계의 합격 기준이다.
- 그 브라우저 안에만 남는 임시 저장이다 — 대표에게 한 줄로 말해 준다. 진짜 저장은 이 회차 후반(`indeans-erp-data`, Supabase)이다.

### 9. 화면마다 설계 선언 쓰기 (만들기 전에)

`references/design-statement.md`를 읽고 `assets/screens.template.md`를 `company/screens.md`로 만들어 **화면마다** 다섯 줄을 쓴다.

| 줄 | 쓰는 것 |
|---|---|
| 목적 | 이 화면이 끝내 주는 일 한 문장 |
| 주 사용자 | 가장 자주 여는 사람 한 명(역할)과 얼마나 자주 |
| 기기 | 어디서·어떤 기기로·어떤 손으로 |
| 가장 중요한 행동 하나 | 이 화면에서 가장 많이 누를 것 하나 |
| 쓰지 않을 것 | 일부러 넣지 않는 것 — 비워 두지 않는다(비우면 AI가 채운다) |

- 근거는 `structure.md`·`profile.md`·`flows.md`에서 찾는다. 없으면 짐작하지 말고 `(인터뷰에 없음 — 기본값: …)`으로 적는다.
- 다 쓰고 한 번 묻는다: **"다른 회사 이름만 바꿔 넣어도 그대로 맞는 화면인가?"** 그렇다면 이 회사에서만 나오는 것 하나(회사 말 그대로의 제목·이 회사의 '오늘'·하루에 가장 자주 묻는 질문에 바로 답하는 자리)를 넣고 여섯째 줄에 적는다. 색·모양으로 특색을 내지 않는다 — 디자인은 대표가 이미 골랐다.
- 세 화면의 선언을 한 번에 보여 주고 "이 선언대로 만들겠습니다"라고 알린다. 따로 묻지 않는다 — 고칠 것이 있으면 대표가 말한다.

### 10. 화면 3개 만들기 — 모바일 설계 순서대로

규칙은 세 곳에 있다. **화면을 쓰기 전에 읽는다.**

- `references/screen-rules.md` — 세 화면의 공통 규칙
- `indeans-erp-design` 스킬의 `references/structures.md` — 고른 구조의 배치 규칙
- 같은 스킬의 `references/families.md` — 고른 스타일(패밀리)의 모양 규칙(그 스타일 절만 읽는다)

배치는 구조 규칙이, 모양은 스타일 규칙이 공통 규칙보다 앞선다. 단 **가로 밀림·누르는 크기·글자 대비·입력 칸 글자(`var(--fs-input)`)는 어느 규칙도 덮지 못한다.**

화면 하나마다 **맥락 → 구조 → 비주얼 → 감정 → 마무리** 순서로 정한다(자세히는 `references/design-statement.md` 2절). 앞 단계가 정해지기 전에 뒤 단계를 만지지 않는다. 휴대폰 가로 375px에서 먼저 맞춘다.

1. **맥락** — 선언의 목적·주 사용자·기기를 다시 읽고, 이 화면으로 들어오는 길과 나가는 길을 정한다.
2. **구조** — 꼭 필요한 것만 남긴다. 가장 중요한 행동 하나를 엄지가 닿는 아래쪽(폰)에 둔다. 비었을 때(0건) 보여 줄 문장과 버튼을 여기서 정한다. 배치·클래스 이름은 목업 `.owner/design/src/<구조>.html`에서 그대로 가져온다 — 새 클래스를 만들기 전에 `layout.css`·`base.css`에 있는지 먼저 본다. 부품도 새로 짓지 않는다 — 화면 위에 잠깐 띄우는 창은 시트(`dialog.sheet`), 몇 개 중 하나 고르기는 상태 칩(`.chips`·`.chip`), 0건은 빈 화면(`.empty`), 목록 표는 표 역할(`role`), 진행 보드형의 폰 화면은 열 탭(`.col-tabs`). 목록은 `references/screen-rules.md` 「목업 부품」.
3. **비주얼** — 색·글자 크기·간격·모서리·그림자는 `tokens.css`의 `var(--…)`만 쓴다. **강조색 자리를 섞지 않는다** — `--primary` 는 버튼 면에만(그 위 글자 `--primary-on`), 바탕 위 강조 글자·탭 밑줄·선택 테두리·포커스는 `--primary-text`, 입력 칸·보조 버튼·칩 테두리는 `--border-input`. 시트·큰 상자 모서리는 `--radius-lg`, 그림자는 `--shadow`·`--shadow-md`·`--shadow-lg` 만(고른 스타일이 그림자를 안 쓰면 값이 `none`). 위계는 크기·굵기·옅기로 만들고 라벨은 값보다 작게, 강조색은 본문에서 두 곳 이하.
4. **감정** — 저장하면 목록으로 돌아가 방금 그 줄이 보인다. 막히면 무엇이 문제이고 다음에 무엇을 하면 되는지 그 자리에서 말한다. 축하 장식은 넣지 않는다.
5. **마무리** — 비었을 때·불러오는 중·실패했을 때·정상 네 상태를 다 만든다. 375에서 좌우로 밀리지 않는다. 쓰지 않은 장식을 지운다.

화면별 요점:

- **목록** — 한 줄에 3~4가지. 고른 구조가 진행 보드형이면 목록 화면이 보드가 된다. 정렬과 개수 상한을 같이 건다.
- **상세·입력** — 새로 만들기와 고치기가 같은 화면. 필수 항목이 비면 저장을 막고 **그 칸 바로 아래**에 무엇이 비었는지 적는다. **단계를 고르는 칸을 처음부터 넣는다**(기본값은 `flows.md`의 첫 단계) — 나중에 붙이면 복구 실습에서 되돌린 건의 단계를 고칠 방법이 없어 전원이 같은 곳에서 막힌다.
- **오늘 현황** — 오늘 해야 할 것과 단계별 개수. 숫자를 누르면 그 상태로 걸러진 목록으로 간다. "큰 숫자 칸 세 개" 틀로 시작하지 않는다.
- **회사 말 + 조사** — 회사 말을 문장에 끼울 때 `'주문' + '을(를)'` 같은 글자를 화면에 내보내지 않는다. 조사가 필요 없는 문장(`{항목} 칸이 비었습니다`)을 먼저 쓰고, 그래도 필요하면 받침으로 고른다 — `references/screen-rules.md` 「회사 말 + 조사」.


터미널에 찍힌 주소(`http://localhost:5173` 형태, 숫자는 다를 수 있다)를 연다: `node .owner/hooks/open.mjs http://localhost:5173`

### 12. 스스로 점검 (대표에게 보여 주기 전에)

`references/self-review.md`의 점검표로 본다. 다섯 묶음이다.

| 묶음 | 보는 것 |
|---|---|
| 접근성 | 포커스가 보이나 · 입력 칸마다 보이는 이름표 · 글자 대비(토큰 글자색만 — 강조 글자는 `--primary-text`) · 입력 칸 테두리(`--border-input`) · 누르는 것은 버튼 · 표 역할 |
| 폼 | 오류는 그 칸 바로 아래 · 필수 표시 · 입력 칸 글자 `var(--fs-input)`·높이 `var(--tap)` · 숫자 자판 · 두 번 저장 막기 |
| 상태 | 비었을 때 · 불러오는 중 · 실패했을 때 · 정상 |
| 성능 | 목록은 정렬 + 개수 상한 · 같은 계산을 다시 그릴 때마다 반복하지 않는다 |
| 안티-제네릭 | 왼쪽 색 막대 · 카드 안 카드 · 장식(이모지·그라데이션·직접 적은 그림자) · 큰 숫자 칸 틀 · 목업에 있는 부품을 새로 짓기 · 인터넷 글꼴 · 뭉뚱그린 문구 · 가짜 같은 데이터 |

- 결과는 `파일:줄 — 무엇이 걸렸나`로 적고, 걸린 것은 **지금 고친다.** 못 고친 것만 "미해결 문제"와 보고서의 "남은 문제"로 보낸다. `company/screens.md`의 "스스로 점검 결과"에 한 줄씩 남긴다.
- 대표에게는 파일·줄이 아니라 화면의 말로 전한다.

### 13. 커밋하고 검수 먼저 (대표에게 보여 주기 전에)

대표에게 눌러 보라고 부탁하기 **전에** 검수를 끝낸다. 확인을 부탁한 뒤에 끝내려 하면 검수 훅이 막아서, 대표는 AI 가 검수를 마칠 때까지(15분 넘게) 답할 수 없다(2026-10-09 리허설).

1. 대표에게 한 줄 먼저: "화면 세 개를 다 만들었습니다. 보여 드리기 전에 검수를 먼저 받겠습니다(10~15분)."
2. 커밋한다 — 검수 표식은 커밋된 자리를 기준으로 남는다.
   ```
   git add -A
   git commit -m "초안 앱 1차 — 화면 3개"
   ```
3. **`indeans-erp-check`** 를 읽고 그 절차대로 한다 — 위험 등급표대로 감독 판정 → 검증 실측 → 보고서 → `.owner/last-check.json` 갱신. 반려되면 고치고 다시 받는다(최대 2번). 고친 것은 커밋한다. 검수의 보고서는 초안 보고서와 **같은 제목·같은 `--slug`**(예: `--slug draft-app`)로 만든다 — 절차 16에서 같은 이름으로 다시 만들어 화면 설명·대표 확인 결과를 더한다(파일 하나).
4. 앱은 계속 띄워 둔다 — 다음 절차에서 대표가 누른다.

### 14. 확인 체크리스트 (대표가 직접)

대표에게 **직접 눌러 보게 한다.** AI가 다 확인했다고 말하고 넘어가지 않는다. 하나씩 읽어 주고 확인받는다. 안 되는 항목이 있으면 고친 뒤 다시 본다.

| 화면 | 무엇이 보여야 하나 |
|---|---|
| 목록 | 예시 데이터가 보이고, 한 줄만 봐도 "어느 건인지·지금 어느 단계인지" 안다. 줄을 누르면 그 건의 상세로 넘어간다 |
| 상세·입력 | 새 건을 만들어 저장하면 목록에 늘어난다. 상태를 바꾸고 저장하면 목록의 표시가 바뀐다 |
| 상세·입력 | 필수 항목을 비우고 저장하면 막히고, 무엇이 비었는지 그 칸 아래에 나온다 |
| 오늘 현황 | 오늘 해야 할 것이 보이고, 단계별로 몇 건인지 숫자가 있다 |
| 공통 | 새로고침해도 방금 넣은 것이 그대로 있다. 휴대폰 크기(375)에서 글자가 잘리거나 가로로 밀리지 않는다 |

`company/scope.md`의 "성공 기준" 체크박스도 같이 채운다.

안 되는 항목을 고쳤으면 커밋한다. 고친 것이 화면 동작이면 끝낼 때 검수 훅이 다시 요구할 수 있다 — 그때는 절차 13처럼 `indeans-erp-check` 로 그 부분만 받는다.

### 16. 초안 보고서, 그리고 저장·배포로

마지막 보고는 3줄: 무엇이 됐는지 / 무엇이 아직인지 / 다음 작업(새 대화에서 `indeans-erp-data` — 저장과 인터넷 주소).

### 17. 두 번째 흐름 추가 모드

이미 화면 3개가 있을 때만 한다. `.owner/state.md`의 **미해결 문제가 남아 있으면 먼저 닫는다** — 첫 흐름이 안정되기 전에 확장하지 않는다.

6. 그다음 체크리스트(절차 14)를 두 흐름 모두 대표가 직접 다시 눌러 본다.

- 설계 선언 없이 화면부터 만들기.
- `structure.md`의 "이번에 만들지 않을 것"에 있는 기능 만들기. 저장 연결·배포(이 회차 후반 `indeans-erp-data`), 로그인·권한(권한 단계), 알림·운영 보고(운영 보고 단계)가 여기 든다.

- 대표 확인 없이 `structure.md`와 다르게 만들기. 다르게 만들고 싶으면 문서를 먼저 고친다.

## 앞선 수강생 분기

초안이 이미 돌고 있으면 두 번째 흐름 추가(절차 17) 또는 아래 중 하나.

1. **목록 다듬기** — 건수가 많은 회사라면 검색창·기간 고르기·상태별 묶어 보기를 붙인다. 정렬과 개수 제한을 함께 건다.
2. **입력 줄이기** — 직원이 가장 많이 쓰는 화면에서 손이 몇 번 가는지 세고, 기본값·최근 값 불러오기로 줄인다. 줄인 뒤 그 화면의 설계 선언을 고친다.
3. **내보내기** — 목록을 CSV로 내려받는 버튼 하나. 엑셀을 놓기 어려운 회사에 효과가 크다.

## 자주 막히는 지점

- **생성기가 "폴더가 비어 있지 않다"고 묻는다** → 절차 3의 임시 폴더 방식을 쓴다. "기존 파일 삭제"를 고르면 `company/` 문서가 날아간다. 절대 고르지 않는다.
- **`npm run dev`는 도는데 흰 화면** → 브라우저 개발자 도구의 빨간 글씨를 읽는다. 대개 파일 이름 대소문자나 불러오기 경로 문제다.
- **고른 디자인이 화면에 안 보인다** → `src/main.tsx`에 `import './styles/tokens.css'`가 있는지 본다(절차 5). 또는 화면 파일에 색이 직접 적혀 토큰을 덮고 있다.
- **글자 모양만 선택창과 다르다(시스템 글꼴로 보인다)** → `src/styles/fonts/`가 지워졌거나 옮겨졌다. `node .owner/hooks/design-pick.mjs --code <design.code>` 로 다시 만든다(바뀐 CSS 는 `.owner/tmp/design-backup/` 에 먼저 남는다).
- **강조 글자·탭 밑줄이 흐리거나 안 읽힌다** → `var(--primary)`를 글자색·얇은 선에 썼다. `var(--primary-text)`로 바꾼다(`--primary`는 버튼 면 전용).
- **목업과 인상이 다르다** → 목업 `.owner/design/src/<구조>.html`의 클래스 대신 새 클래스를 지어 썼다. 목업의 클래스 이름으로 되돌린다.
- **새로고침하면 입력한 게 사라진다** → `save()`가 안 불리고 있다. 저장 버튼과 상태 변경 두 군데 모두에서 저장하는지 본다.
- **글자가 화면 밖으로 밀린다** → 대개 표나 가로 정렬이다. `references/screen-rules.md`의 열 폭 규칙(`minmax(0, 1fr)`)을 적용한다.
- **사진을 못 찍는다** → playwright가 없거나(절차 4) 앱이 안 떠 있다. 앱을 띄운 뒤 그 주소를 `--url`로 준다.
- **대표가 "생각한 거랑 다르다"고 한다** → 좋은 신호다. 코드를 바로 고치지 말고 `structure.md`나 `screens.md`의 어느 줄과 다른지부터 찾는다. 문서를 고치고 다시 만드는 편이 빠르다.
