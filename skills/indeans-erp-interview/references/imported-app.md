# 가져온 앱 1차 — 축약 모드

다른 도구로 만들어 온 앱이 있는 대표의 1차 인터뷰다. `indeans-erp-rebuild` 절차 5가 같은 대화에서 이 스킬을 부를 때, 또는 진단에서 `imported_app.detected` 가 true 이고 `interview.round` 가 0일 때 쓴다(`imported_app` 블록이 없는 옛 설치는 false 로 본다).

**줄이는 것은 "이미 화면에 있는 것을 다시 묻는 질문"뿐이다.** 업종 깔때기·덮개 점검표·한 번에 한 질문·회사 말 그대로 — 1차의 규칙은 그대로다.

## 1. 시작 전에 화면을 먼저 읽는다

말을 걸기 전에 `company/rebuild-diagnosis.md`(있으면)와 앱 화면 파일을 읽어 아래를 뽑아 둔다. 진단 문서가 없으면 `src/` 의 화면 파일과 메뉴·제목·칸 이름을 직접 읽는다.

| 뽑는 것 | 어디서 | 1차의 어느 칸을 대신하나 |
|---|---|---|
| 관리 단위 후보 | 목록 화면 제목·한 건 입력 화면 이름(예: "Orders" → 주문, "Bookings" → 예약) | 1-14 |
| 한 건에 적는 항목 | 입력 칸 이름 | 1-4(파는 것)의 보조 근거 · 3차 항목 제안의 재료 |
| 단계(상태) 이름 | 상태 칸의 고르기 값 | 1-5(고비 수)의 근거 |
| 쓰는 사람 | 담당자 칸·역할 흔적 | 1-10(사람)의 보조 근거 |
| 기기 | 진단의 375 폭 상태, 대표 말 | 1-11 |
| 회사 말 후보 | 화면 글자(영어면 우리말로 바꾼 후보를 만들어 둔다) | 「화면에서 쓸 말」 후보 |

## 2. 묻는 순서

1. **1-1 그대로** — "회사(사업자) 이름과 대표님을 어떻게 부르면 될까요?"
2. **업종 깔때기 그대로** — 1-2 대분류 → 1-3 소분류와 한 줄 소개 → 팩 1차 세부. 앱 화면이 업종을 짐작하게 해도 **고르는 것은 대표**다. 앱에서 짐작한 업종을 보기로 먼저 내밀지 않는다.
3. **화면에 이미 보이는 것은 확인만 — 최대 3개, 한 메시지에 묶어도 된다**("아니면 알려 주세요"를 붙인다). 1-5(단계·고비 수)와 1-14(관리 단위)는 화면의 상태 값·목록 이름으로 여기서 확인한다. 예:
   - "앱에서 한 건을 '주문'이라고 부르고 계신데, 평소에도 '주문'이라고 하시는 것 맞죠?"
   - "단계가 접수 → 진행 → 완료 세 개로 되어 있는데, 실제로도 이렇게 나뉘나요?"
   - 영어 화면이면: "화면에 'Bookings'라고 되어 있는데, 회사에서는 뭐라고 부르세요?"
   - 맞다고 하면 그 칸은 `답함`으로 채운다. 다르다고 하면 대표 말로 적고 다르다는 것을 진단 문서 9번(회사 말)에 한 줄 더한다.
4. **남은 1차 세부는 확인형 묶음 두 개로** — 화면·진단에서 짐작한 값을 넣어 묻고, 대표가 한 번에 답하면 그대로 적는다(틀린 것만 고쳐 달라고 한다). 묶음 ① 고객: 주 고객 · 고객이 화면을 직접 보나 · 돈 받는 방식(금액 없이). 묶음 ② 규모·기기: 사업장 · 사람(역할·밖 근무) · 기기 · 월 건수 · 동시 진행 건수. **"한 번에 한 질문" 규칙의 유일한 예외**다 — 교재 B1 이 "1차 인터뷰(짧게)"를 약속한다.
5. **추가 질문 두 개**(한 번에 하나, 원문 그대로 시작):
   - **"이 앱으로 풀려던 문제 하나가 무엇이었나요?"** — "다 편하게"면 되묻는다: "이 앱을 만들기 전에 가장 손이 많이 가던 일이 무엇이었나요?"
   - **"지금 이 앱에서 제일 아쉬운 것은 무엇인가요?"** — 화면 이름이나 손으로 하는 일로 받는다. "디자인"이면 "어느 화면에서 무엇이 아쉬우세요?" 한 번만 되묻는다.
6. **디자인 힌트** — 일곱 줄 중 화면·진단으로 아는 것(기기·단계 수·고객 화면·밖 근무)은 채워 두고, 간판·로고 색과 "지금 앱의 이 색은 그대로 두고 싶으세요, 바꾸고 싶으세요?"만 한 메시지로 묻는다. 진단의 '지금 쓰는 색'을 내 색 후보로 먼저 내밀지 않는다.
7. **1차 요약 확인** — SKILL 절차 2의 요약 형태 그대로.

**상한 — 질문 메시지 12개**(1-1 1 · 업종 깔때기 ≤3 · 확인 ≤3 · 묶음 2 · 추가 2 · 디자인 힌트 1 · 요약 1). 넘을 것 같으면 묶음으로 합친다. 리허설 D(2026-10-11)에서 하나씩 물어 23개가 됐다 — 축약 없이 받은 1차(21개)보다 많았다.

## 3. 적는 곳

- `company/profile.md` — 평소 1차와 같다(디자인 힌트·1차 요약 포함). 화면에서 확인한 관리 단위·단계 이름은 원문 메모에 "(앱 화면에서 확인)"을 붙인다.
- 추가 질문 두 개의 답 — `company/rebuild-diagnosis.md` 「대표가 말한 것」에 **대표의 말 그대로**. 진단 문서가 없으면 `company/profile.md` 1차 요약 아래 「가져온 앱 — 대표가 말한 것」 두 줄로 두고, 리빌딩 스킬이 진단 문서를 만들 때 옮긴다.
- 상태 기록 — 평소 1차와 같다(`interview.round` 1 · `company.*`). `next_action` 만 다르다: `"indeans-erp-rebuild — 개선 방향 제안(같은 대화에서 이어서)"`.

## 4. 끝맺음 — 디자인 선택창을 열지 않는다

평소 1차는 끝나면 같은 대화에서 디자인 선택창을 연다. **가져온 앱은 열지 않는다.** "1차는 끝났습니다. 이어서 앱을 어떻게 바꿀지 제안드리겠습니다"라고 말하고 `indeans-erp-rebuild` 절차 6(개선 방향 제안서)으로 돌아간다. 선택창은 대표가 제안서를 고른 뒤 리빌딩 스킬이 연다.

## 5. 2·3차 (2회차)

2·3차는 평소대로 한다. 다른 점 둘:

- 3차의 화면·항목 제안은 **앱에 이미 있는 화면과 칸을 먼저 넣고** 팩 항목은 빈 곳만 채운다(리빌딩이 재배치한 화면 셋이 그대로 출발점이다).
- 3차를 닫은 뒤 끝맺음이 **초안이 아니다** — `imported_app.stage` 가 `"reported"`(리빌딩 1단계 — 전후 보고까지 끝)이면 "다음은 새 대화에서 `indeans-erp-data` 스킬로 리빌딩 2단계(저장·배포)를 합니다. 초안은 새로 만들지 않습니다"라고 안내하고 `next_action` 을 `"indeans-erp-data — 리빌딩 2단계: 저장·배포(기존 DB 분기, 새 대화)"` 로 적는다. `stage` 가 그보다 앞(`"design"`·`"screens"`·`"checked"`)이면 `indeans-erp-rebuild` 로 돌아가 1단계를 먼저 마친다.
