# 인디언즈 사람·권한

2회차 뒤 실습. 저장과 배포를 끝낸 앱에 **누가 무엇을 보는지**를 붙인다.

역할은 **대표(`owner`)와 직원(`staff`) 두 개로 시작한다.** 고객 역할은 그 사업에 정말 필요할 때만 만든다(절차 3-4의 한 문항으로 판단한다). 역할이 적을 때가 확인이 가장 싸다.

## 언제 쓰나

- 앱을 **대표 혼자 말고 다른 사람도** 쓰게 될 때.
- "이건 직원에게는 안 보였으면", "직원이 자기 것만 보게" 라는 말이 나올 때.
- 직원이 자기 기기로 접속해 실제 입력을 해야 할 때(2회차 과제의 전제).

쓰지 않는 경우: 아직 데이터가 브라우저 저장뿐이다(→ 먼저 `indeans-erp-data`), 단계·상태 이야기다(→ `indeans-erp-workflow`), 채널로 보내는 알림 이야기다(→ `indeans-erp-channel`).

## 시작 전 상태 진단

읽고 나서 말을 건다. 읽기 전에 질문하지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · 미해결 문제 · 다음 행동 |
| `.owner/progress.json` | 저장·배포가 끝났나 |
| `company/profile.md` | 업종·근무자 현황(역할별 인원)·고객이 직접 쓰는지 |
| `company/flows.md` | 단계별 **담당** — 오늘 역할 이름의 출발점 |
| `company/structure.md` | 화면 목록 — 역할별 첫 화면을 여기서 고른다 |
| `company/improve-plan.md` | `indeans-erp-review` 가 넘긴 "보이면 안 되는 항목" 메모 — **인터뷰 답이 이걸 뒤집지 않는지 대조한다** |
| `company/people.md` | **있으면 두 번째** — 아래 분기 참조 |
| `supabase/migrations/` | 표 목록, 이미 있는 규칙(`policy`), 역할 표가 있는지 |
| `src/` | 로그인 화면이 있는지, 화면이 역할로 갈라지는지 |
| `.env.local` | Supabase 주소·공개 키가 들어 있는지 (**값은 화면에 출력하지 않는다**) |

**상태 문서가 코드와 다르면 문서를 믿지 않는다.** 실제를 확인한 뒤 문서를 고치고 시작한다.

판정과 분기:

- **처음**(로그인 없음) → 절차 0부터 전부.
- **진행 중**(로그인은 되는데 모두 같은 화면) → 인터뷰는 3-2·3-3만 하고 절차 6부터.
- **완료**(역할별 화면·데이터 규칙·기록까지 있음) → 「앞선 수강생 분기」로 간다.

진단을 한 문단으로 보고한 뒤 시작한다. 예: "저장과 주소는 끝났고, 지금은 로그인한 사람 모두가 같은 화면을 봅니다. 오늘 역할을 둘로 나눕니다. 질문 다섯 개 드리겠습니다."

## 계정이 아직 없을 때

Supabase 계정이 늦어져 로그인을 못 붙였어도 **멈추지 않는다.**

1. 인터뷰와 `company/people.md` 는 **그대로 한다.** 이게 오늘의 본편이다.
2. 역할 표·판정 함수·데이터 규칙은 **새 번호 SQL 파일로 써 두고 실행하지 않는다.**
3. 역할별 화면은 **임시 역할 전환 스위치**로 확인하고, 그 스위치를 지울 자리를 파일 주석·문서·커밋 메시지 세 곳에 적는다.
4. `people.md` 의 확인 항목은 **'확인 불가 — 계정 없음'** 으로 남긴다. 빈칸으로 두지 않는다.

화면에도 한 줄 적는다: **이것은 잠금이 아니라 연습입니다.** 계정이 열리는 날 2·3번을 실제로 실행하는 것이 과제다.

## 절차

### 0. 되돌릴 지점 만들기

```bash
git add -A && git commit -m "사람·권한 작업 전 상태"
```

권한 작업은 **데이터가 안 보이게 되는 실수**가 가장 흔하다. 되돌릴 지점 없이 시작하지 않는다.

### 1. 원리를 먼저 설명한다 (3분, 네 문장 이내)

`references/roles-basics.md` 를 읽고 요약해서 말한다. 특정 회사의 역할 이름을 나열하지 않는다. 전할 것은 네 가지다.

1. 역할은 **직함이 아니라 "무엇을 볼 수 있는가"** 로 나눈다. 보는 범위가 같으면 직함이 달라도 하나로 합친다.
2. 화면에서 숨기는 것은 **숨긴 게 아니다.** 데이터 쪽에서 막아야 막힌 것이다.
3. 권한 설계는 "누구에게 보여 줄까"가 아니라 **"누구에게는 절대 안 보여야 하나"** 부터 적는다.
4. 처음에는 **전부 잠그고** 필요한 것만 하나씩 연다. 반대 순서로 하면 열린 문이 남는다.

### 2. 우리 회사로 되묻는다

"이 앱을 열게 될 사람은 누구인가요?"

### 3. 인터뷰 — 한 번에 하나씩

질문 원문은 아래 그대로. 답을 한 줄로 되읽어 확인하고 다음으로 간다. 다섯 개를 다 받기 전에 코드를 만들지 않는다. 자세한 되묻기는 `references/interview-questions.md`.

**3-1. 누가 쓰나**
> "이 앱을 열게 될 사람을 전부 말씀해 주세요. 대표님 본인, 사무실 직원, 밖에서 일하는 직원 중에 누가 들어가나요?"

판단 기준: 사람 수가 아니라 **종류**를 센다. 기본은 **대표와 직원 둘**이다. 종류가 셋 이상 나오면 "보는 게 거의 같은 분들끼리" 묶어 둘로 줄인다. 역할 이름은 회사 말로 바꿔도 된다(예: 직원 → 기사, 담당).

**3-2. 각자 봐야 할 것**
> "직원이 이 앱을 열면 **가장 먼저 무엇을 봐야** 하나요? 그 사람 일에 꼭 필요한 화면 하나만요."

판단 기준: 역할마다 하나씩 받는다. 여기서 나온 답이 그 역할의 **첫 화면**이다. `company/structure.md` 의 화면 목록에 없는 화면이 나오면 그건 오늘 만들 것이 아니라 다음 개선 항목이다.

**3-3. 보면 안 되는 것 (가장 중요)**
> "직원에게는 **절대 보이면 안 되는 것**이 뭔가요? 지금은 무엇으로 막고 계시나요?"

판단 기준: 역할마다 하나 이상 받는다. "딱히 없다"는 답이면 금액·단가·다른 사람 연락처·아직 확정 안 된 일정으로 되묻는다. 여기서 나온 목록이 나중에 **확인할 체크리스트**가 된다.

**3-4. 고객 역할이 필요한가 (한 문항으로 판단)**
> "이 앱에 **고객이 직접 로그인해서** 자기 것을 보는 날이 오나요? 아니면 대표님과 직원만 쓰나요?"

판단 기준:

- "직원만 쓴다" → **고객 역할을 만들지 않는다.** `people.md` 에 "고객 역할: 없음 — 대표 판단"이라고 적고 넘어간다. 안 쓰는 역할을 미리 만들면 확인해야 할 조합만 늘어난다.
- "고객도 본다" → 한 번 더 묻는다: **"고객이 보는 화면은 직원 화면에서 몇 개를 가린 것인가요, 아니면 아예 다른 화면인가요?"** 고객 화면은 대개 **다른 화면**이다. 내부 표에서 칸만 숨기는 방식은 언젠가 새는 길이 생긴다. 오늘은 역할만 만들어 두고 화면은 다음 회차로 넘긴다.

**3-5. 기록이 필요한 행동**
> "나중에 **'이거 누가 언제 했지'** 하고 찾게 될 일이 뭐가 있나요?"

판단 기준: 보통 금액 수정·상태 되돌리기·삭제·사람 추가. 두세 개면 충분하다. 전부 기록하면 아무도 안 본다.

**3-6. 그만두면**
> "직원이 그만두면 그 계정은 어떻게 하고 싶으세요? 지웠으면 하나요, 못 들어오게만 하면 되나요?"

판단 기준: 대부분 "못 들어오게만"이 맞다. 계정을 지우면 그 사람이 남긴 기록의 작성자도 같이 사라질 수 있다.

### 4. 정리해서 읽어 드린다

역할 표 한 장으로 정리해 읽어 주고 틀린 곳만 고친다. **"보면 안 되는 것" 목록은 한 줄씩** 확인받는다. 그리고 `company/improve-plan.md` 의 메모와 다른 곳이 있으면 그 자리에서 알린다: "지난 회차에는 이렇게 적어 두셨는데 오늘 답과 다릅니다. 어느 쪽으로 할까요?"

### 5. 문서로 남긴다

`assets/people-template.md` 를 복사해 **`company/people.md`** 로 저장한다. 절 순서와 표 형식은 바꾸지 않는다.

### 6. 무엇을 만들지 말하고 동의를 받는다

다섯 가지다. 하나씩 설명한다.

1. **로그인** — 이메일과 비밀번호로 들어온다.
2. **역할 표** — 누가 어떤 역할인지 적어 두는 표 하나.
3. **데이터 규칙** — 역할별로 어느 데이터까지 나가는지를 데이터베이스가 직접 판정한다.
4. **역할별 화면** — 로그인하면 역할에 맞는 첫 화면이 뜬다.
5. **변경 기록** — 3-5에서 고른 행동만 누가 언제 했는지 남는다.

### 7. 구현 — 잠그고 시작한다

순서를 지킨다. `references/roles-basics.md` 의 예시와 `assets/role-check-template.sql` 을 쓴다.

1. **로그인**: 이메일 로그인을 붙인다. 가입은 대표가 **초대해서 만드는 방식**으로 둔다. 누구나 가입되는 화면을 열어 두지 않는다.
2. **역할 표**: 로그인 계정과 1:1로 붙는 표(`app_users`)를 쓴다(2회차에 이미 만들었다). 역할 칸은 **비워 둘 수 없게** 하고, 활성 여부 칸을 같이 둔다.
3. **판정 함수**: 지금 로그인한 사람의 역할을 돌려주는 함수 하나(`my_role()`)를 만든다. **이 함수의 실행 권한을 로그인 사용자에게서 회수하지 않는다** — 규칙 안에서 부르는 함수는 부르는 사람의 권한으로 실행되기 때문에, 회수하면 그 함수를 쓰는 **표가 통째로** 안 열린다.
4. **전부 잠그기**: 모든 표에 행 수준 보안을 켠다. 이 시점에서 앱은 아무것도 안 보인다. **정상이다.**
5. **넓은 규칙부터 좁히기**: 2회차에 넣은 "우리 회사 사람이면 본다" 규칙을 **먼저 확인하고 좁힌다.** 좁은 규칙을 새로 추가해도 넓은 규칙이 그대로 통과시킨다 — 규칙은 더할수록 넓어진다.
6. **필요한 것만 열기**: 표마다 역할별 규칙을 붙인다. 검사는 **허용 목록**으로 쓴다(`coalesce(my_role(),'') in ('owner','staff')`). "이 역할이 아니면 거부"처럼 쓰면 역할이 빈 계정이 통과한다.
7. **역할별 화면**: 로그인 후 역할에 따라 첫 화면을 나눈다. 화면 분기는 **편의**일 뿐이다 — 5·6번이 진짜 방어선이다.
8. **변경 기록**: 3-5에서 고른 행동에만 기록을 남긴다(무엇을·누가·언제·무엇에서 무엇으로).
9. **막을 것 확인**: 새로 만든 표·저장소가 로그인 안 한 사람(`anon`)에게 열려 있지 않은지 본다.

### 8. 접근 차단 확인 — `erp-verifier` 에게 맡긴다

**이 절차를 생략하지 않는다.** "규칙을 만들었다"와 "실제로 그렇게 보인다"는 다른 문장이다.

직접 캡처하지 말고 **`erp-verifier` 를 불러 실측을 맡긴다.** 넘길 것은 세 가지다.

1. `company/people.md` 의 **"보면 안 되는 것" 목록**(한 줄씩 대조할 항목).
2. 역할별 테스트 계정(대표·직원 각 1개, 고객 역할을 만들었으면 1개 더). 계정은 가짜 이름으로 만든다.
3. 확인해야 할 경로: 목록 · 상세 · 검색 · 사진·파일 · **숨긴 화면의 주소를 직접 입력**.

검증자에게 요구할 결과:

- 역할별 첫 화면 캡처(375·1280).
- "보면 안 되는 것" 한 줄씩의 관찰 결과. 그 기능이 아직 앱에 없으면 **'해당 없음'** 이라고 적게 한다 — 없는 것을 확인했다고 적으면 나중에 그 길이 열릴 때 아무도 다시 안 본다.
- **역할 칸이 빈 계정**으로 로그인한 결과. 아무것도 안 보여야 정상이다.
- 권한을 붙인 뒤 **원래 잘 되던 화면들이 그대로 되는지.** 새 규칙이 기존 화면을 죽이는 일이 잦다.

검증자는 판정하지 않는다. 관찰 사실만 받아서 `company/people.md` 의 확인 표에 옮긴다. 한 줄이라도 "보였다"가 나오면 배포하지 않고 6번으로 돌아간다.

### 9. 검수와 상태 문서

권한 조건이 바뀌었으므로 **`indeans-erp-check` 를 호출한다.** 감독 판정 → 검증 실측 → 작업 보고서까지 그 스킬이 이어서 한다(8번의 실측 결과를 그대로 넘긴다).

그다음 `.owner/state.md` 를 고친다.

- **현재 기능** — "역할 둘(대표·직원), 직원은 <무엇>을 못 본다(확인함)".
- **미해결 문제** — 남은 것(예: "고객 화면은 안 만들기로 함 — 대표 판단").
- **다음 행동** — 다음 스킬.

`.owner/progress.json` 의 `app.roles`(만든 역할 목록)·`next_action`·`updated_at` 을 고친다. 2회차 결과(직원 계정으로 입력하고 다시 접속해도 보인다)가 확인되면 `sessions.2.done` 도 `true` 로 적는다.

```bash
git add -A && git commit -m "사람·권한: 로그인·역할·데이터 규칙·변경 기록"
```

## 하지 않는 것

- 역할을 셋 이상으로 시작하지 않는다. 대표·직원 둘이 기본이고, 고객은 3-4에서 "필요하다"가 나올 때만 만든다.
- 특정 회사의 역할 이름을 그대로 쓰게 하지 않는다. 회사 말로 받는다.
- 화면에서 숨기는 것으로 끝내지 않는다. 데이터 규칙 없이 "안 보이게 했습니다"라고 보고하지 않는다.
- 접근 차단 확인을 말로 대신하지 않는다. `erp-verifier` 의 관찰 사실이 없으면 끝난 것이 아니다.
- 권한 규칙에 쓰는 함수의 실행 권한을 회수하지 않는다.
- 비밀번호·접속 키·토큰을 화면이나 기록 파일에 출력하지 않는다.
- 기존 마이그레이션 파일을 고치지 않는다. 새 번호 파일을 만든다.
- 고객 실명·연락처를 예시 데이터로 넣지 않는다. 테스트 계정은 가짜 이름으로.

## 앞선 수강생 분기

이미 역할별 화면과 규칙이 도는 경우 **하나만** 고른다.

1. **고객용 화면 분리** — 고객은 내부 화면의 축소판이 아니라 **다른 화면**을 본다. `company/people.md` 의 고객 공개 범위에 적힌 것만 담은 화면을 새로 만든다.
2. **팀 단위 격리** — 지점·팀이 둘 이상이면 "직원이면 다 보인다"는 규칙이 격리를 무력화한다. 역할 검사에 **소속 검사**를 더한다. 이때 양쪽이 모두 비어 있는 경우를 `=` 로 비교하면 판정 불가가 되어 아무것도 안 보인다 — `is not distinct from` 을 쓴다.
3. **간단 감사 스크립트** — 표마다 ① 행 수준 보안이 켜져 있나 ② 로그인 안 한 사람에게 열려 있나 를 세어 출력하는 스크립트를 만든다. 사람의 검토보다 이게 재발을 더 잘 막는다.

## 자주 막히는 지점

- **규칙을 켰더니 아무것도 안 보인다** — 대개 정상 순서다. 규칙을 켠 표에 허용 규칙을 아직 안 붙였거나, 판정 함수의 실행 권한이 없다. 후자면 그 표 전체가 죽는다.
- **대표 계정인데도 안 보인다** — 역할 표에 본인 행이 없거나 역할 칸이 비었다. 로그인한 계정의 역할을 먼저 출력해 확인한다.
- **좁은 규칙을 넣었는데 여전히 다 보인다** — 2회차의 넓은 규칙이 남아 있다. 규칙은 더해질수록 넓어진다. 넓은 것을 고쳐야 한다.
- **로그인은 되는데 새로고침하면 풀린다** — 로그인 상태를 앱이 기억하도록 세션 복원을 붙이지 않은 것이다.
- **직원에게 금액이 계속 보인다** — 화면에서만 숨겼을 가능성이 높다. 데이터 규칙에서 그 칸을 빼거나, 금액 없는 별도 조회를 쓴다.
- **차단했는데 그 사람이 계속 쓴다** — 계정을 막아도 **이미 받아 간 로그인 증표는 유효 기간까지 그대로 통한다.** 두 가지를 같이 한다: ① 활성 여부를 데이터 규칙 안에 넣어 증표가 남아 있어도 데이터가 안 나가게 ② 접속 기록을 정리한다. 방법은 쓰는 서비스의 최신 문서를 확인한다.
- **"나중에 권한 붙이면 안 되나요"** — 붙일 수는 있지만, 그때는 화면이 여러 개라 확인할 곳이 늘어난다. 표가 적은 지금이 가장 싸다.
