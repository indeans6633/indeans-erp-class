# 인디언즈 사람·권한

권한 단계 실습. 저장·배포가 끝난 앱(회사 명단에 있으면 모두 같은 것을 보는 상태)에 **누가 무엇을 보는지**를 나눈다.

역할은 **대표(`owner`)와 직원(`staff`) 두 개로 시작한다.** 고객 역할은 그 사업에 정말 필요할 때만 만든다(인터뷰 3-4). 역할이 적을 때가 확인이 가장 싸다.

인디언즈가 권한 사고에서 굳힌 원칙 다섯 가지를 그대로 쓴다. 사고 경위는 `references/lessons.md`.

1. **화면 숨김 ≠ 데이터베이스 차단.** 막았다는 근거는 가장 권한 낮은 계정으로 실제로 열어 본 결과뿐이다.
2. **좁히기 전에 넓은 규칙부터 지운다.** 규칙은 더할수록 넓어진다.
3. **검사는 허용 목록으로만.** 빈칸은 "아니오"가 아니다 — 역할이 빈 계정이 거부 목록 검사를 통과한다.
4. **판정 함수의 실행 권한은 거두지 않는다.** 거두면 그 함수를 쓰는 표가 통째로 안 열린다.
5. **권한 높은 함수에는 가드 세 줄.** 행 수준 규칙을 지나치는 함수라 가드가 없으면 우회로가 된다.

## 언제 쓰나

- 앱을 대표 혼자 말고 다른 사람도 쓰는데 **보는 범위를 나눠야** 할 때.
- "이건 직원에게는 안 보였으면", "직원이 자기 것만 보게"라는 말이 나올 때.
- 역할을 하나 더 만들 때(「새 역할을 더할 때」), 직원이 그만둘 때(차단 절차).

쓰지 않는 경우: 데이터가 아직 브라우저 저장뿐이다(→ 먼저 `indeans-erp-data`), 단계·상태 이야기다(→ `indeans-erp-workflow`), 알림 받는 사람 이야기다(→ `indeans-erp-channel`), 금액을 담는 일이다(→ 이 스킬 뒤에 `indeans-erp-money`).

## 시작 전 상태 진단

읽고 나서 말을 건다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` · `.owner/progress.json` | 저장·배포가 끝났나(`app.supabase_connected`·`app.deploy_url`), 이미 만든 역할(`app.roles`) |
| `company/profile.md` · `company/flows.md` | 근무자 현황·고객이 직접 쓰는지 · 단계별 **담당**(역할 이름의 출발점) |
| `company/structure.md` | 화면 목록 — 역할별 첫 화면을 여기서 고른다 |
| `company/improve-plan.md` | "보이면 안 되는 항목" 메모 — **인터뷰 답이 이걸 뒤집지 않는지 대조한다** |
| `company/people.md` | **있으면 두 번째** — 아래 분기 |
| `company/data.md` | 표 목록·마이그레이션 실행 기록 |
| `supabase/migrations/` **전체** | 표마다 걸린 규칙(`create policy`·`drop policy`), `for all`·`using (true)` 같은 넓은 규칙, 판정 함수 |
| `.owner/precedents.md` | 권한 쪽 판례 — 같은 유형이 있었으면 그 "다음부터"를 확인 항목에 넣는다 |
| `src/` | 로그인 화면·역할로 갈라지는 화면이 있나 |

**상태 문서가 코드와 다르면 문서를 믿지 않는다.** 실제를 확인한 뒤 문서를 고치고 시작한다.

- **저장·배포 전** → 멈추고 `indeans-erp-data` 로 보낸다. 잠글 데이터가 아직 없다.
- **처음**(명단은 있는데 모두 같은 화면) → 절차 0부터 전부.
- **진행 중**(역할은 있는데 규칙·화면 중 일부만) → 인터뷰는 3-2·3-3만 확인하고 빠진 절차부터.
- **완료**(노출 표·규칙·화면·실측까지 있음) → 「앞선 수강생 분기」.

진단을 한 문단으로 보고한 뒤 시작한다. 예: "저장과 주소는 끝났고, 지금은 명단에 있는 사람 모두가 같은 화면을 봅니다. 오늘 역할을 둘로 나눕니다. 질문 다섯 개 드리겠습니다."

## 계정이 아직 없을 때

Supabase 계정이 없으면 먼저 `indeans-erp-setup` 의 계정 절차로 보낸다. 오늘 안 되면 멈추지 않되:

1. 인터뷰·노출 표·`company/people.md` 는 **그대로 한다.** 이게 오늘의 본편이다.
2. 역할 표·판정 함수·규칙은 **새 번호 SQL 파일로 써 두고 실행하지 않는다**(`company/data.md` 실행 기록에 "아직 실행 안 함").
3. 역할별 화면은 **임시 역할 전환 스위치**로 확인하고, 그 스위치를 지울 자리를 파일 주석·문서·커밋 메시지 세 곳에 적는다. 화면에도 한 줄: **이것은 잠금이 아니라 연습입니다.**
4. `people.md` 의 확인 항목은 **'확인 불가 — 계정 없음'** 으로 남긴다. 감독은 이 경우를 조건부 승인으로 다룬다(조건 세 줄).

## 절차

### 0. 되돌릴 지점

```bash
git add -A && git commit -m "사람·권한 작업 전 상태"
```

권한 작업은 **데이터가 안 보이게 되는 실수**가 가장 흔하다. 되돌릴 지점 없이 시작하지 않는다.

### 1. 원리를 먼저 설명한다 (3분, 네 문장 이내)

`references/roles-basics.md` 1절을 요약해서 말한다. 특정 회사의 역할 이름을 나열하지 않는다.

1. 역할은 **직함이 아니라 "무엇을 볼 수 있는가"** 로 나눈다.
2. 화면에서 숨기는 것은 숨긴 게 아니다. 데이터 쪽에서 막아야 막힌 것이다.
3. "누구에게 보여 줄까"가 아니라 **"누구에게는 절대 안 보여야 하나"** 부터 적는다.
4. 처음에는 **전부 잠그고** 필요한 것만 하나씩 연다.

### 2·3. 인터뷰 — 한 번에 하나씩

질문 원문은 아래 그대로. 답을 한 줄로 되읽어 확인하고 다음으로 간다. 다 받기 전에 코드를 만들지 않는다. 되묻기와 업종별 예는 `references/interview-questions.md`.

- **3-1 누가 쓰나** — "이 앱을 열게 될 사람을 전부 말씀해 주세요. 대표님 본인, 사무실 직원, 밖에서 일하는 직원 중에 누가 들어가나요?" → 사람 수가 아니라 **종류**를 센다. 셋 이상이면 "보는 게 거의 같은 분들끼리" 묶어 둘로 줄인다.
- **3-2 각자 봐야 할 것** — "직원이 이 앱을 열면 **가장 먼저 무엇을 봐야** 하나요?" → 그 역할의 **첫 화면**. 화면 목록에 없는 화면이면 다음 개선 항목이다.
- **3-3 보면 안 되는 것(가장 중요)** — "직원에게는 **절대 보이면 안 되는 것**이 뭔가요? 지금은 무엇으로 막고 계시나요?" → "딱히 없다"면 금액·단가·다른 사람 연락처·확정 안 된 일정으로 하나씩 되묻는다. 이 목록이 실측 체크리스트가 된다.
- **3-4 고객 역할** — "이 앱에 **고객이 직접 로그인해서** 자기 것을 보는 날이 오나요?" → "아니오"면 만들지 않고 "고객 역할: 없음 — 대표 판단"을 적는다. "예"면 고객 화면은 내부 화면의 축소판이 아니라 **다른 화면**이다 — 오늘은 역할만, 화면은 다음으로.
- **3-5 기록이 필요한 행동** — "나중에 **'이거 누가 언제 했지'** 하고 찾게 될 일이 뭐가 있나요?" → 두세 개(상태 되돌리기·삭제·사람 추가 등). 전부 기록하면 아무도 안 본다.
- **3-6 그만두면** — "직원이 그만두면 그 계정은 지웠으면 하나요, 못 들어오게만 하면 되나요?" → 대부분 "못 들어오게만"(차단). 지우면 그 사람이 남긴 기록의 작성자가 사라질 수 있다.

### 4. 정리해서 읽어 드린다

역할 표 한 장으로 읽어 주고 틀린 곳만 고친다. "보면 안 되는 것"은 한 줄씩 확인받는다. `improve-plan.md` 메모와 다르면 그 자리에서 알린다: "지난번에는 이렇게 적어 두셨는데 오늘 답과 다릅니다. 어느 쪽으로 할까요?"

### 5. 노출 표를 먼저 그린다 — 코드보다 먼저

`assets/people-template.md` 를 `company/people.md` 로 만들고, **3절 노출 표**를 채운다: 행은 데이터(표마다, 그리고 같은 데이터의 다른 길 — 상세·검색·사진·파일·내보내기·알림), 열은 역할 × 동작(읽기·넣기·고치기·지우기). 칸마다 `전부 / 자기 것만 / 안 됨`.

- 이 표가 정책의 설계도다. 정책 한 줄은 이 표의 한 칸이다. 표에 없는 정책을 만들지 않는다.
- 직원에게 안 보여야 할 **칸**(금액·단가)이 같은 표에 있으면 줄 단위 규칙으로는 못 가린다 — 그 칸을 대표만 읽는 별도 표로 옮기거나(돈은 `indeans-erp-money`), 그 칸을 뺀 조회를 따로 둔다. 노출 표에 그렇게 적는다.

### 6. 무엇을 만들지 말하고 동의를 받는다

로그인 정리 · 역할 표 · 데이터 규칙(데이터베이스가 직접 판정) · 역할별 첫 화면 · 변경 기록 · 차단 절차. 하나씩 설명한다.

### 7. 구현 — 순서를 지킨다

`assets/role-check-template.sql` 을 다음 번호 파일로 옮겨 고친다(`supabase/migrations/` 를 열어 마지막 번호 +1).

1. **로그인** — 가입 화면은 열지 않는다(대표가 계정을 만들어 준다). 새로고침해도 로그인이 유지되게(세션 복원).
2. **역할 표** — 2회차의 `app_users` 를 그대로 쓰고 역할 칸에 **허용 값 목록(check 제약)** 을 건다. 비워 둘 수 없게, 활성(`active`) 칸과 함께.
3. **판정 함수 `my_role()`** — 가드 세 줄: `set search_path = public, pg_temp` · `public`·`anon` 에게서 회수 · `authenticated` 에게 실행 권한(**회수 금지**). 활성이 꺼진 사람은 빈 값을 돌려받는다 — 차단의 진짜 방어선이다.
4. **넓은 규칙부터 지운다** — 템플릿 0번 묶음. 같은 표에 걸린 규칙을 `supabase/migrations/` **전체**에서 찾아(`create policy … on <표>`) 이름을 모두 적고, `for all`·`using (true)`·2회차의 "회사 사람이면 전부" 규칙을 0번 묶음에 더한다.
5. **표마다 동작별 규칙** — 노출 표의 칸대로. 소속 검사(`company_id = my_company()`)와 역할 검사(`coalesce(my_role(),'') in (…)`)를 같이 쓰고, 규칙마다 `to authenticated`.
6. **같은 데이터의 다른 길** — 사진·파일을 파일 저장소(Storage)에 두면 저장소 정책도 같은 조건으로. 데이터를 돌려주는 함수가 있으면 함수 안에도 같은 검사. 목록만 막고 파일·함수를 열어 두면 샌다.
7. **권한 높은 함수(`security definer`)를 새로 만들면** 함수 안에 역할·소속 검사를 넣는다. 함수 본문의 거부 검사는 `coalesce` 없이 쓰지 않는다(`if coalesce(my_role(),'') not in ('owner') then` — 빈 값이면 검사가 실행되지 않고 통과한다).
8. **역할별 화면** — 로그인 후 역할에 따라 첫 화면을 나눈다. 역할이 없거나 비면 아무 화면도 열지 않고 안내만. 역할이 바뀌면(로그아웃·계정 전환) 열려 있던 화면을 닫는다. 화면 분기는 **편의**일 뿐이다.
9. **변경 기록** — 3-5에서 고른 행동에만. **앱이 실제로 기록을 넣는 자리까지** 만든다(표만 만들고 끝내면 아무것도 안 남는데 남는다고 믿게 된다).
10. **차단 절차** — 활성 끄기(`active = false`) + 그 사람의 로그인 기록 정리(SQL Editor 에서 `auth.sessions` 의 그 사람 줄을 지운다 — 이미 받아 간 출입증은 만료까지 남을 수 있지만, 3번 덕분에 데이터는 안 나간다). 대표 화면에 "사용 중지" 버튼으로 만들면 실수가 준다.

### 8. 실행 전 — 게이트와 롤백 시뮬

1. `npm run check` — 막힘(잠금·정책·함수 안전장치·판정 함수 실행 권한·비밀값·뷰·정책 대상·비로그인 권한·넓은 읽기 정책·돈 표 규칙·DO 블록 안 보안 변경)이 없어야 한다. 이 검사는 글자만 본다 — 통과했다고 잠겼다고 말하지 않는다.
2. **롤백 시뮬** — `indeans-erp-check` 의 `references/rollback-sim.md` 틀 1에 이 파일을 넣고 SQL Editor 에서 돌린다. 직원·대표·로그인 안 함의 줄 수가 노출 표와 같아야 적용한다. 다르면 4번(지울 규칙)부터 다시 본다.
3. 적용 → `company/data.md` 실행 기록 한 줄 → `references/roles-basics.md` 5절 확인 질의(한 덩어리)로 잠금·규칙·실행 권한 점검.

### 9. 접근 차단 실측 — `erp-verifier` 에게 맡긴다

**생략하지 않는다.** "규칙을 만들었다"와 "실제로 그렇게 보인다"는 다른 문장이다. 넘길 것: `people.md` 의 "보면 안 되는 것" 목록 · 역할별 테스트 계정(가짜 이름 — 대표가 `.env.local` 에 `TEST_<역할>_EMAIL`·`TEST_<역할>_PASSWORD` 로 넣는다) · 확인할 길 목록.

| 실측 항목 | 정상 |
|---|---|
| 역할별 첫 화면(375·1280) | 노출 표대로 |
| "보면 안 되는 것" 한 줄씩 | 안 보임 — 그 기능이 아직 없으면 **'해당 없음'**(없는 것을 "확인함"으로 적지 않는다) |
| 숨긴 화면 주소를 직접 입력 | 데이터가 안 나온다 |
| 그 역할로 표를 직접 읽기(저장소 층) | 노출 표의 줄 수만 |
| 로그인 안 한 상태로 표 읽기 | 빈 결과 또는 권한 오류 |
| 역할이 빈 계정 · 차단한 계정 | 아무것도 안 보인다 |
| 사진·파일 주소 직접 열기 | 권한 없는 역할에게 안 열린다 |
| 권한 붙이기 전에 되던 화면들 | 그대로 된다(새 규칙이 기존 화면을 죽이는 일이 잦다) |

검증자는 판정하지 않는다. 관찰 사실을 `people.md` 확인 표에 옮긴다. 한 줄이라도 "보였다"가 나오면 배포하지 않고 7단계로 돌아간다.

### 10. 검수·감사와 상태 문서

권한 조건이 바뀌었으므로 **`indeans-erp-check` 를 호출한다**(위험 등급 1). 9번 실측 결과를 그대로 넘긴다. 적용 뒤 `erp-auditor` 감사(권한 항목 R1~R8)를 한 번 돌린다 — check 6단계.

`.owner/state.md` — "역할 둘(대표·직원), 직원은 <무엇>을 못 본다(실측함)". `.owner/progress.json` — `app.roles`·`next_action`·`updated_at`. 회차 완료 표시는 그 회차 `course/session-0N/outcomes.md` 의 필수 결과가 모두 확인됐을 때만 적는다.

```bash
git add -A && git commit -m "사람·권한: 노출 표·역할·데이터 규칙·화면·기록·차단"
```

## 새 역할을 더할 때 — 체크리스트

역할 하나는 확인할 조합을 곱으로 늘린다. 더하기 전에 "보는 범위가 기존 역할과 정말 다른가"를 먼저 묻는다.

1. `people.md` 역할 표와 **노출 표에 열을 하나 더해** 칸을 전부 채운다.
2. 역할 허용 값 목록(check 제약)에 더한다 — 새 번호 파일.
3. 표마다 규칙의 역할 목록에 **넣을지 하나씩** 정한다(기존 목록을 통째로 복사하지 않는다).
4. **단독 권한**(돈·지우기·사람 관리)이 걸린 규칙과 함수는 따로 점검한다 — 새 역할이 실수로 대표 권한을 얻는 자리다.
5. 화면 쪽: 역할 목록 · 첫 화면 분기 · 메뉴 · 주소 보호 · 화면에 보이는 역할 이름.
6. 알림 받는 사람 표(`company/channel.md`)에 그 역할이 받을 것·받지 않을 것.
7. 롤백 시뮬 → 적용 → 새 역할 테스트 계정으로 9번 실측.

## 하지 않는 것

- 역할을 셋 이상으로 시작하지 않는다. 특정 회사의 역할 이름을 그대로 쓰게 하지 않는다(회사 말로 받는다).
- 화면에서 숨기는 것으로 끝내지 않는다. 데이터 규칙 없이 "안 보이게 했습니다"라고 보고하지 않는다.
- 접근 차단 실측을 말로 대신하지 않는다. 롤백 시뮬 없이 규칙을 적용하지 않는다.
- 판정 함수의 실행 권한을 회수하지 않는다. 거부 목록(`<>`·`not in`)으로 검사하지 않는다.
- 기존 마이그레이션 파일을 고치지 않는다. 비밀번호·접속 키·토큰을 화면이나 기록 파일에 출력하지 않는다.
- 고객 실명·연락처를 예시 데이터로 넣지 않는다. 테스트 계정은 가짜 이름으로.

## 앞선 수강생 분기

이미 역할별 화면·규칙·실측이 도는 경우 **하나만** 고른다.

1. **고객용 화면 분리** — 고객은 내부 화면의 축소판이 아니라 **다른 화면**을 본다. `people.md` 의 고객 공개 범위만 담은 화면을 새로 만들고, 노출 표에 고객 열을 채운 뒤 7~9단계를 그대로 돈다.
2. **팀·지점 단위 격리** — 지점·팀이 둘 이상이면 "직원이면 다 보인다"가 격리를 무력화한다. 역할 검사에 **소속 검사**를 더한다. 양쪽이 모두 빈 경우(본사 × 본사)를 `=` 로 비교하면 판정 불가가 되어 아무것도 안 보인다 — `is not distinct from` 을 쓴다.
3. **정기 실측** — 9번 표의 저장소 층 항목을 임시 스크립트 대신 `scripts/role-check.mjs` 로 남겨 주간 점검 때 돌린다(테스트 계정으로 표마다 줄 수만 출력). 사람의 검토보다 이게 재발을 잘 막는다.

## 자주 막히는 지점

- **규칙을 켰더니 아무것도 안 보인다** — 허용 규칙을 아직 안 붙였거나, 판정 함수의 실행 권한이 없다. 후자면 그 표 전체가 죽는다(롤백 시뮬에서 "permission denied for function").
- **대표 계정인데도 안 보인다** — 명단에 본인 줄이 없거나 역할이 비었거나 `active` 가 꺼졌다.
- **좁은 규칙을 넣었는데 여전히 다 보인다** — 넓은 규칙이 남아 있다. 같은 표의 규칙을 전체에서 다시 센다(7단계 4번).
- **직원에게 금액이 계속 보인다** — 화면에서만 숨겼거나, 금액 칸이 직원이 읽는 표에 있다. 칸을 옮기거나 금액 없는 조회를 쓴다(5단계).
- **차단했는데 그 사람이 계속 쓴다** — 활성 여부가 데이터 규칙 안(판정 함수)에 들어 있는지 보고, 로그인 기록을 정리한다(7단계 10번).
- **로그인은 되는데 새로고침하면 풀린다** — 세션 복원을 붙이지 않았다.
- **"나중에 권한 붙이면 안 되나요"** — 붙일 수는 있지만 화면이 늘수록 확인할 곳이 늘어난다. 표가 적은 지금이 가장 싸다.
