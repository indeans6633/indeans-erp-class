# 인디언즈 가져온 앱 리빌딩

**이 스킬의 역할은 "처음 가져온 외부 앱의 진입점"이다.** 백업 → 진단 → 방향 제안(대표가 고름) → 디자인 통일·화면 재배치 → 전후 보고까지 한 줄로 이어 간다.

회차 사이에 써 보고 온 앱의 막힌 곳 1~2건을 고치는 일은 **`indeans-erp-review`** 가 한다. 여기는 남이 만든 앱을 처음 받아 "우리 기준의 앱"으로 바꾸는 첫 자리다. 진단 점검표는 review 의 두 참고 파일을 같이 쓴다(복사하지 않는다).

수강생이 바라는 것은 "바뀐 체감"이다. 그래서 오늘 손대는 것은 **눈에 보이고 위험이 낮은 것**(모양·화면 묶음·오늘 현황·검수)으로 하고, 저장 방식·로그인처럼 데이터가 걸린 것은 2회차와 권한 단계로 보낸다.

## 언제 쓰나

- 설치기가 "이 폴더에 이미 앱이 있습니다"라고 알렸을 때 · `indeans-erp-setup` 이 기존 앱을 감지하고 넘겼을 때.
- 대표가 "다른 도구로 만든 앱을 가져왔다", "만들어 둔 앱을 우리 방식으로 바꾸고 싶다"고 할 때.

쓰지 않는 경우: 이 번들로 처음부터 만든 앱(→ `indeans-erp-review`) · 앱이 안 켜지는 고장 하나만(→ `indeans-erp-routine` 의 `references/one-problem.md`) · 저장·배포(→ 2회차 `indeans-erp-data`).

## 시작 전 상태 진단

먼저 읽고 판정한다. 읽기 전에 말을 걸지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/progress.json` | `imported_app`(`detected`·`backup_commit`·`diagnosed_at`·`interview_done`·`plan_chosen`·`screens_done`·`stage` — **블록이나 칸이 없으면 비어 있는 것으로 본다**) · `company.name` · `interview.round` · `design.code` |
| `.owner/state.md` | 미해결 문제 · 다음 행동 |
| `package.json` | 의존성(스택) · 실행 명령(`dev`·`start`·`build`) · 설치 때 도는 명령(`postinstall`·`prepare`) |
| `src/`·`app/`·`pages/` 아래 화면 파일 | 화면 개수·이름 — 아래 감지 기준 |
| `.gitignore` · `git ls-files` | `.env` 계열이 기록에 들어가 있는지(**파일을 열지 않는다**) |
| `company/rebuild-*.md` · `.owner/backup/` · `reports/*리빌딩*` | 이 스킬이 어디까지 했나(아래 체크포인트와 대조) |

### 기존 앱 감지 기준 (설치기·시작 점검 공통 — 이 절이 단일 원본)

세 가지가 **모두** 맞으면 "가져온 앱"이다(처음 판정할 때).

1. `package.json` 의 `dependencies` 가 하나 이상이거나, `dependencies`·`devDependencies` 에 UI 틀(react·vue·svelte·next·nuxt·@angular/core·solid-js·preact·lit·astro)이 있다.
2. `src/`·`app/`·`pages/` 아래(7단계 깊이까지, `src/styles/` 제외)에 화면 파일이 있다 — `.jsx`·`.tsx`·`.vue`·`.svelte`·`.astro` 1개 이상, **또는** `.js`·`.ts` 가 있고 맨 위·`src/`·`app/` 에 `index.html`·`app.html` 이 있다. `.js`·`.ts` 만으로는 앱이 아니다. **번들 설치 골격(`src/styles/` 만 있는 것)은 앱이 아니다.**
3. `.owner/progress.json` 의 `company.name` 이 비어 있다(파일이 없어도 비어 있는 것으로 본다). 파일이 있는데 읽히지 않으면 판정하지 않고 "진행 문서를 읽지 못했습니다"라고 알린 뒤 `indeans-erp-setup` 으로 보낸다.

`install.mjs` 는 설치 전에 이 기준으로 보고 새로 만드는 진행 문서에 `imported_app.detected` 를 적는다(이미 있던 진행 문서는 건드리지 않는다). **이 스킬은 시작할 때 실물로 다시 판정해**, 기준이 맞는데 `detected` 가 false 면 true 로 고친다(설치 뒤에 앱을 옮겨 왔거나 옛 진행 문서다). 여러 앱이 든 저장소(`apps/*`)·7단계보다 깊은 화면은 지원 범위 밖이다(아래 「지원 범위와 한계」).

### 판정과 분기 — 체크포인트

**이미 시작된 리빌딩이 우선이다.** `detected` 가 true 이고 `backup_commit` 이 있으면 기준 3(회사 이름)은 보지 않는다 — 1차 인터뷰가 회사 이름을 채운 뒤에도 이어 간다. 그 밖에는 위 기준으로 판정한다.

- **대상 아님** — 기준이 안 맞고 시작된 기록도 없다 → "이 폴더는 가져온 앱이 아닙니다"라고 알리고 멈춘다. 앱이 없으면 `indeans-erp-setup`, 번들로 만든 앱이면 `indeans-erp-review`.
- **이어 가기** — `imported_app` 의 칸을 순서대로 보고 **첫 번째로 비어 있는 것**부터 한다:

| 비어 있는 칸 | 하는 절차 |
|---|---|
| `backup_commit` | 1~2 (되돌릴 지점 · 전체 백업) |
| `diagnosed_at` | 3~4 (진단 · 전 사진 · 변경 전 빌드) |
| `interview_done` false | 5 (1차 축약 — `interview.round` 1 이상이면 true 로 적고 넘어간다) |
| `plan_chosen` 빈 배열 | 6 (제안서를 다시 보여 주고 질문부터 — 제안서가 없으면 쓰고) |
| `stage` null | 7 (디자인 — 고르지 않았으면 건너뛰고 `"design"` 으로) |
| `stage` `"design"` | 8 (화면 재배치 — 같은 규칙. `screens_done` 에 든 화면은 건너뛰고 남은 화면부터) |
| `stage` `"screens"` | 9 (스스로 점검·검수) |
| `stage` `"checked"` | 10~12 (후 사진 · 대표 확인 · 전후 보고 · 상태) |
| `stage` `"reported"` | **1단계 끝.** 2회차면 "2·3차 인터뷰(`indeans-erp-interview`) → 리빌딩 2단계(저장·배포 — `indeans-erp-data` 의 가져온 앱 분기)"로 안내 |
| `stage` `"data"` | 「앞선 수강생 분기」 |

**상태 문서와 실제가 다르면 실제를 믿는다**(예: `backup_commit` 이 적혀 있는데 그 커밋이 없다 → 1부터). 판정을 한 문장으로 먼저 알린다. 예: "다른 도구로 만든 앱이 있습니다. 먼저 되돌릴 지점과 백업을 만들고 진단부터 하겠습니다. 대표님이 고르시기 전에는 아무것도 고치지 않습니다."

## 절차

**스킬 폴더** = 이 파일이 있는 폴더(`.claude/skills/indeans-erp-rebuild/` 또는 `.agents/skills/indeans-erp-rebuild/` — 있는 쪽). 명령의 `<스킬 폴더>` 를 그 경로로 바꾸고, 경로는 늘 따옴표로 감싼다.

### 1. 되돌릴 지점 — 비밀값을 빼고 커밋

1. `git rev-parse --show-toplevel` 과 지금 폴더가 **같은 경로인지** 본다(윈도우는 `/`·`\`·대소문자가 섞인다). 다르거나 오류면 이 폴더에서 `git init`.
2. `.gitignore` 에 `.env`·`.env.*`·`.envrc`·`.owner/tmp/`·`.owner/backup/` 줄이 있는지 본다. 없으면 "이 줄들을 넣겠습니다"라고 알리고 넣는다.
3. **커밋 전 확인** — 진단 스크립트를 먼저 한 번 돌린다(읽기만 한다): `node "<스킬 폴더>/assets/rebuild-scan.mjs" --out ".owner/tmp/rebuild-scan.md"`. 결과 8번의 `.env` 계열 파일과 **「커밋에서 뺄 후보」**(소스 안 키 모양 파일 · 링크·하드 링크 — `.env` 를 다른 이름으로 연결했을 수 있다)를 `git status --porcelain` 의 변경·미추적 목록과 대조한다. 값은 열지 않는다.
4. 커밋 — `.env` 계열과 3의 후보를 **빼고** 스테이징한다. 제외 패턴은 **이미 스테이징된 것을 빼지 못하므로** 먼저 전부 내린다:

```
git reset -q
git add -A -- . ":(exclude,glob)**/.env*" ":(exclude)<후보 경로>"
git diff --cached --name-only
```

   마지막 목록(이번에 기록될 파일)에 `.env` 계열이나 후보가 보이면 `git restore --staged "<경로>"` 로 빼고 목록을 다시 본다. 깨끗할 때만:

```
git commit -m "리빌딩 전 상태 저장"
git rev-parse HEAD
```

- 후보가 없으면 `":(exclude)<후보 경로>"` 부분은 뺀다(여럿이면 하나씩 이어 쓴다).
- 이미 기록에 들어 있는 `.env` 는 여기서 손대지 않는다 — 진단 8번 **치명**으로 올리고, 처리(`.gitignore` + `git rm --cached`)는 제안서에서 대표가 고른 뒤에 한다. 기록 다시 쓰기(이력 재작성)는 하지 않는다(안내만).
- 후보를 뺐으면 "이 파일은 비밀 키가 들어 있을 수 있어 기록에 넣지 않았습니다(값은 보지 않았습니다)"라고 알리고 진단 문서 머리에 적는다.
- 커밋이 실패하면(사용자 이름 미설정·커밋 훅 거절) 오류 원문을 보여 주고 멈춘다. 사용자 이름은 대표에게 확인한 뒤 이 폴더에만 설정한다(`git config user.name "<이름>"`). 바뀐 것이 없어 커밋이 안 되면 지금 `HEAD` 가 되돌릴 지점이다.

### 2. 전체 백업

git 기록은 git 이 아는 파일만 지킨다. 기록에서 빠진 파일(대표가 따로 둔 자료 등)까지 지키려고 폴더를 한 벌 더 둔다. **앱(`npm run dev`)이 켜져 있으면 끄고** 한다.

```
node "<스킬 폴더>/assets/rebuild-backup.mjs"
```

- `.owner/backup/before-rebuild-<날짜>-<시분>/` 에 복사되고 `__rebuild-backup-manifest.json`(파일별 해시·실패 목록)이 남는다. `.env` 계열은 열지도 복사하지도 않고 이름만 적는다.
- **종료 코드 0(실패 0)일 때만 완료 백업이다.** 2면 실패 목록을 보여 주고 원인(잠긴 파일·권한)을 없앤 뒤 다시 실행한다.
- 대표에게 한 줄: "이 백업은 앱 폴더를 지킵니다. 데이터베이스와 브라우저 안 데이터는 이 백업으로 돌아오지 않습니다 — 오늘은 그쪽을 건드리지 않습니다."
- **중단 조건**: 1의 커밋 해시를 확인했고 백업 실패가 0이면 `imported_app.backup_commit` 에 그 해시를 적는다(`detected` 도 true). 둘 중 하나라도 아니면 다음 절차로 가지 않는다.

### 3. 자동 진단

```
node "<스킬 폴더>/assets/rebuild-scan.mjs" --out ".owner/tmp/rebuild-scan.md"
```

스크립트는 읽기만 한다(비밀값은 파일 이름과 종류만, 모든 줄에 가리기). 결과를 **`references/diagnosis.md` 기준으로 다시 판정해** `assets/rebuild-diagnosis.template.md` 를 `company/rebuild-diagnosis.md` 로 채운다. 열 가지 항목:

스택 · 화면 수와 이름 · 저장 방식(브라우저/Supabase/기타/없음) · 로그인 · 권한 · 디자인 토큰 유무 · 검수·검사 체계 · 비밀값 노출(커밋된 `.env`, 소스 안 키 모양 — 파일 이름만) · 회사 말 사용 · 휴대폰 375 폭 상태.

- 스크립트의 "못 찾음"은 "없음"이 아니다 — 코드·캡처로 확인한다.
- 화면 점검은 `indeans-erp-review` 의 `references/review-checklist.md` 1~6절, 디자인 감사는 같은 스킬의 `references/design-audit.md` 1~5절로 본다(찾기만).
- **치명**(커밋된 비밀값 · 실제로 쓰는 데이터베이스가 잠금 없이 열림)이 있으면 진단을 다 쓰기 전이라도 대표에게 먼저 한 줄로 알린다.
- **운영 데이터 질문** — 결과 3번이 "살아 있을 수 있음"(또는 확실하지 않음)이면 대표에게 하나만 묻는다: **"지금 이 앱에 실제 업무 데이터가 들어 있나요?"** 답을 진단 문서 머리에 적는다. 이후 모든 기능 확인은 `references/restyle.md` 1절 4번(추가 → 수정 → 자기가 넣은 시험 행만 삭제, 실제 데이터가 있으면 시험 행 1개만)을 따른다.

### 4. 전 화면 사진 (before) · 변경 전 빌드

1. **실행 전 확인** — 결과 1번의 "데이터를 바꿀 수 있는 명령"(`postinstall`·`prepare`·`predev`·`dev`·`prebuild`·`build` 에 migrate·seed·db 류)이 있으면 실행하기 전에 대표에게 묻는다: "앱을 켜면 데이터베이스를 바꾸는 명령(○○)이 같이 돕니다. 켜도 될까요?" 아니면 켜지 않고 "실행 불가 — 대표 보류"로 둔다.
2. `node_modules` 가 없으면 `npm install`(2~5분, 끊지 않는다). playwright 가 없으면 `npm i -D playwright` → `npx playwright install chromium` — 사진 도구 한 줄이 `package.json` 에 더해진다고 알린다.
3. **변경 전 빌드** — `npm run build` 를 한 번 돌려 결과를 진단 문서 「변경 전 빌드」에 적는다(성공 / 실패 — 오류 첫 줄). 나중에 회귀인지 원래 문제인지 가른다.
4. 다른 창(백그라운드)에서 `npm run dev`(없으면 `npm start`) → 터미널이 알려 준 주소를 쓴다. 첫 화면 + 최대 두 화면(가장 자주 쓰는 목록과 입력 화면)을 찍는다 — `references/diagnosis.md` 「전 사진 고르는 법」. 띄울 때 받은 **PID 를 적어 두고, 끝나면 그 번호로만 끈다**(`taskkill /PID <번호>` · `kill <번호>`). 이름으로 전부 끄는 명령(`taskkill /IM node.exe`·`pkill node`)은 쓰지 않는다 — 다른 프로젝트 서버와 AI 도구 자신까지 꺼진다.

```
node .owner/hooks/capture.mjs --url http://localhost:5173 --out reports/shots/rebuild-before --name before-home
node .owner/hooks/capture.mjs --url http://localhost:5173 --click "<목록으로 가는 버튼 글자>" --out reports/shots/rebuild-before --name before-list
```

- 앱이 안 뜨면 오류 원문을 진단 문서 "실행 기록"에 적고 **실행 불가**로 둔 채 계속한다. 고쳐서 띄우지 않는다 — 고르기 전이다.
- 375 사진으로 진단표 10번을 채운다. 진단 문서를 다 쓰면 `imported_app.diagnosed_at` 에 지금 시각을 적고 커밋한다(`리빌딩 진단` — 1의 제외 규칙 그대로). 대표에게 "한눈에" 세 줄을 읽어 준다.

### 5. 1차 인터뷰 — 축약 모드

`company/profile.md` 가 있고 `interview.round` 1 이상이면 건너뛴다. 아니면 같은 대화에서 **`indeans-erp-interview` 를 읽고 「가져온 앱 1차」 분기**대로 한다(그 스킬의 `references/imported-app.md`). 요점:

- 회사·업종 깔때기(1-1 ~ 1-3, 업종 세부)는 **그대로** 묻는다. 앱 화면에 이미 보이는 것(관리 단위·항목·단계 이름)은 **"이렇게 부르시는 것 맞죠?"로 확인만** 한다.
- 추가 질문 두 개(한 번에 하나): **"이 앱으로 풀려던 문제 하나가 무엇이었나요?"** · **"지금 이 앱에서 제일 아쉬운 것은 무엇인가요?"** — 답은 진단 문서 「대표가 말한 것」에 그대로. 디자인 힌트(간판·로고 색 포함)는 그대로 받는다.
- 1차가 끝나도 **디자인 선택창을 바로 열지 않고 이 스킬로 돌아온다**(여기서는 제안서가 먼저다). 돌아오면 `imported_app.interview_done` 을 true 로.

### 6. 개선 방향 제안서 — 대표가 고른다

`assets/rebuild-plan.template.md` 를 `company/rebuild-plan.md` 로 채운다. 인디언즈 기준 다섯 축, 축마다 **지금 → 바꾸면 → 체감 포인트 → 언제**(1회차 오늘 / 2회차 / 권한 단계 / 운영 보고 단계).

| 축 | 보는 것 |
|---|---|
| ① 구조 | 관리 단위 하나 · 화면 셋(목록 · 상세·입력 · 오늘 현황) — 지금 화면 → 새 자리 대응표(기능은 하나도 지우지 않는다) |
| ② 디자인 | 선택창으로 하나로 통일 · 회사 말 · 휴대폰 폭 |
| ③ 데이터·권한 | 남는 저장 · 백업 · 잠금 · 역할 · 커밋된 비밀값 |
| ④ 검수·보고 체계 | 검수 훅 · 감독 판정 · 작업 보고서 |
| ⑤ 운영 보고 | 정해진 시각에 받는 사람별 보고 |

**권장안은 하나다**: 오늘(1회차) = **디자인 통일 + 오늘 현황 화면 + 검수 체계 통과.** 저장·권한은 2회차·권한 단계. 대표가 말한 "풀려던 문제·제일 아쉬운 것"과 권장안을 한 줄로 잇는다. 커밋된 비밀값이 있으면 "기록에서 빼기(오늘 — `.gitignore` + `git rm --cached`) · 키 새로 발급(대표)"을 권장안에 한 줄 더한다.

제안서를 축마다 두세 줄로 줄여 보여 주고 **질문은 하나만** 한다:

> "오늘은 권장안대로 디자인을 통일하고 오늘 현황 화면을 더한 뒤 검수까지 받겠습니다. 저장 방식과 로그인은 2회차에 합니다. 이대로 할까요, 바꾸고 싶은 줄이 있으면 말씀해 주세요."

- 답을 듣기 전에는 **아무 파일도 고치지 않는다.** "여기까지"면 제안서·상태 문서만 커밋하고 끝낸다(다음에 부르면 이 질문부터).
- 고른 것을 제안서 맨 위 "대표가 고른 것"과 `imported_app.plan_chosen`(축 번호와 한 줄 — 예 `["②디자인 통일", "①오늘 현황", "④검수"]`)에 적고 커밋한다(`리빌딩 방향 — 대표 선택`). 비밀값 정리를 골랐으면 이때 같이 한다.
- **고른 축만 실행한다.** 절차 7은 ②축이, 절차 8은 ①축이 `plan_chosen` 에 있을 때만 한다(없으면 실행 기록에 "건너뜀"). 검수(절차 9)는 화면을 바꿨으면 늘 한다(검수 훅이 요구한다). 오늘 안 하기로 한 줄은 「오늘 하지 않는 것」, 고른 범위 밖에서 걸린 문제는 「보류 항목」 — 둘 다 전후 보고서의 남은 로드맵이 된다.

### 7. 디자인 통일 (②축을 골랐을 때)

1. **기존 스타일 백업** — 진단 6번의 전역 스타일·설정 파일 전부(`src/styles/` 에 `tokens.css`·`base.css`·`layout.css` 가 이미 있으면 그것도 — `references/restyle.md` 2-2):
   ```
   node "<스킬 폴더>/assets/rebuild-backup.mjs" --styles "<파일>" "<파일>"
   ```
   종료 코드 0 이 아니면 멈춘다. 만들어진 `styles-before-<날짜>-<시분>/` 를 제안서 실행 기록에 적는다.
2. **선택창** — `indeans-erp-design` 을 읽고 그 절차 1~5를 따른다(선택창이 바로 열린다). 추천은 `company/profile.md` 의 디자인 힌트(간판·로고 색)로 한다. 진단 6번의 '지금 쓰는 색'은 대표가 인터뷰에서 "그대로 두고 싶다"고 했을 때만 내 색으로 쓰고, 싫다고 한 색은 권하지 않는다. 그 스킬의 절차 6~8(앱에 적용)은 **이 스킬의 3·4번이 대신한다**.
3. **토큰 연결** — `references/restyle.md` 2-3~2-6. 전역 CSS 의 값은 `var(--…)` 로, Tailwind 면 설정에 **병합**해 연결한다. **클래스를 전부 바꾸지 않는다.** Tailwind 진입 CSS 의 지시문은 지우지 않는다.
4. **부르는 자리** — `references/restyle.md` 2-1 의 프레임워크별 표대로. **표에 없는 구조면 멈추고 대표에게 묻는다.**
5. 띄워서 기존 기능을 시험 행 규칙으로 한 번씩 누르고 커밋한다(`디자인 통일 — <조합 코드>`). `stage` 를 `"design"` 으로.

### 8. 화면 3개로 재배치 (①축을 골랐을 때)

`indeans-erp-draft` 의 `references/screen-rules.md` 가 기준이고, 가져온 앱이라서 다른 점은 `references/restyle.md` 1·3절이다.

- **지키는 것**: 기존 기능·데이터 보존 · **저장 방식은 오늘 바꾸지 않는다** · 브라우저 저장 키·표 이름을 바꾸지 않는다 · 한 번에 한 화면.
- 화면마다 설계 선언 다섯 줄을 먼저 쓴다 — `indeans-erp-draft` 의 `references/design-statement.md` 형식으로 `company/screens.md`(템플릿은 그 스킬의 `assets/screens.template.md`). 화면 감독이 이것으로 판정한다.
- 제안서 ①축 대응표대로 목록 → 상세·입력 → 오늘 현황. **오늘 현황이 없으면 추가한다**(있는 데이터를 읽기만). 남는 화면은 지우지 않고 메뉴 끝으로. 목록을 나눠 보이면 전체 건수·더 보기·전체 검색(restyle 3절).
- 화면 글자를 회사 말로. 휴대폰에서 표는 카드로 접는다.
- 화면 하나를 끝낼 때마다 띄워서 기존 기능을 시험 행 규칙으로 누르고, 새로고침해도 전에 넣어 둔 데이터가 보이는지 본다. 화면마다 커밋하고 그 화면 이름을 `imported_app.screens_done` 에 더한다. **대응표의 대상 화면을 전부 끝낸 뒤에만** `stage` 를 `"screens"` 로.

### 9. 스스로 점검과 검수 (대표에게 보여 주기 전에)

1. `indeans-erp-draft` 의 `references/self-review.md` 로 본다. **고른 범위 안에서 걸린 것만** 지금 고치고, 범위 밖은 제안서 「보류 항목」에 적는다. `npm run build` 결과를 「변경 전 빌드」와 비교한다(restyle 4절).
2. 대표에게 한 줄: "다 바꿨습니다. 보여 드리기 전에 검수를 먼저 받겠습니다(10~15분)."
3. 커밋(`리빌딩 1단계 — <고른 축>`) → **`indeans-erp-check`** 를 읽고 그 절차대로. 진단 문서의 디자인 감사 표를 변경 요약의 "확인받고 싶은 것"에 넣는다. 반려면 고치고 다시(최대 2번). 검수 보고서는 `--title "리빌딩 검수" --slug 리빌딩-검수` 로 만든다(전후 보고서와 **다른** 이름). 통과하면 `stage` 를 `"checked"` 로.

### 10. 후 사진과 대표 확인

1. 절차 4와 **같은 화면·같은 폭**을 `--out reports/shots/rebuild-after --name after-<화면>` 으로 찍는다. 오늘 현황은 새 화면이니 375·1280 한 번씩 더.
2. 대표에게 직접 눌러 보게 한다(하나씩 읽어 준다): ① 휴대폰 폭에서 옆으로 밀리지 않는다 ② 오늘 현황에 오늘 할 것이 보이고 숫자를 누르면 걸러진다 ③ 전에 넣어 둔 데이터가 그대로 보인다(**전에 쓰던 그 브라우저·그 주소로**) ④ 새 건을 넣고 새로고침해도 남는다(실제 데이터가 있는 앱이면 시험 건 하나를 넣고 확인 뒤 그것만 지운다) ⑤ 전에 되던 기능이 그대로 된다.
3. 안 되는 것은 고치고 커밋한다. 화면 동작을 고쳤으면 검수를 그 부분만 다시 받는다.

### 11. 전후 비교 보고서

`indeans-erp-report` 를 읽고 그 절차 3~5(본문 → 생성 → 보여 주기)를 따른다. 다른 점 셋:

1. **나란히 사진** — 화면·폭마다 전·후를 한 장으로 붙인다(생성기는 사진을 위아래로 쌓기만 한다):
   ```
   node "<스킬 폴더>/assets/side-by-side.mjs" --before "reports/shots/rebuild-before/before-list-375.png" --after "reports/shots/rebuild-after/after-list-375.png" --out "reports/shots/rebuild-compare/list-375.png" --title "목록 · 휴대폰"
   ```
   종료 코드 3(붙이는 도구 문제)이면 전·후 사진을 따로 `--shot` 으로 넣고 설명에 "전"·"후"를 적는다. 1이면 메시지대로(사진 다시 찍기·다른 출력 이름). 전 사진이 없으면(실행 불가) 후 사진만.

3. **생성** — 제목·이름을 고정한다(검수 보고서와 다른 slug):
   ```
   node .owner/hooks/report.mjs --title "리빌딩 전후" --slug 리빌딩-전후 --body .owner/tmp/rebuild-report.md --shot reports/shots/rebuild-compare/list-375.png --caption "목록 · 휴대폰 — 왼쪽 전, 오른쪽 후"
   ```
   결과는 `reports/<날짜>-리빌딩-전후.html`. 나란히 사진은 2~4장.

### 12. 상태 문서 갱신과 커밋

- `.owner/state.md` — **현재 기능**: 되는 일을 한 줄씩(가져온 기능 + 오늘 현황 + "저장은 아직 브라우저" 같은 사실). **선택한 디자인**: 디자인 스킬이 적은 그대로. **미해결 문제**: 진단의 치명·손볼 것·보류 항목 중 오늘 안 한 것. **다음 행동**: "2회차 — 2·3차 인터뷰(`indeans-erp-interview`) → 리빌딩 2단계: 저장·배포(`indeans-erp-data` 의 가져온 앱 분기 — 초안 `indeans-erp-draft` 는 건너뛴다)". 새 절 제목을 만들지 않는다.

마지막 보고는 3줄: 무엇이 바뀌었나(전후 보고서 경로) / 오늘 바꾸지 않은 것 / 다음(2회차 — 새 대화에서 `indeans-erp-interview` 2차부터).

## 하지 않는 것

- 대표가 고르기 전에 코드·스타일·설정을 고치기. 절차 1~6은 백업·읽기·문서만이다(`.gitignore` 줄 추가와 사진 도구 설치는 알리고 한다).
- 고르지 않은 축을 실행하기 · 범위 밖 문제를 그 자리에서 고치기(보류 항목으로).
- `.env` 계열 파일을 열거나, 값을 대화·문서·보고서에 옮기기. 새 키를 대화로 받기. 기록 다시 쓰기(이력 재작성).
- 이미 있던 업무 데이터를 수정·삭제해 시험하기(시험 행만).
- **저장 방식 바꾸기**·로그인·역할을 오늘 만들기. 2회차·권한 단계다.
- 브라우저 저장 키·표 이름·상태 저장 값 바꾸기. 기존 기능·화면 지우기.
- 다른 화면 틀로 옮기기, 라우터·UI 부품 묶음 바꾸기, Tailwind 클래스 전면 치환·설정 통째 교체.
- 기존 데이터베이스 기록(`supabase/migrations/`)을 고치거나·옮기거나(`legacy/` 폴더 등)·이름을 바꾸거나·다시 만들기 — 2회차 `indeans-erp-data` 가 다음 번호로 이어 붙인다(프로젝트를 지웠어도 같다).
- 진단 점검표를 새로 지어 쓰기 · 감독 판정을 흉내 내기(`indeans-erp-check` 를 부른다).
- 자기가 띄운 서버가 아닌 프로세스를 끄기 — 이름으로 전부 끄는 명령(`taskkill /IM`·`pkill`·`killall`·`Stop-Process -Name`)은 쓰지 않는다(명령 보호 훅이 막는다). 띄운 PID 만 끈다.

## 지원 범위와 한계

아래에 해당하면 **짐작으로 진행하지 않고 멈춰서 대표에게 한 줄로 말한다** — "이 앱은 ○○ 구조라 이 스킬이 바로 다루지 못합니다. ○○부터 정하겠습니다."

- 여러 앱이 든 저장소(`apps/*`·`packages/*`·workspaces) · 화면이 `src/` 아래 7단계보다 깊다 → 어느 앱을 볼지 대표와 정하고, 그 앱 폴더를 프로젝트로 다시 시작한다.
- 전역 스타일 진입점이 `restyle.md` 2-1 표에 없다(Angular·Remix·Astro 등) → 토큰을 어디서 부를지 대표와 확인.
- 저장이 Firebase·직접 만든 서버·구글 시트 → 오늘은 그대로. 2회차에 둘지 옮길지 대표가 정한다(`indeans-erp-data`).
- 설치·실행 명령이 데이터베이스를 바꾼다(migrate·seed) → 대표가 허락하기 전에는 켜지 않는다.
- 프로젝트 안 데이터 파일(SQLite 등)·실행 중인 앱 → 앱을 끄고 백업. 원격 DB·브라우저 데이터는 폴더 백업으로 돌아오지 않는다.
- 진단 스크립트는 파일 512KB·3,000개까지만 읽는다(넘은 것은 "건너뜀"으로 적힌다) · 과거 커밋 이력의 비밀값은 검사하지 않는다.

## 앞선 수강생 분기

`stage` 가 `"data"` 이거나, 1단계를 일찍 끝냈으면 하나를 고른다.

1. **남은 화면 정리** — 메뉴 끝으로 보낸 화면 중 안 쓰는 것을 대표와 하나씩 보고, 쓰는 것은 회사 말·토큰으로 맞춘다. 지울지는 대표가 정한다(지우기 전에 커밋).
2. **입력 줄이기** — 입력 화면에서 손이 몇 번 가는지 세고 기본값·최근 값으로 줄인다. 설계 선언을 같이 고친다.
3. **회차 사이 진단으로** — 직원이 며칠 써 본 뒤라면 `indeans-erp-review`(세 줄 기록 → 개선 1~2건)로 넘어간다.

## 자주 막히는 지점

- **`npm install` 이 실패한다** — 의존성 판이 오래됐거나 섞였다. 오류 원문을 진단 "실행 기록"에 적고 실행 불가로 진행한다. 고치는 것은 제안서에 "실행 복구"로 올려 대표가 고르게 한다.
- **화면은 뜨는데 다른 주소로 열린다** — 터미널이 알려 준 주소를 그대로 쓴다(5173 이 아닐 수 있다).
- **토큰을 넣었더니 화면 전체가 맨 글자가 됐다** — Tailwind 진입 CSS 의 지시문을 지웠거나 그 파일 import 가 빠졌다. 이번 작업의 `styles-before-<날짜>-<시분>/` 에서 원본을 보고 되살린다.
- **글자 크기·여백이 이상하게 커졌다** — 번들 `base.css` 와 앱의 초기화 CSS 가 겹쳤다. 부르는 순서(restyle 2-1)를 먼저 보고, 그래도면 `base.css` 는 고치지 말고 앱 쪽 CSS 에서 그 화면만 맞춰 `company/design.md` "값을 바꾼 곳"에 적는다.
- **전에 넣어 둔 데이터가 안 보인다** — 원인은 셋 중 하나다: ① 저장 키 이름을 바꿨다(진단 3번의 키 목록과 지금 코드를 대조해 되돌린다) ② **다른 브라우저·다른 프로필**에서 열었다 ③ **다른 주소·포트**(예: 전엔 `localhost:3000`, 지금 `localhost:5173`)로 열었다 — 브라우저 저장은 주소마다 따로다. 전에 쓰던 브라우저·주소로 다시 열어 확인한 뒤 판정한다. 데이터가 남아 있다고 먼저 단정하지 않는다.
- **대표가 "전부 다 바꿔 주세요"** — 권장안을 다시 읽어 주고 "저장과 로그인은 데이터가 걸려 있어 2회차에 백업을 먼저 만들고 합니다"를 한 줄. 그래도 원하면 제안서의 '언제'를 바꿔 적되 오늘은 디자인·화면·검수까지만 한다.
- **대표가 기존 색을 그대로 쓰고 싶다** — 선택창의 '내 색'에 그 색을 넣는다. 엔진이 글자 대비를 맞춰 준다(보정 내용을 한 줄 알린다).
- **진단 스크립트가 영어 글자를 너무 많이 잡는다** — 코드 안 이름까지 잡은 것이다. 화면에 실제로 보이는 것만 진단표에 옮긴다.
