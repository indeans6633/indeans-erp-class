# 가져온 앱 진단 기준 — 열 가지 항목

`indeans-erp-rebuild` 절차 3이 읽는다. 자동 진단 스크립트(`assets/rebuild-scan.mjs`)가 글자로 찾은 결과를 이 기준으로 **다시 판정**해 `company/rebuild-diagnosis.md` 진단표에 적는다. 스크립트 결과를 그대로 옮기지 않는다 — 글자로 찾은 것은 틀릴 수 있다(예: 영어 글자가 실제로는 코드 안 이름일 수 있다). **스크립트의 "못 찾음"은 "없음"이 아니다** — 자동으로 확인하지 못한 것이니 코드·캡처로 확인해 적고, 확인 못 하면 "확인 못 함"으로 둔다(좋음으로 짐작하지 않는다).

화면 점검과 디자인 감사는 이 문서에 다시 쓰지 않는다. **`indeans-erp-review` 의 두 참고 파일을 그대로 쓴다:**

- 화면 점검 — `indeans-erp-review/references/review-checklist.md` 1~6절(첫 화면·목록·입력·흐름·말·모바일). 7절 이후는 리빌딩 뒤 회차 사이 진단(review)의 몫이다.
- 디자인 감사 — `indeans-erp-review/references/design-audit.md` 1~5절(AI 티 패턴·타이포 위계·여백 일관성·회사 말 일치·기록하는 법). 고칠 때 쓰는 말(6절)은 리빌딩 절차 7·8에서 쓴다.

두 파일은 같은 도구 폴더 안 옆 스킬에 있다(`.claude/skills/indeans-erp-review/references/` 또는 `.agents/skills/indeans-erp-review/references/`).

## 상태 세 가지

- **좋음** — 그대로 둬도 된다.
- **손볼 것** — 오늘 또는 정해진 단계에서 바꾼다. 제안서의 어느 축으로 갈지 정한다.
- **치명** — 데이터나 비밀값이 새거나 잃을 수 있다. 진단 직후 대표에게 먼저 알리고, 제안서 맨 위에 올린다. 치명은 이 두 가지뿐이다: **커밋된 비밀값**, **잠금 없이 인터넷에 열린 데이터베이스(실제로 쓰는 중일 때)**. 나머지는 아무리 불편해도 손볼 것이다.

## 1. 스택

- 보는 것: 화면 틀(React·Vue 등) · 만드는 도구(Vite 등) · TypeScript · 모양 라이브러리(Tailwind·UI 부품 묶음) · 화면 이동 방식 · 실행 명령.
- 판정: 번들의 전제(Vite + React + TypeScript)와 다르다고 **손볼 것이 아니다.** 바꾸는 일(다른 틀로 옮기기)은 리빌딩이 하지 않는다. JavaScript 면 그대로 JavaScript 로 둔다. Next.js 처럼 서버 기능이 섞인 틀이면 "저장·배포 단계에서 방법이 달라질 수 있음"을 한 줄 남긴다.
- `npm run dev` 가 없고 `start` 만 있으면 그것을 쓴다. 둘 다 없으면 `index.html` 하나짜리 앱일 수 있다 — 파일로 연다.

## 2. 화면 수와 이름

- 보는 것: 화면 파일 목록과 실제로 눌러 갈 수 있는 화면. 메뉴에서 갈 수 없는 화면(만들다 만 것)은 따로 적는다.
- 판정: 3개 규칙(목록 · 상세·입력 · 오늘 현황)과 대응이 안 되면 손볼 것. **오늘 현황(오늘 할 일·단계별 개수)이 없으면 반드시 손볼 것**으로 적는다 — 권장안의 한 줄이다.
- 화면 이름이 영어면 9번에도 같이 적는다.

## 3. 저장 방식

네 가지 중 하나로 적는다: **브라우저**(localStorage·IndexedDB — 그 컴퓨터 그 브라우저에만) · **Supabase** · **기타**(Firebase·직접 만든 서버·구글 시트 등) · **없음**(새로고침하면 사라짐).

- 연결 코드는 있는데 실제로는 브라우저에 저장하는 "폴백"이 흔하다. 스크립트가 "한 파일에서 같이 쓴다"고 하면 그 파일을 열어 **지금 실제로 어느 쪽에 쓰는지**를 확인해 적는다(접속 정보가 비어 있으면 브라우저로 빠지는 코드가 많다).
- **브라우저 저장 키 이름을 꼭 적는다**(스크립트 결과의 "브라우저 저장 키" — 실제 저장 호출과 `persist` 이름만 모은 것). "못 찾음"이면 저장 코드(감싼 함수·동적 키)를 직접 읽어 적는다. 리빌딩 때 이 이름을 바꾸면 대표가 넣어 둔 데이터가 화면에서 사라진다.
- **운영 데이터 여부** — 스크립트의 "운영 데이터 연결 가능성"이 "살아 있을 수 있음"이면(또는 확실하지 않으면) 쓰기 시험 전에 대표에게 **한 번만** 묻는다: "지금 이 앱에 실제 업무 데이터가 들어 있나요?" 답을 진단 문서 머리의 "실제 업무 데이터" 줄에 적는다. 예면 기능 확인은 읽기 + 시험 행 1개만(`restyle.md` 1절 4번). 접속 정보 파일(`.env` 계열)은 이 판단을 위해서도 열지 않는다.
- 판정: 브라우저·없음은 손볼 것(2회차). 기타는 손볼 것 + "2회차에 그대로 둘지 옮길지 대표가 정함" 한 줄.

## 4·5. 로그인 · 권한

- 스크립트가 로그인·역할 흔적을 "못 찾음"이라 해도 단정하지 않는다 — 캡처에서 로그인 화면이 뜨는지, 서버 쪽 확인이 있는지 보고 적는다.
- 로그인이 없으면 손볼 것(2회차 — 저장과 함께). 로그인이 있으면 "누가 계정을 만드나(누구나 가입되나)"를 본다 — 누구나 가입되면 손볼 것.
- 역할이 화면에서만 나뉘어 있으면(버튼 숨김) "화면 숨김 ≠ 차단"으로 적고 권한 단계로 보낸다.
- 리빌딩 오늘 분에서는 둘 다 바꾸지 않는다.

## 6. 디자인 토큰

- 보는 것: 색·크기를 한 곳에서 바꾸는 자리(CSS 변수·Tailwind 설정·테마 파일)가 있나, 화면 파일에 직접 적은 색·크기가 몇 곳인가, 가장 많이 쓴 색.
- 판정: 직접 적은 색이 화면 파일에 흩어져 있으면 손볼 것(오늘 — 디자인 통일). 가장 많이 쓴 색은 **'지금 쓰는 색'** 으로만 적는다 — '내 색' 후보로 올리지 않는다(간판·로고 색은 인터뷰에서 대표가 말한다. 다른 도구가 고른 색을 후보로 내밀면 대표가 그 색에 끌려간다). 대표가 "그대로 두고 싶다"고 하면 그때 내 색이 된다.
- 전역 스타일·설정 파일 목록을 빠짐없이 적는다 — 절차 7에서 이 목록을 백업한다.

## 7. 검수·검사 체계

- 보는 것: `package.json` 의 `check`·`test`·`lint` · 시험 파일 · 번들 검수 훅 설치 여부 · 화면 사진 도구.
- 판정: 없으면 손볼 것(④축 — 오늘). 번들을 설치했으면 검수 훅은 이미 돈다. 고정 검사(`npm run check`)는 2회차 저장 단계에서 마이그레이션 게이트와 함께 붙는다.

## 8. 비밀값 노출 — 파일 이름만

**`.env` 로 시작하는 파일은 열지 않는다.** 있는지와 git 이 추적하는지만 본다. 값을 화면·문서·대화에 옮기지 않는다.

- 스크립트는 **마지막 커밋에 든 것**과 **스테이징만 된 것**을 나눠 적는다. 스테이징만 된 `.env` 는 절차 1이 커밋에서 빼므로 치명이 아니다. 과거 커밋 이력은 검사하지 않는다 — 진단표에 "이력 미검사"를 한 줄 적는다.
- **커밋된 `.env`**(예시 파일 `.env.example`·`.env.sample` 은 값이 비어 있는지만 파일 크기·이름으로 짐작하고 열지 않는다) → **치명.** 대표에게 바로 알린다: "접속 정보 파일이 저장 기록에 들어가 있습니다. 값은 열어 보지 않았습니다. 그 서비스에서 키를 새로 발급받는 것이 정답이고, 기록에서 빼는 것은 오늘 제가 할 수 있습니다." 제안서 ③축 맨 위 줄로 올린다.
  - 오늘 할 수 있는 것: `.gitignore` 에 `.env` 계열 줄 추가 + `git rm --cached "<파일>"`(파일은 그 자리에 남고 다음 커밋부터 기록에서 빠진다). **진단에서는 하지 않는다** — 제안서 ③축에 올려 대표가 고른 뒤에 한다. 예전 커밋에는 그대로 남는다는 것을 같이 말한다. 기록을 다시 쓰는 일(이력 재작성)은 하지 않는다 — 필요하면 "키 새로 발급이 정답이고, 기록 다시 쓰기는 전문가와 따로"라고만 안내한다.
  - 키 새로 발급은 대표가 그 서비스 화면에서 한다. AI 가 대신하지 않고, 새 키를 대화에 받지 않는다.
- **소스 안 키 모양** → 스크립트가 적은 파일 이름과 종류만 옮긴다. 그 파일을 열어 확인해야 하면 **그 줄을 화면에 출력하지 않고** 종류(공개용 키인지 비밀 키인지)만 판단한다. 공개용 키(`anon`·`publishable`)는 손볼 것(2회차에 `.env.local` 로), 비밀 키(`service_role`·`secret`·결제 비밀 키)는 치명.
- `.gitignore` 판정은 스크립트의 `git check-ignore` 결과(실제 파일·가상 경로)로 한다. "무시 안 됨"이면 절차 1에서 커밋하기 **전에** 줄을 넣는다. 그래도 절차 1은 `.env` 계열을 스테이징에서 빼고 커밋한다(줄이 있어도 이미 추적 중인 파일은 무시되지 않는다).

## 9. 회사 말

- 보는 것: 화면에 보이는 글자(제목·버튼·칸 이름·빈 화면·오류)가 영어인가, 개발 용어(Submit·ID·null·CRUD·Dashboard)가 보이나.
- 판정: 영어·개발 용어가 화면에 보이면 손볼 것(오늘 — 디자인 통일과 함께 회사 말로). 회사 말은 1차 인터뷰 축약에서 대표에게 확인한 말을 쓴다("이 화면을 '접수'라고 부르시는 것 맞죠?"·"'납품 건'이라고 부르시죠?" 처럼 — 말은 그 회사 것).
- 코드 안 이름(변수·파일 이름)은 바꾸지 않는다. 화면에 보이는 글자만.

## 10. 휴대폰 375 폭

- 보는 것: 캡처 375장에서 좌우로 밀리는 곳 · 잘린 글자 · 손가락으로 누르기 작은 버튼. 스크립트의 "표 머리 칸 5개 이상"·"고정 폭"·"좁은 화면 규칙 없는 격자"는 **어디를 먼저 볼지** 알려 주는 단서다 — 판정은 캡처로 한다.
- viewport 설정을 스크립트가 못 찾았으면 "없음"이 아니라 "확인 못 함"이다(Next 등은 자동으로 넣는다) — 375 캡처에서 PC 화면이 줄어 보이면 그때 손볼 것.
- 판정: 밀림·잘림이 있으면 손볼 것(오늘 — 화면 재배치에서 카드로 접기). 캡처를 못 찍었으면 "판정 불가 — 실행 불가" 또는 "판정 불가 — 사진 도구 없음"으로 적는다. 짐작으로 좋음을 적지 않는다.

## 12. 변경 전 빌드 (회귀 구분용 — 진단표 밖 별도 절)

- 절차 4에서 고치기 전에 `npm run build` 를 한 번 돌려 진단 문서 「변경 전 빌드」에 결과(성공 / 실패 — 오류 첫 줄 원문)를 적는다. `build`·`prebuild` 에 데이터를 바꾸는 명령이 있으면(스크립트 1번) 돌리기 전에 대표에게 묻는다.
- 리빌딩 뒤 빌드가 실패하면 이 기록과 비교해 "원래 있던 문제"와 "이번 변경이 만든 회귀"를 가른다.

## 전 사진(before) 고르는 법

- **첫 화면 + 최대 두 화면** — 대표가 가장 자주 쓴다고 한 화면(대개 목록)과 입력 화면. 설정·도움말 화면은 찍지 않는다.
- 폭은 375·1280 두 가지. 이름은 `before-<화면>` 으로 주고(`--name before-list`), 저장 폴더는 `reports/shots/rebuild-before/`. 후 사진은 같은 화면·같은 폭·`after-<화면>` 으로 찍어 짝을 맞춘다.
- 주소 없이 버튼으로 넘어가는 화면은 `--click "<화면에 보이는 글자>"` 로 찍는다(영어 화면이면 영어 글자 그대로).
- 앱이 안 뜨면 오류 원문을 진단 문서 "실행 기록"에 그대로 적고 **실행 불가**로 둔다. 고쳐서 띄우려고 하지 않는다 — 고르기 전에는 고치지 않는다. 후 사진만 있는 전후 보고서가 된다.

## 진단을 대표에게 말할 때

- 세 줄로 줄여 읽어 준다(진단 문서 "한눈에"). 나쁜 말로 시작하지 않는다 — "만들어 오신 것 중 ○○는 그대로 씁니다"를 한 줄 먼저.
- 치명이 있으면 그것을 첫 줄로. 없으면 "급한 것은 없습니다".
- 파일 이름·코드 이름을 말하지 않는다. "예약 표가 휴대폰에서 옆으로 밀립니다"처럼 화면의 말로.
