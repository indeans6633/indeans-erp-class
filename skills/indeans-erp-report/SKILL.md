# 인디언즈 작업 보고서

**이 스킬의 역할은 "방금 한 작업을 대표에게 보여 주는 것"이다.** 잘 만들었는지 판정받는 일은 `indeans-erp-check`가 한다.

보고서는 `reports/<날짜>-<제목>.html` 파일 한 장이다. **내 컴퓨터 안에서만 만들어지고 어디로도 전송되지 않는다.** Claude Code와 Codex 양쪽에서 같은 방법으로 만든다.

## 언제 쓰나

- 작업을 끝낼 때마다(초안 생성·개선·저장 연결·배포·권한·운영 보고 — 무엇이든).
- 회차 마지막에 "오늘 무엇을 했는지" 한 장으로 남길 때.
- `indeans-erp-check`가 감독 판정·실측을 마친 뒤(그 결과를 보고서에 더한다).

수업 시간에 따로 배우는 주제가 아니다. **다른 스킬이 끝나면서 부르는 기본 동작**이다.

## 시작 전 상태 진단

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 이번에 무엇을 하려 했는지(다음 행동)·미해결 문제 |
| `git status` · `git log --oneline -5` | 방금 무엇이 바뀌었는지. **추측하지 않고 실제 변경을 본다** |
| `reports/` | 오늘 날짜 보고서가 이미 있는지 |
| `company/structure.md` | 화면 이름·회사에서 쓰는 말·"이번에 만들지 않을 것" |
| `package.json` | 앱을 띄우는 명령(보통 `npm run dev`) |
| `.owner/hooks/report.mjs` · `capture.mjs` | 보고서 생성기와 캡처 도구가 설치돼 있는지 |

판정과 분기:

- **바뀐 것 없음** — 커밋도 변경도 없다 → 보고서를 만들지 않는다. "보고할 변경이 없습니다"라고 한 줄로 알리고 멈춘다.
- **오늘 보고서 있음** — 같은 작업의 연장이면 **같은 제목·같은 `--slug`로 다시 만들어** 그 파일을 갱신한다(파일이 하나로 유지된다). 다른 작업이면 새 제목으로 만든다.
- **화면이 안 바뀐 작업**(문서·설정만) → 캡처 없이 글만으로 만든다. 없는 사진을 만들지 않는다.
- **생성기 없음** — `.owner/hooks/report.mjs`가 없다 → 설치기를 다시 돌리게 안내한다.

판정을 한 문장으로 먼저 알린다. 예: "오늘 초안 앱을 만든 변경이 있습니다. 첫 작업 보고서를 만들겠습니다."

## 절차

### 1. 무엇이 바뀌었는지 확인

```
git status --porcelain
git log --oneline -5
git diff --stat HEAD~1
```

- 대화 기억이 아니라 **실제 변경 목록**을 근거로 쓴다. 기억과 다르면 실제를 따른다.
- 바뀐 것을 대표의 말로 묶는다. 예: 파일 세 개가 바뀌었어도 대표에게는 "목록 화면 한 곳"이다.

### 2. 화면 사진 찍기 (화면이 바뀐 작업만)

앱을 다른 창에서 띄운 뒤 찍는다.

```
npm run dev
```

터미널에 찍힌 주소를 그대로 쓴다(5173이 쓰이고 있으면 5174로 뜬다 — 짐작하지 않는다).

```
node .owner/hooks/capture.mjs --url http://localhost:5173 --path "/" --name list
```

- 폭은 휴대폰(375)·PC(1280) 두 장이 기본이다. 사진은 `reports/shots/<날짜>/`에 쌓인다.
- **보고서에 넣는 것은 1~3장.** 많이 넣으면 대표가 안 본다. 바뀐 화면만 고른다.
- 이 스크립트는 화면이 낸 오류도 함께 알려 준다. **오류가 있으면 보고서의 "남은 문제"에 적는다** — 조용히 넘기지 않는다.
- 캡처 도구가 없다고 나오면(종료 코드 3) 사진 없이 진행하고, 마지막에 설치 방법을 한 줄로 안내한다.

### 3. 본문 쓰기

`assets/report.template.md`를 채워 임시 파일에 쓴다. 따옴표·줄바꿈이 섞이므로 **명령에 본문을 직접 붙여 넣지 않고 파일로 넘긴다.**

```
.owner/tmp/report-body.md
```

문장 규칙(이 스킬의 핵심이다):

- **전엔 / 후엔 / 왜** 세 줄로 쓴다. 바뀐 것마다 이 세 줄.
- 화면은 **회사에서 부르는 이름**으로 쓴다(`structure.md`의 이름).
- **쓰지 않는 말**: 컴포넌트, 함수, 변수, 상태(state), 커밋, 리팩터링, 마이그레이션, 라우팅, 타입, 배열, 훅, API. 파일 경로(`src/screens/…`)와 커밋 번호도 쓰지 않는다.
- 바꿔 쓰는 말: "화면", "목록", "입력 칸", "저장해 두는 곳", "되돌릴 지점", "정리했습니다".
- 대표가 한 말을 인용하면 그대로 쓴다. 요약하지 않는다.
- 안 된 것·못 한 것을 반드시 적는다. 잘된 것만 적은 보고서는 다음 회차에 대표를 속인다.
- 분량은 화면 한 눈에 읽히는 정도. 한 절에 다섯 줄을 넘기지 않는다.

### 4. 보고서 만들기

```
node .owner/hooks/report.mjs --title "오늘 현황 화면 추가" --body .owner/tmp/report-body.md \
  --shot reports/shots/2026-09-18/list-375.png --caption "휴대폰에서 본 목록" \
  --shot reports/shots/2026-09-18/list-1280.png --caption "PC에서 본 목록"
```

- `--title`은 대표가 목록에서 보고 알아볼 제목이다. 회사 말로, 열 자 안팎.
- 사진 경로는 **실제로 찍힌 파일 이름**을 쓴다(캡처 명령이 끝에 목록을 찍어 준다).
- 같은 파일을 갱신하려면 `--slug`를 처음과 같게 준다.
- 만들어지면 브라우저가 열린다. 안 열리면 나온 경로를 대표에게 알려 주고 직접 열게 한다(`node .owner/hooks/open.mjs <경로>`).
- 만든 뒤 임시 본문 파일(`.owner/tmp/report-body.md`)은 지운다.

### 5. 대표에게 보여 주고 한 줄 받기

보고서가 열리면 묻는다(질문 1개): **"여기 적힌 것 중에 사실과 다른 데가 있을까요?"**

- 다르다고 하면 본문을 고쳐 **같은 제목·같은 `--slug`로 다시 만든다.**
- 대표가 새 요청을 하면 그것은 다음 작업이다. 이 보고서에 넣지 않는다.

### 6. 상태 문서 갱신과 커밋

`.owner/state.md`와 `.owner/progress.json`을 갱신한다.

- `state.md` → "현재 기능"에 이번에 된 것, "미해결 문제"에 보고서의 남은 문제, "다음 행동"에 다음 스킬.
- `progress.json` → 해당 값과 `updated_at`.

```
git add -A
git commit -m "작업 보고서 — 오늘 현황 화면 추가"
```

**`.owner/last-check.json`은 건드리지 않는다.** 그 표식은 `indeans-erp-check`가 감독 판정·실측까지 마친 뒤에만 갱신한다. 보고서만 만들고 표식을 갱신하면 검수를 건너뛴 것이 된다.

## 산출물

| 경로 | 내용 |
|---|---|
| `reports/<날짜>-<제목>.html` | 작업 보고서 한 장(브라우저로 열린다) |
| `reports/shots/<날짜>/…` | 화면 사진(휴대폰·PC) |
| `.owner/state.md`·`.owner/progress.json` | 갱신 |
| 커밋 1개 | `작업 보고서 — {제목}` |

보고서는 회차마다 `reports/`에 쌓인다. 최종 회 시연에서 이 폴더를 순서대로 열면 두 달간의 변화가 그대로 보인다.

## 하지 않는 것

- 판정. 승인·반려는 감독 에이전트가 한다(`indeans-erp-check`).
- 코드 수정. 보고서를 쓰다가 문제를 발견하면 보고서에 적고, 고치는 것은 다음 작업으로 둔다.
- `.owner/last-check.json` 갱신.
- 사진 없는데 있는 것처럼 쓰기. 못 찍었으면 "사진은 못 찍었습니다"라고 적는다.
- 잘된 것만 적기. 안 된 것·남은 문제를 같은 무게로 적는다.
- 코드 용어·파일 경로·커밋 번호 쓰기.
- 고객 실명·연락처·금액이 보이는 화면 캡처. 예시 데이터 화면으로 찍는다.
- 보고서를 어디로 보내기(메일·메신저·업로드). 이 스킬은 파일 한 장만 만든다. 정해진 시각에 채널로 받는 보고는 3회차의 `indeans-erp-digest`다.
- 한 보고서에 여러 작업 몰아 넣기. 작업 하나에 보고서 하나다.

## 앞선 수강생 분기

보고서를 이미 여러 장 만들어 본 대표에게는 아래 중 하나를 제안한다.

1. **직원에게 보여 줄 판** — 같은 내용을 "이번 주부터 이렇게 하세요" 문장으로 다시 써서 직원용 보고서를 한 장 만든다. 화면 사진만 그대로 쓴다.
2. **회차 요약** — 그 회차의 보고서 세 장을 한 장으로 묶는다(제목·한 줄 요약만 모은다). 최종 회 시연 대본의 뼈대가 된다.
3. **전·후 나란히** — 바꾸기 전 사진을 미리 찍어 두고 같은 화면의 전·후를 나란히 넣는다. 대표가 가장 빨리 이해하는 형태다.

## 자주 막히는 지점

- **본문에 따옴표·줄바꿈이 많아 명령이 깨진다** → 본문은 항상 파일로 넘긴다(`--body <파일>`). 명령 줄에 본문을 붙여 넣지 않는다.
- **사진이 보고서에 안 나온다** → 경로가 틀렸다. 캡처 명령이 끝에 찍어 준 파일 목록을 그대로 복사해 쓴다. 없는 경로는 건너뛰고 만들어지므로 조용히 빠진다.
- **브라우저가 안 열린다** → 나온 경로를 `node .owner/hooks/open.mjs <경로>`로 다시 열거나, 파일을 두 번 눌러 열게 안내한다.
- **보고서가 계속 새 파일로 쌓인다** → 같은 작업의 갱신이면 `--slug`를 같게 준다.
- **무엇을 적을지 모르겠다** → `git diff --stat`을 보고 "이 변경이 대표에게 어떤 차이로 느껴지나"만 쓴다. 파일 이름을 나열하지 않는다.
- **대표가 "무슨 말인지 모르겠다"고 한다** → 코드 용어가 남아 있는 것이다. 그 문장을 지우고 화면에서 무엇이 달라 보이는지로 다시 쓴다.
