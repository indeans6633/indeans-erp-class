# 인디언즈 앱 진단·개선

**이 스킬의 역할은 "가져온 앱 진단·개선"이다.** 회차 사이에 대표와 직원이 실제로 써 본 앱을 열어 무엇이 막혔는지 찾고, 그중 1~2건을 고친다.

고친 것을 감독에게 판정받고 검증 캡처까지 남기는 일은 **`indeans-erp-check`** 가 한다. 무엇을 고칠지 정하는 자리가 여기고, 고친 것이 맞는지 보는 자리가 거기다. 둘을 겹쳐 하지 않는다.

## 언제 쓰나

- 회차를 시작할 때. 지난 회차 이후 써 본 결과를 받아 1~2건을 고친다(2회차 첫 실습, 이후 회차 공통).
- "써 보니 이게 안 된다", "직원이 여기서 멈춘다"는 말이 나왔을 때.

쓰지 않는 경우: 지금 당장 앱이 안 돌아가는 고장 하나(→ `indeans-erp-routine` 의 `references/one-problem.md`), 바꾼 것을 검수받는 일(→ `indeans-erp-check`), 저장·배포(→ `indeans-erp-data`).

## 시작 전 상태 진단

먼저 읽고 판정한다. 읽기 전에 말을 걸지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · 선택한 디자인 · **미해결 문제** · 다음 행동 |
| `.owner/progress.json` | 어느 회차·어느 스킬까지 끝났나 |
| `company/log.md` | 회차 사이 세 줄 기록(시도한 업무 · 막힌 지점 · 원하는 변화) |
| `company/structure.md` | 화면 목록 · 한 건에 적는 항목 · **이번에 만들지 않을 것** |
| `company/profile.md` | 업종, 회사가 실제로 쓰는 말 |
| `company/flows.md` | 첫 업무 흐름의 단계 순서·담당·완료 증거 |
| `src/` 아래 화면 파일이 모인 폴더 | 화면 개수·이름, 입력 폼, 화면 사이 이동 |
| 저장 담당 파일(`storage`·`store`·`db`·`supabase` 중 하나로 이름 붙은 파일) | 지금 어디에 저장되나 |
| `package.json` · `.owner/last-check.json` | 실행 명령(보통 `npm run dev`), 마지막 검수 시점 |

**폴더·파일 이름이 다를 수 있다.** `screens` 가 없으면 `pages`·`views`·`routes` 를 찾는다. 지정한 이름이 없다고 "없음"으로 판정하기 전에 `src/` 아래를 한 번 훑는다.

**상태 문서가 코드·배포와 다르면 문서를 믿지 않는다.** 실제를 확인해 `.owner/state.md` 를 먼저 고치고 시작한다. 예: 문서에는 "배포 완료"인데 주소가 없으면 그 줄을 지운다.

판정과 분기:

- **미완** — 화면이 없거나 `npm run dev` 가 실패한다 → 개선이 아니라 **복구**부터. "지금 무엇이 안 되나요?" 한 가지만 물어 그것만 고친다. 화면이 열리면 절차 1로 돌아온다.
- **기본** — 화면이 열리고 예시 데이터가 보인다 → 절차 0부터 순서대로.
- **앞선** — 앱이 돌고 **실제 업무로 며칠 이상 써 봤다** → 절차 1~3을 15분 안에 끝내고 「앞선 수강생 분기」에서 주제 하나를 고른다.

판정을 한 문장으로 말하고 시작한다. 예: "화면이 다 열리고, 지난 회차 기록에 막힌 지점이 두 줄 있습니다. 그것부터 보겠습니다."

## 절차

### 0. 되돌릴 지점 만들기

```bash
git add -A
git commit -m "개선 전 상태 저장"
```

`git rev-parse --show-toplevel` 과 현재 폴더를 나란히 찍어 **두 경로가 같은지** 먼저 본다(윈도우는 `/` 와 `\`, 대소문자가 섞여 눈으로만 보면 틀리기 쉽다). 다르거나 오류가 나면 이 폴더에서 `git init` 부터 한다.

대표에게는 이렇게 말한다: "지금 모습을 사진 찍어 뒀습니다. 고치다 잘못돼도 여기로 돌아옵니다."

### 1. 세 줄 기록을 먼저 읽는다

이 절차를 건너뛰지 않는다. **대표가 회차 사이에 실제로 겪은 것이 오늘 고칠 것의 출발점**이고, 같은 기록이 최종 회 시연의 재료가 된다.

읽는 순서: `company/log.md` → 없으면 `.owner/state.md` 의 '미해결 문제'.

**기록이 있으면** 세 줄을 대표에게 그대로 읽어 주고 확인한다: "지난번에 이렇게 적어 두셨습니다. 지금도 같습니까?"

**기록이 없으면** 그 자리에서 받는다. 한 번에 하나씩 묻는다.

1. > "지난번 이후로 이 앱으로 **해 보려 한 업무**가 무엇이었나요?"
2. > "그중에 **막힌 지점**은 어디였나요? 손으로 하거나 그만둔 자리요."
3. > "그게 어떻게 **바뀌면** 되겠습니까?"

받은 세 줄을 `assets/log.template.md` 형식으로 `company/log.md` 맨 위에 추가한다(최신이 위). 대표의 말을 요약하지 말고 그대로 넣는다.

직원이 겪은 것을 대표가 옮겨 말하면 사실이 흐려진다. 그때는 그렇게 표시한다: `막힌 지점: (직원 말 전달) ...`

### 2. 막힌 자리를 앱에서 다시 해 본다

`npm run dev` 로 앱을 띄우고, **1번에서 나온 그 업무를 대표가 직접 다시 해 본다.** 코드를 읽어 추측하기 전에 화면에서 한 번 재현한다.

- 재현되면 그 화면·그 버튼이 개선 1번 후보다.
- 재현되지 않으면 되는 경우와 안 되는 경우의 차이를 찾는다(다른 계정? 다른 값? 폰에서만?). 차이를 못 찾으면 이번에는 고치지 않고 `company/log.md` 에 관찰 항목으로 남긴다.

### 3. 분석 — 네 가지만 본다

`references/review-checklist.md` 를 읽고 아래 네 묶음으로 목록을 만든다. 코드를 읽어 근거를 찾되, 대표에게는 **화면의 말**로 설명한다.

1. **화면이 할 일을 하나** — `company/structure.md` 의 화면 목록과 실제 화면이 같나. 한 화면이 두 역할을 겸하고 있지 않나.
2. **흐름 끊김** — 입력을 마치면 어디로 가나. `company/flows.md` 의 단계 중 앱에 없는 단계는 무엇인가.
3. **입력 불편** — 필수 칸이 몇 개인가(폰에서 5개를 넘으면 표시). 오늘 날짜·담당자 같은 기본값이 비어 있나. 같은 값을 두 번 넣게 하나.
4. **이름 불일치** — `company/profile.md` 의 용어와 화면 라벨이 다른 곳. 같은 것을 두 이름으로 부르는 곳.

출력은 표 하나로 만든다. 항목마다 한 줄이다.

| 번호 | 묶음 | 증상(대표의 말로) | 어디(화면·파일) | 불편한 정도 |
|---|---|---|---|---|

불편한 정도는 **매일 걸린다 / 가끔 걸린다 / 언젠가 걸린다** 셋 중 하나로만 쓴다. 숫자로 매기지 않는다.

표는 **다섯 줄을 넘기지 않는다.** 넘으면 '매일 걸린다'만 남기고 나머지는 계획서 4절(오늘 안 하기로 한 것)로 내린다. 자주 나오는 문제와 그 자리에서 쓰는 지시문은 `references/common-fixes.md` 에 있다.

**`company/structure.md` 의 '이번에 만들지 않을 것' 에 적힌 항목은 개선 후보에 올리지 않는다.** 대표가 다시 요청하면 그때 그 줄을 지우고 올린다.

### 4. 개선 인터뷰 — 한 번에 하나, 다섯 문항 이내

표를 3~5줄로 줄여 보여 준 뒤 시작한다. **한 번에 한 질문만** 하고, 답을 받은 다음 질문을 정한다.

- **Q1(필수)** "이 중에서 **가장 불편한 것 하나만** 고르면 무엇인가요?"
  - "전부 다"라고 하면 되묻는다: "어제 이 앱으로 하려다 손으로 하신 일이 있나요? 그게 1번입니다."
- **Q2(필수)** "그게 불편할 때 지금은 어떻게 하세요? 그냥 참으시나요, 다른 걸로 하시나요?"
  - "엑셀로 따로 적는다" 계열이면 그 엑셀 칸이 곧 부족한 입력 칸이다.
- **Q3** "그게 고쳐지면 무엇이 달라져야 합니까? 화면으로 말씀해 주세요."
  - 눈으로 확인할 수 있는 문장이 나와야 한다. "편해진다"는 확인 기준이 못 되니 한 번 더 묻는다: **"고쳐진 다음에 무엇이 보이면 '됐다'고 하시겠어요?"**
- **Q4** "이 일을 대표님 말고 다른 사람도 하나요? 한다면 그 사람 화면도 같이 고쳐야 할까요?"
- **Q5** "하나만 더 고칠 수 있다면 두 번째는 무엇인가요?"

고칠 1~2건과 확인 기준이 나오면 거기서 멈춘다.

**멈추는 규칙**: 답이 "표를 하나 더 만들어야 한다", "칸을 새로 추가해야 한다" 계열이면 저장하는 모양이 바뀐다는 뜻이다. 그 항목에 `데이터 영향: 있음` 을 표시한다. `indeans-erp-data` 가 표를 만들 때 이 표시를 읽는다.

### 5. 개선 계획서 쓰기

`assets/improve-plan.template.md` 를 그대로 채워 `company/improve-plan.md` 로 저장한다(이미 있으면 맨 위에 이번 회차 절을 추가하고 지난 내용은 지우지 않는다). 항목마다 반드시 있어야 하는 것:

- **전** — 지금 어떻게 되어 있나(대표가 겪은 말로).
- **후** — 고치면 어떻게 되나(눈으로 확인 가능한 문장으로).
- **확인 방법** — 대표가 직접 누르는 순서 3단계 이내.
- **데이터 영향** — 있음/없음.
- **되돌릴 지점** — 0단계에서 만든 커밋.

계획서를 보여 주고 "이대로 고칠까요?"를 묻는다. **승인 전에는 코드를 고치지 않는다.**

### 6. 개선 적용 — 한 번에 한 건

1. 1번 항목만 고친다. 고친 뒤 앱을 띄워 **대표가 직접** 확인한다.
2. 통과하면 커밋한다: `git commit -am "개선 1: <한 줄 요약>"`. 그다음 계획서의 '커밋' 칸에 번호를 적고 그 변경도 커밋한다.
3. 그다음 2번 항목으로 넘어간다. 두 건을 한꺼번에 고치지 않는다 — 문제가 생겼을 때 어느 쪽 때문인지 모르게 된다.

지키는 범위:

- 화면 이름·항목 이름은 **회사가 쓰는 말**로 바꾼다. 영어로 바꾸지 않는다.
- 고른 디자인 방향(`src/styles/tokens.css`)은 건드리지 않는다. 색과 모양을 바꾸는 것은 개선이 아니다.
- 새 화면을 추가하는 개선은 하지 않는다. 예외: 3단계에서 "이 단계가 앱에 아예 없다"가 1번으로 뽑혔을 때.
- 예시 데이터는 지우지 않는다. 화면이 안 나올 때 비교할 기준이 된다.

### 7. 확인 — 대표가 직접 눌러 본다

"다 됐습니다"로 끝내지 않는다. 계획서의 **확인 방법**을 대표에게 읽어 주고 그대로 하게 한다.

1. 앱을 새로고침한다.
2. 계획서에 적은 순서대로 누른다.
3. "후" 문장이 실제로 보이는지 대표가 말한다.

통과하면 계획서의 해당 줄에 `완료(날짜)` 를 적는다. 통과 못 하면 **되돌리기 전에 한 가지만 먼저 본다: 확인 방법에 적은 순서가 실제 화면과 같은가**(칸 이름·버튼 이름). 확인 방법이 틀린 것을 앱이 틀린 것으로 오해해 멀쩡한 개선을 되돌리는 일이 흔하다. 그래도 안 되면 되돌리고(`git reset --hard <커밋>`) 무엇이 달랐는지 계획서에 한 줄 남긴다. 되돌리는 것은 실패가 아니라 절차다.

### 8. 검수로 넘긴다

화면·저장·권한 중 하나라도 바뀌었으면 **`indeans-erp-check` 를 호출한다.** 감독 판정 → 검증 캡처 → 작업 보고서까지 그 스킬이 이어서 한다.

문구·주석만 바꿨으면 호출하지 않아도 된다. 판단이 애매하면 호출한다 — 검수를 한 번 더 도는 비용이 못 본 채 배포하는 비용보다 싸다.

### 9. 상태 문서 갱신과 커밋

`.owner/state.md` 의 네 절을 고친다.

- **현재 기능** — 이번에 고친 것을 한 줄 추가.
- **선택한 디자인** — 건드리지 않았으면 그대로.
- **미해결 문제** — 해결한 줄은 지운다. 오늘 안 하기로 한 것과 재현 안 된 것은 남긴다.
- **다음 행동** — 이번 회차의 다음 단계(예: "저장·배포(`indeans-erp-data`)").

`.owner/progress.json` 의 `open_problems`(남은 것)·`next_action`(다음 행동)·`updated_at` 을 고친다. 없는 키를 새로 만들지 않는다 — 템플릿에 있는 키만 쓴다.

```bash
git add -A
git commit -m "진단·개선 <N>건과 상태 갱신"
```

## 산출물

| 경로 | 내용 | 템플릿 |
|---|---|---|
| `company/log.md` | 회차 사이 세 줄 기록(최신이 위) | `assets/log.template.md` |
| `company/improve-plan.md` | 분석 표 · 개선 항목(전/후/확인/데이터 영향) · 완료 표시 | `assets/improve-plan.template.md` |
| 코드 변경 | 개선 1~2건, 항목마다 커밋 1개 | — |
| `.owner/state.md` · `.owner/progress.json` | 갱신 | — |

## 하지 않는 것

- 세 줄 기록을 읽지 않고 개선 항목을 고르지 않는다. 앱을 훑어 나온 문제보다 **실제로 막힌 자리**가 먼저다.
- 대표가 고르지 않은 것을 "겸사겸사" 고치지 않는다. 눈에 띈 코드 문제도 계획서에 적어만 두고 넘어간다.
- `company/structure.md` 의 '이번에 만들지 않을 것' 을 대표 승인 없이 되살리지 않는다.
- 감독 판정·검증 캡처를 이 스킬에서 흉내내지 않는다. `indeans-erp-check` 를 부른다.
- 저장·배포·권한 설계를 여기서 하지 않는다(`indeans-erp-data`·`indeans-erp-people`).
- 디자인 전면 교체, 라이브러리 추가, 폴더 구조 재편은 하지 않는다.
- 대표의 말을 요약해 바꿔 쓰지 않는다. 그대로 적는다.

## 앞선 수강생 분기

상태 진단이 **앞선**이면 아래 셋 중 대표가 하나를 고른다. 오늘 끝나는 크기로만 한다.

1. **검색·재입력·인계 병목** — 건수가 늘면 목록에서 찾는 데 걸린다. 검색 칸 하나 또는 상태 필터 하나를 넣고, 같은 값을 두 번 넣는 자리를 없앤다.
2. **직원이 멈추는 자리** — 직원에게 물을 질문 3개(무슨 화면 · 무엇을 눌렀나 · 화면에 뜬 글자)를 만들어 대표가 받아 오게 한다. 다음 회차 1번 후보가 여기서 나온다.
3. **놓치는 지점 표시** — 사람이 잊어서 새는 지점 하나를 고른다(예: 정해진 날이 지났는데 다음 단계로 안 넘어간 건). 앱 안 배지나 목록 맨 위 줄로만 표시한다. 채널로 보내는 것은 `indeans-erp-digest` 다.

## 자주 막히는 지점

- **"전부 다 불편하다"** — 목록을 더 보여 주지 말고 어제 손으로 한 일을 묻는다. 손으로 한 일이 1번이다.
- **세 줄 기록이 비어 있다** — 못 써 온 것이 아니라 못 써 본 것이다. "왜 못 써 보셨나요?"를 물으면 그 답이 1번 개선 항목이다(대개 로그인·주소·속도).
- **고쳤는데 화면이 그대로다** — 새로고침, 그다음 `npm run dev` 재시작. 그래도 그대로면 고친 파일이 실제로 쓰이는 파일인지 확인한다(같은 이름의 화면이 두 개인 경우가 흔하다).
- **고치자 다른 데가 깨졌다** — 원인을 찾기 전에 되돌린다. 되돌린 다음 한 번에 한 가지만 다시 고친다.
- **대표가 "이것도 해 주세요"를 계속 낸다** — 거절하지 말고 계획서 맨 아래 "다음에" 칸에 적는다. 오늘의 1~2건은 그대로 간다.
- **화면 말을 바꿨더니 코드가 깨졌다** — 화면에 보이는 글자만 바꾸고 코드 이름은 그대로 둬도 된다. `company/profile.md` 의 용어표에 "화면에서는 이렇게 부른다"를 적어 둔다.
- **예시 데이터가 우리 회사와 너무 다르다** — 이것 자체가 1번 개선 후보다. 예시 데이터를 회사 말로 바꾸면 남은 문제의 절반이 눈에 보인다.
