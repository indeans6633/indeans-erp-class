# 인디언즈 주간 점검·복구 실습·30일 계획

실사용 준비 단계 실습. 회사 앱은 만들고 끝나는 물건이 아니라 **매주 조금씩 고쳐 나가는 도구**다. 이 스킬은 실사용을 시작하기 전에 세 가지를 끝내고, 그 뒤로 매주 돈다.

1. **주간 점검 루틴** — 요일과 시각을 정하고 첫 회를 그 자리에서 한 번 돈다.
2. **복구 실습** — 백업에서 실제로 한 줄을 되돌려 본다(1회, 생략하지 않는다).
3. **30일 계획** — 다음 30일에 고칠 3건과 멈추는 기준.

검수 체계(감독 2종·검증자·검수 훅·배포 직전 훅)는 1회차 설치 직후부터 이미 돌고 있다. **오늘 새로 켜는 것이 아니다.** 오늘 더해지는 것은 **매주 도는 자리** 하나다: 감사관(`erp-auditor`)이 데이터와 정책의 실태를 보고, 판례 노트가 같은 실수를 규칙으로 바꾼다. 인디언즈도 자체 앱을 이렇게 돌린다 — 되돌리기 어려운 것은 배포 전에, 되돌릴 수 있는 것은 주간 점검에서 모아서 본다.

## 언제 쓰나

- 실사용을 시작하기 전 — 세팅 모드.
- 수료 후 매주 정해진 요일에(30~60분) — 실행 모드. **알림 훅(`.owner/hooks/erp-reminder.mjs`)이 새 대화를 열 때 7일이 넘었으면 알려 준다.**
- 앱을 쓰다가 불편한 것이 여러 개 쌓였을 때, 판례 노트에 승격 대기 줄이 생겼을 때.

**급한 고장 하나를 당장 잡아야 하면** 이 루틴을 기다리지 않는다. `references/one-problem.md` 의 순서(증상 → 재현 → 되돌릴 지점 → 원인 → 최소 수정 → 확인 → 기록)를 따른다.

쓰지 않는 경우: 회차 사이에 써 본 것을 받아 개선하는 자리(→ `indeans-erp-review`), 최종 회 시연 준비(→ `indeans-erp-showcase`).

| 상태 | 판정 기준 | 분기 |
|---|---|---|
| A. 세팅 | `company/routine.md` 없음 | **세팅 모드** — 절차 0~5 |
| B. 실행 | 마지막 점검이 7~14일 전 | **실행 모드** — 일곱 단계 |
| C. 밀림 | 15일 이상 / 기록 없음 | 밀린 주를 소급해 쓰지 않는다. **이번 주 한 건만** 하고 공백 사유를 한 줄 |
| D. 복구 미실습 | `backup.md` 6절이 비어 있음 | 실행 모드라도 **복구 실습을 먼저** |
| E. 배포 전 | 배포 주소 없음 | 화면이 내 컴퓨터에서 열리면 캡처는 그대로, 내려받기 버튼이 있으면 복구 실습도 그대로. 정말 못 하는 것만 "해당 없음 — 이유" |

판정을 두세 줄로 보고한 뒤 시작한다.

## 절차 — 세팅 모드

### 0. 되돌릴 지점

```bash
git add -A && git commit -m "주간 점검 루틴 세팅 전"
```

### 1. 루틴 정하기 (질문 둘)

1. > "매주 언제 30분을 앱 점검에 쓰시겠습니까? **요일과 시각**으로 정해 주세요."
2. > "그 시간에 앱을 가장 많이 쓰는 분이 같이 앉을 수 있습니까? 혼자라면 혼자라고 답해 주세요."

"시간 날 때"는 정한 것이 아니다. 정해지면 **달력 반복 일정**에 넣게 안내하고, 알림 훅이 7일 넘으면 새 대화에서 알려 준다고 말한다. `assets/routine.template.md` 를 `company/routine.md` 로 채운다.

### 2. 복구 실습 — 백업에서 한 줄 되돌리기 (1회, 생략 금지)

목적은 **되돌릴 수 있다는 것을 몸으로 아는 것**이다. 순서는 `company/backup.md` 5절을 그대로 쓴다.

1. 앱에서 내려받기 버튼으로 파일을 받는다. **파일을 열어 내용이 들어 있는지, 줄 수가 앱 전체 건수와 같은지** 본다.
2. 지울 줄을 고른다. **반드시 예시 데이터 한 줄** — "이 줄은 지워도 되는 연습용 줄입니까?" 답을 받은 뒤에.
3. 앱에서 그 줄을 지우고 → 목록에서 사라진 것을 확인하고 → 파일을 보고 **다시 입력**하고 → 돌아왔는지 확인한다. **걸린 시간**을 잰다.

`company/backup.md` 6절에 적는다: `<날짜> / 1줄 되살리기 <N>분 / 막힌 것: <그대로> / 그래서 고칠 것: <후보>`. **막힌 것이 곧 다음 개선 항목이다.** 표가 통째로 날아간 경우의 복구는 **읽기만 한다** — 실습으로 표를 지우지 않는다.

### 3. 30일 계획 (질문 다섯)

1. > "앞으로 30일 안에 고치고 싶은 것을 딱 하나만 고른다면 무엇인가요?" 2. > "그다음은요?"(셋째까지)
3. > "이 앱을 누가, 어디까지 쓰게 하실 건가요?"
4. > "데이터가 다 날아가면 무엇이 가장 아깝습니까?" (`backup.md` 1절이 있으면 **다시 묻지 말고 읽어 주고 바뀐 것만**)
5. > "지금 앱 때문에 매달 나가는 돈이 얼마인지 알고 계신가요?" (청구 전이면 "아직 없음 — 가입하는 날 무료 범위 숫자를 여기 적는다")

- 개선 3건은 각각 **한 주 안에 끝나는 크기.** 크면 "하나의 화면, 한 번의 수정으로 줄이면 무엇이 남습니까?"
- 끝 기준이 없으면 "그게 다 됐으면, 어느 화면을 열어서 무엇을 보면 '됐구나' 하실까요?"
- 복구 실습의 '막힌 것'을 후보에 넣는다. `assets/plan-30d.template.md` 를 `company/plan-30d.md` 로.

**실사용을 시작하기 전에 두 가지를 같이 챙긴다.**

- **가치 가설 시작값** — `company/roadmap.md` 의 가치 가설 시작값을 실사용 시작 전에 직접 재서 적는다. 시작값이 `(어림)` 이면 정해 둔 방법(누가·언제·무엇으로)으로 대표가 직접 세어 `(잰 값 <날짜>)` 로 고친다 — AI 가 지어 넣지 않는다. 가치 가설이 비어 있으면 `indeans-erp-interview` 의 미뤄 둔 질문(3-9 가치 가설)부터 묻게 한다.
- **요금제** — 실사용을 시작할 때 Supabase 는 Pro(월 $25)를 권한다(무료는 1주일 미사용 정지 · 프로젝트 2개 · 자동 백업 없음). Vercel 무료(Hobby)는 개인·비상업 용도라 회사에서 계속 쓰려면 Pro(월 $20) 전환이 약관상 맞다. 바꿀지·언제는 대표가 정하고 `plan-30d.md` 4절(비용)에 적는다 — AI 가 대신 결제하거나 정하지 않는다.

### 4. 첫 회를 그 자리에서 한 번 돈다

세팅으로 끝내지 않는다. 아래 일곱 단계를 **오늘 한 번** 돈다. 개선 1건은 `plan-30d.md` 1번이나 복구 실습에서 나온 것.

### 5. 상태 문서 갱신과 커밋

`.owner/state.md` — 다음 행동: "2주 실사용 + 매주 <요일> 점검, 최종 회 시연 준비(`indeans-erp-showcase`)". `.owner/progress.json` — `open_problems`·`next_action`·`updated_at`. 회차 완료 표시는 그 회차 `course/session-0N/outcomes.md` 의 필수 결과가 모두 확인됐을 때만.

```bash
git add -A && git commit -m "주간 점검 루틴·복구 실습·30일 계획"
```

## 실행 절차 — 매주 일곱 단계

### 1) 감사와 오류 모음

**감사 먼저.** `erp-auditor` 를 부른다(1차: 읽기 전용 질의 `.owner/tmp/audit.sql` → 대표가 SQL Editor 에서 실행해 결과를 `.owner/tmp/audit-result.csv` 로 저장 → 2차: 결과 읽기). 감사 기록은 `reports/<날짜>-감사.md`(건수·행 id 만). **치명**이 있으면 이번 주 개선 1건은 그것이다.

그다음 대표에게:

> "지난 한 주 동안 앱을 쓰다가 '어?' 했던 순간을 하나씩 말씀해 주세요. 사소해도 괜찮습니다."

나온 것마다 네 칸 — 증상(대표의 말 그대로) · 기대 · 실제 · 재현 순서. 모르는 칸은 AI가 앱을 읽고 **추정이라고 표시해서** 채운다. **못 재현하는 것은 이번 주에 고치지 않는다.** 자주 나오는 증상은 `references/common-problems.md`.

### 2) 이번 주 개선 1건 — 요구와 계획 대조

모인 것 중 **한 건만** 고른다(위에서부터): ① 감사 치명 · 데이터가 잘못 저장되는 것 · 못 봐야 할 사람에게 보이는 것 ② 매일 쓰는 화면의 불편 ③ 가끔 쓰는 화면의 불편 ④ 있으면 좋은 기능 → 미룬다.

고른 뒤 대표의 요구를 **그대로 옮겨 적고** 계획을 세워 대조한다.

| 요구 원문(대표의 말) | 계획의 어느 줄이 이걸 하나 | 판정 |
|---|---|---|
| "<원문>" | <계획 항목> | 그대로 / 줄임 / 바꿈 / 빠짐 |

'줄임·바꿈·빠짐'이 하나라도 있으면 진행 전에 알린다: "말씀하신 것 중 이 부분은 이번 주에 하지 않으려 합니다. 이유는 <이유>입니다. 괜찮을까요?" 편하다는 이유로 요구를 조용히 줄이거나 바꾸지 않는다 — 이 표가 이 루틴의 핵심이다.

계획이 **돈·권한·데이터 구조**를 건드리면(위험 등급 1) `references/supervisor-checklist.md` 의 계획 컨펌을 먼저 하고, 고친 뒤 `indeans-erp-check` 를 부른다.

### 3) 되돌릴 지점

```bash
git add -A && git commit -m "<개선 제목> 작업 전"
```

커밋 번호(앞 7자리)를 점검 기록에 적는다.

### 4) 확인 캡처

고치기 전과 후를 같은 조건으로 찍는다. 다른 창에서 `npm run dev` 를 띄워 두고:

```bash
node .owner/hooks/capture.mjs --url http://localhost:5173 --path "/" --name before
node .owner/hooks/capture.mjs --url http://localhost:5173 --path "/" --click "<버튼 글자>" --name before-detail
```

버튼을 눌러야 나오는 화면은 `--click` 으로 그 상태를 만든 뒤 찍는다. 찍은 파일을 `company/checkups/screens/<연-주>-before.png`·`-after.png` 로 옮긴다. 고친 뒤 다시 찍을 때는 **바뀐 화면만 375** 로. 화면이 없는 변경이면 **바뀐 값을 눈으로 확인한 결과**를 두 줄로. 캡처 없이 "됐습니다"라고 보고하지 않는다.

### 5) 백업·보고 확인

- 내려받기를 한 번 실행하고 파일 날짜·크기를 적는다. **받은 파일의 줄 수(머리글 빼고)와 앱 전체 건수를 맞춰 본다** — 다르면 백업이 보이는 것만 받고 있다. 그 자리에서 고친다.
- 지난주 파일과 크기가 비슷한지 본다. 갑자기 줄었으면 멈추고 원인을 찾는다. 한 달에 한 번은 파일을 실제로 연다.
- **운영 보고가 매일 왔는지**(`company/digest.md` 6절의 발송 기록 조회). 안 온 날이 있으면 이번 주 1순위다.

### 6) 비용 확인

AI 도구 구독과 클라우드(데이터·배포) 두 줄. 무료 범위 안인지, 지난달보다 늘었는지. `plan-30d.md` 4절이 채워져 있으면 **다시 묻지 말고 옮겨 적은 뒤 바뀐 것만.** 한도를 넘었으면 새 기능을 멈추고 그것부터.

### 7) 두 AI 교차 검토

만든 AI와 **다른 AI**가 읽기 전용으로 요구와 결과를 대조한다. 순서와 요청 문장은 `references/cross-check.md`, 보내는 명령은 `indeans-erp-crosscheck` 의 `references/commands.md`. 검토자에게 주는 것은 **요구 원문 · 바뀐 파일의 코드(비공개 정보 점검 뒤)**뿐이다(만든 쪽의 결론은 주지 않는다). 검토자는 빈 임시 폴더에서 돈다. 결과는 **맞음 / 빠짐 / 바뀜** 중 하나이고, 돈·권한에 걸리는 지적은 `indeans-erp-check` 의 감독 판정으로 넘긴다. 도구가 하나뿐이면 같은 도구의 **새 대화**에서 코드만 보고 검토하게 한다.

### 마무리 — 기록·판례·표식

1. `assets/checkup.template.md` 를 `company/checkups/<연-주>.md` 로 만들어 일곱 단계 결과를 채운다(예: `2026-41.md` — 2026년 41번째 주).
2. **판례 노트** — 이번 주에 반려·되돌림·감사 치명·주의·"고친 줄 알았는데 안 고쳐짐"이 있었으면 `.owner/precedents.md` 에 한 줄씩(형식은 `references/precedents.md`). 같은 유형이 두 번째면 승격 칸을 `대기` 로.
3. **승격** — `대기` 줄이 있으면 이번 주에 처리한다: 기계가 막을 수 있으면 고정 검사(`scripts/migration-gate.mjs`)에 항목을, 판단이 필요하면 `.claude/agents/<이름>.md`·`.codex/agents/<이름>.toml` 양쪽의 "우리 회사 규칙" 절에 확인 절차 한 줄을 더하고 승격 칸을 `완료 — <올린 곳>` 으로(`references/precedents.md` 승격 절).
4. **표식** — `.owner/last-review.json` 을 쓴다. 알림 훅은 이 파일의 `at` 으로 7일을 센다.

```json
{ "at": "2026-10-08T10:30:00+09:00", "period": "2026-41", "record": "company/checkups/2026-41.md", "audit": "이상 없음", "by": "indeans-erp-routine" }
```

5. `.owner/state.md` 의 '미해결 문제'와 '다음 행동'을 고치고 커밋한다: `git add -A && git commit -m "<연-주> 주간 점검"`.

## 하지 않는 것

- 복구 실습을 건너뛰지 않는다. **실제 업무 데이터로 복구 실습을 하지 않는다.** 실습으로 표를 지우지 않는다.
- 한 주에 두 건 이상 고치지 않는다(오타·안내 문구·주석처럼 동작과 데이터가 전혀 안 바뀌는 한 줄 수정은 건수에 넣지 않는다).
- 요구를 임의로 줄이거나 바꾸지 않는다. 재현되지 않는 문제를 추측으로 고치지 않는다.
- 되돌릴 지점 없이 고치지 않는다. 캡처·확인 없이 "고쳤습니다"라고 보고하지 않는다.
- 교차 검토 때 만든 쪽의 결론을 검토자에게 알려 주지 않는다. 감사관에게 고치게 하지 않는다.
- 점검 기록·판례 노트에 고객 실명·연락처·계좌·실제 금액을 적지 않는다. 밀린 주를 지어내 채우지 않는다.
- 에이전트 파일의 기존 규칙을 지우거나 바꾸지 않는다. 승격은 "우리 회사 규칙" 절에 **더하기만** 한다.

## 앞선 수강생 분기

- **점검 스크립트** — 매주 손으로 보던 것 중 기계가 볼 수 있는 것(같은 건이 두 번 저장됐는지, 담당자가 빈 건)을 감사 질의 덩어리에 고정 항목으로 남겨 매주 같은 질의를 돌린다.
- **직원 신고 창구** — 직원이 불편을 그때그때 남길 곳(메모·양식)을 만들고, 1단계에서 그것부터 읽는다.
- **월 1회 깊은 점검** — 넷째 주에는 개선 대신 권한 전수 실측(역할별 계정으로 노출 표 한 바퀴)과 복구 실습을 한 번 더 한다. 돈을 담았으면 맞춰 보는 숫자(`money.md` 9절)도.

## 자주 막히는 지점

- **"이번 주엔 문제가 없었다"** — `plan-30d.md` 의 개선 1건을 가져온다. 그것도 없으면 안 쓰는 화면 하나를 지운다. 루틴은 거르지 않는다.
- **고칠 게 너무 많아 못 고른다** — 2단계의 우선순위로 기계적으로 고른다. 고민 시간을 5분 넘기지 않는다.
- **알림이 매번 뜬다** — 마무리 4번(`last-review.json`)을 빠뜨렸다. 점검을 마쳤으면 그 파일을 쓴다.
- **복구 실습에서 다시 입력이 안 된다** — 파일에 그 칸이 없거나 날짜 형식이 달라서다. 그것이 실습의 성과다. 개선 후보로 올린다.
- **내려받은 파일이 비어 있다** — 버튼이 옛 저장소(예시 데이터)를 읽고 있다. `indeans-erp-data` 7절 7번.
- **감사 결과 파일을 못 만들었다** — SQL Editor 결과 위의 내려받기(CSV)로 받거나, 결과 표를 그대로 복사해 `.owner/tmp/audit-result.txt` 로 저장해도 된다.
- **교차 검토가 서로 다른 말을 한다** — 어느 쪽이 맞는지 AI에게 묻지 말고 **앱에서 직접 확인**한다.
- **설치기를 다시 돌렸더니 에이전트 파일 옆에 `.new` 가 생겼다** — 승격한 규칙이 있어서다. `.new` 를 받아들이고 "우리 회사 규칙" 절만 옮긴다(`references/precedents.md`).
- **두 달째 안 돌았다** — 밀린 것을 채우지 말고 이번 주 것만 한다. 공백 사유 한 줄이면 된다.
