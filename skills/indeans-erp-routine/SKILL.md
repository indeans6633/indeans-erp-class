# 인디언즈 주간 루틴·복구 실습·30일 계획

4회차 뒤 실습. 회사 앱은 만들고 끝나는 물건이 아니라 **매주 조금씩 고쳐 나가는 도구**다. 이 스킬은 실사용을 시작하기 전에 세 가지를 끝낸다.

1. **주간 루틴** — 요일과 시각을 정하고 첫 회를 그 자리에서 한 번 돈다.
2. **복구 실습** — 백업에서 실제로 한 줄을 되돌려 본다(1회, 생략하지 않는다).
3. **30일 계획** — 다음 30일에 고칠 3건과 멈추는 기준.

검수 체계(감독 2종·검증자·훅)는 1회차 설치 직후부터 이미 돌고 있다. **오늘 새로 켜는 것이 아니다.** 무엇이 언제 도는지 궁금하면 `indeans-erp-check` 문서를 같이 읽는다.

## 언제 쓰나

- 4회차(실사용을 시작하기 전) — 세팅 모드.
- 수료 후 매주 정해진 요일에(권장: 주 1회 30~60분) — 실행 모드.
- 앱을 쓰다가 불편한 것이 여러 개 쌓였을 때.

**급한 고장 하나를 당장 잡아야 하면** 이 루틴을 기다리지 않는다. `references/one-problem.md` 의 순서(증상 → 재현 → 되돌릴 지점 → 원인 → 최소 수정 → 확인 → 기록)를 그대로 따른다. 이 스킬은 **모아서 주기적으로** 도는 쪽이다.

쓰지 않는 경우: 회차 사이에 써 본 것을 받아 개선하는 자리(→ `indeans-erp-review`), 최종 회 시연 준비(→ `indeans-erp-showcase`).

| D. 복구 미실습 | `company/backup.md` 6절이 비어 있음 | 실행 모드라도 **절차 2(복구 실습)를 먼저** 한다 |

판정을 두세 줄로 보고한 뒤 시작한다.

## 절차 — 세팅 모드 (4회차)

### 0. 되돌릴 지점

```bash
git add -A && git commit -m "주간 루틴 세팅 전"
```

### 1. 루틴 정하기 (질문 둘)

한 번에 하나씩 묻는다.

1. > "매주 언제 30분을 앱 점검에 쓰시겠습니까? **요일과 시각**으로 정해 주세요."
2. > "그 시간에 앱을 가장 많이 쓰는 분이 같이 앉을 수 있습니까? 혼자라면 혼자라고 답해 주세요."

"시간 날 때"는 정한 것이 아니다. 요일과 시각이 비면 다시 묻는다. 정해지면 그 자리에서 **달력 반복 일정**에 넣게 안내한다.

`assets/routine.template.md` 를 `company/routine.md` 로 옮겨 답을 채운다.

### 2. 복구 실습 — 백업에서 한 줄 되돌리기 (1회, 생략 금지)

목적은 파일을 만드는 게 아니라 **되돌릴 수 있다는 것을 몸으로 아는 것**이다. 순서는 `company/backup.md`(2회차에 만든 문서)의 5절을 그대로 쓴다.

1. 앱에서 내려받기 버튼을 눌러 파일을 받는다. **파일을 열어 내용이 실제로 들어 있는지 눈으로 본다.**
2. 지울 줄을 고른다. **반드시 예시 데이터 한 줄이다.** 실제 업무 데이터로는 하지 않는다 — 대표에게 "이 줄은 지워도 되는 연습용 줄입니까?"를 묻고 답을 받은 뒤에 지운다.
3. 앱에서 그 줄을 지운다.
4. 목록에서 사라진 것을 확인한다.
5. 내려받은 파일을 보고 그 줄을 앱에서 **다시 입력한다.**
6. 목록에 돌아왔는지 확인하고 **걸린 시간**을 적는다.

`company/backup.md` 6절에 이 형식으로 적는다.

```
<YYYY-MM-DD> / 1줄 되살리기 <N>분
막힌 것: <있었던 그대로>
그래서 고칠 것: <다음 개선 후보>
```

**막힌 것이 곧 다음 개선 항목이다.** 예: "파일에 담당자 칸이 없어서 누가 넣은 건지 몰랐다" → 내려받기에 그 칸을 추가한다. 그 항목을 `company/plan-30d.md` 개선 후보로 올린다.

표가 통째로 날아간 경우의 복구는 **읽기만 한다**(`company/backup.md` 5절 아래). 실습으로 표를 지우지 않는다.

### 3. 30일 계획 (질문 다섯)

한 번에 하나씩 묻고, 답을 받은 뒤 다음으로 간다.

1. > "앞으로 30일 안에 고치고 싶은 것을 딱 하나만 고른다면 무엇인가요?"
2. > "그다음은요?" (두 번째, 세 번째까지 받는다)
3. > "이 앱을 누가, 어디까지 쓰게 하실 건가요? 대표님 혼자인가요, 직원까지인가요, 고객도 보나요?"
4. > "데이터가 다 날아가면 무엇이 가장 아깝습니까?" (`company/backup.md` 1절이 이미 채워져 있으면 **다시 묻지 말고 읽어 주고 바뀐 것만 확인한다**)
5. > "지금 앱 때문에 매달 나가는 돈이 얼마인지 알고 계신가요?"

- 개선 3건은 각각 **한 주 안에 끝나는 크기**여야 한다. "전체 개편"·"자동화 전부" 같은 답이 나오면 되묻는다: **"그것을 하나의 화면, 한 번의 수정으로 줄이면 무엇이 남습니까?"**
- "무엇이 되면 끝인지"에 답이 안 나오면: **"그게 다 됐으면, 어느 화면을 열어서 무엇을 보면 '됐구나' 하실까요?"**
- 아직 청구가 시작되지 않았으면 5번은 **"아직 없음 — 가입하는 날 무료 범위 숫자를 여기 적는다"** 로 적는다. 칸을 비우지도, 없는 금액을 지어내지도 않는다.
- 2단계의 복구 실습에서 나온 '막힌 것'을 개선 후보에 넣는다.

`assets/plan-30d.template.md` 를 `company/plan-30d.md` 로 채운다.

### 4. 첫 회를 그 자리에서 한 번 돈다

세팅으로 끝내지 않는다. 아래 '실행 절차'의 일곱 단계를 **오늘 한 번** 돈다. 개선 1건은 `plan-30d.md` 의 1번이나 복구 실습에서 나온 것으로 고른다.

### 5. 상태 문서 갱신과 커밋

`.owner/state.md` 를 고친다.

- **현재 기능** — 바뀐 것이 있으면 한 줄 추가.
- **미해결 문제** — 해결한 줄은 지우고, 다음 주로 넘긴 것은 남긴다.
- **다음 행동** — "2주 실사용 + 매주 <요일> 루틴, 최종 회 시연 준비(`indeans-erp-showcase`)".

`.owner/progress.json` 의 `sessions.4.done` 을 `true` 로, `open_problems`·`next_action`·`updated_at` 을 고친다.

```bash
git add -A && git commit -m "주간 루틴·복구 실습·30일 계획"
```

## 실행 절차 — 매주 일곱 단계

### 1) 오류 모음

> "지난 한 주 동안 앱을 쓰다가 '어?' 했던 순간을 하나씩 말씀해 주세요. 사소해도 괜찮습니다."

나온 것마다 네 칸을 채운다. 대표가 모르는 칸은 AI가 앱을 읽고 **추정이라고 표시해서** 채운다.

| 칸 | 내용 | 비어 있으면 |
|---|---|---|
| 증상 | 대표의 말 그대로 | — |
| 기대 | 무엇이 나와야 했나 | "그때 무엇이 나올 거라고 생각하셨나요?" |
| 실제 | 무엇이 나왔나 | "대신 무엇이 나왔나요?" |
| 재현 | 어떤 순서로 하면 다시 나오나 | "안 나온다"면 그렇게 적는다. **못 재현하는 것은 이번 주에 고치지 않는다** |

`company/log.md` 에 회차 사이 기록이 있으면 그것부터 읽는다. 자주 나오는 증상은 `references/common-problems.md` 에 확인 순서가 있다.

### 2) 이번 주 개선 1건 — 요구와 계획 대조

모인 것 중 **한 건만** 고른다. 고르는 기준(위에서부터):

1. 데이터가 잘못 저장되는 것 · 못 봐야 할 사람에게 보이는 것 → 무조건 1순위
2. 매일 쓰는 화면의 불편
3. 가끔 쓰는 화면의 불편
4. 있으면 좋은 기능 → **다음으로 미룬다**

고른 뒤 대표의 요구를 **그대로 옮겨 적고** 계획을 세운 다음 대조한다.

| 요구 원문(대표의 말) | 계획의 어느 줄이 이걸 하나 | 판정 |
|---|---|---|
| "<원문>" | <계획 항목> | 그대로 / 줄임 / 바꿈 / 빠짐 |

**'줄임·바꿈·빠짐'이 하나라도 있으면 진행 전에 대표에게 알린다.**

> "말씀하신 것 중 이 부분은 이번 주에 하지 않으려 합니다. 이유는 <이유> 입니다. 이렇게 해도 괜찮을까요?"

편하다는 이유로 요구를 조용히 줄이거나 다른 것으로 바꾸지 않는다. 이 표가 이 루틴의 핵심이다.

계획이 **돈·권한·데이터 구조**를 건드리면 `references/supervisor-checklist.md` 의 '계획 컨펌' 항목을 먼저 통과시키고, 고친 뒤에는 `indeans-erp-check` 를 부른다.

### 3) 되돌릴 지점

```bash
git add -A && git commit -m "<개선 제목> 작업 전"
```

커밋 번호(앞 7자리)를 주간 기록에 적는다.

### 4) 확인 캡처

고치기 전과 후를 같은 조건으로 찍는다. 다른 창에서 `npm run dev` 를 띄워 두고:

```bash
node .owner/hooks/capture.mjs --url http://localhost:5173 --path "/" --name before
```

찍은 파일을 `company/weekly/screens/<연-주>-before.png`·`-after.png` 로 옮긴다. 화면이 없는 변경(데이터 구조 등)이면 대신 **바뀐 값을 눈으로 확인한 결과**를 두 줄로 적는다.

캡처 없이 "됐습니다"라고 보고하지 않는다.

### 5) 백업 확인

- 내려받기를 한 번 실행하고 파일 날짜·크기를 적는다.
- 지난주 파일과 크기가 비슷한지 본다. 갑자기 줄었으면 멈추고 원인을 찾는다.
- 한 달에 한 번은 **파일을 실제로 열어 본다.**
- **운영 보고가 매일 오고 있는지 같이 본다**(`company/digest.md` 5절의 발송 기록 조회). 안 온 날이 있으면 그것이 이번 주 1순위다.

### 6) 비용 확인

AI 도구 구독과 클라우드(데이터·배포) 두 줄. 이번 달 사용량이 무료 범위 안인지, 지난달보다 늘었는지 적는다. `company/plan-30d.md` 4절이 이미 채워져 있으면 **다시 묻지 말고 그 값을 옮겨 적은 뒤 바뀐 것만 확인한다.** 한도를 넘었으면 새 기능을 멈추고 그것부터 처리한다.

### 7) 두 AI 교차 검토

만든 AI와 **다른 AI**가 읽기 전용으로 요구와 결과를 대조한다. 명령과 요청 문장은 `references/cross-check.md`.

- Claude Code로 만들었으면 → Codex가 검토 / Codex로 만들었으면 → Claude Code가 검토.
- 검토자에게 주는 것: **요구 원문 · 바뀐 파일 목록.** 만든 쪽의 결론이나 "잘 됐다"는 설명은 주지 않는다.
- 결과는 세 가지 중 하나로 받는다: **맞음 / 빠짐 / 바뀜.** '빠짐·바뀜'이면 이번 주에 고치거나, 못 고치면 다음 주 1순위로 올린다.
- 도구가 하나뿐이면 같은 도구의 **새 대화**에서 코드만 보고 검토하게 한다(이전 대화 내용을 넣지 않는다).

### 마무리

`assets/weekly.template.md` 를 `company/weekly/<연-주>.md` 로 만들어 일곱 단계 결과를 채운다(예: `2026-38.md` — 2026년 38번째 주). 같은 실수를 또 하지 않기 위해 남길 것이 생겼으면 `references/casebook-template.md` 로 `company/casebook/` 에 한 건 기록한다.

마지막으로 `.owner/state.md` 의 '미해결 문제'와 '다음 행동'을 고치고 커밋한다.

```bash
git add -A && git commit -m "<연-주> 주간 점검"
```

## 하지 않는 것

- 복구 실습을 건너뛰지 않는다. 되돌려 본 적 없는 백업은 백업이 아니다.
- **실제 업무 데이터로 복구 실습을 하지 않는다.** 지우는 줄은 예시 데이터이고, 대표의 확인을 받는다.
- 실습으로 표를 지우거나 되돌리기 어려운 조작을 하지 않는다.
- 한 주에 두 건 이상 고치지 않는다. **다만 오타·안내 문구·주석처럼 화면 동작과 데이터가 전혀 바뀌지 않는 한 줄 수정은 건수에 넣지 않는다.**
- 요구를 임의로 줄이거나 다른 것으로 바꾸지 않는다. 바꿔야 하면 먼저 묻는다.
- 재현되지 않는 문제를 추측으로 고치지 않는다. 관찰 항목으로 남긴다.
- 되돌릴 지점 없이 파일을 고치지 않는다.
- 캡처·확인 없이 "고쳤습니다"라고 보고하지 않는다.
- 교차 검토 때 만든 쪽의 결론을 검토자에게 알려 주지 않는다.
- 주간 기록에 고객 실명·연락처·계좌·실제 금액을 적지 않는다. 건수·구간으로 적는다.
- 밀린 주를 나중에 지어내 채우지 않는다.

## 앞선 수강생 분기

- **점검 스크립트** — 매주 손으로 보던 것 중 기계가 볼 수 있는 것을 `scripts/check.mjs` 한 파일로 만든다(예: 같은 건이 두 번 저장됐는지, 담당자가 비어 있는 건이 있는지, 합계가 맞는지). 판단이 필요한 것은 넣지 않는다. 매주 1단계 전에 한 번 돌린다.
- **판례집 운영** — `company/casebook/` 이 3건 이상 쌓이면 개선 계획을 세울 때 먼저 읽는다. 같은 유형이 두 번 나오면 사람이 조심하는 대신 **점검 스크립트 항목으로 바꾼다.**
- **직원 신고 창구** — 직원이 불편을 그때그때 남길 곳(메모·양식)을 만들고, 1단계에서 그것부터 읽는다.
- **월 1회 깊은 점검** — 넷째 주에는 개선 대신 권한(누가 무엇을 보나) 전수 확인과 복구 실습을 한 번 더 한다.

## 자주 막히는 지점

- **"이번 주엔 문제가 없었다"** — 그러면 `plan-30d.md` 의 개선 1건을 가져온다. 그것도 없으면 안 쓰는 화면 하나를 지운다. 루틴은 거르지 않는다.
- **고칠 게 너무 많아 못 고른다** — 2단계의 우선순위 네 줄로 기계적으로 고른다. 고민 시간을 5분 넘기지 않는다.
- **복구 실습에서 다시 입력이 안 된다** — 파일에 그 칸이 없거나 날짜 형식이 달라서다. 그것이 실습의 성과다. 그대로 적고 개선 후보로 올린다.
- **내려받은 파일이 비어 있다** — 버튼이 옛 저장소(예시 데이터)를 읽고 있다. `indeans-erp-data` 6단계 8번을 다시 본다.
- **교차 검토가 서로 다른 말을 한다** — 어느 쪽이 맞는지 AI에게 묻지 말고 **앱에서 직접 확인**한다. 화면을 열어 눈으로 본 것이 판정이다.
- **되돌리려는데 커밋이 없다** — 다음부터 3단계를 건너뛰지 않는다. 지금은 프로젝트 폴더를 복사해 두고 진행한다.
- **주간 기록을 쓰다가 시간이 다 간다** — 기록은 한 줄씩이면 충분하다. 문장을 다듬지 않는다.
- **두 달째 안 돌았다** — 밀린 것을 채우지 말고 이번 주 것만 한다. 공백 사유 한 줄이면 된다.
