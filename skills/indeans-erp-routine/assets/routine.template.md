# 우리 회사 앱 주간 루틴 — <회사 이름>

정한 날 <YYYY-MM-DD> · 작성 `indeans-erp-routine` · 업태 <company/profile.md 의 업태>

## 1. 언제 · 누가

| 항목 | 내용 |
|---|---|
| 요일·시각 | 매주 <요일> <시각> |
| 걸리는 시간 | 30~60분 |
| 참여 | <대표 혼자 / 대표 + 앱을 가장 많이 쓰는 직원> |
| 달력에 넣었나 | 예 / 아직 |
| 거를 수 있는 주 | <예: 휴가 주 — 다음 주에 이어서 하고 밀린 것은 채우지 않는다> |
| 기록 위치 | `company/checkups/<연-주>.md` (예: `2026-41.md`) · 감사 기록 `reports/<날짜>-감사.md` · 표식 `.owner/last-review.json` |

"시간 날 때"는 정한 것이 아니다. 요일과 시각이 비어 있으면 아직 루틴이 없다.

## 2. 매주 하는 일곱 가지

1. 감사와 오류 모음 — `erp-auditor` 감사(읽기 전용) + 지난주에 '어?' 했던 순간(증상·기대·실제·재현)
2. 이번 주 개선 **1건** — 요구 원문과 계획 대조(줄이거나 바꾸지 않았는지)
3. 되돌릴 지점 만들기 — 커밋
4. 확인 캡처 — 고치기 전/후
5. 백업 확인 — 내려받기 실행, 파일 날짜·크기, **운영 보고가 매일 왔는지**
6. 비용 확인 — 구독·클라우드
7. 두 AI 교차 검토 — 만든 쪽과 다른 AI가 읽기 전용으로 대조

마무리: 점검 기록 · 판례 노트(`.owner/precedents.md`) 한 줄·승격 · `.owner/last-review.json` 갱신. 7일이 넘으면 새 대화를 열 때 알림 훅(`erp-reminder`)이 알려 준다.

## 3. 고칠 것을 고르는 순서

1. 데이터가 잘못 저장되는 것 · 못 봐야 할 사람에게 보이는 것
2. 매일 쓰는 화면의 불편
3. 가끔 쓰는 화면의 불편
4. 있으면 좋은 기능 → 미룬다

## 4. 새 기능을 멈추는 기준

아래 중 하나라도 해당하면 개선 대신 그것부터 처리한다.

- 데이터가 잘못 저장되는 것이 발견됐다
- 못 봐야 할 사람에게 화면이 보였다
- 직원이 "앱 때문에 더 오래 걸린다"고 말했다
- 운영 보고가 이틀 이상 안 왔다
- 월 비용이 한도(<금액대>)를 넘었다

## 5. 검토가 필요한 작업 (1인 회사 기준)

`indeans-erp-check` 의 위험 등급표를 그대로 쓴다.

| 등급 | 바꾸는 것 | 하기 전 | 배포 전 |
|---|---|---|---|
| 1 | 권한 · 돈 · 새 표 구조 · 삭제 조건 · 배포 설정 | 계획을 글로 적고 다른 AI에게 읽힌다 | `erp-supervisor` 판정 + 실측(정책이면 롤백 시뮬, 돈이면 손계산 1건) + 적용 뒤 감사 |
| 2 | 새 화면·화면 동작 | 화면 이름과 하는 일을 한 줄로 | `erp-design-supervisor` + 캡처 375·1280 |
| 3 | 읽기 전용 · 보고 문구 · 설정 값 | 생략 | 그 동작 1회 확인 + `npm run check` |
| 4 | 오타 · 문구 · 정해진 색 | 생략 | 생략 |

상세는 스킬의 `references/supervisor-checklist.md`.
