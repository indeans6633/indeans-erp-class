# 두 AI 교차 검토 — 주간 요구 대조

주간 점검 7단계에서 쓴다. 만든 AI 와 **다른 AI** 가 이번 주에 고친 것을 **요구 원문과 대조**한다(맞음 / 빠짐 / 바뀜). 1등급 변경의 결함을 찾는 일은 `indeans-erp-crosscheck` 가 한다. 보내는 방식(프롬프트 파일 · 코드 붙이기 · 비공개 정보 점검 · 빈 폴더 실행)은 그 스킬과 같고, 명령은 `indeans-erp-crosscheck` 의 `references/commands.md` 에 있다.

만든 AI 에게 "잘 됐냐"고 물으면 거의 "잘 됐다"고 한다. 자기가 만든 것을 자기가 채점하기 때문이다. 인디언즈도 중요한 판단에서 다른 계열 AI 의 독립 의견을 이렇게 받는다.

## 원칙 다섯 가지

1. **결론을 주지 않는다.** 요구 원문과 코드만 준다. "이렇게 고쳤는데 괜찮지?"라고 물으면 따라 말한다.
2. **코드를 붙여 넣는다 — 목록만 주지 않는다.** 바뀐 파일의 코드를 줄 번호와 함께 프롬프트에 붙인다(commands.md 1절). 목록만 주면 검토자의 읽기 전용 상자(샌드박스)가 파일을 못 읽어 "판정 불가"로 끝나는 일이 있다. 붙인 뒤에는 비공개 정보 점검(commands.md 2절)을 통과해야 보낸다.
3. **빈 임시 폴더에서 돌린다.** 프로젝트 폴더에서 돌리면 검토자가 우리 보고서·상태 문서를 읽고, 우리 검수 훅·지침이 검토자 쪽에서도 돈다(commands.md 0절). 검토자는 읽기만 한다.
4. **판정은 세 가지로 받는다.** 맞음 / 빠짐 / 바뀜.
5. **돈·권한에 걸리는 지적은 감독이 판정한다.** `indeans-erp-check` 의 "확인받고 싶은 것"으로 넘긴다. 두 AI 의 말이 갈리면 어느 쪽이 맞냐고 AI 에게 다시 묻지 않고, 감독 판정과 앱 직접 확인으로 가린다.

## 준비물 — 검토자에게 줄 것

1. 요구 원문(대표가 한 말 그대로)과 확인 기준(무엇이 되면 끝인지)
2. 바뀐 파일 — 이번 주 개선 커밋에서 뽑는다: `git diff --name-only HEAD~1 HEAD`. `.env*` · `.owner/` · `reports/` · `company/` 는 빼고 5개 이하로.

## 보내는 순서

1. 아래 문장을 `.owner/tmp/crosscheck-{날짜}.txt` 맨 위에 쓰고 `{ }` 를 채운다.

   ```text
   당신은 이 변경을 처음 보는 독립 검토자다. 만든 쪽의 설명과 결론은 일부러 주지 않았다. 아래 요구 원문과 코드만 보고 대조한다. 파일을 고치거나 명령을 실행하지 않는다.
   요구 원문: "{대표의 말 그대로}"
   확인 기준: {무엇이 되면 끝인지}
   확인할 것만 답한다. (1) 요구 중 구현에 빠진 것 (2) 요구와 다르게 해석한 것 (3) 돈 계산이나 누가 무엇을 보는지에 영향이 가는 변경
   더 나은 방법은 제안하지 말고, 빠진 것과 어긋난 것만 목록으로 쓴다. 각 항목 끝에 맞음 / 빠짐 / 바뀜 중 하나와 근거 파일:줄을 붙인다.
   코드 — 바뀐 파일 전문, 줄 번호 붙음
   ```

2. commands.md 1절 명령으로 코드를 이어 붙인다(끝에 "한국어로 답한다."가 붙는다).
3. commands.md 2절 점검 명령을 돌린다. `STOP` 이면 보내지 않는다. 이름과 실제 금액은 눈으로 본다.
4. 만든 도구의 반대편으로 보낸다 — Claude Code 로 만들었으면 3절(검토자 Codex), Codex 로 만들었으면 4절(검토자 Claude Code). 제한 시간은 10분.
5. 답(`.owner/tmp/crosscheck-out-{날짜}.md`)을 주간 기록 7절에 그대로 옮긴다.

## 도구가 하나뿐일 때

같은 도구를 새 대화로 부른다(commands.md 6절 — 명령으로 부르는 것 자체가 새 대화다). 이전 대화 내용은 붙이지 않는다. 같은 AI 라 독립성은 약하지만 안 하는 것보다 낫다. 기록에 "같은 도구 새 대화"라고 적는다.

## 검토 결과 처리

| 판정 | 뜻 | 처리 |
|---|---|---|
| 맞음 | 요구대로 됐다 | 주간 기록에 "맞음"만 적고 끝 |
| 빠짐 | 요구 중 안 된 것이 있다 | 이번 주에 마저 하거나, 못 하면 다음 주 1순위 + 대표에게 보고 |
| 바뀜 | 요구와 다르게 됐다 | **반드시 대표에게 알린다.** 바뀐 채로 두려면 대표의 답을 받는다 |

(3) 돈 계산·권한에 영향이 간다는 지적이 나오면 배포를 멈추고 `indeans-erp-check` 로 감독 판정부터 받는다.

## 비용

- Claude Code · Codex 모두 구독 사용량을 쓴다. 주 1회 한 번이면 부담이 크지 않다. 파일이 많으면 5개 이하로 줄이고, 400줄이 넘는 파일은 바뀐 부분만 붙인다(commands.md 1절).
- 고객 실명·연락처·계좌·실제 금액을 프롬프트에 넣지 않는다. 검토에 필요 없고, 보낸 글은 외부 회사의 서버로 간다.

## 자주 막히는 지점

- **검토자가 "전체적으로 잘 되어 있습니다"만 말한다** — 요구 원문을 문장 단위로 쪼개서 한 문장씩 대조시킨다. "이 문장은 어디서 처리되나?"
- **검토자가 "파일을 읽지 못했다·확인할 수 없다"고 답한다** — 코드를 붙이지 않고 목록만 줬다. 그건 검토가 된 것이 아니다. commands.md 1절로 코드를 붙여 다시 보낸다.
- **검토자가 파일을 고쳐 버렸다** — 읽기 전용·빈 폴더 명령(commands.md 3·4절)을 쓰지 않았다. 되돌린 뒤 그 명령으로 다시 한다.
- **답 끝이 검토가 아니라 "검수 스킬을 부르겠다"는 말이다** — 프로젝트 폴더에서 돌려 우리 훅이 끼었다. 빈 폴더에서 돌린다.
- **지적이 너무 많다** — 이번 요구와 무관한 것은 목록으로만 남기고 다음으로 미룬다. 한 주에 한 건 원칙은 유지한다.
- **명령이 실행되지 않는다** — 설치·로그인 상태를 먼저 확인한다(1회차 `indeans-erp-setup`). 안 되면 그 주는 같은 도구 새 대화로 대체하고 기록에 남긴다.
