# 지금 막힌 문제 하나 잡기 (급할 때 쓰는 순서)

주간 루틴은 **모아서 주기적으로** 도는 자리입니다. 지금 당장 앱이 안 돌아 일이 멈췄으면 루틴을 기다리지 않고 이 순서를 씁니다.

문제를 고치다 더 망가지는 일은 거의 **재현하지 않고 추측으로 고쳐서** 생깁니다. 이 문서는 순서를 지키게 하는 장치입니다.

> 증상 → 재현 → 되돌릴 지점 → 원인 검증 → 최소 수정 → 확인 → 기록

한 번에 **문제 하나**만 다룹니다. 다른 문제가 보여도 목록에만 적어 두고 이번엔 손대지 않습니다.

---

## 먼저 보는 것 (읽고 나서 말을 건다)

- `company/log.md` · `company/weekly/` 최근 기록 — 같은 증상을 전에 겪었나. **있으면 그때의 원인·수정을 먼저 읽는다.**
- `company/casebook/` — 같은 유형의 판례.
- `git log --oneline -15` — 최근에 무엇이 바뀌었나. 어제까지 되던 것이면 답이 여기 있을 때가 많다.
- `git status` — 저장 안 된 변경이 남아 있나.
- `.owner/state.md` — 미해결 문제에 이미 적혀 있나.

상황별 첫 수:

| 상황 | 첫 수 |
|---|---|
| 전에 같은 증상을 겪었다 | 그때의 원인을 먼저 확인한다. 같은 원인이면 3단계로 건너뛴다 |
| 마지막 커밋·배포 직후 시작됐다 | 그 변경을 1순위 가설로 둔다. **되돌려 보는 것이 가장 빠른 확인**이다 |
| 저장 안 된 변경이 남아 있다 | 먼저 커밋하거나 따로 보관한다. 이 상태로 고치면 되돌릴 수 없다 |
| 데이터가 잘못 저장되고 있다 | **먼저 백업을 받고** 시작한다. 고치는 동안 그 화면 사용을 잠시 멈춘다 |
| 아무도 앱을 못 쓴다(흰 화면) | 원인 찾기보다 **직전 상태로 되돌리는 것이 먼저**다. 되돌린 뒤 원인을 찾는다 |

## 1단계 — 증상 정리 (대표의 말 그대로)

> "어떤 화면에서 무엇을 하셨을 때, 무엇이 나왔나요? 보신 대로 말씀해 주세요."

받은 말을 **고치지 말고 그대로** 적습니다. "저장이 안 돼요"를 "저장 처리 오류"로 바꿔 적지 않습니다. 그다음 세 가지를 하나씩 묻습니다.

1. > "그때 무엇이 나올 거라고 생각하셨나요?" (기대)
2. > "대신 무엇이 나왔나요? 화면에 글자가 떴다면 그대로 읽어 주세요." (실제)
3. > "언제부터 이랬나요? 어제는 됐습니까?" (시작 시점)

화면에 뜬 글자는 **그대로** 받아 적습니다. 요약하지 않습니다.

## 2단계 — 재현 순서 만들기

```
1. <어느 화면을 연다>
2. <무엇을 입력한다 — 값도 적는다>
3. <어느 버튼을 누른다>
→ 기대: <  > / 실제: <  >
```

그리고 실제로 한 번 해 봅니다. 세 가지 중 하나가 나옵니다.

| 결과 | 다음 |
|---|---|
| 그대로 재현됨 | 3단계로 |
| 어떤 때만 나옴 | 되는 경우와 안 되는 경우의 **차이**를 찾는다(다른 계정? 다른 값? 폰에서만?). 차이를 찾을 때까지 고치지 않는다 |
| 재현 안 됨 | **고치지 않는다.** 증상과 조건을 `company/log.md` 에 관찰 항목으로 남기고, 다음에 나오면 화면을 사진으로 찍어 두게 안내한다 |

재현되지 않는 것을 고치면, 고쳤는지 아닌지 확인할 방법이 없습니다.

## 3단계 — 되돌릴 지점

```bash
git add -A
git commit -m "<증상> 수정 전"
```

커밋 번호 앞 7자리를 적어 둡니다. 데이터가 걸린 문제면 **데이터 백업도 함께** 받습니다.

## 4단계 — 원인 가설을 하나씩 검증

가설을 3개까지 적고 **가능성이 높은 순서가 아니라 확인이 쉬운 순서**로 검증합니다. 한 번에 하나씩, 확인이 끝나기 전에 다음으로 넘어가지 않습니다.

| # | 가설 | 어떻게 확인하나 | 결과 |
|---|---|---|---|
| 1 | <  > | <눌러 본다 / 값을 본다 / 되돌려 본다> | 맞음 / 아님 |

확인 방법의 원칙:

- **눈으로 본 것만 결과로 적습니다.** "아마 이것 때문일 겁니다"는 결과가 아닙니다.
- 확인하려고 코드를 고치지 않습니다. 고쳐야만 확인되는 가설은 뒤로 미룹니다.
- 최근 변경이 의심되면 그 커밋으로 잠깐 되돌려 증상이 사라지는지 봅니다. 사라지면 원인이 그 안에 있습니다.
- 한 번에 한 가지만 바꿉니다. 두 가지를 같이 바꾸면 무엇이 효과였는지 모릅니다.
- `references/common-problems.md` 에 같은 증상이 있으면 거기 적힌 **확인 순서**를 먼저 따릅니다.

세 가설이 모두 아니면 2단계로 돌아가 재현 조건을 좁힙니다. 가설을 늘리지 않습니다.

## 5단계 — 최소 수정

원인이 확인된 뒤에만 고칩니다. 범위는 **그 증상을 없애는 데 필요한 만큼**입니다.

- 같이 눈에 띈 다른 문제는 목록에만 적습니다.
- 구조를 바꾸거나 화면을 새로 만들지 않습니다.
- 고친 내용을 한 문장으로 설명할 수 없으면 범위가 넓은 것입니다. 줄입니다.
- 돈 계산·권한·데이터 구조가 걸린 수정이면 배포 전에 `indeans-erp-check` 를 부릅니다.

## 6단계 — 확인

1. **2단계의 재현 순서를 그대로 다시 합니다.** 이번엔 기대한 것이 나와야 합니다.
2. 고친 화면을 찍습니다(`node .owner/hooks/capture.mjs --url http://localhost:5173 --path "/" --name after`).
3. 같은 데이터를 쓰는 **다른 화면 한두 개**를 열어 봅니다. 한쪽을 고치고 다른 쪽이 깨지는 일이 흔합니다.
4. 배포했다면 배포 주소를 새 창에서 열어 확인합니다. 옛 화면이 보이면 강제 새로고침.
5. 데이터가 걸린 문제면 잘못 저장된 기존 데이터도 손봐야 하는지 대표에게 묻습니다.

> "앞으로는 정상입니다. 그런데 이미 잘못 들어간 <건수>건이 있는데, 이것도 지금 손볼까요?"

확인이 끝나면 커밋합니다.

```bash
git add -A
git commit -m "<증상> 수정 — 원인: <한 줄>"
```

## 7단계 — 기록

- `company/log.md` 맨 위에 한 건 남깁니다(증상·재현·원인·수정·확인). 대표의 말을 그대로 씁니다.
- 되돌려야 했거나 같은 문제가 두 번째면 `references/casebook-template.md` 로 `company/casebook/` 에 판례를 남깁니다.
- `.owner/state.md` 의 '미해결 문제'에서 해결한 줄을 지우고, 남은 관찰 항목은 남깁니다.
- 원인이 "확인을 빠뜨려서"였다면 주간 점검 항목이나 작은 확인 스크립트로 바꿉니다. **조심하는 것은 세 번째에 또 실패합니다.**

## 하지 않는 것

- 재현되지 않는 문제를 고치지 않습니다.
- 원인을 확인하기 전에 코드를 고치지 않습니다("일단 이렇게 해 볼까요" 금지).
- 한 번에 두 가지를 바꾸지 않습니다.
- 문제와 무관한 정리·개선을 같이 하지 않습니다.
- 되돌릴 지점 없이 시작하지 않습니다.
- 대표의 말을 전문 용어로 바꿔 기록하지 않습니다.
- 잘못 저장된 데이터를 대표에게 묻지 않고 지우거나 바꾸지 않습니다.
- 기록에 고객 실명·연락처·계좌·실제 금액을 남기지 않습니다.

## 자주 막히는 지점

- **"그냥 다 안 돼요"** — 범위를 좁힙니다. "어느 화면이 마지막으로 정상이었나요?" 하나만 골라 시작합니다.
- **화면에 뜬 글자를 못 봤다** — 다시 재현하면서 화면을 사진으로 찍게 합니다. 글자 한 줄이 원인을 바로 알려 줄 때가 많습니다.
- **고쳤는데 그대로다** — 옛 화면이 남아 있거나(강제 새로고침), 다른 주소를 보고 있거나, 배포가 안 끝난 것입니다. `references/common-problems.md` 3번·15번.
- **고치다 더 망가졌다** — 3단계 커밋으로 되돌린 뒤 처음부터 다시 합니다. 되돌리는 것은 실패가 아닙니다.
- **원인이 안 나오고 시간이 간다** — 30분이 넘으면 멈춥니다. 확인한 것과 아닌 것을 기록하고, 대표에게 임시 방법(손으로 처리)을 안내한 뒤 다음 자리에서 이어 합니다.
- **급해서 순서를 건너뛰고 싶다** — 아무도 앱을 못 쓰는 상황만 예외입니다. 그때는 되돌리기가 먼저고, 원인 찾기는 그다음입니다.
- **직원이 겪은 문제다** — 대표가 옮겨 말하면 사실이 흐려집니다. 직원에게 물을 질문 세 개(무슨 화면 · 무엇을 눌렀나 · 화면에 뜬 글자)를 만들어 전달합니다.
