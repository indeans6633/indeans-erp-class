# 감독 체크리스트 (1인 회사용)

규모가 있는 회사는 만드는 사람과 검토하는 사람을 나눕니다. 혼자라면 **사람 대신 순서로** 나눕니다. 세 자리만 있으면 됩니다: 시작 전(계획 컨펌) · 배포 전(리뷰) · 매주(정례).

원칙 하나: **되돌리기 어려운 실수는 먼저 검토하고, 되돌릴 수 있는 실수는 나중에 모아서 본다.** 그리고 같은 유형의 실수가 반복되면 감독을 더 꼼꼼하게 만드는 것보다 **기계 점검(고정 검사·감사 질의)으로 막는 것**이 먼저입니다 — 사람과 감독은 같은 것을 두 번 놓칩니다.

배포 전 리뷰는 1회차 설치 때부터 이미 자동으로 돌고 있습니다 — 영향 있는 변경이면 검수 훅이 `indeans-erp-check` 를 요구하고, 배포 명령 직전에는 배포 훅이 빌드·고정 검사·커밋을 다시 봅니다. **이 문서는 그 앞자리(계획 컨펌)와 매주 정례에서 사람이 직접 볼 항목**입니다.

## 위험 등급 — 무엇을 어디까지 검토하나

`indeans-erp-check` 의 위험 등급표와 같은 기준입니다.

| 등급 | 바꾸는 것 | 계획 컨펌 | 배포 전 리뷰 | 주간 정례 |
|---|---|---|---|---|
| 1 | 권한(누가 무엇을 보나) · 돈(금액·계산·입금·증빙) · 새 표 구조 · 삭제 조건 · 배포 설정 | 새 돈 흐름·새 규칙 구조일 때 필수 | `erp-supervisor` 판정 + 롤백 시뮬·역할별 실측·손계산 1건 + 적용 뒤 감사 | 감사(`erp-auditor`) |
| 2 | 새 화면·새 흐름·화면 동작 | 화면 이름과 하는 일 한 줄 | `erp-design-supervisor` + 전/후 캡처 | 월 1회 모아서 화면 한 바퀴 |
| 3 | 읽기 전용 조회·보고 문구·설정 값 | 생략 | 그 동작 1회 + 고정 검사 | — |
| 4 | 오타·문구·정해진 색 | 생략 | 생략(빌드로 확인) | — |

"되돌릴 수 있나"로 판단합니다. 잘못 저장된 금액·잘못 보인 화면은 되돌려도 이미 벌어진 일이고, 버튼 색은 다시 바꾸면 그만입니다. **"읽기 전용"이어도 새 뷰·데이터를 돌려주는 새 함수는 1등급**입니다(새 노출 경로).

## 1. 계획 컨펌 (고치기 전 10분)

혼자 하는 대신 **글로 적고 다른 AI에게 읽힙니다.** 적을 것은 네 줄입니다.

1. 무엇을 — 대표의 요구 원문 그대로
2. 어디를 — 어떤 화면·어떤 데이터
3. 어떻게 — 사람이 쓰는 말로(코드 설명 말고)
4. 안 하는 것 — 이번엔 손대지 않을 범위

다른 AI에게 보낼 때 묻는 문장:

```text
아래는 내가 우리 회사 앱에 하려는 변경 계획이다. 코드는 아직 고치지 않았다.
요구 원문과 계획을 대조해서 (1) 요구 중 계획에 빠진 것 (2) 요구와 다르게 해석한 것
(3) 이 변경이 돈 계산이나 누가 무엇을 보는지에 영향을 주는지만 지적해라.
더 좋은 방법을 제안하지 말고, 빠진 것과 어긋난 것만 말해라.
```

**"편하니까 이렇게 하자"로 요구가 바뀌는 것**이 가장 흔한 사고입니다. 요구 원문을 옆에 두고 대조하는 것이 이 자리의 목적입니다. 판례 노트(`.owner/precedents.md`)에 같은 유형이 있으면 그 줄의 "다음부터"를 계획에 넣습니다.

## 2. 배포 전 리뷰 (올리기 전 10분)

- [ ] 요구 원문의 문장 하나하나가 실제로 되는지 앱에서 눌러 봤다.
- [ ] 고치기 전/후 화면을 캡처했다.
- [ ] 돈·수량이 걸린 변경이면 **실제 1건**을 넣어 숫자를 손으로 계산해 맞춰 봤다.
- [ ] 권한이 걸린 변경이면 **롤백 시뮬**을 돌렸고, **역할마다 로그인해** 보여야 할 것과 보이면 안 되는 것을 확인했다.
- [ ] 데이터 구조를 바꿨으면 바꾸기 전에 백업을 받았다.
- [ ] `npm run check`(고정 검사)에 막힘이 없다.
- [ ] 되돌릴 커밋 번호를 적어 뒀다.
- [ ] 폰 폭(가로 375)에서 화면이 옆으로 밀리지 않는다.
- [ ] 배포 뒤 주소를 새 창에서 열어 실제로 바뀐 것을 확인했다(배포 뒤 스모크).
- [ ] `indeans-erp-check` 를 돌려 등급에 맞는 감독 판정과 실측 결과를 받았다.

하나라도 비면 배포하지 않습니다. 배포 명령 직전 훅이 빌드·고정 검사·커밋을 다시 막아 주지만, 위 목록의 대부분은 훅이 볼 수 없는 것입니다.

## 3. 주간 정례 (매주 30~60분)

`indeans-erp-routine` 의 일곱 단계가 그대로 주간 정례입니다. 그중 검토에 해당하는 자리는:

- 1단계 감사(`erp-auditor`) — 데이터와 규칙의 실태
- 2단계 요구↔계획 대조표
- 7단계 두 AI 교차 검토
- 마무리의 판례 노트 승격
- 넷째 주에는 개선 대신 **권한 전수 실측 + 백업 복구 연습**

## 검토에서 자주 나오는 지적 (미리 확인하면 줄어듭니다)

| 유형 | 확인 방법 |
|---|---|
| 요구가 조용히 줄었다 | 요구 원문 한 문장씩 표에 넣고 대응 항목이 있는지 본다 |
| 고객·직원이 남의 것을 본다 | 역할별로 실제 로그인해 목록을 연다. 코드 설명으로 넘기지 않는다 |
| 좁혔는데 그대로 다 보인다 | 같은 표의 규칙을 전체에서 세어 넓은 것이 남았는지 본다 |
| 합계가 화면마다 다르다 | 같은 값을 두 화면에서 읽고 손으로 계산한 값과 맞춘다. 계산이 서버 한 곳에 있는지 본다 |
| 목록에 최근 것이 안 보인다 | 정렬 기준과 한 번에 가져오는 개수를 확인한다 |
| 모바일에서 옆으로 밀린다 | 가로 375에서 열고 좌우로 밀리는지 본다 |
| 고친 뒤 다른 화면이 깨졌다 | 같은 데이터를 쓰는 화면을 목록으로 적어 두고 그 화면들을 한 번씩 연다 |

## 혼자 검토할 때의 함정

- **만든 직후에 검토하지 않습니다.** 최소 10분 뒤, 가능하면 다음 날 봅니다.
- 검토하는 AI에게 "이렇게 고쳤는데 괜찮지?"라고 묻지 않습니다. **요구와 바뀐 파일만** 주고 대조를 시킵니다.
- 검토 결과가 서로 다르면 AI에게 다시 묻지 말고 **앱을 직접 열어** 확인합니다.
- 다시 받기는 두 번까지입니다. 두 번 반려되면 범위를 줄이거나 되돌리는 것을 대표가 정합니다.
- 같은 유형의 지적이 두 번 나오면 판례 노트에서 **규칙으로 승격**합니다(먼저 기계 점검, 안 되면 감독 확인 절차).
