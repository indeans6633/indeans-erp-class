# 감독 체크리스트 (1인 회사용 축약)

규모가 있는 회사는 만드는 사람과 검토하는 사람을 나눕니다. 혼자라면 **사람 대신 순서로** 나눕니다. 세 자리만 있으면 됩니다: 시작 전(계획 컨펌) · 배포 전(리뷰) · 매주(정례).

원칙 하나: **되돌리기 어려운 실수는 먼저 검토하고, 되돌릴 수 있는 실수는 나중에 모아서 본다.**

배포 전 리뷰는 1회차 설치 때부터 이미 자동으로 돌고 있습니다 — 화면·데이터 구조·권한·배포가 바뀌면 검수 훅이 `indeans-erp-check` 를 요구하고, 그 스킬이 감독 판정(`erp-supervisor`·`erp-design-supervisor`)과 실측(`erp-verifier`)까지 이어서 합니다. **이 문서는 그 앞자리(계획 컨펌)와 매주 정례에서 사람이 직접 볼 항목**입니다.

## 위험 등급 — 무엇을 어디까지 검토하나

| 바꾸는 것 | 계획 컨펌 | 배포 전 리뷰 | 주간 정례 |
|---|---|---|---|
| 돈·수량·합계 계산, 상태를 되돌릴 수 없는 처리 | 필수 | 필수 + 실제 1건 확인 | 지난달 계산 결과 훑기 |
| 누가 무엇을 보는가(권한·역할·고객 화면) | 필수 | 필수 + 역할별로 직접 열어 보기 | 분기 1회 전수 확인 |
| 데이터 구조(표·열 추가·삭제) | 필수 | 필수 + 백업 먼저 | — |
| 새 화면·새 흐름 | 화면 이름과 하는 일 한 줄 | 전/후 캡처 | — |
| 글자·색·배치 | 생략 | 캡처만 | 월 1회 모아서 |
| 오타·한 줄 수정 | 생략 | 생략 | — |

"되돌릴 수 있나"로 판단합니다. 잘못 저장된 금액·잘못 보인 화면은 되돌려도 이미 벌어진 일이고, 버튼 색은 다시 바꾸면 그만입니다.

## 1. 계획 컨펌 (고치기 전 10분)

혼자 하는 대신 **글로 적고 다른 AI에게 읽힙니다.** 적을 것은 네 줄입니다.

1. 무엇을 — 대표의 요구 원문 그대로
2. 어디를 — 어떤 화면·어떤 데이터
3. 어떻게 — 사람이 쓰는 말로(코드 설명 말고)
4. 안 하는 것 — 이번엔 손대지 않을 범위

다른 AI에게 보낼 때 묻는 문장:

```text
아래는 내가 우리 회사 앱에 하려는 변경 계획이다. 코드는 아직 고치지 않았다.
요구 원문과 계획을 대조해서 (1) 요구 중 계획에 빠진 것 (2) 요구와 다르게 해석한 것
(3) 이 변경이 돈 계산이나 누가 무엇을 보는지에 영향을 주는지만 지적해라.
더 좋은 방법을 제안하지 말고, 빠진 것과 어긋난 것만 말해라.
```

**"편하니까 이렇게 하자"로 요구가 바뀌는 것**이 가장 흔한 사고입니다. 요구 원문을 옆에 두고 대조하는 것이 이 자리의 목적입니다.

## 2. 배포 전 리뷰 (올리기 전 10분)

- [ ] 요구 원문의 문장 하나하나가 실제로 되는지 앱에서 눌러 봤다.
- [ ] 고치기 전/후 화면을 캡처했다.
- [ ] 돈·수량이 걸린 변경이면 **실제 1건**을 넣어 숫자를 손으로 계산해 맞춰 봤다.
- [ ] 권한이 걸린 변경이면 **역할마다 로그인해** 보여야 할 것과 보이면 안 되는 것을 확인했다.
- [ ] 데이터 구조를 바꿨으면 바꾸기 전에 백업을 받았다.
- [ ] 되돌릴 커밋 번호를 적어 뒀다.
- [ ] 폰 폭(가로 375)에서 화면이 옆으로 밀리지 않는다.
- [ ] 배포 뒤 주소를 새 창에서 열어 실제로 바뀐 것을 확인했다.
- [ ] `indeans-erp-check` 를 돌려 감독 판정과 실측 결과를 받았다(화면·데이터·권한·배포가 바뀐 경우).

하나라도 비면 배포하지 않습니다. 빈 칸을 채울 시간이 없으면 다음 주로 미룹니다.

## 3. 주간 정례 (매주 30~60분)

`indeans-erp-routine` 의 일곱 단계가 그대로 주간 정례입니다. 그중 검토에 해당하는 자리는:

- 2단계 요구↔계획 대조표
- 7단계 두 AI 교차 검토
- 넷째 주에는 개선 대신 **권한 전수 확인 + 백업 복구 연습**

## 검토에서 자주 나오는 지적 (미리 확인하면 줄어듭니다)

| 유형 | 확인 방법 |
|---|---|
| 요구가 조용히 줄었다 | 요구 원문 한 문장씩 표에 넣고 대응 항목이 있는지 본다 |
| 고객·직원이 남의 것을 본다 | 역할별로 실제 로그인해 목록을 연다. 코드 설명으로 넘기지 않는다 |
| 합계가 화면마다 다르다 | 같은 값을 두 화면에서 읽고 손으로 계산한 값과 맞춘다 |
| 목록에 최근 것이 안 보인다 | 정렬 기준과 한 번에 가져오는 개수를 확인한다 |
| 모바일에서 옆으로 밀린다 | 가로 360에서 열고 좌우로 밀리는지 본다 |
| 고친 뒤 다른 화면이 깨졌다 | 같은 데이터를 쓰는 화면을 목록으로 적어 두고 그 화면들을 한 번씩 연다 |

## 혼자 검토할 때의 함정

- **만든 직후에 검토하지 않습니다.** 최소 10분 뒤, 가능하면 다음 날 봅니다.
- 검토하는 AI에게 "이렇게 고쳤는데 괜찮지?"라고 묻지 않습니다. 같은 결론을 따라 말합니다. **요구와 바뀐 파일만** 주고 대조를 시킵니다.
- 검토 결과가 서로 다르면 AI에게 다시 묻지 말고 **앱을 직접 열어** 확인합니다.
- 같은 유형의 지적이 두 번 나오면 사람이 조심하는 대신 **매주 돌리는 점검 항목**으로 바꿉니다.
