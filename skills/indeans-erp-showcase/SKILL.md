# 인디언즈 최종 회 시연 준비 (1인 10분)

최종 회(본 과정 종료 2주 뒤)에 각자 10분 동안 보여 주는 자리를 준비한다. 구성은 고정이다.

| 구간 | 분 | 무엇을 |
|---|---|---|
| 시연 | 5 | 첫 줄은 **풀려던 문제와 잰 숫자**(15초) → **직원이 실제로 처리한 업무 1건**을 흐름대로 끝까지 |
| 2주 사용 결과 | 3 | 회차 사이 기록·건수·**전후 측정표**·되돌린 것(실패 포함) |
| 다음 개선 순서 | 2 | `company/plan-30d.md` 의 3건 중 순서와 이유 |

시연은 잘 보이게 꾸미는 자리가 아니다. **지금 실제로 도는 것만 보여 주고, 안 되는 것은 안 된다고 말하는 것**이 이 스킬의 기준이다. 그래서 시연 전에 **완료선 네 줄**을 증거로 확인한다(절차 1).

30일 계획을 처음 세우는 일은 `indeans-erp-routine` 이 한다. 이 스킬은 그 문서를 **읽고 순서만 확정**한다(같은 질문을 두 번 하지 않는다).

## 언제 쓰나

- 최종 회 전(2주 실사용이 끝날 무렵) — 완성 모드.
- 실사용 준비 단계 끝에 **대본 틀과 완료선 확인표만** 잡아 둘 때 — 틀 모드(빈칸은 2주 뒤에 채운다).
- 수업이 끝난 뒤 직원·동업자·거래처에 앱을 설명해야 할 때.

쓰지 않는 경우: 주간 루틴·30일 계획을 세우는 일(→ `indeans-erp-routine`), 앱을 고치는 일(→ `indeans-erp-review`).

읽고 나서 말을 건다. 없는 문서는 없는 대로 진행한다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · 미해결 문제 · 회차 기록 · **회차 사이 기록 표** |
| `.owner/progress.json` | 회차별 완료·배포 주소·창구·보고 상태(`digest.first_received`) |

| `src/` 화면 파일 · `reports/` · `git log --oneline -40` | 실제로 도는 화면, 그동안의 작업 보고서, 바뀐 것의 증거 |

**상태 문서가 실제와 다르면 문서를 믿지 않는다.** 배포 주소가 적혀 있는데 안 열리면 그 줄을 먼저 고친다.

판정과 분기: **여러 줄이 동시에 해당할 수 있다. 해당하는 줄을 전부 적용한다.**

| 상태 | 판정 기준 | 분기 |
|---|---|---|
| A. 틀 모드 | 실사용 준비 단계 직후 · `company/log.md` 에 2주 기록이 아직 없음 | 절차 1·2·3·7만 하고 나머지는 `(2주 뒤)` 로 비워 둔다 |
| B. 완성 | 2주 기록이 있고 실제 건이 쌓였다 | 절차 1~9 전부 |
| C. 갱신 | `company/showcase.md` 있음 | 앱과 문서를 다시 읽고 **바뀐 부분만** 고친다. 완료선 확인표는 **매번 다시** 확인한다. 기존 문장을 함부로 버리지 않는다 |
| D. 배포 전 | 배포 주소 없음 | 시연은 내 컴퓨터 화면으로 구성하고, 배포를 '다음 개선 순서' 1번으로 올린다. 시연에서 "아직 제 컴퓨터에서만 돕니다"라고 말한다 |
| E. 직원 사용 없음 | 대표 혼자만 써 봤다 | 절차 4를 **대표 본인이 처리한 업무 1건**으로 바꾸고, 직원이 못 쓴 이유를 2주 사용 결과에 한 줄로 넣는다(그 이유가 가장 쓸모 있는 이야기다) |

판정을 두세 줄로 먼저 보고한 뒤 시작한다.

## 절차

### 0. 되돌릴 지점

```bash
git add -A
git commit -m "시연 준비 전 상태"
```

### 1. 완료선 네 줄 확인 (시연 전 확인표)

이 과정의 완료선은 네 줄이다. **시연 전에 하나씩 증거로 확인하고** `company/showcase.md` 맨 위 "시연 전 확인표"에 적는다. 기억이나 상태 문서의 말이 아니라 **기록과 실측**으로 본다.

| 완료선 | 무엇으로 확인하나 | 없거나 오래됐으면 |
|---|---|---|
| 감독 판정 통과 | `.owner/last-check.json` 의 `result` 가 승인(또는 조건 반영) **그리고** `node .owner/hooks/erp-check.mjs --tool claude --debug`(Codex 면 `--tool codex`)가 `판정: 통과` — 그 뒤에 검수받지 않은 변경이 없다 | `indeans-erp-check` 로 지금 검수를 마친다 |
| 권한 차단 실측 | `company/people.md` 의 확인 결과 — 다른 역할 계정과 로그아웃 상태로 숨긴 화면 주소를 **직접 열었을 때 안 보였다**는 검증자 관찰과 날짜 | 화면에서 안 보이는 것만으로는 통과가 아니다. `erp-verifier` 에게 그 실측을 맡긴다 |
| 운영 보고 수신 | `company/digest.md` · `progress.json` 의 `digest.first_received` · 폰에 온 **가장 최근 보고**(PC와 AI 도구를 끈 날에도 왔나) | 안 온 날과 이유를 적는다. 고치는 일은 `indeans-erp-digest` 다 |
| 감사(`erp-auditor`) 통과 | 마지막 감사 판정 원문과 날짜. 그 뒤에 화면·저장·권한이 바뀌었으면 오래된 것이다 | `erp-auditor` 에게 지금 감사를 맡기고(`erp-auditor 에이전트로 감사해 줘.`) 판정 원문을 그대로 적는다 |

- 네 줄을 **통과 / 아직 — 이유** 둘로만 적는다. "거의 됨"은 아직이다.
- **아직인 줄을 숨기지 않는다.** 대본의 "솔직하게 말할 것"에 넣고, 다음 개선 순서(절차 6)에서 1번 후보로 올린다. 특히 권한 차단이 아직이면 직원에게 넓히기 전에 그것부터다.
- 검수·실측·감사를 **다시 돌려 보는 것**은 확인이지 고치는 것이 아니다. 시연을 위해 이 자리에서 앱을 급히 고치지 않는다.

### 2. 실제로 도는 화면 확인

`src/` 를 읽어 화면 목록을 뽑고, 각 화면이 (ㄱ)실제 데이터로 도는지 (ㄴ)예시 데이터로만 도는지 (ㄷ)버튼만 있고 동작 안 하는지 표로 정리해 보여 준다. 그다음 질문 하나.

> "이 중에서 지난 2주 동안 **실제로 써 보신 화면**은 어느 것인가요?"

여기서 고른 화면이 시연의 중심이다. 나머지는 시연에서 다루지 않는다.

### 3. 10분 대본 틀 만들기

`assets/showcase.template.md` 를 `company/showcase.md` 로 만든다. 절 제목과 순서를 바꾸지 않는다. 절차 1의 확인표를 맨 위에 채운다. 틀 모드면 여기까지 하고 절차 7로 간다.

각 구간의 분과 줄 수를 먼저 못 박는다. **화면 수가 아니라 시간으로 자른다.**

**전후 측정표 옮기기** — `company/roadmap.md` 실사용 준비 단계의 가치 가설 표를 읽어 `company/showcase.md` 의 전후 측정표에 가치 가설 · 시작값 · 측정 방법을 그대로 옮긴다. 2주 뒤 값은 `(2주 뒤)` 로 비워 둔다(틀 모드에서도 여기까지 한다). 시작값이 아직 `(어림)` 이면 비고에 적고 대표에게 한 줄 알린다: "실제 일에 쓰기 전에 같은 방법으로 직접 세어 두셔야 2주 뒤에 견줄 수 있습니다." 가치 가설이 없거나 `(미정)` 이면 **지어내지 않는다** — 표에 `없음 — 정하지 않았음` 을 적고, 대본 첫 줄은 풀려던 문제만 말한다.

### 4. 시연 5분 — 직원이 실제 처리한 업무 1건

질문 하나.

> "지난 2주 동안 **직원분이 이 앱으로 실제 처리한 일** 하나를 말씀해 주세요. 어떤 일이었고 누가 어디까지 했나요?"

- 그 한 건을 **처음부터 끝까지 하나의 흐름**으로 배열한다(업태별 예: 제조 = 주문 접수 → 생산 지시 → 출고 기록 / 서비스 = 접수 → 방문 일정 → 완료 보고 / 유통 = 입고 → 재고 확인 → 출고 / 예약업 = 예약 → 확인 연락 → 방문 처리). 화면을 하나씩 나열하지 말고 **일이 흘러가는 순서**로 짠다.
- **직원이 실제로 누른 화면과 계정으로** 시연한다. 대표 계정으로만 보여 주면 "직원도 쓴다"는 말의 증거가 없다.
- 그 건에서 **막혔던 자리 한 곳**을 시연 안에 넣는다. 고쳤으면 전/후를, 못 고쳤으면 "여기서 아직 손으로 합니다"를 말한다.
- 대본은 화면당 2~3문장, 클릭 순서까지 적는다. 총 5분을 넘기지 않는다.
- 운영 보고가 오고 있으면 폰에 온 보고 화면 한 장을 시연 끝에 붙인다(10초). 보고 문장에 고객 이름·금액이 없는지 확인한 뒤에만 보여 준다.

### 5. 2주 사용 결과 3분

재료는 `company/log.md` 의 세 줄 기록과 `git log`, 그리고 절차 3에서 옮긴 전후 측정표다. 네 항목으로 만든다.

1. **얼마나 썼나** — 실제 처리 건수 · 쓴 사람 수 · 어느 화면을 가장 많이 썼나. 숫자는 앱 데이터에서 직접 센다(**건수만**, 금액은 쓰지 않는다).
2. **무엇이 달라졌나** — 전에는 어디에 적었고 지금은 어디에 적나. 세 줄 기록의 '원하는 변화'가 실제로 됐는지.
3. **되돌린 것 / 안 된 것** — 한 항목은 반드시 여기에 쓴다. 이렇게 묻는다.

> "2주 동안 하려다 안 됐거나, 고쳐 놓고 되돌린 일이 하나 있나요? **그게 다른 분들한테 제일 도움이 되는 이야기입니다.**"

잘된 것만 있는 시연은 다른 수강생에게 도움이 되지 않는다.

4. **전후 측정표** — 2주 뒤 값을 채운다. 묻는 말: **"2주 동안 {측정 방법}으로 다시 재 보셨나요? 몇이었나요?"**
   - **대표가 잰 값만** 적는다. 앱 기록으로 셀 수 있는 항목이면 대표와 같이 센다. AI가 짐작하거나 늘려 적지 않는다.
   - 시작값과 같은 방법이 아니었거나 기간이 다르면 비고에 적는다. 시작값이 어림이면 비고에 `시작값은 어림`. 안 줄었거나 늘었으면 **그대로** 적고 이유를 한 줄 — 그것도 결과다.
   - 재지 않았으면 `재지 않음` 으로 두고 "5. 솔직하게 말할 것"에 넣는다.
   - 이 표의 첫 줄로 **대본 첫 줄**("0. 한 줄 소개")을 채운다: "{풀려던 문제}. {측정 항목}이 {시작값}에서 {2주 뒤 값}이 됐습니다(직접 잰 값)."

### 6. 다음 개선 순서 2분

`company/plan-30d.md` 의 개선 3건을 읽어 주고 질문 하나만 한다.

> "2주 써 보신 지금, 이 셋 중 **먼저 할 것**이 바뀌었습니까?"

- 절차 1에서 **아직**인 완료선이 있으면 질문 전에 한 줄로 알린다: "완료선 중 ○○이 아직입니다. 이것을 1번으로 올리기를 권합니다." 권하는 것은 한 번이고, 정하는 것은 대표다.
- 순서가 바뀌면 `plan-30d.md` 의 순서를 고치고(원본은 그 문서다), `company/showcase.md` 에는 순서와 한 줄 이유만 옮긴다.
- 새 항목이 나오면 3건 안에서 바꾼다. **넷으로 늘리지 않는다.**
- 각 항목에 "무엇이 보이면 끝인지"가 없으면 그 자리에서 받는다: **"그게 다 됐으면 어느 화면을 열어서 무엇을 보면 '됐구나' 하실까요?"**

### 7. 화면 캡처 목록

시연 순서대로 캡처할 화면을 목록으로 만든다. 각 항목: 화면 이름 · 무엇을 보여 주는 장면 · 폰(가로 375) / PC(가로 1280) 중 어느 쪽.

캡처는 앱을 **예시 데이터로** 띄워 두고 찍는다. 예시는 PowerShell 기준이다.

```
# 첫 화면
node .owner/hooks/capture.mjs --url http://localhost:5173 --name 01-list
# 버튼·탭으로 넘어가는 화면 — 화면에 보이는 글자를 그대로 준다
node .owner/hooks/capture.mjs --url http://localhost:5173 --click "오늘 현황" --name 02-today
```

- 주소가 따로 있는 화면은 `--path "/orders"`(Git Bash 에서는 `--path "//orders"`). 버튼으로만 넘어가는 화면은 `--path` 로 못 가니 `--click` 을 쓴다.
- **로그인이 있는 앱은 이 명령으로 로그인 화면만 찍힌다.** 로그인 뒤 화면은 대표가 시연용(예시 데이터) 계정으로 들어가 폰·PC의 화면 캡처로 직접 찍는다.
- 찍은 파일을 `company/screens/` 에 `01-목록.png` 처럼 번호를 붙여 옮긴다.

캡처 전 반드시 확인한다: **고객 실명·연락처·계좌·금액·주소가 화면에 있으면 예시 값으로 바꾼 뒤** 찍는다. 바꾸기 어려우면 그 화면은 빼거나 가린다.

**관리 단위 이름 자체가 주소·상호가 되는 업태**(출장 수리·배송·시설 관리 등)는 그 칸도 확인 대상이다. 고객 이름을 지워도 주소가 남는다. 공유용 캡처는 **예시 데이터로 찍는 것을 기본**으로 한다.

### 8. 말할 문장 만들기

읽을 원고가 아니라 **한 줄 카드**로 만든다. 문장 뼈대는 `references/talk-examples.md` 에서 업태에 맞는 것을 가져온다. 화면당 1~2줄, 대표가 평소 쓰는 말투로. 전문 용어는 풀어 쓴다. 초안을 보여 주고 질문 하나.

> "이 문장, 평소에 쓰시는 말투인가요? 어색한 문장은 그대로 고쳐 주세요."

### 9. 리허설 1회

시간을 재면서 한 번 돌린다. 5분·3분·2분 구간이 넘치면 **빨리 말하지 말고 항목을 줄인다.** 결과(실제 걸린 시간·넘친 구간)를 `company/showcase.md` 맨 아래에 적는다.

끝으로 `.owner/state.md` 의 '다음 행동'을 "최종 회 시연(<날짜>) — 대본 `company/showcase.md`" 로 고치고, `.owner/progress.json` 의 `sessions.final.done`(시연을 마친 뒤)·`next_action`·`updated_at` 을 고친다.

```bash
git add -A
git commit -m "최종 회 시연 준비(완료선 확인표·10분 대본·캡처 목록·다음 개선 순서)"
```

## 하지 않는 것

- 대표 대신 시연하지 않는다. 문장은 만들어 주되 말하는 사람은 대표다.
- **없는 기능을 있는 것처럼 쓰지 않는다.** 화면만 있고 동작하지 않으면 "화면만 있음"이라고 적는다.
- **완료선을 증거 없이 "통과"로 적지 않는다.** 판정 원문·실측 관찰·받은 보고가 없으면 "아직"이다.
- **전후 측정표에 재지 않은 숫자를 적지 않는다.** 어림·짐작·AI가 추정한 값을 잰 값처럼 쓰지 않고, 줄어든 폭을 배수로 바꿔 말하지 않는다. 금액은 쓰지 않는다.
- 직원이 처리한 사례가 없는데 있는 것처럼 만들지 않는다. 없으면 없는 이유를 말하는 것이 시연 내용이다.
- 30일 계획을 여기서 새로 인터뷰하지 않는다(`indeans-erp-routine` 의 문서를 읽는다).
- 시연을 위해 앱을 급히 고치지 않는다. 고치고 싶은 것은 `plan-30d.md` 로 보낸다.
- 고객 실명·연락처·계좌·단가·거래처명을 자료나 캡처에 남기지 않는다.
- 다른 회사·다른 수강생의 화면을 자기 자료에 넣지 않는다.
- 갤러리에 자동으로 올리거나 어딘가로 전송하지 않는다. 파일만 만든다.
- 다음 개선에 "AI가 알아서 해 줄 것" 같은 항목을 넣지 않는다. 항목마다 **누가 언제** 하는지 적는다.

## 앞선 수강생 분기

직원·고객이 이미 쓰고 있거나 실제 건이 많이 쌓였으면 아래에서 하나를 더 한다.

1. **안 쓰는 화면 정리** — 2주 동안 한 번도 안 열린 화면을 찾아 "이건 안 쓰게 됐고 이유는 이렇습니다"로 다룬다. 이 내용이 가장 도움이 되는 시연이 된다.
2. **직원 말 그대로 한 줄** — 직원에게 "이 앱 때문에 편해진 것 / 더 번거로워진 것"을 한 줄씩 받아 온다. 대표의 해석을 붙이지 않고 그대로 읽는다.
3. **다음 30일 뒤까지** — 개선 3건 다음에 갈 곳(직원 전체 사용 / 고객 화면 공개 / 다른 도구 연결) 중 어디까지인지 한 문단.
4. **공유 양식** — 다른 수강생에게 공유하고 싶은 기능이 있을 때만 `references/gallery-template.md` 로 `company/gallery-entry.md` 를 만든다. **묻지 않고 만들지 않는다.** 제출은 대표가 직접 한다.

## 자주 막히는 지점

- **시연 중 옛 화면이 보인다** — 배포 직후 브라우저에 남은 옛 화면이다. 시연 전에 배포 주소를 새 창에서 열어 확인하고, 안 되면 강제 새로고침. 그래도 안 되면 내 컴퓨터 화면으로 시연한다.
- **로그인 시연에서 막힌다** — 시연용 계정과 비밀번호는 `company/showcase.md` 가 **아니라** 대표 본인만 보는 곳에 적어 두고, 시연 전에 미리 로그인해 둔다.
- **직원 계정으로 보여 주려는데 화면이 비어 있다** — 권한이 제대로 걸린 것일 수 있다. 그 자체를 시연 내용으로 쓴다("직원에게는 이게 안 보입니다").
- **완료선 하나가 계속 "아직"이다** — 그대로 시연한다. 왜 아직인지와 언제 하는지를 말하는 것이 꾸며 낸 "통과"보다 다른 수강생에게 훨씬 쓸모 있다.
- **보여 줄 실제 건이 없다** — 2주 동안 못 쓴 이유를 찾는 것이 먼저다. 그 이유(로그인·속도·입력 칸)가 다음 개선 1번이고, 시연에서는 그 이야기를 한다.
- **10분을 넘긴다** — 거의 항상 시연이 길어진다. 화면을 3개 이하로 줄인다.
- **캡처에 실제 고객 정보가 들어갔다** — 다시 찍는다. 이미 공유했으면 파일을 내리고 다시 올린다.
- **앱이 당일 안 열린다** — 전날 커밋으로 되돌린 뒤 그 상태로 시연한다. 되돌린 사실을 그대로 말한다.
