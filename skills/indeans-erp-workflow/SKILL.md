# 인디언즈 업무 흐름 확장

4회차 앞 실습. 3회차까지 만든 앱(목록·상세·오늘 할 일 + 저장·배포·사람·보고)에 **단계와 다음 행동**을 붙인다.

이 스킬에는 모드가 둘 있다.

| 모드 | 언제 | 무엇을 |
|---|---|---|
| **A. 첫 흐름에 단계 붙이기** | 기본 | 단계(상태)·전이 규칙·목록 필터·상세의 다음 할 일 |
| **B. 두 번째 흐름** | **첫 흐름이 안정된 사람만** | 다른 종류의 일을 같은 방식으로 한 번 더 |

B의 조건은 아래 상태 진단에서 기계적으로 판정한다. **조건을 못 채우면 B로 가지 않는다.** 두 번째 흐름을 붙이면 안 끝난 첫 흐름이 영구히 안 끝난다.

## 언제 쓰나

- 기록은 쌓이는데 **"이 건이 지금 어디까지 왔는지"** 가 안 보일 때.
- 목록이 한 덩어리라 무엇부터 해야 할지 고르는 데 시간이 걸릴 때.
- 첫 흐름이 안정돼 두 번째 흐름을 담고 싶을 때(모드 B).

쓰지 않는 경우: 아직 초안 앱이 없다(→ `indeans-erp-draft`), 사람·권한 이야기다(→ `indeans-erp-people`), 채널로 보내는 보고다(→ `indeans-erp-digest`), 지금 막힌 문제 하나를 잡는 일이다(→ `indeans-erp-routine` 의 `references/one-problem.md`).

## 시작 전 상태 진단

아래를 **읽고 나서** 대표에게 말을 건다. 읽기 전에 질문하지 않는다.

| 읽을 것 | 무엇을 보나 |
|---|---|
| `.owner/state.md` | 현재 기능 · **미해결 문제**(B 조건) · 다음 행동 |
| `.owner/progress.json` | 회차별 완료 표시, 저장·배포·창구·보고 상태 |
| `company/profile.md` | 업태·회사 규모·관리 단위(일 한 건을 무엇이라 부르는가) |
| `company/flows.md` | 1회차에 고른 첫 업무 흐름과 "아직 담지 않는 흐름" |
| `company/structure.md` | 화면 목록과 **이번에 만들지 않을 것** |
| `company/improve-plan.md` · `company/log.md` | 회차 사이 기록 중 흐름과 관련된 것 |
| `company/workflow.md` | **있으면 이번이 두 번째** — 아래 분기 |
| `src/` 목록·상세 화면 | 상태 비슷한 값(`status`·단계·체크 표시)이 이미 있나 |
| `supabase/migrations/` | 표에 상태 칸이 있나. 없으면 새 번호 파일이 필요하다 |

**상태 문서가 코드·배포와 다르면 문서를 믿지 않는다.** 실제(파일·화면·표)를 확인한 뒤 문서를 고치고 시작한다.

판정과 분기:

- **처음** — `company/workflow.md` 없음 → **모드 A**, 절차 0부터 전부.
- **진행 중** — 문서는 있는데 앱에 상태가 없음 → **모드 A**, 인터뷰는 확인만 하고(3-1) 절차 5부터.
- **A 완료** — 문서·상태·필터·다음 할 일이 모두 있음 → **B 조건 검사**로 간다.

**B 조건 검사** (넷을 모두 통과해야 B로 간다)

1. `.owner/state.md` 의 **'미해결 문제'가 비어 있다**(또는 "없음"). 한 줄이라도 남아 있으면 그것부터 처리한다.
2. 앱이 배포된 주소가 있고, 대표 말고 **한 사람 이상이 실제로 입력해 봤다**.
3. 첫 흐름으로 처리한 **실제 건이 3건 이상**이다(지어낸 예시 데이터는 세지 않는다).
4. `company/backup.md` 의 되돌리는 순서가 채워져 있다.

통과하지 못하면 이렇게 말하고 모드 A의 마무리로 돌아간다.

> "두 번째 흐름은 첫 흐름이 자리 잡은 뒤가 빠릅니다. 지금은 <남은 항목> 이 남아 있어서, 오늘은 그것부터 끝내겠습니다."

판정을 한 문단으로 보고한 뒤 시작한다. 예: "목록과 상세는 있고 단계는 없습니다. 오늘은 단계를 정해 붙입니다. 질문 여섯 개만 드리겠습니다."

## 절차

### 0. 되돌릴 지점 만들기

작업 전에 커밋한다. 대표에게는 "지금 상태를 저장해 두고 시작합니다. 마음에 안 들면 여기로 되돌립니다"라고만 말한다.

```bash
git add -A && git commit -m "업무 흐름 작업 전 상태"
```

커밋이 안 되면 이유를 한 줄로 알리고, `git rev-parse --show-toplevel` 이 지금 폴더를 가리키는지 확인한다(다른 상위 저장소에 커밋되는 일이 있다). 그래도 안 되면 폴더를 통째로 복사해 둔 뒤 진행한다.

### 1. 왜 단계를 나누는지 먼저 설명한다 (2분, 세 문장 이내)

`references/indeans-flow-generalized.md` 를 읽고, 대표의 업태에 맞춰 세 문장으로 요약한다. 길게 옮기지 않는다. 핵심은 하나다.

> 단계를 나누는 이유는 보고용이 아니라 **다음에 할 일을 자동으로 정하기 위해서**다. 단계가 있으면 "이 건 어떻게 됐지"를 묻는 전화가 줄어든다.

### 2. 우리 회사로 되묻는다

다른 회사의 단계를 그대로 쓰라고 하지 않는다. 항상 이 말로 넘어간다: "저희가 예로 든 건 그 회사 방식입니다. 대표님 회사는 어떻게 부르시나요?"

### 3. 인터뷰 — 한 번에 하나씩 묻는다

질문 원문은 아래 그대로 쓴다. 답이 짧으면 예시를 **다른 업태 두 개**로 들어 준다(제조·서비스·유통·예약업 중). 답을 받으면 한 줄로 되읽어 확인하고 다음 질문으로 간다. 여섯 개를 다 묻기 전에 코드를 만들지 않는다. 자세한 되묻기는 `references/interview-questions.md`.

**3-1. 단계 이름**
> "일이 하나 들어와서 완전히 끝날 때까지, 회사에서 **실제로 쓰는 말로** 단계를 순서대로 말씀해 주세요. 세 개여도 되고 일곱 개여도 됩니다."

판단 기준: 3~7개면 적당하다. 두 개 이하면 "중간에 기다리는 구간"을 되묻는다. 여덟 개가 넘으면 "이 중에 담당자가 바뀌지 않는 단계는 붙여도 될까요"로 줄인다. 회사 말 그대로 적는다(영어로 바꾸지 않는다).

**3-2. 완료 증거**
> "그 단계가 끝났다는 걸 **무엇을 보고** 아시나요? 서명받은 종이, 입금, 사진, 문자 회신 같은 것 중에 뭐가 남나요?"

판단 기준: 단계마다 하나씩 받는다. "느낌으로 안다"는 답이 나오면 그 단계는 **사람이 직접 눌러 넘기는 단계**로 둔다. 증거가 있는 단계는 나중에 자동으로 넘길 후보다.

**3-3. 다음 담당**
> "그 단계가 끝나면 **다음은 누가** 이어받나요? 이름 말고 역할로요."

판단 기준: 여기서 나온 역할이 `company/people.md` 의 역할과 다르면 그 자리에서 알린다. 역할을 새로 만드는 일은 오늘 하지 않는다(`indeans-erp-people`).

**3-4. 빠지는 경우**
> "이 단계를 **건너뛰는 경우**가 있나요? 어떤 때 그런가요?"

판단 기준: 건너뛰기가 있으면 전이 표에 **두 갈래**로 적는다. "원래는 안 되는데 가끔 그런다"는 답도 그대로 적는다 — 현실이 규칙이다.

**3-5. 되돌아가는 경우**
> "**뒤로 되돌아가는** 일은 있나요? 어떤 때 그런가요?"

판단 기준: 되돌리기를 막지 않는다. 대신 되돌릴 수 있는 방향만 정한다(예: 진행 → 대기는 되지만 완료 → 접수는 안 된다).

**3-6. 고객이 보는 단계**
> "이 단계들 중에 **고객에게 알려 주는 것**은 어디까지인가요? 그리고 **고객이 보면 안 되는 단계 이름**이 있나요?"

판단 기준: 내부 전용 단계가 있으면 `workflow.md` 에 표시한다. 고객용 화면은 오늘 만들지 않는다.

### 4. 정리해서 읽어 드린다

받은 답을 표 한 장으로 정리해 대표 말로 읽어 준다. "이렇게 이해했는데 맞나요?" 틀린 곳만 고친다. 여기서 **대표가 고친 내용이 진짜 답**이다.

### 5. 문서로 남긴다

`assets/workflow-template.md` 를 복사해 **`company/workflow.md`** 로 저장한다. 절 순서와 표 형식은 바꾸지 않는다(다른 스킬이 읽는다). 빈칸은 `(미정)` 이라고 적고 비워 두지 않는다.

모드 B면 **1차 내용을 지우지 않고** 두 번째 흐름 절을 아래에 덧붙인다.

### 6. 무엇을 만들지 먼저 말하고 동의를 받는다

`references/state-patterns.md` 를 읽은 뒤, 아래 세 가지를 **한 화면씩** 설명하고 시작한다.

1. **상태 값과 전이 규칙** — 단계 목록을 데이터에 저장한다. 어느 상태에서 어디로 갈 수 있는지 표를 코드 한 곳에만 둔다.
2. **목록 필터** — 목록 위에 단계별 버튼을 둔다. 첫 화면은 "끝난 것 빼고"가 기본이다.
3. **상세의 다음 할 일** — 상세 화면 맨 위에 "다음 할 일: ○○" 한 줄과 넘기는 버튼 하나.

대표가 "이건 우리랑 안 맞는다"고 하면 그 말을 따른다.

### 7. 구현

순서를 지킨다. 한 번에 하나씩 만들고 화면을 보여 준다.

1. 상태 값을 한 파일에 정의한다(`src/domain/status.ts` 권장). **저장하는 값은 영문 코드, 화면에 보이는 글자는 회사 말**로 따로 둔다 — 나중에 이름을 바꿔도 과거 기록이 안 깨진다.
2. 전이 규칙을 같은 파일에 표로 둔다. "어느 상태에서 어디로" 판정은 이 함수 하나만 쓴다.
3. 상태 값을 바꾸면 **이미 저장된 값을 읽는 길**(CSV 내려받기·예시 데이터·운영 보고 함수)을 같이 고친다. 한 곳이라도 옛 글자를 그대로 두면 그 데이터만 목록에서 사라진다. **3회차에 만든 운영 보고 함수가 상태 값을 세고 있다** — 그 함수도 같이 고친다.
4. 데이터에 상태 칸을 만든다. `supabase/migrations/` 의 **다음 번호** 파일로 추가하고(기존 파일을 고치지 않는다), 기본값을 첫 단계로 둔다. **빈 상태를 허용하지 않는다.**
5. 상태가 바뀔 때 **언제·무엇에서 무엇으로·누가** 바꿨는지 같이 저장한다(`status_changed_at` 과 간단한 이력 표).
6. 목록 필터와 상세의 "다음 할 일"을 붙인다.
7. 목록 조회에는 **정렬과 개수 제한**을 반드시 넣는다. 지금은 데이터가 적어 괜찮아 보여도 몇 달 뒤 조용히 잘린다.

### 8. 눈으로 확인한다

대표가 직접 해 보게 한다. AI가 "됐습니다"라고 말하는 것으로 끝내지 않는다.

- 실제 건 하나를 첫 단계부터 마지막까지 **끝까지 옮겨 본다.**
- 한 번 **되돌려 본다.**
- 금지된 이동(예: 완료 → 접수)을 눌러 보고 막히는지 본다.
- 목록에서 단계별 버튼을 눌러 건수가 바뀌는지 본다.
- 폰에서도 한 번 해 본다(직원은 대개 폰으로 쓴다).

### 9. 검수와 상태 문서

화면과 저장 구조가 바뀌었으므로 **`indeans-erp-check` 를 호출한다.** 감독 판정 → `erp-verifier` 실측 → 작업 보고서까지 그 스킬이 이어서 한다.

그다음 `.owner/state.md` 를 고친다.

- **현재 기능** — "단계 <N>개, 목록 단계별 필터, 상세에 다음 할 일" 처럼 사실만.
- **미해결 문제** — 오늘 못 한 것(예: "건너뛰기 예외는 아직 안 담음"). 해결한 줄은 지운다.
- **다음 행동** — 다음 스킬(예: "주간 루틴·복구 실습(`indeans-erp-routine`)").

`.owner/progress.json` 의 `open_problems`·`next_action`·`updated_at` 을 고친다(4회차 완료 표시는 `indeans-erp-routine` 이 끝낼 때 적는다).

```bash
git add -A && git commit -m "업무 흐름: 단계와 다음 할 일"
```

## 하지 않는 것

- 다른 회사의 단계 이름을 그대로 쓰게 하지 않는다. 항상 회사 말로 받는다.
- 인터뷰 여섯 개를 끝내기 전에 코드를 만들지 않는다.
- 상태를 늘리자고 먼저 제안하지 않는다. 단계는 **줄이는 쪽**이 대체로 맞다.
- **B 조건을 채우지 않은 사람에게 두 번째 흐름을 만들지 않는다.** 미해결 문제가 남아 있으면 그것이 먼저다.
- `company/structure.md` 의 '이번에 만들지 않을 것' 을 대표 승인 없이 되살리지 않는다.
- 고객용 화면을 오늘 만들지 않는다.
- 새 역할을 만들지 않는다(`indeans-erp-people`).
- 기존 마이그레이션 파일을 고치지 않는다. 항상 새 번호 파일을 만든다.
- 상태 값을 바꾸면서 운영 보고 함수·내려받기를 그대로 두지 않는다.

## 앞선 수강생 분기

B 조건을 통과했으면 아래에서 **하나만** 고른다.

1. **두 번째 흐름** — `company/flows.md` 의 "아직 담지 않는 흐름"에서 하나 올린다. 대개 첫 흐름의 앞(문의가 들어와서 일이 되기까지)이나 뒤(끝난 뒤 정산·후속)다. 절차 3-1·3-2·3-3만 그 흐름에 대해 다시 하고, 화면은 **기존 목록에 종류 구분을 더하는 쪽**을 먼저 검토한다(화면을 늘리는 것보다 싸다).
2. **기한 지난 항목 표시** — 단계마다 "며칠 안에 다음으로 넘어가야 하는가"를 묻고, 넘긴 건을 목록 맨 위에 다르게 표시한다. 채널로 보내는 것은 `indeans-erp-digest` 다.
3. **고객용 조회 화면** — `company/workflow.md` 의 '고객 공개 범위'에 적힌 단계만 보이는 화면을 만든다. 내부 단계 이름을 고객 말로 바꾼 표를 먼저 만든다. 로그인 없이 링크로 여는 방식이면 **추측 못 할 긴 주소**를 쓰고, 그 주소로 무엇이 보이는지 대표에게 확인받는다.

## 자주 막히는 지점

- **단계가 15개 나온다** — 그건 단계가 아니라 할 일 목록이다. "담당자가 바뀌는 지점"만 단계로 남기고 나머지는 그 단계 안의 체크 항목으로 내린다.
- **단계마다 조건이 다 다르다** — 예외를 전부 담으려 하지 말고 가장 흔한 한 줄기를 먼저 만든다. 예외는 메모 칸으로 받아 두고 다음 회차에 본다.
- **상태를 바꿨는데 목록에서 안 사라진다** — 기본 필터가 "끝난 것 빼고"인지, 저장 후 목록을 다시 읽는지 확인한다.
- **상태 이름을 바꿨더니 과거 데이터가 사라졌다** — 저장 값과 화면 글자를 분리하지 않은 것이다. `references/state-patterns.md` 1번. 값은 그대로 두고 표시 이름만 바꾼다.
- **상태를 바꾼 뒤 운영 보고 건수가 0이 됐다** — 보고 함수가 옛 상태 값을 세고 있다. 절차 7-3.
- **"이건 상태가 두 개다"** — 예: 돈은 안 받았는데 작업은 끝났다. 억지로 한 줄에 넣지 말고 **칸을 두 개로** 나눈다(진행 상태 / 결제 상태). 대신 각 칸은 하나의 값만 갖는다.
- **직원이 단계를 안 넘긴다** — 버튼이 폰에서 눌리는 자리에 없거나, 넘기면 무엇이 좋은지 모르는 것이다. 직원에게 물을 질문 세 개(무슨 화면 · 무엇을 눌렀나 · 화면에 뜬 글자)를 만들어 대표가 받아 오게 한다.
