# 상태 설계에서 자주 하는 실수 6가지

구현(SKILL.md 절차 7번) 전에 읽는다. 각 항목은 **증상 → 왜 생기나 → 이렇게 한다** 순이다.
여섯 가지 모두 실제로 흔하고, 나중에 고칠수록 비싸진다. 특히 1·3번은 데이터가 쌓인 뒤에는 되돌리기 어렵다.

---

## 1. 화면에 보이는 글자를 그대로 저장한다

**증상**: 상태 이름을 "작업중"에서 "진행중"으로 바꿨더니 예전 건들이 목록에서 사라진다. 필터를 눌러도 안 나온다.

**왜 생기나**: 저장된 값이 곧 화면 글자라서, 글자를 바꾸는 순간 옛날 값과 새 값이 다른 것이 된다. 띄어쓰기 하나만 달라도 남남이다.

**이렇게 한다**: 저장하는 값(영문 코드)과 화면에 보이는 글자를 **따로 둔다.**

```ts
// src/domain/status.ts
export const STATUS = ['inquiry', 'confirmed', 'in_progress', 'done', 'canceled'] as const
export const STATUS_LABEL: Record<(typeof STATUS)[number], string> = {
  inquiry: '문의',
  confirmed: '확정',
  in_progress: '작업중',
  done: '완료',
  canceled: '취소',
}
```

이름을 바꿀 때는 `STATUS_LABEL` 의 글자만 고친다. 저장된 데이터는 건드리지 않는다.

---

## 2. 한 건의 상태가 여러 곳에 흩어진다

**증상**: 상태는 "완료"인데 체크박스는 안 채워져 있다. 어느 쪽이 맞는지 아무도 모른다.

**왜 생기나**: 상태 칸을 만들어 놓고, 화면을 고칠 때마다 체크박스·날짜 칸을 하나씩 더 붙였기 때문이다. 같은 사실을 두 곳에 적으면 언젠가 어긋난다.

**이렇게 한다**: **한 건의 현재 위치는 한 칸에만 적는다.** 날짜·체크는 "언제 그 상태가 됐는가"를 기록하는 용도로만 두고, 판정에는 쓰지 않는다. 목록 필터·화면 분기는 전부 상태 칸 하나만 본다.

성격이 다른 진행이 둘이면(예: 작업 진행과 결제 진행) 칸을 **두 개로 나눈다.** 대신 각 칸은 값을 하나만 갖는다.

---

## 3. 빈 상태를 허용한다

**증상**: 목록 건수를 다 더해도 전체 건수보다 적다. 어느 필터에도 안 걸리는 건이 있다.

**왜 생기나**: 상태 칸이 비어 있는 행은 `상태 = '완료'` 에도 `상태 <> '완료'` 에도 안 걸린다. 빈칸은 "아니오"가 아니라 **판정 불가**다. 이 유형은 조회뿐 아니라 권한 검사에서도 그대로 통과하는 사고로 이어진다.

**이렇게 한다**
- 상태 칸에 **기본값**을 준다(보통 첫 단계).
- 빈칸을 **금지**한다. Supabase라면 `not null default 'inquiry'`.
- 기존 데이터를 먼저 채운 뒤 금지 규칙을 건다. 순서를 반대로 하면 적용이 실패한다.

```sql
update jobs set status = 'inquiry' where status is null;
alter table jobs alter column status set default 'inquiry';
alter table jobs alter column status set not null;
```

---

## 4. 끝나는 방법이 한 가지뿐이다

**증상**: 취소된 건이 "완료"에 섞여 있다. 보류된 건이 진행 목록에 계속 떠 있어서 매번 눈으로 걸러 낸다.

**왜 생기나**: 끝나는 상태를 "완료" 하나만 만들었기 때문이다. 갈 데가 없는 건은 가장 가까운 칸으로 들어간다.

**이렇게 한다**: 끝나는 상태를 보통 셋으로 둔다 — **정상 완료 / 취소 / 보류.** 그리고 목록 기본 필터는 "끝난 것 빼고"로 한다. 집계(월별 건수·매출)는 정상 완료만 센다.

취소에는 **이유 한 줄**을 같이 받는다. 나중에 가장 자주 들여다보는 기록이 된다.

---

## 5. 어디서 어디로 갈 수 있는지 표가 없다

**증상**: 완료된 건이 갑자기 접수로 돌아가 있다. 누가 눌렀는지 모른다. 또는 반대로, 잘못 누른 걸 되돌릴 방법이 없어서 데이터를 손으로 고친다.

**왜 생기나**: 상태를 드롭다운으로 두고 아무 값이나 고를 수 있게 만들었거나, 앞으로만 가게 막아 버렸기 때문이다.

**이렇게 한다**: 전이 표를 **코드 한 곳**에 두고, 상태를 바꾸는 모든 화면이 이 함수만 쓴다.

```ts
const NEXT: Record<string, string[]> = {
  inquiry: ['confirmed', 'canceled'],
  confirmed: ['in_progress', 'inquiry', 'canceled'], // 확정 취소는 문의로 되돌린다
  in_progress: ['done', 'confirmed', 'canceled'],
  done: [],        // 완료에서 되돌리려면 대표만
  canceled: ['inquiry'],
}
export const canMove = (from: string, to: string) => (NEXT[from] ?? []).includes(to)
```

되돌리기를 금지하지 않는다. **되돌릴 수 있는 방향만** 정한다. 화면에는 갈 수 있는 곳만 버튼으로 보여 준다.

## 6. 바뀐 기록을 안 남긴다

**증상**: "이거 언제 완료 처리했지?" 에 답할 수 없다. 고객이 날짜를 물으면 메신저를 뒤진다.

**왜 생기나**: 상태 칸을 덮어쓰기만 하기 때문이다. 덮어쓰면 이전 값은 사라진다.

**이렇게 한다**: 상태를 바꿀 때 **언제·무엇에서 무엇으로**를 같이 남긴다. 간단히 시작해도 된다.

```sql
create table status_log (
  id uuid primary key default gen_random_uuid(),
  job_id uuid not null references jobs(id) on delete cascade,
  from_status text,
  to_status text not null,
  changed_at timestamptz not null default now()
);
```

누가 바꿨는지(`changed_by`)는 로그인을 붙이는 실습(`indeans-erp-people`)에서 추가한다. 그때 칸 하나만 더 붙이면 된다.

---

## 덧 — 목록 조회의 기본값

상태와 직접 관계는 없지만 같이 챙긴다. **목록·집계 조회에는 정렬과 개수 제한을 넣는다.** 제한 없이 전부 불러오는 조회는 데이터가 일정량을 넘으면 **오류 없이 조용히 잘린다.** 최근 건이 그냥 안 보이는 식이다. "지금은 데이터가 적어서 괜찮다"는 몇 달짜리 유예일 뿐이다.
